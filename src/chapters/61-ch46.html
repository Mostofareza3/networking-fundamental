Chapter 46

CDN — Content Delivery Network

Chapter 36-এ আমরা দেখেছি latency-র বড় অংশ ভৌত দূরত্ব থেকে আসে, এবং সেটি কমানো যায় না। CDN-এর ধারণাটি তাই বিপরীত দিক থেকে: দূরত্ব কমাও না, বরং content-কে কাছে নিয়ে এসো।

46.1 Why does this exist?

Origin server ভার্জিনিয়ায়। ব্যবহারকারী ঢাকায়।

  প্রতিটি request:
    ঢাকা ──────────────────────▶ ভার্জিনিয়া
                 RTT ≈ 250ms

  একটি page-এ ৫০টি resource
  Connection reuse সত্ত্বেও কয়েকটি round trip
  → ব্যবহারকারী কয়েক সেকেন্ড অপেক্ষা করেন

  আর logo.png প্রতিটি ব্যবহারকারীর জন্য
  ★ একই ★ — তবু প্রতিবার ১২,০০০ km পাড়ি দিচ্ছে।

CDN-এর প্রশ্ন:
  "যদি একই জিনিস বারবার একই পথে যায়,
   সেটি গন্তব্যের কাছে রেখে দিলেই তো হয়?"

46.3 ব্যবহারকারী কীভাবে নিকটতম edge-এ পৌঁছান

পদ্ধতিকীভাবেসীমাবদ্ধতা
GeoDNSDNS query-র উৎস দেখে ভিন্ন IP ফেরত দেওয়াResolver-এর অবস্থান দেখে, ব্যবহারকারীর নয় (৮.৮.৮.৮ ব্যবহার করলে ভুল হতে পারে; EDNS Client Subnet কিছুটা সমাধান করে)
Anycastএকই IP বহু জায়গায় ঘোষণা; BGP নিকটতমটিতে পাঠায় (Ch 27, 42)"নিকটতম" BGP-র হিসাবে, ভৌগোলিকভাবে নয় — কখনো কখনো অপ্রত্যাশিত
দুটোর সমন্বয়বেশিরভাগ বড় CDN দুটোই ব্যবহার করে—

46.4 কী cache করা যায়

সহজে cache-যোগ্য:
  ✓ Image, video, font
  ✓ CSS, JavaScript (hash-যুক্ত নামে হলে আদর্শ)
  ✓ Static HTML
  ✓ API-র public, অপরিবর্তনশীল response

কঠিন বা অসম্ভব:
  ✗ ব্যবহারকারী-নির্দিষ্ট content (dashboard, cart)
  ✗ প্রতিবার বদলায় এমন data
  ✗ POST/PUT/DELETE-এর response
  ✗ Authentication-নির্ভর content


Cache-এর নিয়ন্ত্রণ HTTP header দিয়ে (Ch 28, 29):

  Cache-Control: public, max-age=31536000, immutable
                 │       │                 │
          যেকেউ cache   ১ বছর         "কখনো বদলাবে না,
          করতে পারে                    যাচাইও করো না"

  Cache-Control: private, max-age=0, must-revalidate
                 │
          শুধু browser, CDN নয়

  Cache-Control: no-store
          কোথাও রাখা যাবে না (সংবেদনশীল data)

  Vary: Accept-Encoding, Accept-Language
          এই header-এর ভিন্ন মানে ভিন্ন cache entry
✓ Cache-busting-এর সঠিক pattern
✗ ভুল পদ্ধতি:
   /app.js  +  Cache-Control: max-age=300
   → প্রতি ৫ মিনিটে যাচাই (অপ্রয়োজনীয় request)
   → deploy করলেও ৫ মিনিট পুরনো version চলবে

✓ সঠিক পদ্ধতি — content hash সহ নাম:
   /app.a3f9c2.js  +  max-age=31536000, immutable
   → এক বছর cache, কখনো যাচাই করার দরকার নেই
   → deploy করলে ★নতুন নাম★ → নতুন URL → স্বয়ংক্রিয়ভাবে
     নতুন ফাইল নামবে

   আর HTML (যা এই নামগুলো উল্লেখ করে):
   /index.html  +  Cache-Control: no-cache
   → সবসময় যাচাই (কিন্তু 304 হলে সস্তা, Ch 29)

★ এটাই আধুনিক frontend build tool-এর default —
  এবং এর কারণ ঠিক এই caching কৌশল।

46.5 CDN শুধু cache নয়

সুবিধাব্যাখ্যা
LatencyContent ব্যবহারকারীর কাছে — মূল উদ্দেশ্য
TLS termination কাছেHandshake-এর RTT গুলো ৮ms-এ, ২৫০ms-এ নয় — এমনকি cache miss হলেও এটি বড় জয়
Origin-এর load কমে৯৫%+ request edge-এই মেটে
Bandwidth খরচOrigin-এর egress bandwidth অনেক কম
DDoS শোষণআক্রমণ শত শত edge-এ ছড়িয়ে যায়, origin অক্ষত থাকে
উন্নত network pathEdge → origin পথে CDN-এর নিজস্ব optimized backbone, public Internet নয়
স্বয়ংক্রিয় HTTP/3, BrotliOrigin পুরনো হলেও edge আধুনিক protocol দেয়
Edge computeCloudflare Workers, Lambda@Edge — logic-ও ব্যবহারকারীর কাছে
⚙️ Developer Perspective — একটি অবমূল্যায়িত সুবিধা

অনেকে ভাবেন CDN শুধু static ফাইলের জন্য। কিন্তু সম্পূর্ণ dynamic, কখনো cache না হওয়া API-র জন্যও CDN মূল্যবান। কারণ:

CDN ছাড়া (ঢাকা → ভার্জিনিয়া, RTT 250ms):
  TCP handshake  : 250 ms
  TLS handshake  : 250 ms
  Request/response: 250 ms
  ─────────────────────────
                 : 750 ms

CDN সহ (edge ঢাকায়, RTT 8ms; edge→origin optimized):
  TCP handshake  :   8 ms   ← edge-এর সাথে
  TLS handshake  :   8 ms   ← edge-এর সাথে
  Request        :   8 ms
  Edge → origin  : ~180 ms  ← CDN-এর নিজস্ব backbone,
                              এবং connection ইতিমধ্যে গরম
  ─────────────────────────
                 : ~204 ms  ★ ৭৩% কম ★

handshake গুলো কাছে হওয়াতেই বড় সাশ্রয় — cache-এর কোনো ভূমিকা ছাড়াই।

46.6 Cache invalidation

⚠️ "Computer science-এর দুটি কঠিন সমস্যা"

একটি পুরনো কৌতুক: "কম্পিউটার বিজ্ঞানে মাত্র দুটি কঠিন সমস্যা — cache invalidation এবং নামকরণ।" CDN-এ প্রথমটি বাস্তব ও দৈনন্দিন।

কৌশল ১ — TTL-এর মেয়াদ শেষ হতে দিন
  সরল, কিন্তু ধীর। জরুরি সংশোধনে অকার্যকর।

কৌশল ২ — Purge / invalidate
  API দিয়ে edge-দের বলুন "এই URL মুছে ফেলো"
  বেশিরভাগ CDN-এ সেকেন্ডের মধ্যে হয়
  কিন্তু হাজারো URL একসাথে purge করা ধীর

কৌশল ৩ — Cache tag / surrogate key ★ সবচেয়ে ভালো ★
  Response-এ tag দিন:
      Surrogate-Key: product-123 category-shoes
  পরে একটি tag purge করলেই সব সংশ্লিষ্ট URL যাবে
  → "product 123 বদলেছে" = একটি API call

কৌশল ৪ — Content hash সহ নাম ★ সবচেয়ে নির্ভরযোগ্য ★
  invalidation-এর দরকারই নেই — নতুন content = নতুন URL
  পুরনোটা কেউ চাইবে না, ধীরে ধীরে মুছে যাবে

কৌশল ৪ সম্ভব হলে সেটিই বেছে নিন — invalidation-এর সমস্যাটাই তখন অস্তিত্বহীন হয়ে যায়।

🧪 Lab 46 — CDN-এর আচরণ পর্যবেক্ষণ

আমরা কী দেখতে চাইছি? — একটি CDN-এর cache hit/miss, edge-এর অবস্থান, এবং তার প্রভাব।

bash
# CDN-এর header দেখুন
curl -sI https://www.cloudflare.com | grep -iE "cf-|cache|age|server"

# Cache HIT vs MISS
URL=https://www.cloudflare.com/favicon.ico
echo "১ম:"; curl -sI $URL | grep -i "cf-cache-status\|age"
echo "২য়:"; curl -sI $URL | grep -i "cf-cache-status\|age"

# আপনি কোন edge-এ পৌঁছাচ্ছেন
curl -s https://www.cloudflare.com/cdn-cgi/trace | grep -E "colo|ip|loc"
#  colo = data center-এর কোড (DAC = ঢাকা, SIN = সিঙ্গাপুর)

# একই hostname বিভিন্ন resolver থেকে (GeoDNS-এর প্রমাণ)
for r in 8.8.8.8 1.1.1.1; do
  echo "$r → $(dig @$r +short www.cloudflare.com | head -1)"
done

# CDN-এ এবং origin-এ latency তুলনা
curl -w "CDN:    %{time_total}s\n" -o /dev/null -s https://www.cloudflare.com

যা লক্ষ্য করবেন: cf-cache-status: HIT বা MISS; age: 3421 মানে এই copy টি ৩৪২১ সেকেন্ড ধরে cache-এ আছে। /cdn-cgi/trace-এর colo= মান দেখাবে আপনি কোন data center-এ পৌঁছেছেন — বাংলাদেশ থেকে সাধারণত DAC, SIN বা BOM। প্রথম request MISS, দ্বিতীয়টি HIT হওয়ার কথা।

আমরা কী শিখলাম: CDN কোনো বিমূর্ততা নয় — আপনি ঠিক কোন শহরের কোন যন্ত্রে পৌঁছাচ্ছেন তা দেখতে পাচ্ছেন, এবং cache-এর অবস্থাও header-এ স্পষ্ট। এই header গুলোই CDN-সংক্রান্ত সমস্যা নির্ণয়ের প্রধান হাতিয়ার।

📌 Chapter Summary
  • CDN দূরত্ব কমায় না — content-কে ব্যবহারকারীর কাছে নিয়ে আসে।
  • Cache HIT = edge থেকে সরাসরি (মিলিসেকেন্ড); MISS = origin থেকে এনে cache করা।
  • ব্যবহারকারী edge-এ পৌঁছান GeoDNS ও Anycast-এর মাধ্যমে।
  • Dynamic API-র জন্যও CDN মূল্যবান — TLS handshake কাছে হওয়ায় বড় সাশ্রয়।
  • Cache-busting-এর সঠিক pattern: content hash সহ নাম + immutable; HTML-এ no-cache।
  • CDN আরও দেয়: DDoS শোষণ, origin-এর load ও bandwidth সাশ্রয়, আধুনিক protocol, edge compute।
  • Cache invalidation-এর সেরা সমাধান হলো invalidation-এর প্রয়োজন না রাখা (hash-যুক্ত নাম)।
✓ Quick Check
কখনো cache না হওয়া একটি dynamic API-তেও CDN কেন সাহায্য করে?

কারণ TCP ও TLS handshake ব্যবহারকারীর কাছের edge-এর সাথে হয় (৮ms), origin-এর সাথে নয় (২৫০ms)। এতেই দুটি RTT সাশ্রয় হয়। উপরন্তু edge থেকে origin-এ CDN-এর নিজস্ব optimized backbone ব্যবহৃত হয় এবং সেই connection সাধারণত ইতিমধ্যে গরম (keep-alive)। ফলে মোট সময় ৭৫০ms থেকে ২০০ms-এ নামতে পারে, কোনো caching ছাড়াই।

app.js-এ এক বছরের max-age দিলে নতুন deploy কীভাবে পৌঁছাবে?

ফাইলের নামে content hash রাখুন: app.a3f9c2.js। Deploy করলে content বদলায় → hash বদলায় → নতুন URL তৈরি হয়। HTML (যা no-cache দিয়ে সবসময় যাচাই হয়) নতুন নামটি উল্লেখ করে, তাই browser স্বয়ংক্রিয়ভাবে নতুন ফাইল নামায়। পুরনো URL-টি কেউ আর চায় না বলে ধীরে ধীরে cache থেকে মুছে যায়। এতে invalidation-এর প্রয়োজনই থাকে না।

GeoDNS কখন ভুল edge-এ পাঠাতে পারে?

যখন ব্যবহারকারী তার নিজের এলাকার বাইরের resolver ব্যবহার করেন — যেমন ঢাকা থেকে 8.8.8.8। CDN তখন resolver-এর অবস্থান (যা হয়তো সিঙ্গাপুর) দেখে সিদ্ধান্ত নেয়, ব্যবহারকারীর নয়। EDNS Client Subnet এটি কিছুটা সমাধান করে — resolver ব্যবহারকারীর subnet-এর একটি সংক্ষিপ্ত অংশ query-র সাথে পাঠায়। Anycast-এ এই সমস্যা নেই, কারণ routing নিজেই প্রকৃত packet-এর উৎস অনুযায়ী কাজ করে।

Vary: Accept-Encoding header কেন দরকার?

এটি cache-কে বলে যে Accept-Encoding header-এর ভিন্ন মানের জন্য ভিন্ন cache entry রাখতে হবে। ছাড়া দিলে cache একটি gzip-compressed response এমন একটি client-কে দিয়ে দিতে পারে যে gzip বোঝে না — ফলে ভাঙা content। একইভাবে Vary: Accept-Language ভিন্ন ভাষার version আলাদা রাখে। তবে সতর্কতা: অতিরিক্ত Vary (যেমন User-Agent) cache-এর কার্যকারিতা প্রায় শূন্য করে দেয়।
