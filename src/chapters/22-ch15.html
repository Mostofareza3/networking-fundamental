Chapter 15

Why Do We Need a Transport Layer?

IP আপনাকে একটি machine-এ পৌঁছে দেয়। কিন্তু machine-এ nginx, PostgreSQL, SSH, Redis — সবাই একই IP-তে বসে আছে। কে পাবে এই packet? এই একটি প্রশ্নের উত্তরই transport layer-এর জন্ম দিয়েছে।

15.1 Why does this exist?

একটি server: 203.0.113.50

    ┌──────────────────────────────────────┐
    │  nginx        (web)                  │
    │  PostgreSQL   (database)             │
    │  Redis        (cache)                │
    │  sshd         (remote login)         │
    │  node app     (API)                  │
    └──────────────────────────────────────┘
              সবাই একই IP-তে

একটি packet এল: dst IP = 203.0.113.50

    ⇒ কাকে দেব???

IP-এর কাছে এই প্রশ্নের কোনো উত্তর নেই।
IP header-এ শুধু আছে: কোন machine। কোন process নয়।
💡 Why Port

সমাধান: প্রতিটি চলমান network-service-কে একটি সংখ্যা দাও, এবং সেই সংখ্যাটি transport header-এ লিখে দাও। এই সংখ্যাটিই port।

একে বলা হয় multiplexing / demultiplexing: একটি IP address-এর উপর দিয়ে বহু আলাদা কথোপকথন চালানো (mux), এবং প্রাপ্ত প্রান্তে সেগুলোকে আবার আলাদা করা (demux)। উল্লেখ্য, আমরা এই একই pattern আগেও দেখেছি — Ethernet-এর EtherType, IP-এর Protocol field। প্রতিটি layer-ই তার উপরের একাধিক ভোক্তার মধ্যে বণ্টন করে।

15.2 Port

একটি port (পোর্ট) হলো একটি ১৬-bit সংখ্যা (০–৬৫৫৩৫) যা একটি নির্দিষ্ট machine-এর একটি নির্দিষ্ট network-service-কে চিহ্নিত করে।

              IP Address  +  Port
                   │           │
            "কোন machine"  "কোন service"

   203.0.113.50 : 443    →  nginx
   203.0.113.50 : 5432   →  PostgreSQL
   203.0.113.50 : 6379   →  Redis
   203.0.113.50 : 22     →  sshd

মনে রাখার উপমা:
   IP   = একটি ভবনের ঠিকানা
   Port = সেই ভবনের ফ্ল্যাট নম্বর
⚠️ Port কোনো physical জিনিস নয়

"Port" শব্দটি বিভ্রান্তিকর কারণ switch-এরও physical port আছে। কিন্তু transport-layer port সম্পূর্ণ বিমূর্ত সংখ্যা — এটি একটি software ধারণা, kernel-এর একটি table-এর index মাত্র। কোনো তার নেই, কোনো socket নেই দেয়ালে। এটি নিছক একটি label যা kernel-কে বলে দেয় কোন process-কে data দিতে হবে।

এটি একটি ঐতিহাসিক নিরাপত্তা-ব্যবস্থা: multi-user system-এ যেন যেকোনো সাধারণ user port 22-তে একটি নকল SSH server চালিয়ে অন্যদের password চুরি করতে না পারে। আজকের container যুগে এই সুরক্ষার প্রাসঙ্গিকতা কমেছে, তবু নিয়মটি রয়ে গেছে।

এজন্যই বাস্তবে Node.js/Python app গুলো 3000/8000-এ চলে এবং সামনে একটি reverse proxy (nginx) বসে যে root হিসেবে চালু হয়ে port 80/443 ধরে, তারপর অধিকার ছেড়ে দেয়। Linux-এ বিকল্প আছে: CAP_NET_BIND_SERVICE capability দিয়ে root ছাড়াই নিচু port-এ bind করা যায়।

15.4 Source Port এবং Destination Port

প্রতিটি TCP/UDP header-এ দুটি port থাকে। কেন?

আপনার browser → example.com

Request packet:
    src IP  : 192.168.1.5      src port : 51234  ← OS বেছে দিল
    dst IP  : 93.184.215.14    dst port : 443    ← আপনি জানতেন

Response packet (সব উল্টো):
    src IP  : 93.184.215.14    src port : 443
    dst IP  : 192.168.1.5      dst port : 51234  ← এখানেই ফিরবে

Source port ছাড়া server জানত না উত্তরটা কোথায় পাঠাতে হবে —
এবং আপনার OS জানত না কোন browser tab-এর জন্য এই উত্তর।
🧠 Mental Model — Ephemeral port কেন দরকার

আপনি একই সাথে example.com-এর তিনটি tab খুললেন। তিনটি connection-ই যাচ্ছে 93.184.215.14:443-এ। তাহলে উত্তরগুলো আলাদা হবে কীভাবে?

Tab 1: 192.168.1.5:51234 → 93.184.215.14:443
Tab 2: 192.168.1.5:51235 → 93.184.215.14:443
Tab 3: 192.168.1.5:51236 → 93.184.215.14:443
                    ↑
              শুধু এটিই আলাদা

Source port-ই তিনটি কথোপকথনকে আলাদা করে রাখে। এজন্যই একে "ephemeral" (ক্ষণস্থায়ী) বলা হয় — connection শেষে সংখ্যাটি ফেরত চলে যায় pool-এ।

15.5 4-Tuple — একটি connection-এর প্রকৃত পরিচয়

একটি TCP connection চিহ্নিত হয় চারটি জিনিস দিয়ে:

    ┌────────────────────────────────────────┐
    │  1. Source IP                          │
    │  2. Source Port                        │
    │  3. Destination IP                     │
    │  4. Destination Port                   │
    └────────────────────────────────────────┘
    (কঠোরভাবে বললে protocol সহ 5-tuple)

এই চারটির সমন্বয় অনন্য হলেই সেটি একটি আলাদা connection।

উদাহরণ — একই server-এ ৩টি client:

  (203.0.113.9,  51234, 10.0.0.5, 443)  ← connection A
  (203.0.113.9,  51235, 10.0.0.5, 443)  ← connection B (একই client!)
  (198.51.100.7, 40000, 10.0.0.5, 443)  ← connection C (ভিন্ন client)

তিনটিই server-এর port 443-এ। কিন্তু 4-tuple আলাদা,
তাই তিনটি সম্পূর্ণ স্বাধীন connection।
⚙️ Developer Perspective — একটি চিরন্তন প্রশ্নের উত্তর

"একটি server port 443-এ হাজারো client সামলায় কীভাবে? Port তো একটাই!"

উত্তর: Server-এর দিকে port একটাই, কিন্তু connection-এর পরিচয় port নয় — 4-tuple। প্রতিটি client-এর ভিন্ন IP বা ভিন্ন source port থাকায় প্রতিটি 4-tuple অনন্য। Kernel একটি hash table রাখে যেখানে key হলো এই 4-tuple, আর value হলো socket। তাই তাত্ত্বিকভাবে একটি server port একই client থেকে ৬৫,৫৩৫টি এবং ভিন্ন client থেকে কার্যত অসীম connection নিতে পারে — প্রকৃত সীমা memory এবং file descriptor।

15.6 Common Confusions

MYTH

একটি server-এ একবারে ৬৫,৫৩৫টির বেশি connection সম্ভব নয়, কারণ port তো এতগুলোই।

REALITY

৬৫,৫৩৫-এর সীমাটি প্রযোজ্য একটি নির্দিষ্ট client IP থেকে একটি নির্দিষ্ট server IP:port-এ। ভিন্ন client IP থেকে আসা connection-গুলো ভিন্ন 4-tuple তৈরি করে, তাই তারা এই সীমার মধ্যে পড়ে না। বাস্তব সীমা হলো memory, file descriptor limit (ulimit -n), এবং kernel-এর connection tracking table। একটি tuned Linux server লক্ষাধিক concurrent connection সামলাতে পারে।

তবে client-এর দিকে এই সীমাটি বাস্তব: একটি load-testing machine একটি server-এ ~২৮,০০০-এর বেশি connection খুলতে পারে না (default ephemeral range), যদি না আপনি range বাড়ান বা একাধিক source IP ব্যবহার করেন।

MYTH

দুটি program কখনোই একই port ব্যবহার করতে পারে না।

REALITY

কয়েকটি ক্ষেত্রে পারে: (১) ভিন্ন protocol — একটি TCP 53-এ, অন্যটি UDP 53-এ; এরা সম্পূর্ণ আলাদা namespace। (২) ভিন্ন IP — একটি 192.168.1.5:8080-এ, অন্যটি 10.0.0.5:8080-এ। (৩) SO_REUSEPORT — আধুনিক Linux-এ একাধিক process ইচ্ছাকৃতভাবে একই port share করতে পারে এবং kernel তাদের মধ্যে load balance করে (nginx এভাবেই multi-worker চালায়)। (৪) ভিন্ন network namespace (container)।

🧪 Lab 15 — Port এবং 4-tuple বাস্তবে দেখুন

আমরা কী দেখতে চাইছি? — একই gantavya-তে একাধিক connection খুললে source port কীভাবে তাদের আলাদা রাখছে।

bash
# আপনার machine-এ এখন কী কী শুনছে
ss -tuln                # Linux
lsof -i -P -n | grep LISTEN    # macOS

# একই server-এ তিনটি connection খুলুন এবং দেখুন
for i in 1 2 3; do (curl -s https://example.com > /dev/null &) ; done
ss -tn 'dst example.com' 2>/dev/null || ss -tn | head

# ephemeral port-এর পরিসর দেখুন
cat /proc/sys/net/ipv4/ip_local_port_range     # Linux
sysctl net.inet.ip.portrange.first             # macOS

যা লক্ষ্য করবেন: ss -tn-এর output-এ Local Address:Port আর Peer Address:Port — এই দুটি জোড়াই সেই 4-tuple। একাধিক connection-এ Peer একই (93.184.215.14:443) কিন্তু Local Port ভিন্ন। ip_local_port_range সাধারণত 32768 60999 দেখাবে — এই পরিসর থেকেই OS বেছে নেয়।

আমরা কী শিখলাম: 4-tuple কোনো তাত্ত্বিক ধারণা নয় — এটি ঠিক যা ss প্রতিটি লাইনে দেখাচ্ছে। এবং source port automatically বণ্টিত হচ্ছে, আপনি কখনো এটি নিয়ে ভাবেননি — কারণ OS আপনার হয়ে কাজটি করে দিচ্ছে।

📌 Chapter Summary
  • IP পৌঁছে দেয় machine পর্যন্ত; port পৌঁছে দেয় process পর্যন্ত।
  • Port একটি ১৬-bit বিমূর্ত সংখ্যা — কোনো physical জিনিস নয়।
  • 0–1023 well-known (root লাগে), 1024–49151 registered, 49152+ ephemeral।
  • প্রতিটি packet-এ দুটি port — source (উত্তর কোথায় ফিরবে) এবং destination (কে পাবে)।
  • একটি connection-এর পরিচয় 4-tuple: (src IP, src port, dst IP, dst port)।
  • একই server port হাজারো connection নিতে পারে, কারণ প্রতিটি 4-tuple আলাদা।
✓ Quick Check
একটি IP address কেন একটি application-কে চিহ্নিত করার জন্য যথেষ্ট নয়?

কারণ একটি machine-এ (একটি IP-তে) বহু process একসাথে network ব্যবহার করে। IP header-এ শুধু "কোন machine" আছে, "কোন process" নেই। Transport header-এর port number সেই তথ্যটি যোগ করে। তাই একটি network service-কে সম্পূর্ণ চিহ্নিত করতে লাগে protocol + IP + port।

Client-এর source port কে ঠিক করে এবং কেন?

OS (kernel) ephemeral range থেকে একটি অব্যবহৃত port বেছে দেয়, সাধারণত connect()-এর সময়। দরকার হয় দুটি কারণে: (১) server জানতে হবে উত্তর কোন port-এ পাঠাতে হবে, (২) একই client থেকে একই server-এ একাধিক connection আলাদা করতে হবে — source port-ই তাদের একমাত্র পার্থক্য।

একই machine-এ TCP 8080 এবং UDP 8080 কি একসাথে ব্যবহার করা যায়?

হ্যাঁ। TCP এবং UDP-র port namespace সম্পূর্ণ আলাদা, কারণ IP header-এর Protocol field (6 বনাম 17) দিয়েই kernel প্রথমে আলাদা করে ফেলে। DNS এর সবচেয়ে পরিচিত উদাহরণ — সে TCP 53 এবং UDP 53 দুটোতেই শোনে।

একটি load testing tool একটি server-এ ~২৮,০০০ connection-এর পর ব্যর্থ হচ্ছে। কারণ কী?

Client-এর ephemeral port ফুরিয়ে গেছে। Default range (32768–60999) দেয় প্রায় ২৮,০০০টি port, এবং একই gantavya (IP:port)-এর জন্য প্রতিটি connection-এর আলাদা source port লাগে। এছাড়া বন্ধ connection গুলো TIME_WAIT-এ আটকে থাকে (Ch 22), যা সমস্যা বাড়ায়। সমাধান: port range বাড়ানো, একাধিক source IP ব্যবহার, বা connection reuse (keep-alive)।
