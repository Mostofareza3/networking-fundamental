Chapter 20

Flow Control — Receiver-কে ডুবতে না দেওয়া

একটি শক্তিশালী server একটি দুর্বল IoT device-এ data পাঠাচ্ছে। Network-এ কোনো সমস্যা নেই, কিন্তু receiver process করতে পারছে না। TCP এই পরিস্থিতি কীভাবে সামলায় — এবং এর সাথে আপনার code-এর backpressure-এর সম্পর্ক কী?

20.1 Why does this exist?

Sender: 1 Gbps server, দ্রুত ডেটা তৈরি করছে
Receiver: ছোট device, ধীরে process করছে

Sender পাঠাল ────────────────────────────▶ Receiver buffer
                                              [████████] পূর্ণ!
Sender আরও পাঠাল ──────────────────────────▶ ✗ জায়গা নেই
                                              → ফেলে দিতে হবে
                                              → TCP retransmit করবে
                                              → আবার ফেলে দেবে
                                              → অসীম চক্র

Network দোষী নয়, congestion নেই, packet loss নেই — শুধু receiver পারছে না। এটি একটি সম্পূর্ণ আলাদা সমস্যা, এবং এর সমাধানও আলাদা।

💡 Why Flow Control

সমাধান সহজ এবং মার্জিত: receiver নিজেই বলে দেবে সে আর কতটুকু নিতে পারবে। প্রতিটি ACK-এর সাথে সে একটি সংখ্যা পাঠায় — receive window। Sender সেই সীমা মেনে চলে।

এটি একটি explicit, receiver-driven ব্যবস্থা — congestion control-এর ঠিক উল্টো, যেখানে sender অনুমান করে (Ch 21)।

20.2 Receive Window

Receiver-এর buffer:

  ┌────────────────────────────────────────────────┐
  │ ▓▓▓▓▓▓▓▓▓▓▓▓ │              ফাঁকা                 │
  │ পেয়েছি,       │                                 │
  │ app পড়েনি     │                                 │
  └──────────────┴─────────────────────────────────┘
                 ◀────── rwnd = 32 KB ─────────────▶

  প্রতিটি ACK-এ receiver এই সংখ্যাটি পাঠায়:
      ACK = 5001, window = 32768

  Sender-এর নিয়ম:
      উড়ন্ত (unacknowledged) data ≤ rwnd


Application যত পড়ে, তত জায়গা খালি হয়:

  app read() করল 20 KB
  ┌──────┬─────────────────────────────────────────┐
  │ ▓▓▓  │                 ফাঁকা                     │
  └──────┴─────────────────────────────────────────┘
         ◀────────── rwnd = 52 KB ─────────────────▶

  পরের ACK-এ:  window = 53248  ← বড় হলো

20.3 Zero Window এবং Window Probe

Receiver-এর buffer সম্পূর্ণ ভরে গেল:

  Receiver ──▶ ACK, window = 0   "থামো! আর নিতে পারছি না"

  Sender পাঠানো বন্ধ করল। কিন্তু এখন একটি সমস্যা:

  পরে receiver-এর application কিছু পড়ল, জায়গা হলো।
  Receiver একটি window update পাঠাল: window = 20000
                                          │
                                          ✗ হারিয়ে গেল!

  এখন deadlock:
    Sender: "window 0, তাই অপেক্ষা করছি"
    Receiver: "আমি তো জায়গা আছে বলেছিলাম, ও পাঠাচ্ছে না কেন?"
    উভয়েই চিরকাল অপেক্ষা করবে।


সমাধান — Persist Timer এবং Window Probe:

  Sender একটি timer চালায়। মেয়াদ শেষে সে একটি
  ছোট probe packet পাঠায় (সাধারণত ১ byte):

  Sender ──▶ [1 byte probe]
  Receiver ──▶ ACK, window = 20000   ← আসল অবস্থা জানা গেল

  Probe-এর ব্যবধান exponentially বাড়তে থাকে:
    5s → 10s → 20s → 40s → 60s (সর্বোচ্চ)
✓ একটি চিরন্তন নকশা-নীতি

এই সমাধানটি একটি সাধারণ distributed systems নীতির উদাহরণ: গুরুত্বপূর্ণ অবস্থার পরিবর্তন শুধু একটি বার্তার উপর নির্ভর করবেন না; পর্যায়ক্রমে যাচাই করার ব্যবস্থা রাখুন। কারণ যেকোনো একক বার্তা হারাতে পারে, এবং তখন দুই পক্ষের ধারণা চিরকালের জন্য ভিন্ন হয়ে যেতে পারে।

আপনি নিজের distributed system-এও একই কৌশল দেখবেন: heartbeat, periodic reconciliation, TTL-ভিত্তিক refresh। TCP-র persist timer এই ধারণার একটি চমৎকার, ছোট উদাহরণ।

20.4 Flow Control এবং আপনার code-এর Backpressure

🧠 Mental Model — একটি অবিচ্ছিন্ন শৃঙ্খল

Flow control কোনো বিচ্ছিন্ন network-বৈশিষ্ট্য নয়। এটি একটি শৃঙ্খলের অংশ, যা আপনার application-এর write() থেকে শুরু করে অন্য প্রান্তের application-এর read() পর্যন্ত বিস্তৃত:

Receiver-এর app ধীরে read() করছে
        ↓
Receiver-এর kernel buffer ভরে যাচ্ছে
        ↓
rwnd ছোট হচ্ছে → ACK-এ সেটি ঘোষিত হচ্ছে
        ↓
Sender-এর kernel পাঠানো কমাচ্ছে
        ↓
Sender-এর send buffer ভরে যাচ্ছে
        ↓
Sender-এর app-এর write() block করছে / EAGAIN দিচ্ছে
        ↓
আপনার code ধীর হয়ে যাচ্ছে — এবং এটাই কাম্য!

Receiver-এর ধীরগতি network পেরিয়ে sender-এর application পর্যন্ত পৌঁছে গেল। এটাই backpressure — এবং এটি TCP-র একটি অন্তর্নিহিত বৈশিষ্ট্য, যা আপনি বিনামূল্যে পাচ্ছেন।

⚙️ Developer Perspective — backpressure উপেক্ষা করলে
js
// ✗ ভুল — backpressure উপেক্ষা করা
for (const row of millionRows) {
  socket.write(JSON.stringify(row));   // return value দেখছি না!
}
// Node.js kernel buffer ভরে গেলে বাকিটা নিজের memory-তে
// জমাতে থাকে → RSS বাড়তে থাকে → OOM kill

// ✓ সঠিক — backpressure মানা
for (const row of millionRows) {
  if (!socket.write(JSON.stringify(row))) {
    await once(socket, "drain");       // kernel buffer খালি হওয়ার অপেক্ষা
  }
}

// ✓ আরও ভালো — stream-কেই কাজটা করতে দিন
pipeline(rowStream, jsonTransform, socket, callback);

"আমার Node.js service-এ memory leak" — এই অভিযোগের একটি বড় অংশ আসলে leak নয়, উপেক্ষিত backpressure। TCP ঠিকই সংকেত দিচ্ছিল, application সেটি শোনেনি এবং data নিজের heap-এ জমিয়েছে।

📌 Chapter Summary
  • Flow control receiver-কে অতিরিক্ত data থেকে রক্ষা করে — network-এর সমস্যা নয়, receiver-এর সামর্থ্যের প্রশ্ন।
  • Receiver প্রতিটি ACK-এ window ঘোষণা করে — একটি স্পষ্ট সংকেত।
  • Window 0 হলে sender থামে; persist timer দিয়ে সে পর্যায়ক্রমে probe পাঠিয়ে deadlock এড়ায়।
  • Flow control আপনার application-এর write() পর্যন্ত পৌঁছায় — এটিই backpressure।
  • Backpressure উপেক্ষা করলে data application-এর নিজের memory-তে জমে (আপাত "memory leak")।
  • কার্যকর window = min(rwnd, cwnd) — flow control ও congestion control একসাথে কাজ করে।
✓ Quick Check
Flow control এবং congestion control — মূল পার্থক্য কী?

Flow control receiver-কে রক্ষা করে এবং এর সংকেত স্পষ্ট — receiver নিজেই window ঘোষণা করে বলে দেয় সে কতটুকু নিতে পারবে। Congestion control network-কে রক্ষা করে এবং এর সংকেত অনুমাননির্ভর — কেউ বলে না, sender packet loss বা বর্ধিত delay দেখে নিজেই সিদ্ধান্ত নেয়।

Window probe না থাকলে কী সমস্যা হতো?

Receiver window=0 ঘোষণা করার পর যখন জায়গা খালি হয় এবং সে window update পাঠায় — সেই update packet-টি হারিয়ে যেতে পারে। তখন sender চিরকাল ভাববে window এখনো 0, আর receiver ভাববে সে জানিয়ে দিয়েছে। Deadlock। Persist timer সেই একক বার্তার উপর নির্ভরতা ভেঙে দেয় — sender নিজেই পর্যায়ক্রমে জিজ্ঞেস করে।

আপনার Node.js service-এর memory ধীরে ধীরে বাড়ছে, একটি বড় data pipeline চালানোর সময়। প্রথম সন্দেহ?

উপেক্ষিত backpressure। socket.write()-এর return value না দেখলে (বা stream.pipe()/pipeline() ব্যবহার না করলে) kernel buffer ভরে যাওয়ার পর Node.js বাকি data নিজের heap-এ জমাতে থাকে। এটি leak নয় — data যথাসময়ে যাবে — কিন্তু receiver যদি যথেষ্ট ধীর হয়, heap বাড়তেই থাকবে যতক্ষণ না OOM। সমাধান: drain event মানুন বা pipeline() ব্যবহার করুন।

Sender-এর কার্যকর window কীভাবে নির্ধারিত হয়?

min(rwnd, cwnd) — receive window এবং congestion window-এর যেটি ছোট। Receiver ধীর হলে rwnd সীমাবদ্ধকারী; network ভিড় থাকলে cwnd। ss -ti দিয়ে দুটোই দেখে বোঝা যায় কোনটি প্রকৃত bottleneck।
