Chapter 16

Sockets — Application এবং Network-এর সংযোগস্থল

এই chapter টি বইয়ের সেই বিন্দু যেখানে networking আর operating system একসাথে মিশে যায়। Socket হলো সেই abstraction যার মাধ্যমে আপনার লেখা প্রতিটি লাইন network-এ পৌঁছায় — fetch(), net.connect(), database driver, সবকিছুর নিচে একটি socket আছে।

16.1 Why does this exist?

আপনার application user space-এ চলে। Network hardware-এ পৌঁছাতে হলে kernel-এর মধ্য দিয়ে যেতে হবে (OS fundamentals থেকে এটি পরিচিত)। কিন্তু কী interface দিয়ে?

Unix-এর নকশাগত সিদ্ধান্ত ছিল চমৎকার: network connection-কেও file-এর মতো দেখাও।

File-এর সাথে যা করেন:          Socket-এর সাথেও তাই:

  fd = open("file.txt")          fd = socket(...)
  read(fd, buf, n)               read(fd, buf, n)     ← একই call!
  write(fd, buf, n)              write(fd, buf, n)    ← একই call!
  close(fd)                      close(fd)            ← একই call!

দুটোই একটি সংখ্যা — file descriptor।
Kernel-এর table-এ একটি index মাত্র।
💡 Why এই abstraction গুরুত্বপূর্ণ

"সবকিছু একটি file descriptor" — এই নকশার ফলে select(), poll(), epoll, kqueue-এর মতো ব্যবস্থা একসাথে file, socket, pipe, timer সবকিছুর উপর কাজ করতে পারে। এটিই Node.js-এর event loop, nginx-এর event-driven model, এবং Go-এর runtime scheduler-এর ভিত্তি। আপনি যখন epoll-এর নাম শোনেন, সে আসলে একগুচ্ছ socket fd-র উপর নজর রাখছে।

16.2 Socket কী

একটি socket (সকেট) হলো একটি communication endpoint — kernel-এর ভেতরে একটি data structure যা একটি network connection-এর সব অবস্থা ধরে রাখে, এবং যার সাথে আপনার application একটি file descriptor-এর মাধ্যমে কথা বলে।

একটি socket-এর সাথে যুক্ত থাকে:

  ┌─────────────────────────────────────────┐
  │ Protocol      : TCP / UDP               │
  │ Local IP      : 192.168.1.5             │
  │ Local Port    : 51234                   │
  │ Remote IP     : 93.184.215.14           │
  │ Remote Port   : 443                     │
  │ State         : ESTABLISHED             │
  │ Send buffer   : [ যা পাঠানো বাকি ]        │
  │ Recv buffer   : [ যা এসেছে, পড়া হয়নি ]   │
  │ TCP state     : seq, ack, window, RTT   │
  └─────────────────────────────────────────┘

আপনার code এর কিছুই দেখে না — শুধু একটি সংখ্যা:  fd = 7

🧠 Mental Model — Socket একটি সীমান্ত

Socket হলো সেই রেখা যেখানে আপনার দায়িত্ব শেষ এবং kernel-এর দায়িত্ব শুরু। আপনি write() করলেন — এর মানে "এই bytes গুলো kernel-এর send buffer-এ রাখলাম"। এর মানে এই নয় যে data পাঠানো হয়ে গেছে, বা গন্তব্যে পৌঁছেছে, বা receiver পড়েছে।

এই পার্থক্যটি গুরুত্বপূর্ণ: write() সফল হওয়া মানে শুধু "kernel দায়িত্ব নিয়েছে"। Kernel পরে নিজের সময়মতো, নিজের মতো ভাগ করে, প্রয়োজনে বারবার চেষ্টা করে সেটি পাঠাবে।

✓ সবচেয়ে গুরুত্বপূর্ণ সূক্ষ্মতা — দুই ধরনের socket

এটি নতুনদের কাছে বিভ্রান্তিকর, কিন্তু ধারণাটি মৌলিক:

  • Listening socket — একটি মাত্র, শুধু (local IP, local port) জানে। এর কোনো peer নেই। এর কাজ শুধু নতুন connection তৈরি করা। ss-এ এটি LISTEN অবস্থায় দেখায়।
  • Connected socket — প্রতিটি client-এর জন্য একটি করে, সম্পূর্ণ 4-tuple জানে। প্রকৃত data এদের দিয়েই যায়। ss-এ ESTAB।

একটি web server-এ ১টি listening socket এবং ১০,০০০টি connected socket থাকতে পারে — সবগুলোরই local port 443। এতে কোনো সংঘাত নেই, কারণ প্রতিটির 4-tuple আলাদা।

16.7 Code — তিনটি স্তরে একই জিনিস

উচ্চ স্তরে socket গুলো লুকানো, কিন্তু নিচে তারাই আছে:

js
// এই এক লাইন যা যা করে
const res = await fetch("https://api.example.com/users");
//  1. DNS resolve  → getaddrinfo() syscall
//  2. socket()      → একটি fd তৈরি
//  3. connect()     → TCP handshake
//  4. TLS handshake → certificate যাচাই, key বিনিময়
//  5. write()       → HTTP request bytes
//  6. read()        → response bytes
//  7. close() বা keep-alive pool-এ ফেরত

// নিচু স্তরে, একই জিনিস স্পষ্টভাবে:
const net = require("net");

const server = net.createServer((socket) => {
  // এই socket = accept()-এর ফেরত দেওয়া conn_fd
  console.log("client:", socket.remoteAddress, socket.remotePort);

  socket.on("data", (chunk) => {      // recv()
    socket.write("Echo: " + chunk);   // send()
  });

  socket.on("end", () => {            // FIN পেয়েছি
    console.log("client চলে গেল");
  });
});

server.listen(8080, "0.0.0.0");        // bind() + listen()

C-তে প্রতিটি ধাপ স্পষ্ট — কোনো কিছু লুকানো নেই:

c
// ---------- SERVER ----------
int fd = socket(AF_INET, SOCK_STREAM, 0);

// "Address already in use" এড়াতে (Ch 22-এ TIME_WAIT দেখুন)
int yes = 1;
setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &yes, sizeof(yes));

struct sockaddr_in addr = {
    .sin_family = AF_INET,
    .sin_port   = htons(8080),        // host → network byte order
    .sin_addr   = { .s_addr = INADDR_ANY }   // 0.0.0.0
};

bind(fd, (struct sockaddr*)&addr, sizeof(addr));
listen(fd, 128);                      // backlog = 128

while (1) {
    struct sockaddr_in cli;
    socklen_t len = sizeof(cli);

    int conn = accept(fd, (struct sockaddr*)&cli, &len);
    //  ↑ এখানে block করে। নতুন একটি fd ফেরত দেয়।

    char buf[1024];
    ssize_t n = recv(conn, buf, sizeof(buf), 0);
    //  ↑ n < requested হতে পারে! TCP byte stream (Ch 4)

    send(conn, buf, n, 0);
    close(conn);                      // শুধু এই connection
}

// ---------- CLIENT ----------
int fd = socket(AF_INET, SOCK_STREAM, 0);
struct sockaddr_in srv = { ... };
connect(fd, (struct sockaddr*)&srv, sizeof(srv));
//  ↑ এর ভেতরেই TCP handshake সম্পন্ন হয়
send(fd, "hello", 5, 0);
recv(fd, buf, sizeof(buf), 0);
close(fd);

Python-এর socket module কার্যত C API-র সরাসরি প্রতিরূপ:

python
import socket

# ---------- SERVER ----------
srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("0.0.0.0", 8080))
srv.listen(128)

while True:
    conn, addr = srv.accept()      # নতুন socket + client-এর ঠিকানা
    print("connected:", addr)      # ('192.168.1.9', 51234)

    data = conn.recv(1024)         # চাওয়া 1024, পেতে পারেন কম
    conn.sendall(b"Echo: " + data) # sendall = সব যাওয়া পর্যন্ত loop
    conn.close()

# ---------- CLIENT ----------
cli = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
cli.connect(("example.com", 80))
print("আমার source port:", cli.getsockname()[1])   # ephemeral!
cli.sendall(b"GET / HTTP/1.1\r\nHost: example.com\r\n\r\n")
print(cli.recv(4096).decode()[:200])
cli.close()

getsockname() চালিয়ে দেখুন — kernel আপনার হয়ে যে source port বেছে নিয়েছে সেটি দেখতে পাবেন।

16.8 Buffer — যেখানে অধিকাংশ বিভ্রান্তি জন্মায়

APPLICATION                KERNEL                  NETWORK

  write("hello")  ──────▶  ┌──────────────┐
                           │ Send Buffer  │ ──────▶  packets
  ✓ ফেরত এল                 │ "hello"      │
  (মানে: kernel নিয়েছে,      └──────────────┘
   পাঠিয়েছে নয়!)

                           ┌──────────────┐
  read(buf)     ◀──────    │ Recv Buffer  │ ◀──────  packets
                           │ "world"      │
  ✓ যা আছে তাই দেয়           └──────────────┘
  (হয়তো আংশিক)
⚠️ তিনটি অনিবার্য সত্য
  1. write() ফেরত আসা মানে পাঠানো হয়েছে নয় — শুধু kernel buffer-এ কপি হয়েছে। এমনকি close()-এর পরও কিছু data পথে থাকতে পারে।
  2. read() চাওয়ার চেয়ে কম দিতে পারে — আপনি ১০০০ চাইলেন, পেলেন ২০০। এটি error নয়, TCP-এর স্বাভাবিক আচরণ (Ch 4)। তাই সবসময় loop-এ পড়তে হয়।
  3. Send buffer ভরে গেলে write() block করে (blocking mode-এ) বা EAGAIN দেয় (non-blocking mode-এ)। এটিই backpressure-এর প্রকৃত রূপ — receiver ধীর হলে সেই ধীরগতি buffer হয়ে আপনার write() পর্যন্ত পৌঁছায় (Ch 20)।
⚙️ Node.js-এ এটি যেভাবে দেখা যায়
js
const ok = socket.write(bigChunk);
if (!ok) {
  // kernel buffer ভরা — thamun
  socket.once("drain", () => resume());
}

// অথবা stream.pipe() নিজেই এটি সামলায়:
readStream.pipe(socket);   // backpressure স্বয়ংক্রিয়

write()-এর false return করা আর 'drain' event — এই দুটি সরাসরি kernel socket buffer-এর অবস্থার প্রতিফলন। Stream API এই OS-স্তরের বাস্তবতাকেই একটি সুন্দর মোড়কে দেয়।

🧪 Lab 16 — Socket-এর জীবনচক্র নিজের চোখে

আমরা কী দেখতে চাইছি? — listening socket এবং connected socket-এর পার্থক্য, এবং একটি connection তৈরি হওয়ার মুহূর্তে kernel-এর table-এ কী যোগ হয়।

bash

# Terminal 2 — listening socket দেখুন
ss -tlnp | grep 8080

# Terminal 3 — একটি connection ধরে রাখুন
nc localhost 8080          # খোলা রাখুন

# এখন LISTEN ছাড়াও দুটি ESTAB দেখবেন
# (একটি client-এর দিক, একটি server-এর দিক — দুটোই এই machine-এ)

যা লক্ষ্য করবেন: LISTEN লাইনে peer address 0.0.0.0:* — অর্থাৎ কোনো নির্দিষ্ট peer নেই। ESTAB লাইনে দুটো প্রান্তেরই সম্পূর্ণ address:port আছে — এটাই 4-tuple। এবং লক্ষ্য করুন LISTEN socket-টি ESTAB তৈরি হওয়ার পরেও টিকে আছে — সে পরের client-এর জন্য অপেক্ষা করছে।

আমরা কী শিখলাম: accept() যে "নতুন socket" ফেরত দেয় সেটি কোনো রূপক নয় — ss-এ আপনি দুটি আলাদা entry দেখতে পাচ্ছেন। একটি connection মানে kernel-এর ভেতরে একটি প্রকৃত, আলাদা data structure।

📌 Chapter Summary
  • Socket = communication endpoint; application-এর কাছে এটি একটি file descriptor।
  • Server: socket → bind → listen → accept → recv/send → close।
  • Client: socket → connect → send/recv → close। bind() লাগে না।
  • accept() একটি নতুন socket ফেরত দেয় — listening socket আলাদা, connected socket আলাদা।
  • connect()-এর ভেতরেই routing lookup, source port বাছাই, এবং TCP handshake ঘটে।
  • write() সফল = kernel buffer-এ কপি হয়েছে, পাঠানো বা পৌঁছানো নয়।
  • read() চাওয়ার চেয়ে কম দিতে পারে — সবসময় loop-এ পড়ুন।
  • Buffer ভরে গেলে write() আটকায় — এটিই backpressure।
✓ Quick Check
accept() কেন একটি নতুন socket ফেরত দেয়? পুরনোটাই ব্যবহার করলে সমস্যা কী?

কারণ listening socket-এর কোনো peer নেই — সে শুধু (local IP, port) জানে এবং তার কাজ নতুন connection গ্রহণ করা। প্রতিটি client-এর সাথে কথা বলতে দরকার একটি সম্পূর্ণ 4-tuple সহ আলাদা socket, নিজস্ব buffer ও নিজস্ব TCP state সহ। পুরনোটা ব্যবহার করলে দ্বিতীয় client-এর জন্য কোনো জায়গা থাকত না, এবং একাধিক client-এর data মিশে যেত।

write() সফলভাবে ফেরত এল। এর মানে কি data গন্তব্যে পৌঁছেছে?

না। এর একমাত্র অর্থ — bytes গুলো kernel-এর send buffer-এ কপি হয়েছে এবং kernel দায়িত্ব নিয়েছে। তারপর সেগুলো segment-এ ভাগ হবে, পাঠানো হবে, হয়তো হারাবে, আবার পাঠানো হবে। গন্তব্যে পৌঁছেছে কিনা তা জানার একমাত্র উপায় application-স্তরের acknowledgment (যেমন HTTP response) — TCP-এর ACK শুধু kernel পেয়েছে বলে, application পড়েছে বলে নয়।

একটি server-এ ১০,০০০ client যুক্ত। কতটি socket আছে?

১০,০০১টি — একটি listening socket এবং ১০,০০০টি connected socket। সবগুলোর local port একই (যেমন 443), কিন্তু প্রতিটির 4-tuple ভিন্ন। প্রতিটি socket-এর নিজস্ব send/recv buffer আছে, তাই ১০,০০০ connection মানে উল্লেখযোগ্য পরিমাণ kernel memory (এটাই C10K সমস্যার একটি দিক)।

Client-কে কেন bind() করতে হয় না?

কারণ client-এর কোনো নির্দিষ্ট port দরকার নেই — কেউ তার কাছে connect করতে আসছে না। connect()-এর সময় kernel স্বয়ংক্রিয়ভাবে ephemeral range থেকে একটি অব্যবহৃত port বেছে নেয় (implicit bind)। তবে চাইলে client-ও bind() করতে পারে — যেমন যদি নির্দিষ্ট একটি source IP বা port ব্যবহার করতে হয় (firewall নিয়ম বা multi-homed host-এ)।

Socket-কে file descriptor বানানোর সুবিধা কী?

একই API (read, write, close, select/poll/epoll) file, socket, pipe, terminal, timer — সবকিছুতে কাজ করে। ফলে একটি event loop একসাথে file I/O এবং network I/O-র উপর নজর রাখতে পারে। এটিই Node.js, nginx, এবং সব আধুনিক async runtime-এর ভিত্তি।
