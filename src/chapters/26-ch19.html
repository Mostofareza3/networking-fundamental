Chapter 19

TCP Data Transfer — হারানো, নকল, উল্টো ক্রম

Handshake হয়ে গেছে। এখন প্রকৃত data যাচ্ছে — এবং network তার স্বভাব অনুযায়ী কিছু packet হারাবে, কিছু উল্টো ক্রমে পৌঁছে দেবে, কিছু দুবার পাঠাবে। TCP এই তিন ধরনের বিশৃঙ্খলা কীভাবে সামলায়, সেটাই এই chapter।

19.1 স্বাভাবিক প্রবাহ

Sender                                  Receiver
   │  seq=1  (1000 B)                       │
   ├───────────────────────────────────────▶│  buffer: [1..1000]
   │  seq=1001 (1000 B)                     │
   ├───────────────────────────────────────▶│  buffer: [1..2000]
   │                                        │
   │◀───────────────────────────────────────┤
   │            ACK=2001                    │
   │                                        │

লক্ষ্য করুন: প্রতিটি segment-এর জন্য আলাদা ACK আসেনি।
একটি ACK দুটোকেই স্বীকার করেছে — একে বলে
"cumulative ACK": "2000 পর্যন্ত সব পেয়েছি"।

সুবিধা: কম ACK packet।
আরও: বেশিরভাগ TCP implementation প্রতি দুটি segment-এ
একটি ACK পাঠায়, বা 200ms অপেক্ষা করে (delayed ACK) —
যাতে ACK-টি কোনো outgoing data-র সাথে piggyback করা যায়।

19.2 দৃশ্য ১ — Packet হারিয়ে গেল

Sender পাঠাল ৪টি segment:

  Packet 1 (seq=1)      ✓ পৌঁছাল
  Packet 2 (seq=1001)   ✓ পৌঁছাল
  Packet 3 (seq=2001)   ✗ হারিয়ে গেল
  Packet 4 (seq=3001)   ✓ পৌঁছাল

Receiver-এর অবস্থা:
  ┌─────────────────────────────────────────┐
  │ [1..2000]  ✓ ক্রমবদ্ধ, application-কে দেওয়া যাবে │
  │ [2001..3000] ✗ ফাঁকা                     │
  │ [3001..4000] ✓ পেয়েছি, কিন্তু আটকে রাখতে হবে!│
  └─────────────────────────────────────────┘

Receiver কী ACK পাঠাবে? সবসময় "পরবর্তী প্রত্যাশিত byte":

  Packet 1 পেয়ে  → ACK = 1001
  Packet 2 পেয়ে  → ACK = 2001
  Packet 4 পেয়ে  → ACK = 2001  ← আবার একই! (duplicate ACK)
                                  "আমার এখনো 2001 দরকার"

Fast Retransmit — timeout-এর অপেক্ষা না করে

Sender তিনটি duplicate ACK পেলে (মোট চারটি একই ACK):

  ACK=2001
  ACK=2001   ← dup 1
  ACK=2001   ← dup 2
  ACK=2001   ← dup 3   ⚡ Fast Retransmit trigger!

  Sender সঙ্গে সঙ্গে seq=2001 আবার পাঠায় —
  RTO timer শেষ হওয়ার অপেক্ষা না করে।

কেন তিনটি?
  একটি বা দুটি duplicate ACK reordering-এর কারণেও হতে পারে
  (packet 4 packet 3-এর আগে পৌঁছালে)। তিনটি হলে loss-এর
  সম্ভাবনা অনেক বেশি। এটি একটি ভারসাম্য: খুব তাড়াতাড়ি
  পাঠালে অপ্রয়োজনীয় retransmission, দেরি করলে বিলম্ব।

লাভ:
  RTO-ভিত্তিক : ২০০ms – ১s অপেক্ষা
  Fast retrans: ~১ RTT (হয়তো ৩০ms)
  → অনেক দ্রুত পুনরুদ্ধার

SACK — Selective Acknowledgment

Cumulative ACK-এর একটি সীমাবদ্ধতা আছে: ACK=2001 বলে "2000 পর্যন্ত পেয়েছি", কিন্তু বলে না যে packet 4-ও পেয়ে গেছে। Sender অন্ধকারে থাকে — সে হয়তো 3001-ও অপ্রয়োজনীয়ভাবে আবার পাঠাবে।

SACK option যোগ করে receiver বলতে পারে:

  ACK = 2001, SACK = [3001–4000]
   │              │
   │              └─ "এই খণ্ডটিও আমার কাছে আছে"
   └─ "ক্রমবদ্ধভাবে 2000 পর্যন্ত"

ফল: sender জানে ঠিক কোন ফাঁকটি পূরণ করতে হবে।
     শুধু 2001–3000 আবার পাঠাবে, 3001–4000 নয়।

একাধিক ফাঁক থাকলে:
  ACK=2001, SACK=[3001-4000],[5001-6000]

SACK আজ কার্যত সর্বত্র সক্রিয় — handshake-এ আলোচিত হয়।
এটি ছাড়া উচ্চ-loss বা উচ্চ-latency পথে TCP-র
throughput নাটকীয়ভাবে কমে যায়।

19.3 দৃশ্য ২ — উল্টো ক্রমে পৌঁছাল

পাঠানো হলো: 1, 2, 3, 4
পৌঁছাল:      1, 2, 4, 3     ← 4 আগে এল!

(কারণ: ECMP load balancing, ভিন্ন পথ, বা router-এ
 ভিন্ন queue-তে অপেক্ষা)

Receiver যা করে:
  1 পেল → application-কে দেওয়া যায় → ACK=1001
  2 পেল → দেওয়া যায় → ACK=2001
  4 পেল → ফাঁক আছে! buffer-এ রাখো → ACK=2001 (dup)
  3 পেল → ফাঁক পূরণ! এখন 3 এবং 4 দুটোই দেওয়া যায় → ACK=4001

★ গুরুত্বপূর্ণ: application কখনো জানতেই পারল না যে
  packet উল্টো ক্রমে এসেছিল। সে ঠিক ক্রমেই bytes পেল।
  TCP পুরো বিশৃঙ্খলাটা লুকিয়ে ফেলল।
⚠️ Head-of-Line Blocking

উপরের দৃশ্যে একটি লুকানো খরচ আছে: packet 4 receiver-এর buffer-এ পৌঁছে গিয়েও application পড়তে পারেনি, কারণ packet 3 আসেনি। TCP ক্রম রক্ষা করতে বাধ্য, তাই সে অপেক্ষা করে।

একে বলে head-of-line (HOL) blocking — সামনের একজন আটকে থাকলে পেছনের সবাই আটকে থাকে। এটি TCP-র নকশাগত অনিবার্য পরিণতি।

এটিই HTTP/2-এর সবচেয়ে বড় দুর্বলতা: একটি TCP connection-এ ১০০টি stream multiplexed থাকলে, একটি packet হারালে সবগুলো stream আটকে যায় — যদিও ৯৯টির data-ই পৌঁছে গেছে। QUIC ঠিক এই সমস্যাটি সমাধানের জন্যই তৈরি (Ch 45)।

19.4 দৃশ্য ৩ — Duplicate packet

কেন duplicate হয়?
  • ACK পথে হারিয়ে গেল → sender ভাবল data হারিয়েছে → আবার পাঠাল
  • Network-এ কোথাও packet duplicate হলো (বিরল)
  • RTO খুব ছোট ছিল → অকারণে retransmit

Receiver যা করে:
  seq=1001 এল  → গ্রহণ করল, buffer-এ [1001..2000]
  seq=1001 আবার এল → "আমার কাছে তো এটি আছে!"
                     → নীরবে ফেলে দিল
                     → কিন্তু ACK আবার পাঠাল
                       (কারণ sender স্পষ্টতই আগের ACK পায়নি)

Sequence number-ই এখানে সব — TCP জানে ঠিক কোন byte
তার কাছে আছে, তাই duplicate শনাক্ত করা তুচ্ছ ব্যাপার।

19.5 Interactive — চারটি দৃশ্য পাশাপাশি

Sender          Receiver        Receiver Buffer
   │ seq=1    ──────▶│           [1....1000] ✓
   │ seq=1001 ──────▶│           [1....2000] ✓
   │ seq=2001 ──────▶│           [1....3000] ✓
   │◀──── ACK=3001 ──│
   
সব ক্রমবদ্ধ। Application সরাসরি সব পড়তে পারে।
কোনো buffer আটকে নেই। এটাই আদর্শ অবস্থা।
Sender          Receiver        Receiver Buffer
   │ seq=1    ──────▶│           [1....1000] ✓
   │ seq=1001 ───✗   │           ফাঁক!
   │ seq=2001 ──────▶│           [1..1000][____][2001..3000]
   │◀── ACK=1001 ────│           ↑ application এখানেই আটকে
   │ seq=3001 ──────▶│
   │◀── ACK=1001 ────│  dup 1
   │ seq=4001 ──────▶│
   │◀── ACK=1001 ────│  dup 2
   │◀── ACK=1001 ────│  dup 3  ⚡
   │                 │
   │ seq=1001 (retx)▶│           ফাঁক পূরণ!
   │◀── ACK=5001 ────│           সব একসাথে application-কে

লক্ষ্য করুন: 3 টি segment পৌঁছেও অপেক্ষা করছিল।
এটাই head-of-line blocking।
Sender          Receiver        Receiver Buffer
   │ seq=1    ──────▶│           [1....1000] ✓
   │ seq=2001 ──────▶│  ← আগে!   [1..1000][____][2001..3000]
   │◀── ACK=1001 ────│           dup ACK
   │ seq=1001 ──────▶│  ← পরে    ফাঁক পূরণ
   │◀── ACK=3001 ────│           [1....3000] ✓

মাত্র ১টি dup ACK — ৩টি নয়। তাই fast retransmit
trigger হলো না। TCP সঠিকভাবে বুঝল এটি reordering,
loss নয়। এটিই "কেন তিনটি duplicate ACK লাগে"-র উত্তর।
Sender          Receiver        Receiver Buffer
   │ seq=1    ──────▶│           [1....1000] ✓
   │◀── ACK=1001 ─✗  │  ← ACK হারাল
   │                 │
   │  ⏰ timeout      │
   │ seq=1 (retx) ──▶│  "এটা তো আছে!"
   │                 │  ফেলে দিল, কিন্তু...
   │◀── ACK=1001 ────│  ...ACK আবার পাঠাল
   │                 │
   
Data নষ্ট হলো না, শুধু কিছু bandwidth ও সময় নষ্ট।
Sequence number থাকায় duplicate ধরা পড়া তুচ্ছ ব্যাপার।

19.6 Sliding Window — একবারে একটি নয়

এখন পর্যন্ত আমরা যেন ধরে নিচ্ছিলাম sender একটি packet পাঠিয়ে ACK-এর অপেক্ষা করে। সেটি হলে ভয়াবহ ধীর হতো:

Stop-and-wait (যদি এমন হতো):
  RTT = 60ms, MSS = 1460 bytes
  Throughput = 1460 bytes / 0.06s ≈ 24 KB/s
  একটি 1 Gbps line-এও মাত্র 24 KB/s! অগ্রহণযোগ্য।

Sliding window (বাস্তব TCP):
  ACK-এর অপেক্ষা না করেই অনেকগুলো segment পাঠাও

  ┌──── পাঠানো ও ACK পাওয়া ────┬─ পাঠানো, ACK-এর অপেক্ষা ─┬─ এখনো পাঠাইনি ─┐
  │ 1 .......... 5000          │ 5001 ......... 20000   │ 20001 ...      │
  └────────────────────────────┴────────────────────────┴────────────────┘
                                ◀────── window ─────────▶

  ACK এলে window ডানে সরে যায় — তাই "sliding"।

  Throughput = window size / RTT

  Window 64 KB, RTT 60ms  →  64KB/0.06 ≈ 1.07 MB/s
  Window 1 MB,  RTT 60ms  →  16.7 MB/s
🧠 Mental Model — Bandwidth-Delay Product

একটি সূত্র যা বহু "কেন আমার download ধীর" প্রশ্নের উত্তর দেয়:

BDP = Bandwidth × RTT
    = পথে একসাথে কত data "উড়ন্ত" থাকতে পারে

উদাহরণ: 100 Mbps line, RTT 100ms
    BDP = 100,000,000 bit/s × 0.1 s ÷ 8
        = 1,250,000 bytes ≈ 1.25 MB

অর্থাৎ পূর্ণ গতি পেতে window কমপক্ষে 1.25 MB হতে হবে।
Window যদি 64 KB হয় (পুরনো default):
    সর্বোচ্চ throughput = 64 KB / 0.1s = 640 KB/s ≈ 5 Mbps
    → 100 Mbps line-এর মাত্র ৫%!

এটিই "long fat network" সমস্যা। সমাধান window scaling — একটি TCP option যা window-কে ৬৫ KB-র সীমা ছাড়িয়ে ১ GB পর্যন্ত যেতে দেয়। এটি handshake-এ আলোচিত হয় এবং আজ সব আধুনিক system-এ সক্রিয়।

⚙️ Developer Perspective

"আমার সার্ভার আর ক্লায়েন্টের দুটোরই ১ Gbps, কিন্তু transfer ৫ MB/s-এ আটকে আছে" — যদি দুটি মহাদেশের মাঝে হয়, প্রথম সন্দেহ BDP এবং window। যাচাই: ss -ti চালিয়ে cwnd, rcv_space, rtt দেখুন। বহু ক্ষেত্রেই receive window বা congestion window-ই সীমাবদ্ধকারী, bandwidth নয়।

এজন্যই বড় ফাইল আন্তঃমহাদেশীয়ভাবে পাঠাতে মানুষ একাধিক সমান্তরাল TCP connection ব্যবহার করে (যেমন aria2c -x 8) — প্রতিটির নিজস্ব window থাকায় সম্মিলিত throughput বাড়ে।

🧪 Lab 19 — একটি চলমান connection-এর ভেতরটা দেখুন

আমরা কী দেখতে চাইছি? — একটি সক্রিয় TCP connection-এর প্রকৃত RTT, congestion window, এবং retransmission-এর সংখ্যা।

bash
# Terminal 1 — একটি বড় download শুরু করুন
curl -s -o /dev/null https://speed.hetzner.de/100MB.bin &

# Terminal 2 — connection-এর ভেতরের অবস্থা (Linux)
watch -n1 "ss -ti | grep -A1 ESTAB | head -20"

# system-wide retransmission-এর পরিসংখ্যান
netstat -s | grep -i retrans
nstat -az | grep -i retrans      # Linux, আরও বিস্তারিত

যা লক্ষ্য করবেন: ss -ti-এর output-এ পাবেন rtt:32.5/4.2 (RTT ও তার variance), cwnd:120 (congestion window, MSS-এর একক), bytes_retrans: (কত bytes আবার পাঠাতে হয়েছে), retrans:0/3। Download চলাকালীন cwnd-এর সংখ্যাটি বাড়তে দেখবেন — এটাই congestion control-এর কাজ (পরের chapter)।

আমরা কী শিখলাম: TCP-র ভেতরের অবস্থা লুকানো নয় — kernel এই সব পরিমাপ রাখে এবং ss -ti দিয়ে দেখা যায়। ধীর transfer-এর কারণ নির্ণয়ে এটি সবচেয়ে সরাসরি tool: retrans বেশি মানে loss, cwnd ছোট মানে congestion control সীমাবদ্ধ করছে, rtt বেশি মানে দূরত্বই মূল বাধা।

📌 Chapter Summary
  • ACK cumulative — "এই byte পর্যন্ত সব পেয়েছি"।
  • Packet হারালে receiver duplicate ACK পাঠাতে থাকে; ৩টি dup ACK পেলে sender fast retransmit করে (timeout-এর অপেক্ষা না করে)।
  • SACK receiver-কে বলতে দেয় ঠিক কোন খণ্ডগুলো পেয়েছে — অপ্রয়োজনীয় retransmission বাঁচায়।
  • Reordering স্বাভাবিক; TCP নীরবে সাজিয়ে নেয়, application কিছু টের পায় না।
  • Head-of-line blocking: ক্রম রক্ষার মূল্য — একটি হারানো packet পরের সব কিছু আটকে দেয়।
  • Sliding window: ACK-এর অপেক্ষা না করে অনেকগুলো segment পাঠানো।
  • Throughput ≈ window / RTT; BDP = bandwidth × RTT পূর্ণ গতির জন্য প্রয়োজনীয় window।

Fast retransmit-এর জন্য ঠিক তিনটি duplicate ACK কেন?

একটি বা দুটি duplicate ACK সাধারণ reordering-এর কারণেও হতে পারে — packet উল্টো ক্রমে পৌঁছালে receiver duplicate ACK পাঠায়, যদিও কিছু হারায়নি। তিনটি duplicate ACK reordering-এর জন্য অস্বাভাবিক, তাই loss-এর সম্ভাবনা অনেক বেশি। এটি একটি সচেতন ভারসাম্য: কম হলে অপ্রয়োজনীয় retransmission, বেশি হলে পুনরুদ্ধারে দেরি।

Head-of-line blocking কী এবং কেন এটি TCP-তে অনিবার্য?

একটি segment হারালে তার পরের সব segment receiver-এর কাছে পৌঁছে গিয়েও application-কে দেওয়া যায় না, কারণ TCP ক্রম রক্ষার প্রতিশ্রুতি দিয়েছে। অনিবার্য কারণ ordered byte stream-এর সংজ্ঞাই এই — ফাঁক রেখে পরের অংশ দিয়ে দিলে সেটি আর ordered stream থাকে না। HTTP/2-তে একটি connection-এ বহু stream থাকায় এই সমস্যা তীব্র হয়; QUIC প্রতিটি stream-কে স্বাধীন করে এটি সমাধান করে (Ch 45)।

100 Mbps line, RTT 200ms। পূর্ণ গতি পেতে কত বড় window লাগবে?

BDP = 100,000,000 bit/s × 0.2 s = 20,000,000 bit = 2,500,000 bytes ≈ 2.5 MB। ৬৫ KB-র classic TCP window দিয়ে সর্বোচ্চ পাওয়া যেত 65536/0.2 = 327 KB/s ≈ 2.6 Mbps — line-এর মাত্র ২.৬%। এজন্যই window scaling option অপরিহার্য।

SACK না থাকলে সমস্যা কী?

Cumulative ACK শুধু বলে "এই পর্যন্ত ক্রমবদ্ধভাবে পেয়েছি" — ফাঁকের পরের কী কী পৌঁছেছে তা বলে না। SACK ছাড়া sender অন্ধকারে থাকে, এবং অনেক implementation ফাঁকের পরের সবকিছু আবার পাঠায় (go-back-N-এর মতো আচরণ)। উচ্চ-BDP পথে যেখানে একসাথে বহু segment উড়ন্ত থাকে, এটি বিরাট অপচয় এবং throughput নাটকীয়ভাবে কমে যায়।
