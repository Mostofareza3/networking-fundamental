Chapter 3

Network Layers & Encapsulation

OSI-এর সাতটি layer মুখস্থ করা networking শেখা নয়। কিন্তু কেন layer-এ ভাগ করা হলো এবং encapsulation ঠিক কীভাবে কাজ করে — এই দুটি বুঝলে বাকি বইয়ের প্রায় সব কিছু জায়গামতো বসে যাবে।

3.1 Why does this exist?

কল্পনা করুন কেউ একটি single, monolithic protocol লিখল যেটি একসাথে করে: তামার তারে voltage নিয়ন্ত্রণ, পাশের machine খুঁজে বের করা, পৃথিবীর অন্য প্রান্তে পথ নির্ধারণ, হারানো data পুনরায় পাঠানো, encryption, এবং HTTP request-এর গঠন।

এই design-এ ভয়াবহ সমস্যা:

  • Wi-Fi আবিষ্কার হলে পুরো protocol নতুন করে লিখতে হবে — কারণ তামার তারের অংশটা এতে জড়ানো।
  • HTTP-এর নতুন version আনতে হলে routing-এর কোড ছুঁতে হবে।
  • Copper আর fiber-এর জন্য পুরো আলাদা দুটো Internet লাগবে।
💡 Why Layers

Layering হলো networking-এ প্রয়োগ করা separation of concerns। প্রতিটি layer:

  • একটি নির্দিষ্ট সমস্যা সমাধান করে,
  • নিচের layer-এর কাছে একটি নির্দিষ্ট service চায়,
  • উপরের layer-কে একটি নির্দিষ্ট service দেয়,
  • এবং পাশের layer গুলোর ভেতরের কথা জানে না।

ফল: TCP-কে কিছু না বদলে আপনি Ethernet থেকে Wi-Fi-তে যেতে পারেন। HTTP-এর নতুন version আনতে IP-তে হাত দিতে হয় না। এটি software architecture-এর সবচেয়ে সফল প্রয়োগগুলোর একটি — আপনি যদি কখনো interface-based design বা dependency inversion ব্যবহার করে থাকেন, এটি ঠিক সেই ধারণা।

3.2 দুটি model — OSI এবং TCP/IP

OSI model (Open Systems Interconnection) হলো একটি ৭-layer তাত্ত্বিক reference model। TCP/IP model হলো বাস্তবে যেটি Internet চালাচ্ছে সেটি — এতে ৪ বা ৫টি layer।

6PresentationTLS*, encoding

* TLS-কে প্রায়ই "Layer 6" বলা হয়, কিন্তু বাস্তবে সে TCP-এর ঠিক উপরে বসা একটি application-level library। OSI-এর সাথে হুবহু মেলানোর চেষ্টা এখানে বিভ্রান্তিকর।

⚠️ OSI নিয়ে সৎ কথা

OSI-এর ৭ layer একটি শেখানোর কাঠামো, Internet-এর প্রকৃত নকশা নয়। বাস্তবে layer 5 এবং 6 কার্যত ফাঁকা, আর TLS, QUIC, VPN-এর মতো জিনিস পরিষ্কারভাবে কোনো একটি layer-এ বসে না। "Please Do Not Throw Sausage Pizza Away" মুখস্থ করা এই বইয়ের লক্ষ্য নয়। লক্ষ্য হলো এই পাঁচটি দায়িত্ব বোঝা: physical signaling, local delivery, global routing, process-to-process reliability, application semantics। কেউ "Layer 3 problem" বললে যেন বোঝেন সে routing/IP-এর কথা বলছে — এটুকুই যথেষ্ট।

3.3 প্রতিটি layer-এর একটি বাক্যের দায়িত্ব

┌─────────────────────────────────────────────────────────────┐

├─────────────────────────────────────────────────────────────┤

└─────────────────────────────────────────────────────────────┘
🧠 Mental Model — দুটি scope

এই পার্থক্যটি বইয়ের অন্যতম গুরুত্বপূর্ণ ধারণা:

  • Link layer = এক hop। শুধু "আমার থেকে পরের যন্ত্র পর্যন্ত"। প্রতিটি hop-এ নতুন করে লেখা হয়।
  • Network layer = end to end। মূল উৎস থেকে চূড়ান্ত গন্তব্য পর্যন্ত অপরিবর্তিত থাকে।

এজন্যই MAC address প্রতি hop-এ বদলায় কিন্তু destination IP বদলায় না। Chapter 13-এ এটি ধাপে ধাপে দেখব — এবং এটি বুঝলে "router কেন MAC বদলায় কিন্তু IP বদলায় না" প্রশ্নটির উত্তর আপনাআপনি চলে আসে।

3.4 Encapsulation — বইয়ের সবচেয়ে গুরুত্বপূর্ণ ধারণা

Encapsulation (এনক্যাপসুলেশন) হলো সেই প্রক্রিয়া যেখানে প্রতিটি layer উপরের layer-এর পুরো data-কে অস্বচ্ছ payload হিসেবে ধরে নিয়ে তার সামনে (এবং কখনো পেছনে) নিজের header যোগ করে।

মূল কথাটি এই: নিচের layer উপরের layer-এর data-এর ভেতরে কী আছে তা জানে না এবং জানার দরকারও নেই। IP জানে না সে TCP বহন করছে না UDP; সে শুধু জানে "এই বান্ডিলটা ওই address-এ পৌঁছাতে হবে"।

পাঠানোর সময় — নিচে নামা

ধাপ 1 — Application আপনার data দেয়:

        ┌──────────────────────┐
        │  "GET /users ..."    │
        └──────────────────────┘

ধাপ 2 — TCP সামনে নিজের header লাগায় (port, seq, ACK):

        ┌────────┬──────────────────────┐
        │TCP Hdr │  "GET /users ..."    │   = SEGMENT
        └────────┴──────────────────────┘

ধাপ 3 — IP সামনে নিজের header লাগায় (src IP, dst IP, TTL):

    ┌───────┬────────┬──────────────────────┐
    │IP Hdr │TCP Hdr │  "GET /users ..."    │   = PACKET
    └───────┴────────┴──────────────────────┘

ধাপ 4 — Ethernet সামনে header, পেছনে trailer (checksum):

┌────────┬───────┬────────┬──────────────────────┬─────┐
│Eth Hdr │IP Hdr │TCP Hdr │  "GET /users ..."    │ FCS │  = FRAME
└────────┴───────┴────────┴──────────────────────┴─────┘

ধাপ 5 — NIC পুরোটাকে signal-এ বদলায়:

    10110100 01101001 11010010 00101101 ...     = BITS

গ্রহণের সময় — উপরে ওঠা (de-encapsulation)

BITS      →  NIC signal থেকে bit বানায়
   ↓
FRAME     →  "এই MAC কি আমার? হ্যাঁ।" Eth header খুলে ফেলে
   ↓          checksum যাচাই করে
PACKET    →  "এই IP কি আমার? হ্যাঁ।" IP header খুলে ফেলে
   ↓          protocol field দেখে: 6 = TCP
SEGMENT   →  "port 443? কোন socket?" TCP header খুলে ফেলে
   ↓          seq দেখে ঠিক জায়গায় বসায়
DATA      →  Application-এর read() call এই bytes পায়
🧠 Mental Model — চিঠি ও খাম

আপনি একটি চিঠি লিখলেন (application data)। সেটি একটি খামে ভরলেন যাতে ঠিকানা লেখা (IP header)। সেই খামটি ডাকঘরের একটি বস্তায় গেল যাতে "পরের শাখা: চট্টগ্রাম" লেখা (Ethernet frame)। চট্টগ্রামে পৌঁছে বস্তা খোলা হলো এবং খামটি নতুন বস্তায় ভরা হলো "পরের শাখা: হালিশহর" লিখে — খাম অপরিবর্তিত, বস্তা বদলে গেল। এটাই hop-by-hop link layer বনাম end-to-end network layer।

আর গুরুত্বপূর্ণ বিষয়: ডাকঘরের কেউ আপনার চিঠিটা পড়ে না। প্রতিটি layer শুধু নিজের header পড়ে। এটিই encapsulation-এর শক্তি।

3.5 Interactive — একটি packet-এর ভেতরে

নিচের প্রতিটি স্তরে click করে দেখুন সেখানে কী থাকে এবং কে সেটি পড়ে। এটি একটি HTTPS request-এর packet, যা Wi-Fi দিয়ে যাচ্ছে।

▸ যেকোনো স্তরে click করুন — বাইরের মোড়ক সবার উপরে, আপনার data সবার নিচে
L2Ethernet Header14 bytes

কী আছে: Destination MAC (6 B), Source MAC (6 B), EtherType (2 B — 0x0800 মানে ভেতরে IPv4, 0x86DD মানে IPv6, 0x0806 মানে ARP)।

কে পড়ে: switch এবং পরবর্তী hop-এর NIC।

কতদূর টেকে: মাত্র এক hop। প্রতিটি router এই header ফেলে দিয়ে নতুন লেখে। → Chapter 6

L3IP Header20 bytes

কী আছে: Source IP, Destination IP, TTL, Protocol (6 = TCP, 17 = UDP, 1 = ICMP), Total Length, Header Checksum, Fragment fields।

কে পড়ে: পথের প্রতিটি router।

কতদূর টেকে: end to end — গন্তব্য পর্যন্ত IP অপরিবর্তিত (NAT ছাড়া, Ch 34)। শুধু TTL প্রতি hop-এ ১ করে কমে। → Chapter 9

L4TCP Header20+ bytes

কী আছে: Source Port, Destination Port (443), Sequence Number, Acknowledgment Number, Flags (SYN/ACK/FIN/RST/PSH), Window Size, Checksum।

কে পড়ে: শুধু দুই প্রান্তের kernel। মাঝের router-রা সাধারণত এটি পড়েও না — TCP end-to-end।

কাজ: কোন process পাবে (port), কোন ক্রমে বসবে (seq), কী পাওয়া গেছে (ACK)। → Chapter 17–19

TLSTLS Record Header5 bytes

কী আছে: Content Type, TLS version, Record Length। এর পরেই শুরু হয় encrypted অংশ।

গুরুত্বপূর্ণ: এই header-এর নিচের সব কিছু encrypted। পথের কেউ IP, port, packet-এর আকার দেখতে পায় — কিন্তু URL, header, body দেখতে পায় না। → Chapter 31–33

L7HTTP Request (encrypted)variable

কী আছে: GET /users HTTP/1.1, Host:, Authorization:, cookie, body — অর্থাৎ আপনার application যা লিখেছে।

কে পড়ে: শুধু গন্তব্য server-এর application process, TLS decrypt করার পরে। → Chapter 28

L2Ethernet FCS (trailer)4 bytes

কী আছে: Frame Check Sequence — পুরো frame-এর একটি CRC32 checksum।

কাজ: transmission-এ bit নষ্ট হয়েছে কিনা তা শনাক্ত করা। Ethernet ভাঙা frame মেরামত করে না — সে চুপচাপ ফেলে দেয়। মেরামতের দায়িত্ব উপরের layer-এর (TCP)। এটি একটি চমৎকার উদাহরণ: প্রতিটি layer শুধু নিজের দায়িত্ব পালন করে।

3.6 Overhead — একটি হিসাব

Encapsulation বিনামূল্যে আসে না। প্রতিটি header জায়গা নেয়:

একটি সাধারণ 1500-byte Ethernet frame-এ:

  Ethernet header + FCS  :   18 bytes
  IPv4 header            :   20 bytes
  TCP header             :   20 bytes
  ─────────────────────────────────────
  মোট overhead           :   58 bytes
  Application data       : 1442 bytes  (~96%)

কিন্তু আপনি যদি একবারে 1 byte পাঠান:

  overhead : 58 bytes
  data     :  1 byte    (~1.7% efficiency!)
⚙️ Developer Perspective

এজন্যই ১০০০ বার ১ byte পাঠানোর চেয়ে একবারে ১০০০ byte পাঠানো নাটকীয়ভাবে দ্রুত। এজন্যই TCP-এর Nagle's algorithm ছোট write গুলোকে জমা করে একসাথে পাঠায় (আর latency-sensitive application-এ আমরা TCP_NODELAY দিয়ে সেটি বন্ধ করি)। এজন্যই database-এ batch insert দ্রুত, এবং এজন্যই GraphQL/HTTP2-এ request একত্র করার এত চেষ্টা। Per-message overhead হলো একটি বাস্তব খরচ, এবং এটি সরাসরি encapsulation থেকে আসে।

3.7 Common Confusions

MYTH

Data উপর থেকে নিচে নামার সময় প্রতিটি layer আগের layer-এর data-কে বদলে দেয় বা রূপান্তর করে।

REALITY

প্রতিটি layer উপরের layer-এর data-কে অপরিবর্তিত রেখে শুধু নিজের header যোগ করে। আপনার HTTP request-এর bytes যেমন ছিল, তার-এর মধ্য দিয়ে যাওয়ার সময়ও ঠিক তেমনই থাকে — শুধু সামনে-পেছনে কিছু মোড়ক যুক্ত হয়। (ব্যতিক্রম: TLS আসলেই encrypt করে রূপান্তর করে — সেটিই তার কাজ।)

MYTH

Router সব layer খুলে দেখে।

REALITY

একটি সাধারণ router শুধু Layer 2 এবং Layer 3 পর্যন্ত খোলে — frame খুলে IP header দেখে সিদ্ধান্ত নেয়, তারপর নতুন frame বানায়। TCP header তার কাছে অর্থহীন payload মাত্র। (NAT router-রা ব্যতিক্রম — তারা port বদলানোর জন্য TCP/UDP header-এ হাত দেয়, Ch 34। আর Layer-7 load balancer HTTP পর্যন্ত খোলে, Ch 47 — কিন্তু সেটি "router" নয়।)

MYTH

OSI-এর ৭টি layer মুখস্থ না করলে networking শেখা যায় না।

REALITY

বাস্তবে Internet চলে ৪–৫টি layer-এ। "Layer 2 / Layer 3 / Layer 4 / Layer 7" — এই চারটি শব্দ industry-তে ব্যবহৃত হয় এবং এদের অর্থ (link / IP / TCP-UDP / application) জানাই যথেষ্ট। Layer 5 আর 6 বাস্তবে প্রায় কেউ আলাদা করে ব্যবহার করে না।

# তারপর অন্য একটি terminal-এ:
curl -s https://example.com > /dev/null

যা লক্ষ্য করবেন: -e flag link-layer header দেখায়। Output-এ প্রথমে পাবেন দুটি MAC address (aa:bb:cc... > dd:ee:ff...) এবং ethertype IPv4 — এটাই Ethernet header। তারপর IP শব্দের পরে source ও destination IP এবং ttl — এটাই IP header। তারপর Flags [S], seq, win — এটাই TCP header। একটি লাইনেই তিনটি layer, একটির ভেতরে আরেকটি।

আমরা কী শিখলাম: Encapsulation কোনো তাত্ত্বিক চিত্র নয় — এটি তারের ভেতর দিয়ে যাওয়া bytes-এর প্রকৃত বিন্যাস। tcpdump ঠিক এই বিন্যাসটাই parse করে দেখাচ্ছে। → বিস্তারিত Chapter 41।

📌 Chapter Summary
  • Layering = separation of concerns। প্রতিটি layer একটি সমস্যা সমাধান করে এবং পাশেরটির ভেতর জানে না।
  • বাস্তব stack: Application → Transport → Network → Link → Physical।
  • Encapsulation = প্রতিটি layer উপরের সব কিছুকে payload ধরে নিজের header যোগ করে।
  • নিচে নামা: Data → Segment → Packet → Frame → Bits। উপরে ওঠা: ঠিক উল্টো।
  • Link layer এক hop-এর জন্য, Network layer end-to-end — এটিই MAC বদলায় কিন্তু IP বদলায় না-এর কারণ।
  • Header গুলো overhead — তাই ছোট ছোট অনেক write-এর চেয়ে বড় একটি write দক্ষ।
✓ Quick Check
Encapsulation-এর সময় IP layer কি TCP header পড়ে বা বোঝে?

না। IP-এর কাছে TCP segment-টি একটি অস্বচ্ছ byte-এর গুচ্ছ। IP শুধু নিজের header-এর Protocol field-এ 6 লিখে রাখে যাতে গন্তব্যের kernel জানতে পারে payload-টি TCP-কে দিতে হবে। এটাই সঠিক layering — IP জানে কাকে দিতে হবে, কিন্তু ভেতরে কী আছে তা নয়।

Segment, packet এবং frame — এদের সম্পর্ক কী?

এরা একই data-এর ক্রমবর্ধমান মোড়ক। Segment = TCP header + data। Packet = IP header + segment। Frame = Ethernet header + packet + FCS। অর্থাৎ frame-এর ভেতরে packet, packet-এর ভেতরে segment, segment-এর ভেতরে আপনার data।

একটি packet ৫টি router পেরিয়ে গেল। Ethernet header কতবার বদলাল? Destination IP কতবার বদলাল?

Ethernet header বদলাল প্রতিটি hop-এ — অর্থাৎ ৬ বার লেখা হলো (host→R1, R1→R2, R2→R3, R3→R4, R4→R5, R5→server)। Destination IP বদলাল শূন্য বার (NAT না থাকলে)। TTL কমল ৫ বার। এটিই "link = hop-local, network = end-to-end" নীতির সরাসরি ফল।

Ethernet-এর FCS ভাঙা frame শনাক্ত করে ফেলে দেয়, কিন্তু আবার পাঠায় না। এটি কি একটি design ত্রুটি?

না, এটি সচেতন design। Ethernet-এর দায়িত্ব শুধু "নষ্ট data উপরে পাঠাব না" — মেরামত নয়। মেরামত (retransmission) end-to-end সমস্যা, কারণ data ৫টি ভিন্ন link পেরোতে পারে; প্রতিটি link আলাদাভাবে reliability দিলেও end-to-end নির্ভরযোগ্যতার নিশ্চয়তা মেলে না। তাই সেই দায়িত্ব TCP-র, যে দুই প্রান্তে বসে আছে। এটি end-to-end principle-এর ধ্রুপদী উদাহরণ।

1 byte data পাঠাতে তারে সর্বনিম্ন কত byte যায় (TCP/IPv4/Ethernet)?

কমপক্ষে ৫৯ bytes payload+header (14 Eth + 20 IP + 20 TCP + 1 data + 4 FCS = 59)। বাস্তবে Ethernet-এর সর্বনিম্ন frame আকার 64 bytes, তাই padding দিয়ে ৬৪ bytes-এ পৌঁছায় — সাথে preamble ও inter-frame gap আলাদা। অর্থাৎ ১ byte পাঠাতে তারে যায় প্রায় ৮৪ bytes সমতুল্য সময়। এটিই ছোট packet-এর নিদারুণ অদক্ষতা।
