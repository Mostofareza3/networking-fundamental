TCP vs UDP — সঠিক তুলনা

"TCP ধীর, UDP দ্রুত" — এই সরলীকরণটি এতটাই প্রচলিত যে অনেকে এর ভিত্তিতে architecture-এর সিদ্ধান্ত নেন। এটি ভুল, এবং কেন ভুল তা বোঝা গুরুত্বপূর্ণ।

24.2 "TCP ধীর, UDP দ্রুত" — কেন এটি ভুল

MYTH

UDP TCP-র চেয়ে দ্রুত, তাই performance দরকার হলে UDP ব্যবহার করা উচিত।

REALITY

দুটি protocol-ই একই তারে, একই গতিতে packet পাঠায়। "গতি"-র পার্থক্য আসে নির্দিষ্ট পরিস্থিতিতে, এবং সেগুলো জানা জরুরি:

  • UDP-র প্রকৃত সুবিধা: handshake নেই (১ RTT সাশ্রয়), head-of-line blocking নেই, কম header, কম state।
  • কিন্তু: আপনার যদি reliability দরকার হয় এবং আপনি সেটি UDP-র উপর নিজে লেখেন, আপনার implementation প্রায় নিশ্চিতভাবে TCP-র চেয়ে খারাপ হবে — কারণ TCP-র congestion control ৩৫ বছরের গবেষণা ও বাস্তব পরীক্ষার ফসল।
  • বাস্তবে: বড় ফাইল transfer-এ TCP প্রায়ই সরল UDP implementation-এর চেয়ে দ্রুত, কারণ তার congestion control পথের প্রকৃত ক্ষমতা কাজে লাগাতে পারে।
🧠 সঠিক প্রশ্নটি

"কোনটি দ্রুত?" — ভুল প্রশ্ন।
"আমার application-এর জন্য পুরনো data-র কি কোনো মূল্য আছে?" — সঠিক প্রশ্ন।

24.4 QUIC — বিতর্কের অবসান

✓ তৃতীয় পথ

QUIC এই পুরো বিতর্কটিকে অপ্রাসঙ্গিক করে দিয়েছে। সে UDP-র উপর নির্মিত, কিন্তু TCP-র সব নির্ভরযোগ্যতা দেয় — এবং আরও কিছু:

          TCP        UDP        QUIC
Reliable   ✓          ✗          ✓
Ordered    ✓ (সব)     ✗          ✓ (stream-প্রতি)
HOL block  ✓ আছে      ✗ নেই      ✗ নেই ★
Handshake  1 RTT      0          0–1 RTT ★
Encryption আলাদা TLS  আলাদা      অন্তর্নির্মিত ★
Migration  ✗          —          ✓ ★
Where      kernel     kernel     user space ★

শেষ লাইনটি গুরুত্বপূর্ণ: QUIC user space-এ চলে, তাই application update করলেই নতুন congestion control পাওয়া যায় — kernel বা OS update-এর অপেক্ষা করতে হয় না। TCP-র উন্নতি দশকের পর দশক ধরে আটকে ছিল ঠিক এই কারণেই।

📌 Chapter Summary
  • TCP: connection, reliability, ordering, flow ও congestion control — একটি package হিসেবে।
  • UDP: শুধু port + checksum। বাকি সব আপনার দায়িত্ব।
  • "TCP ধীর, UDP দ্রুত" ভুল সরলীকরণ — দুটোই একই গতিতে packet পাঠায়।
  • সঠিক প্রশ্ন: পুরনো data-র কি মূল্য আছে? থাকলে TCP, না থাকলে UDP।
  • UDP-র প্রকৃত সুবিধা: handshake নেই, HOL blocking নেই, multicast সম্ভব, নিজস্ব transport লেখা যায়।
  • নিজে reliability লিখলে সেটি প্রায় নিশ্চিতভাবে TCP-র চেয়ে খারাপ হবে — QUIC ব্যবহার করুন।
  • QUIC = UDP-র নমনীয়তা + TCP-র নির্ভরযোগ্যতা + অন্তর্নির্মিত encryption + connection migration।
✓ Quick Check
"UDP দ্রুত কারণ তার header ছোট" — এই যুক্তি কতটা সঠিক?

খুব সামান্য। ১২ bytes-এর পার্থক্য একটি ১৫০০-byte packet-এ ০.৮% — নগণ্য। UDP-র প্রকৃত সুবিধা header-এর আকার নয়, বরং: (১) handshake না থাকায় ১ RTT সাশ্রয়, (২) head-of-line blocking না থাকা, (৩) retransmission-জনিত বিলম্ব না থাকা, (৪) কম kernel state। Header-এর আকার তালিকার সবচেয়ে নিচে।

একটি multiplayer game-এ খেলোয়াড়ের অবস্থান পাঠাতে কোনটি এবং কেন?

UDP। খেলোয়াড়ের অবস্থান প্রতি ৫০ms-এ update হয়। একটি হারানো update retransmit করে ২০০ms পরে পাওয়ার কোনো মূল্য নেই — ততক্ষণে চারটি নতুন update চলে এসেছে। TCP ব্যবহার করলে সেই পুরনো packet-এর জন্য নতুন update গুলো আটকে থাকত (HOL blocking), ফলে খেলা "rubber-banding" করত। তবে chat বা inventory-র মতো নির্ভরযোগ্য অংশগুলো TCP বা QUIC-এ পাঠানো হয়।

আপনার team একটি "custom reliable UDP protocol" লেখার প্রস্তাব দিয়েছে। কী প্রশ্ন করবেন?

(১) TCP বা QUIC কেন যথেষ্ট নয় — সুনির্দিষ্টভাবে? (২) Congestion control কে লিখবে এবং কীভাবে পরীক্ষা করা হবে? (এটি না থাকলে আপনার protocol network-এর জন্য ক্ষতিকর ও অন্যায্য।) (৩) NAT traversal, MTU discovery, retransmission timing — এগুলো কে সামলাবে? (৪) QUIC কি ব্যবহার করা যায়, যেখানে এই সব সমস্যা ইতিমধ্যে সমাধান করা আছে? বেশিরভাগ ক্ষেত্রে উত্তর হলো — QUIC ব্যবহার করুন।
