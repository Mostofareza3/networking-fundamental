Chapter 8

ARP — IP এবং MAC-এর মাঝের সেতু

আপনার application একটি IP address জানে। আপনার NIC শুধু MAC address বোঝে। এই দুটোর মাঝখানে একটি অনুবাদ দরকার — এবং সেই অনুবাদ কোনো কেন্দ্রীয় ডিরেক্টরি থেকে আসে না, আসে চিৎকার করে জিজ্ঞেস করার মাধ্যমে।

8.1 Why does this exist?

Chapter 6-এ frame তৈরির ধাপগুলোতে আমরা একটি ফাঁকে এসে থেমেছিলাম:

Application জানে :  "192.168.1.10-এ পাঠাও"
                          ↓
IP layer লেখে    :  dst IP = 192.168.1.10   ✓
                          ↓
Ethernet-এর দরকার:  dst MAC = ???           ✗  ← এখানেই সমস্যা
                          ↓
NIC পাঠাতে পারে না, কারণ frame অসম্পূর্ণ

কোনো কেন্দ্রীয় সার্ভার নেই যে বলে দেবে কোন IP-এর বিপরীতে কোন MAC। তাহলে উপায়?

💡 Why ARP

সমাধানটি সরল এবং কিছুটা অসভ্য: পুরো local network-এ চিৎকার করে জিজ্ঞেস করো। যেহেতু broadcast frame সবার কাছে পৌঁছায়, তাই একজন জিজ্ঞেস করে "192.168.1.10 কার?" এবং যার সেই IP, সে উত্তর দেয়। এটি কাজ করে কারণ local segment ছোট এবং broadcast সস্তা — এবং ঠিক এই কারণেই ARP শুধুমাত্র local network-এই সীমাবদ্ধ।

8.2 Core Concept

ARP (Address Resolution Protocol, অ্যাড্রেস রেজোলিউশন প্রোটোকল) হলো সেই protocol যা একটি local network-এ একটি IPv4 address-এর বিপরীতে সংশ্লিষ্ট MAC address খুঁজে বের করে।

Layer: 2 এবং 3-এর মাঝামাঝি EtherType: 0x0806 Scope: শুধু local segment IPv4 only

8.3 কীভাবে কাজ করে — একটি কথোপকথন

ধাপ ১ — ARP REQUEST (broadcast, সবাই পায়)

  ┌─────────────────────────────────────────────┐
  │ Ethernet:  dst = FF:FF:FF:FF:FF:FF  (সবাই)  │
  │            src = AA:AA:AA:AA:AA:AA          │
  │            type = 0x0806 (ARP)              │
  ├─────────────────────────────────────────────┤
  │ ARP:       "Who has 192.168.1.10?           │
  │             Tell 192.168.1.5"               │
  │            sender MAC = AA:AA:AA:AA:AA:AA   │
  │            sender IP  = 192.168.1.5         │
  │            target MAC = 00:00:00:00:00:00   │
  │            target IP  = 192.168.1.10        │
  └─────────────────────────────────────────────┘

           A ──▶ Switch ──┬──▶ B  (আমারই তো!)
                          ├──▶ C  (আমার না, উপেক্ষা)
                          └──▶ D  (আমার না, উপেক্ষা)


ধাপ ২ — ARP REPLY (unicast, শুধু A-এর কাছে)

  ┌─────────────────────────────────────────────┐
  │ Ethernet:  dst = AA:AA:AA:AA:AA:AA  (শুধু A)│
  │            src = BB:BB:BB:BB:BB:BB          │
  ├─────────────────────────────────────────────┤
  │ ARP:       "192.168.1.10 is at              │
  │             BB:BB:BB:BB:BB:BB"              │
  └─────────────────────────────────────────────┘

           B ──▶ Switch ──▶ A  (শুধু A পায়)


ধাপ ৩ — Cache-এ সংরক্ষণ, এবং তারপর আসল data

  A-এর ARP cache:
  ┌────────────────┬───────────────────┬─────────┐
  │ 192.168.1.10   │ BB:BB:BB:BB:BB:BB │ 60s     │
  └────────────────┴───────────────────┴─────────┘

  এখন A-এর আসল frame পাঠানো সম্ভব:
  [dst BB:BB | src AA:AA | 0x0800 | IP packet ...]
🧠 Mental Model

ARP-কে ভাবুন একটি ভরা ঘরে ঢুকে চিৎকার করা: "এখানে ১০ নম্বর টেবিলে কে বসেছে?" সবাই শোনে, কিন্তু শুধু সেই একজন হাত তোলে এবং ব্যক্তিগতভাবে এসে বলে "আমি, আমার নাম রহিম"। বাকিরা প্রশ্নটা শুনে ভুলে যায়। আর আপনি রহিমের নামটা মনে রাখেন — যাতে পরেরবার আবার চিৎকার করতে না হয়।

লক্ষ্য করুন: প্রশ্নটা broadcast, উত্তরটা unicast। এটি একটি সচেতন optimization — উত্তরও broadcast হলে network-এ দ্বিগুণ শব্দ হতো।

8.4 ARP Cache

প্রতিবার ARP করলে প্রতিটি packet-এর আগে একটি round trip লাগত — অগ্রহণযোগ্য। তাই প্রতিটি OS একটি ARP cache (বা neighbor table) রাখে।

bash
$ ip neigh
192.168.1.1  dev wlan0 lladdr a4:2b:b0:11:22:33 REACHABLE
192.168.1.10 dev wlan0 lladdr bb:bb:bb:bb:bb:bb STALE
192.168.1.55 dev wlan0  FAILED
Stateঅর্থ
REACHABLEসম্প্রতি যাচাই হয়েছে, নির্ভরযোগ্য
STALEজানা আছে কিন্তু কিছুক্ষণ ব্যবহার হয়নি; পরের বার ব্যবহারের সময় যাচাই হবে
DELAY / PROBEএই মুহূর্তে যাচাই চলছে
FAILEDজিজ্ঞেস করা হয়েছিল, কেউ উত্তর দেয়নি — ওই IP-তে কেউ নেই

Entry গুলোর একটি নির্দিষ্ট আয়ু আছে (সাধারণত কয়েক সেকেন্ড থেকে কয়েক মিনিট)। কারণটি switch-এর aging-এর মতোই — device বদলাতে পারে, IP পুনর্বণ্টিত হতে পারে, তাই পুরনো তথ্য চিরকাল বিশ্বাস করা যায় না।

8.5 সবচেয়ে গুরুত্বপূর্ণ কথা — ARP কখনো router পেরোয় না

⚠️ ARP কেন শুধু local

ARP request একটি broadcast frame। আর router কখনো broadcast forward করে না (সেটিই তো broadcast domain ভাঙার মানে, Ch 7)। ফলে ARP-এর পরিধি ঠিক এক subnet।

তাহলে দূরের কোনো IP-তে পাঠাতে চাইলে কী হয়? আপনি সেই দূরের IP-এর MAC কোনোদিন জানেন না এবং জানার দরকারও নেই — আপনি gateway-এর MAC জানেন, ব্যস।

দৃশ্য A — Destination আমার subnet-এ (192.168.1.10)

  ARP জিজ্ঞেস করে: "192.168.1.10 কার?"
  উত্তর আসে সরাসরি ওই host থেকে।
  Frame: [dst = host-এর MAC]


দৃশ্য B — Destination দূরে (142.250.190.14 = google.com)

  Routing table বলে: local নয় → gateway 192.168.1.1
  ARP জিজ্ঞেস করে: "192.168.1.1 কার?"      ← gateway-এর MAC!
  Frame: [dst = router-এর MAC | IP dst = 142.250.190.14]
                    ↑                       ↑
              এক hop-এর জন্য          end-to-end

  অর্থাৎ: MAC = পরের hop, IP = চূড়ান্ত গন্তব্য

এই একটি ছবিই Chapter 11 (default gateway) এবং Chapter 13 (packet journey)-এর ভিত্তি। যদি এই বই থেকে একটি ছবি মনে রাখেন, এটি সেই ছবি হোক।

8.6 Gratuitous ARP এবং ARP Spoofing

Gratuitous ARP — কেউ জিজ্ঞেস না করলেও ঘোষণা

একটি host কখনো কখনো নিজের IP-MAC মানচিত্র স্বপ্রণোদিতভাবে broadcast করে। কেন?

  • IP conflict শনাক্তকরণ: boot-এর সময় "এই IP কি অন্য কারো?" — কেউ উত্তর দিলে সংঘাত আছে।
  • Failover: একটি HA setup-এ backup server virtual IP গ্রহণ করলে সে gratuitous ARP পাঠায়, যাতে সবার cache তৎক্ষণাৎ নতুন MAC-এ update হয়। এটি keepalived/VRRP-এর মূল কৌশল।

ARP Spoofing — protocol-টির জন্মগত দুর্বলতা

⚠️ ARP-এ কোনো প্রমাণীকরণ নেই

ARP reply-তে কোনো signature নেই, কোনো যাচাই নেই। যে কেউ যেকোনো সময় বলতে পারে "192.168.1.1 আমার" — এবং সবাই বিশ্বাস করে ফেলে। এতে আক্রমণকারী নিজেকে gateway হিসেবে জাহির করে সব traffic নিজের মধ্য দিয়ে চালাতে পারে (man-in-the-middle)।

এটি ARP-এর নকশাগত সীমাবদ্ধতা — ১৯৮২ সালে যখন এটি লেখা হয়, তখন local network মানেই ছিল বিশ্বস্ত পরিবেশ। আজ এটি আর সত্য নয়।

✓ Developer-এর জন্য উপসংহার

Local network-এর নিরাপত্তার উপর ভরসা করবেন না। আপনার café-র Wi-Fi-তে যে কেউ ARP spoofing করে আপনার সব unencrypted traffic পড়তে পারে। এটিই TLS-এর প্রকৃত যৌক্তিকতা (Ch 31) — নিরাপত্তা আসে end-to-end encryption থেকে, network-এর "বিশ্বস্ততা" থেকে নয়।

8.7 IPv6-এ ARP নেই

IPv6-এ ARP-এর জায়গায় আছে NDP (Neighbor Discovery Protocol), যা ICMPv6-এর উপর চলে।

IPv4 (ARP)IPv6 (NDP)
ARP RequestNeighbor Solicitation (NS)
ARP ReplyNeighbor Advertisement (NA)
Broadcast ব্যবহার করেMulticast ব্যবহার করে — শুধু সম্ভাব্য প্রাপকদের বিরক্ত করে
আলাদা EtherType (0x0806)ICMPv6-এর ভেতরে
শুধু address resolutionrouter discovery, autoconfiguration-ও করে

ধারণাগতভাবে দুটি একই কাজ করে — "এই address-এর যন্ত্রটি কে?" পার্থক্য মূলত দক্ষতায় (broadcast-এর বদলে multicast) এবং পরিধিতে (NDP আরও অনেক কিছু করে)। এই বইয়ে আমরা IPv4/ARP দিয়েই মূল ধারণাগুলো তৈরি করব, কারণ mental model একই।

🧪 Lab 8 — একটি ARP কথোপকথন সরাসরি দেখুন

আমরা কী দেখতে চাইছি? — একটি বাস্তব ARP request ও reply, এবং local বনাম দূরবর্তী গন্তব্যের ক্ষেত্রে আচরণের পার্থক্য।

bash
# Terminal 1 — ARP traffic শুনুন
sudo tcpdump -i any -n arp

# Terminal 2 — cache থেকে একটি entry মুছে আবার ping দিন
sudo ip neigh flush all           # Linux
ping -c 1 192.168.1.1             # আপনার নিজের gateway

# তারপর একটি দূরবর্তী গন্তব্যে
ping -c 1 1.1.1.1

যা লক্ষ্য করবেন: প্রথম ping-এ tcpdump-এ দেখবেন ARP, Request who-has 192.168.1.1 tell 192.168.1.5 এবং তারপর ARP, Reply 192.168.1.1 is-at a4:2b:...। কিন্তু ping 1.1.1.1-এ 1.1.1.1-এর জন্য কোনো ARP হবে না — কারণ সেটি local নয়। বড়জোর gateway-এর জন্য ARP হবে (যদি cache-এ না থাকে)।

আমরা কী শিখলাম: ARP-এর পরিধি হাতে-কলমে প্রমাণিত। আপনার machine দূরবর্তী কোনো host-এর MAC কখনো জিজ্ঞেসই করে না — সে শুধু gateway-এর MAC চায়। "MAC = পরের hop, IP = গন্তব্য" — এটি আর তত্ত্ব নয়, এখন আপনি নিজের চোখে দেখেছেন।

📌 Chapter Summary
  • ARP IPv4 address থেকে MAC address বের করে — IP layer এবং Link layer-এর মধ্যে অনুপস্থিত সংযোগটি পূরণ করে।
  • Request হয় broadcast, reply হয় unicast।
  • ফলাফল ARP cache-এ জমা হয় সীমিত সময়ের জন্য (aging), যাতে পুরনো তথ্যে আটকে না থাকে।
  • ARP কখনো router পেরোয় না — এটি সম্পূর্ণভাবে local segment-এর protocol।
  • দূরবর্তী গন্তব্যের জন্য আপনি gateway-এর MAC ARP করেন, গন্তব্যের নয়। MAC = পরের hop, IP = চূড়ান্ত গন্তব্য।
  • ARP-এ কোনো প্রমাণীকরণ নেই → ARP spoofing সম্ভব → local network কখনো "বিশ্বস্ত" নয় → TLS দরকার।
  • IPv6-এ ARP-এর জায়গায় NDP, যা multicast ব্যবহার করে — কিন্তু ধারণাটি অভিন্ন।
✓ Quick Check
ARP request broadcast কিন্তু reply unicast — কেন এই অসামঞ্জস্য?

Request-কে broadcast হতেই হবে, কারণ জিজ্ঞাসাকারী জানে না কার কাছে জিজ্ঞেস করবে — সেটাই তো প্রশ্ন। কিন্তু উত্তরদাতা ঠিক জানে কার কাছে উত্তর পাঠাতে হবে, কারণ request-এর ভেতরেই sender-এর IP ও MAC দেওয়া আছে। তাই reply unicast করাই যথেষ্ট এবং তাতে অপ্রয়োজনীয় network-শব্দ এড়ানো যায়।

আপনি curl https://github.com চালালেন। GitHub-এর server-এর MAC address জানতে কি ARP হয়?

না, কখনোই না। GitHub-এর server আপনার local segment-এ নেই, আর ARP broadcast router পেরোয় না। আপনার machine শুধু default gateway-এর MAC জানতে ARP করে (তাও যদি cache-এ না থাকে)। GitHub-এর server-এর MAC address আপনার machine কোনোদিন জানে না — এবং সেটির প্রয়োজনও নেই, কারণ MAC কেবল এক hop-এর ব্যাপার।

ARP cache-এ কোনো aging না থাকলে কী কী সমস্যা হতো?

(১) কোনো device-এর NIC বদলালে বা IP অন্য device-এ গেলে আপনি চিরকাল ভুল MAC-এ পাঠাতেন। (২) HA failover কাজ করত না — নতুন server virtual IP নিলেও আপনি পুরনোটাতেই পাঠাতেন। (৩) DHCP-তে IP পুনর্বণ্টন হলে ভুল host-এ traffic যেত। Aging হলো ভুল থেকে স্বয়ংক্রিয় পুনরুদ্ধারের ব্যবস্থা।

ARP spoofing সম্ভব হয় কেন, এবং এর বাস্তব প্রতিকার কী?

সম্ভব হয় কারণ ARP-এ কোনো প্রমাণীকরণ নেই — যেকোনো host যেকোনো IP-এর দাবি করতে পারে এবং সবাই বিনা প্রশ্নে বিশ্বাস করে। Network-স্তরে কিছু প্রশমন আছে (switch-এ Dynamic ARP Inspection, static ARP entry, 802.1X), কিন্তু একজন developer-এর জন্য প্রকৃত প্রতিকার হলো end-to-end encryption — TLS। আক্রমণকারী traffic নিজের মধ্য দিয়ে চালাতে পারলেও encrypted content পড়তে বা বদলাতে পারবে না।

Gratuitous ARP কী এবং কখন এটি দরকার হয়?

কেউ জিজ্ঞেস না করলেও নিজের IP-MAC মানচিত্র broadcast করা। দুটি প্রধান ব্যবহার: (১) boot-এর সময় IP conflict শনাক্ত করা, (২) HA failover-এ — backup server virtual IP গ্রহণ করে gratuitous ARP পাঠায়, যাতে সবার ARP cache তৎক্ষণাৎ নতুন MAC-এ update হয় এবং traffic সেকেন্ডের মধ্যে নতুন server-এ চলে যায়।
