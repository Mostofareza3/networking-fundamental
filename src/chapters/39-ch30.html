Chapter 30

HTTP Connections — 1.0 থেকে 3 পর্যন্ত

HTTP-র প্রতিটি নতুন version মূলত একটি সমস্যারই সমাধান করেছে: একটি TCP connection দিয়ে কীভাবে আরও বেশি কাজ করা যায়। এই বিবর্তনের গল্পটি জানলে HTTP/2 ও HTTP/3-এর নকশা স্বাভাবিক মনে হবে।

30.1 HTTP/1.0 — প্রতিটি request-এ নতুন connection

একটি page-এ ১টি HTML + ৩টি image:

  TCP handshake → GET /index.html → response → close
  TCP handshake → GET /logo.png   → response → close
  TCP handshake → GET /photo.jpg  → response → close
  TCP handshake → GET /icon.png   → response → close

  ৪টি handshake = ৪ × RTT শুধু connection-এর জন্য
  ৪ বার slow start = প্রতিবার cwnd ১০ থেকে শুরু
  ৪ বার TIME_WAIT socket

RTT 60ms হলে শুধু handshake-এই ২৪০ms নষ্ট।

30.2 HTTP/1.1 — Keep-Alive

  TCP handshake
      ├── GET /index.html → response
      ├── GET /logo.png   → response
      ├── GET /photo.jpg  → response
      └── GET /icon.png   → response
  close (বা idle timeout)

  ১টি handshake, ১ বার slow start।
  cwnd বড় হয়ে থাকে, তাই পরের response গুলো দ্রুত।

HTTP/1.1-এ keep-alive ★default★।
বন্ধ করতে চাইলে স্পষ্টভাবে বলতে হয়:
    Connection: close
⚠️ কিন্তু একটি বড় সীমাবদ্ধতা রয়ে গেল

HTTP/1.1-এ একটি connection-এ একবারে একটি request। পরেরটি শুরু করার আগে আগেরটির response সম্পূর্ণ হতে হবে।

  ├── GET /slow-api    → ...... ৩ সেকেন্ড অপেক্ষা ......
  ├── GET /small.css   → এই দুটি সম্পূর্ণ প্রস্তুত থাকলেও
  └── GET /small.js    → অপেক্ষা করছে!

এটি ★application-স্তরের★ head-of-line blocking।
(TCP-স্তরের HOL blocking-এর সাথে গুলিয়ে ফেলবেন না, Ch 19।)

Pipelining নামে একটি সমাধান চেষ্টা করা হয়েছিল — উত্তরের অপেক্ষা না করে পরপর request পাঠানো। কিন্তু response গুলো তখনো ক্রমানুসারে আসতে হতো, তাই HOL blocking রয়ে গেল। উপরন্তু বহু proxy এটি ভুলভাবে implement করেছিল। ফলে সব browser এটি বন্ধ করে রাখে — pipelining কার্যত মৃত।

Browser-দের কৌশল — সমান্তরাল connection

Browser একই origin-এ ৬টি TCP connection খোলে:

  Connection 1: GET /index.html
  Connection 2: GET /style.css
  Connection 3: GET /app.js
  Connection 4: GET /logo.png
  Connection 5: GET /photo.jpg
  Connection 6: GET /icon.png

  → ৬টি সমান্তরাল request

কিন্তু এর মূল্য:
  ✗ ৬ × handshake (এবং HTTPS হলে ৬ × TLS handshake)
  ✗ ৬ × slow start — প্রতিটি ছোট cwnd থেকে শুরু
  ✗ Server-এ ৬ গুণ socket ও memory
  ✗ ৬টি connection নিজেদের মধ্যেই bandwidth-এর
    জন্য প্রতিযোগিতা করে

এবং ৬-এর সীমা থাকায় একটি page-এ ৫০টি resource
থাকলে সেগুলো সারিবদ্ধ হয়ে অপেক্ষা করে।

এই সীমা এড়াতে তখনকার কৌশল ছিল "domain sharding" —
img1.example.com, img2.example.com ইত্যাদি বানিয়ে
৬ × ৩ = ১৮টি connection পাওয়া। HTTP/2-তে এটি
এখন ক্ষতিকর — কারণ multiplexing-এর সুবিধা নষ্ট করে।

30.3 HTTP/2 — Multiplexing

একটি TCP connection, বহু "stream" একসাথে:

  ┌─────────────── একটি TCP connection ────────────────┐
  │                                                    │
  │  Stream 1: ██  ██      ██        GET /index.html   │
  │  Stream 3:   ██   ██  ██         GET /style.css    │
  │  Stream 5:  ██  ██  ██           GET /app.js       │
  │  Stream 7:    ██  ██   ██        GET /logo.png     │
  │                                                    │
  │  ★ frame গুলো মিশে যাচ্ছে, কিন্তু stream ID দিয়ে      │
  │    আলাদা করা যায় ★                                  │
  └────────────────────────────────────────────────────┘

মূল পরিবর্তনগুলো:

1. BINARY FRAMING
   Text-এর বদলে binary frame। Parse করা দ্রুত ও
   দ্ব্যর্থহীন। প্রতিটি frame-এ stream ID থাকে।

2. MULTIPLEXING
   একটি connection-এ বহু request একসাথে, কোনো ক্রম
   বাধ্যতামূলক নয়। ★ application-স্তরের HOL blocking শেষ ★

3. HEADER COMPRESSION (HPACK)
   HTTP header-এ প্রচুর পুনরাবৃত্তি থাকে —
   User-Agent, Accept, Cookie প্রতিটি request-এ একই।
   HPACK একটি ভাগ করা table রাখে; দ্বিতীয়বার
   পুরো header-এর বদলে শুধু একটি index পাঠানো হয়।
   ৮০-৯০% সাশ্রয় সাধারণ।

4. SERVER PUSH
   Server চাওয়ার আগেই resource পাঠাতে পারত।
   ★ বাস্তবে কাজ করেনি (browser-এর cache-এ কী আছে
     server জানে না, তাই প্রায়ই অপচয়) — Chrome এটি
     ২০২২-এ সরিয়ে ফেলেছে। এখন 103 Early Hints
     ব্যবহার করা হয়।

5. STREAM PRIORITY
   কোন resource আগে দরকার তা জানানো যায়।
⚠️ HTTP/2 একটি সমস্যা সমাধান করতে পারেনি

Application-স্তরের HOL blocking গেল। কিন্তু TCP-স্তরের HOL blocking রয়ে গেল — এবং সেটি আরও খারাপ হলো।

একটি TCP connection-এ ১০০টি stream multiplexed।

একটি TCP segment হারাল।

TCP বলে: "ক্রম রক্ষা করতে হবে" (Ch 19)
     → পরের সব segment আটকে গেল
     → ★১০০টি stream-ই আটকে গেল★
       যদিও ৯৯টির data পৌঁছে গেছে!

HTTP/1.1-এ ৬টি আলাদা connection ছিল, তাই একটির
loss শুধু সেটিকেই প্রভাবিত করত।

⇒ উচ্চ packet loss-এর network-এ HTTP/2 কখনো কখনো
  HTTP/1.1-এর চেয়েও খারাপ পারফর্ম করে।

এই সমস্যাটি TCP-র মধ্যে সমাধান করা অসম্ভব — কারণ TCP একটি একক ordered stream, সে জানেই না ভেতরে একাধিক স্বাধীন stream আছে। সমাধান করতে হলে transport layer বদলাতে হবে। এটাই HTTP/3-এর জন্মের কারণ।

30.4 HTTP/3 — QUIC-এর উপর

HTTP/1.1 ও HTTP/2:          HTTP/3:

   HTTP                        HTTP/3
     ↓                           ↓
   TLS                        ┌──────────┐
     ↓                        │  QUIC    │ ← TLS 1.3 ভেতরেই
   TCP                        │ (stream, │   অন্তর্ভুক্ত
     ↓                        │  reliab- │
   IP                         │  ility)  │
                              └────┬─────┘
                                   ↓
                                 UDP
                                   ↓
                                  IP

QUIC কী সমাধান করে:

✓ Stream-প্রতি স্বাধীন reliability
  → একটি stream-এ loss হলে অন্যরা অপ্রভাবিত
  → ★ TCP-স্তরের HOL blocking সম্পূর্ণ শেষ ★

✓ 0-RTT / 1-RTT handshake
  → transport ও crypto handshake একসাথে
  → পুনঃসংযোগে ০ RTT সম্ভব

✓ Connection migration
  → connection ID দিয়ে চিহ্নিত, 4-tuple দিয়ে নয়
  → Wi-Fi থেকে mobile data-তে গেলেও connection টেকে

✓ User space-এ চলে
  → নতুন congestion control পেতে OS update লাগে না
  → দ্রুত পরীক্ষা ও উন্নয়ন সম্ভব

✓ Header ও প্রায় সব metadata encrypted
  → middlebox হস্তক্ষেপ করতে পারে না (ossification-এর
    বিরুদ্ধে সুরক্ষা)

⚙️ Developer Perspective — কোনটি ব্যবহার করবেন
  • HTTP/2 সক্রিয় করুন — nginx/Caddy/Cloudflare-এ কয়েক লাইনের কাজ, এবং প্রায় সব ক্ষেত্রেই উন্নতি।
  • HTTP/2-তে domain sharding বাদ দিন — এটি এখন ক্ষতিকর, কারণ multiplexing-এর সুবিধা নষ্ট করে এবং অতিরিক্ত connection তৈরি করে।
  • File concatenation পুনর্বিবেচনা করুন — HTTP/1.1-এ ৫০টি ছোট ফাইল খারাপ ছিল, HTTP/2-তে ততটা নয় (এবং ছোট ফাইল আলাদা থাকলে cache invalidation ভালো হয়)।
  • HTTP/3 সাধারণত CDN-এর মাধ্যমে — Cloudflare, Fastly-তে toggle করলেই হয়ে যায়।
  • Server push ভুলে যান — এর বদলে 103 Early Hints বা <link rel="preload">।
  • Internal service-এ HTTP/2 (gRPC) — long-lived multiplexed connection microservice-এর জন্য আদর্শ।
🧪 Lab 30 — কোন version ব্যবহার হচ্ছে

আমরা কী দেখতে চাইছি? — বিভিন্ন site কোন HTTP version ব্যবহার করছে, এবং version-ভেদে সময়ের পার্থক্য।

bash
# কোন version আলোচিত হলো?
curl -sI https://www.cloudflare.com | head -1
curl -sI https://example.com | head -1

# জোর করে নির্দিষ্ট version
curl -sI --http1.1 https://www.cloudflare.com | head -1
curl -sI --http2 https://www.cloudflare.com | head -1
curl -sI --http3 https://www.cloudflare.com | head -1   # curl-এ HTTP/3 support লাগবে

# Keep-alive-এর প্রভাব মাপুন
echo "--- আলাদা connection (৫টি) ---"
time (for i in 1 2 3 4 5; do curl -s -o /dev/null https://example.com; done)

echo "--- একই connection (৫টি) ---"
time curl -s -o /dev/null https://example.com \
       -o /dev/null https://example.com \
       -o /dev/null https://example.com \
       -o /dev/null https://example.com \
       -o /dev/null https://example.com

# HTTP/3-এর ঘোষণা দেখুন
curl -sI https://www.cloudflare.com | grep -i alt-svc

যা লক্ষ্য করবেন: প্রথম লাইনে HTTP/2 200 বা HTTP/1.1 200 OK। একই connection-এ ৫টি request আলাদা connection-এর চেয়ে নাটকীয়ভাবে দ্রুত — কারণ handshake ও slow start একবারই হচ্ছে। alt-svc: h3=":443" header-টি browser-কে জানায় "পরের বার HTTP/3-তে এসো" (HTTP/3 আবিষ্কারের প্রমিত উপায়)।

আমরা কী শিখলাম: Connection reuse-এর সুবিধা তাত্ত্বিক নয়, সরাসরি পরিমাপযোগ্য। আর HTTP/3-এ যাওয়ার প্রক্রিয়াটি নিজেই আকর্ষণীয় — প্রথম সংযোগ TCP-তে হয়, তারপর alt-svc দেখে browser পরের বার QUIC চেষ্টা করে।

📌 Chapter Summary
  • HTTP/1.0: প্রতিটি request-এ নতুন connection — চরম অপচয়।
  • HTTP/1.1: keep-alive (default), কিন্তু একটি connection-এ একবারে একটি request।
  • Browser ৬টি সমান্তরাল connection দিয়ে এই সীমা এড়াত — কিন্তু ৬ × handshake ও ৬ × slow start।
  • HTTP/2: binary framing, multiplexing, HPACK — application-স্তরের HOL blocking শেষ।
  • কিন্তু HTTP/2-তে TCP-স্তরের HOL blocking তীব্র হয় — একটি loss সব stream আটকায়।
  • HTTP/3 (QUIC over UDP): stream-প্রতি স্বাধীন reliability, 0–1 RTT handshake, connection migration।
  • HTTP/2-তে domain sharding ও অতিরিক্ত file concatenation এখন ক্ষতিকর।
✓ Quick Check
HTTP/2-তে multiplexing থাকা সত্ত্বেও একটি packet loss কেন সব stream-কে প্রভাবিত করে?

কারণ সব stream একটিই TCP connection-এর উপর দিয়ে যাচ্ছে, এবং TCP নিচের স্তরে কঠোরভাবে ক্রম রক্ষা করে। TCP জানেই না ভেতরে একাধিক স্বাধীন stream আছে — তার কাছে এটি একটি byte stream মাত্র। একটি segment হারালে পরের সব byte আটকে যায় (Ch 19-এর head-of-line blocking), তাই সব stream আটকে যায়। QUIC এটি সমাধান করে transport layer-এই stream-এর ধারণা এনে।

HTTP/2 ব্যবহার করলে domain sharding কেন বাদ দেওয়া উচিত?

Domain sharding-এর উদ্দেশ্য ছিল HTTP/1.1-এর ৬-connection সীমা এড়ানো। HTTP/2-তে একটি connection-এই অসীম multiplexing সম্ভব, তাই sharding কোনো সুবিধা দেয় না — বরং ক্ষতি করে: অতিরিক্ত DNS lookup, অতিরিক্ত TCP + TLS handshake, একাধিক connection-এর মধ্যে bandwidth-এর প্রতিযোগিতা, এবং HPACK-এর header compression table ভাগ হয়ে যাওয়া।

QUIC UDP-র উপর তৈরি — এতে reliability কি হারিয়ে যায়?

না। QUIC নিজেই reliability implement করে — sequence number, acknowledgment, retransmission, congestion control — সবই আছে, শুধু TCP-র বদলে QUIC-এর নিজের স্তরে। পার্থক্য হলো সে এগুলো stream-প্রতি করে, তাই একটি stream-এর loss অন্যদের আটকায় না। UDP এখানে শুধু একটি "খালি ক্যানভাস" — যেহেতু নতুন transport protocol Internet-এ deploy করা প্রায় অসম্ভব (middlebox গুলো অচেনা protocol block করে), তাই UDP-র উপর তৈরি করা হয়েছে।

HTTP/2-র server push কেন ব্যর্থ হলো?

Server জানে না client-এর cache-এ ইতিমধ্যে কী আছে। ফলে সে প্রায়ই এমন resource push করত যা browser-এর কাছে আগে থেকেই ছিল — bandwidth-এর সরাসরি অপচয়, এবং অন্য জরুরি resource-এর সাথে প্রতিযোগিতা। বাস্তব পরিমাপে দেখা গেল বেশিরভাগ ক্ষেত্রে এটি ক্ষতি করছে। Chrome ২০২২-এ support সরিয়ে ফেলে। বিকল্প: 103 Early Hints — server শুধু ইঙ্গিত দেয় কী কী লাগবে, browser সিদ্ধান্ত নেয় সে চাইবে কিনা।
