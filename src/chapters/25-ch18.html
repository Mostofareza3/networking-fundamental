Chapter 18

TCP Three-Way Handshake

তিনটি packet — এবং তার পরেই দুটি machine "connected"। কিন্তু connection বলে বাস্তবে কিছু নেই; তার-এ কোনো circuit তৈরি হয় না। তাহলে এই তিনটি packet ঠিক কী প্রতিষ্ঠা করে?

18.1 Why three packets?

প্রশ্নটা যুক্তিসঙ্গত: একটি "connect করো" packet আর একটি "ঠিক আছে" packet — দুটোই কি যথেষ্ট নয়?

💡 কেন দুটি যথেষ্ট নয়

Handshake-এর মূল উদ্দেশ্য দুটি জিনিস প্রতিষ্ঠা করা, দুই দিকেই:

  1. উভয় পক্ষ নিশ্চিত হয়েছে যে অপর পক্ষ বেঁচে আছে ও প্রস্তুত।
  2. উভয় পক্ষ অপরের Initial Sequence Number জেনেছে।

দুটি packet-এ শুধু client-এর ISN server-এর কাছে পৌঁছাত এবং client জানত server সাড়া দিয়েছে। কিন্তু server জানত না যে তার নিজের ISN client পেয়েছে। তৃতীয় packet (ACK) ঠিক সেই ফাঁকটি পূরণ করে।

এটি computer science-এর একটি সাধারণ সমস্যা — mutual agreement প্রতিষ্ঠা করতে ন্যূনতম তিনটি বার্তা লাগে (দুটি স্বাধীন one-way তথ্য + একটি নিশ্চিতকরণ)।

ℹ️ লক্ষণীয় খুঁটিনাটি
  • ISN দুটি স্বাধীন — client 1000, server 5000। দুই দিকের byte stream সম্পূর্ণ আলাদাভাবে গোনা হয়। TCP full-duplex, তাই দুটি স্বাধীন stream।
  • SYN নিজেই একটি sequence number খায় — এজন্যই ack 1000-এর বদলে 1001। FIN-ও একইভাবে একটি খায়।
  • Options এখানেই আলোচিত হয় — MSS, window scaling, SACK, timestamp। Handshake-এর পরে এগুলো বদলানো যায় না।
  • তৃতীয় packet-এর সাথে data পাঠানো যায় — অনেক implementation ACK-এর সাথেই প্রথম request জুড়ে দেয় (piggyback)।

18.3 Handshake-এর প্রকৃত মূল্য — RTT

Data পাঠানোর আগেই ব্যয় হয় ১ RTT:

  Client                          Server
    │──── SYN ───────────────────▶│   0.5 RTT
    │◀─── SYN-ACK ────────────────│   1.0 RTT
    │──── ACK + প্রথম request ────▶│   1.5 RTT
                                       ↑
                     এখানেই প্রথম byte data পৌঁছাল

Dhaka → Singapore, RTT ≈ 60ms:
    TCP handshake            : 60ms
    + TLS 1.3 handshake      : 60ms
    + HTTP request/response  : 60ms
    ────────────────────────────────
    প্রথম byte পেতে           : ~180ms
    (এখনো কোনো প্রকৃত content আসেনি!)

এজন্যই connection reuse (keep-alive) এত গুরুত্বপূর্ণ —
পরের request-গুলোতে শুধু ৬০ms লাগে, ১৮০ নয়।
⚙️ Developer Perspective

এই হিসাবটিই ব্যাখ্যা করে কেন:

  • HTTP keep-alive এত গুরুত্বপূর্ণ — একই connection পুনর্ব্যবহার করলে handshake-এর খরচ একবারই।
  • Connection pool দরকার — database driver-এ প্রতিটি query-র জন্য নতুন connection মানে প্রতিবার handshake।
  • CDN latency কমায় — handshake কাছের edge-এর সাথে হয়, ৬০ms-এর বদলে ৫ms (Ch 46)।
  • QUIC তৈরি হয়েছে — সে transport ও crypto handshake একসাথে করে, ফলে ১ RTT (বা পুনঃসংযোগে ০ RTT) সাশ্রয় (Ch 45)।

একটি সাধারণ ভুল: microservice-এ প্রতিটি internal call-এ নতুন TCP connection খোলা। ১০০০ call = ১০০০ handshake = অপ্রয়োজনীয় সেকেন্ডের পর সেকেন্ড।

18.4 Backlog Queue — connection যেখানে অপেক্ষা করে

Kernel দুটি queue রাখে:

  ┌──────────────────────────────────────────┐
  │ SYN queue (incomplete)                   │
  │   SYN এসেছে, SYN-ACK পাঠানো হয়েছে,       │
  │   তৃতীয় ACK-এর অপেক্ষা                   │
  │   → net.ipv4.tcp_max_syn_backlog          │
  └──────────────┬───────────────────────────┘
                 │ ACK এল
                 ▼
  ┌──────────────────────────────────────────┐
  │ Accept queue (complete)                  │
  │   Handshake সম্পূর্ণ, ESTABLISHED,        │
  │   application-এর accept() কল-এর অপেক্ষা   │
  │   → listen(fd, backlog)-এর backlog        │
  └──────────────┬───────────────────────────┘
                 │ accept() call করল
                 ▼
           Application-এর হাতে

Accept queue ভরে গেলে:
  নতুন সম্পূর্ণ হওয়া connection ফেলে দেওয়া হয় (নীরবে)
  → client retry করে → দেরি → শেষে timeout
⚠️ একটি বাস্তব উৎপাদন-সমস্যা

আপনার server "ধীর" মনে হচ্ছে, কিন্তু CPU ৩০%, memory ঠিক আছে। সম্ভাব্য কারণ: application accept() যথেষ্ট দ্রুত করছে না (হয়তো প্রতিটি request synchronously handle করছে), ফলে accept queue ভরে যাচ্ছে এবং connection নীরবে ফেলে দেওয়া হচ্ছে।

যাচাই: ss -lnt-এ Send-Q হলো backlog-এর সর্বোচ্চ, Recv-Q হলো বর্তমানে queue-তে অপেক্ষমাণ সংখ্যা। Recv-Q ধারাবাহিকভাবে Send-Q-র কাছাকাছি থাকলে সমস্যা এখানেই। netstat -s | grep -i listen দিয়ে overflow-এর গণনাও দেখা যায়।

18.5 SYN Flood এবং SYN Cookie

Handshake-এর একটি জন্মগত দুর্বলতা: server-কে SYN পাওয়ামাত্রই state রাখতে হয়, তৃতীয় packet আসার আগেই।

আক্রমণ:
  Attacker হাজার হাজার SYN পাঠায়, ভুয়া source IP দিয়ে
    → Server প্রতিটির জন্য SYN queue-তে state রাখে
    → SYN-ACK পাঠায় (যা কোথাও পৌঁছায় না)
    → তৃতীয় ACK কখনো আসে না
    → SYN queue ভরে যায়
    → প্রকৃত ব্যবহারকারীরা connect করতে পারে না

প্রতিকার — SYN Cookie:
  Server SYN queue-তে কিছু রাখে না। বরং সে
  ISN-এর ভেতরেই connection-এর তথ্য cryptographically
  encode করে দেয়।
    → তৃতীয় ACK এলে সেই ack number থেকেই সব তথ্য
      পুনরুদ্ধার করা যায়
    → কোনো state নেই, তাই ভরে যাওয়ারও কিছু নেই

Linux-এ: net.ipv4.tcp_syncookies = 1 (সাধারণত default)
শুধু queue ভরে গেলেই সক্রিয় হয়।
🧪 Lab 18 — Handshake নিজের চোখে

আমরা কী দেখতে চাইছি? — তিনটি packet, তাদের flag, এবং sequence number-এর প্রকৃত বিনিময়।

bash
# Terminal 1 — শুধু handshake-এর packet গুলো ধরুন
sudo tcpdump -i any -n 'tcp[tcpflags] & (tcp-syn|tcp-ack) != 0 and port 80' -c 6

# Terminal 2
curl -s http://example.com > /dev/null

# handshake-এর সময় আলাদা করে দেখুন
curl -w "DNS:      %{time_namelookup}s\nTCP:      %{time_connect}s\nTLS:      %{time_appconnect}s\nফার্স্ট বাইট: %{time_starttransfer}s\nমোট:      %{time_total}s\n" \
     -o /dev/null -s https://example.com

যা লক্ষ্য করবেন: tcpdump-এ পরপর Flags [S], Flags [S.] (SYN-ACK), Flags [.] (ACK) — ঠিক তিনটি। প্রতিটির পাশে seq এবং ack সংখ্যা। curl-এর timing-এ time_connect হলো ঠিক এই handshake-এর সময় (এক RTT), আর time_appconnect − time_connect হলো TLS-এর সময়।

আমরা কী শিখলাম: "Connection" একটি বিমূর্ত ধারণা যা তিনটি প্রকৃত packet দিয়ে প্রতিষ্ঠিত হয়, এবং তার একটি পরিমাপযোগ্য মূল্য আছে — এক RTT। curl-এর timing breakdown ব্যবহার করে আপনি যেকোনো ধীর request-এ ঠিক কোন ধাপে সময় যাচ্ছে তা আলাদা করতে পারবেন।

📌 Chapter Summary
  • Three-way handshake দুটি জিনিস প্রতিষ্ঠা করে দুই দিকেই: অপর পক্ষ সচল, এবং অপর পক্ষের ISN।
  • SYN → SYN-ACK → ACK। প্রতিটি পক্ষের নিজস্ব random ISN।
  • SYN নিজেই একটি sequence number ব্যয় করে (তাই ack = seq + 1)।
  • MSS, window scale, SACK — সব option handshake-এই আলোচিত হয়, পরে নয়।
  • খরচ: ১ RTT, data পাঠানোর আগেই। TLS যোগ হলে আরও।
  • Kernel-এ দুটি queue: SYN queue (অসম্পূর্ণ) ও accept queue (সম্পূর্ণ, accept()-এর অপেক্ষায়)।
  • SYN flood আক্রমণ SYN queue ভরিয়ে দেয়; SYN cookie state ছাড়াই এটি প্রতিহত করে।
✓ Quick Check
দুটি packet-এর handshake কেন যথেষ্ট নয়?

দুটি packet-এ (SYN, SYN-ACK) client নিশ্চিত হয় যে server তার ISN পেয়েছে এবং সাড়া দিয়েছে। কিন্তু server নিশ্চিত হয় না যে তার নিজের ISN client পেয়েছে — SYN-ACK পথে হারিয়ে যেতে পারত। তৃতীয় ACK সেই নিশ্চিতকরণটি দেয়। উভয় দিকের sequence number প্রতিষ্ঠা করতে ন্যূনতম তিনটি বার্তা লাগে।

ISN random হওয়া কেন জরুরি?

দুটি কারণ। (১) পুরনো packet: একই 4-tuple-এর আগের কোনো connection-এর দেরিতে পৌঁছানো packet যেন নতুন connection-এ বৈধ হিসেবে গৃহীত না হয়। (২) নিরাপত্তা: ISN অনুমানযোগ্য হলে আক্রমণকারী সঠিক sequence number সহ নকল packet ঢুকিয়ে connection-এ data inject করতে বা reset করতে পারত।

Dhaka থেকে একটি US server-এ (RTT 250ms) একটি HTTPS request-এ ন্যূনতম কত সময় লাগবে?

আনুমানিক: DNS (যদি cache-এ না থাকে) ~250ms + TCP handshake 250ms + TLS 1.3 handshake 250ms + request/response 250ms = প্রায় ১ সেকেন্ড — কোনো server processing time ছাড়াই, শুধু আলোর গতি ও protocol-এর round trip-এর কারণে। এটিই CDN, connection reuse এবং QUIC-এর অস্তিত্বের যুক্তি।

Accept queue ভরে গেলে কী হয় এবং client কী দেখে?

Kernel সম্পূর্ণ handshake হওয়া নতুন connection নীরবে ফেলে দেয় (বা কিছু ক্ষেত্রে RST পাঠায়)। Client-এর দিকে এটি দেখায় দীর্ঘ বিলম্ব হিসেবে (retry-এর পর retry), অবশেষে timeout বা connection reset। CPU ও memory স্বাভাবিক থাকায় এই সমস্যা নির্ণয় করা কঠিন — ss -lnt-এর Recv-Q দেখাই সবচেয়ে সরাসরি উপায়।
