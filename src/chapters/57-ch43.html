43.2 প্রতিটি স্তরে কী বদলায়

Fieldকে বদলায়কতবার
Ethernet headerপ্রতিটি routerপ্রতিটি hop-এ (১০–২০ বার)
TTLপ্রতিটি routerপ্রতিটি hop-এ ১ কমে
Source IPশুধু NAT১–২ বার (বাসার NAT, CGNAT)
Source portশুধু NAT১–২ বার
Destination IPশুধু load balancer (DNAT করলে)০–১ বার
TCP payloadকেউ না (TLS-এ তো সম্ভবই নয়)০ বার
🧠 Mental Model — তিনটি স্তরের পরিচয়
MAC address  → ★ এক hop ★
                প্রতিটি link-এ নতুন করে লেখা

IP address   → ★ end-to-end ★
                শুধু NAT/LB বদলায়

Port + 4-tuple → ★ connection-এর পরিচয় ★
                  দুই প্রান্তের kernel-এর কাছে অর্থবহ

TLS session  → ★ দুটি application-এর মধ্যে ★
                পথের কেউ পড়তে পারে না

প্রতিটি স্তরের পরিচয়ের একটি নির্দিষ্ট পরিধি আছে — এবং সেই পরিধি বোঝাই networking বোঝার মূল।

43.3 সময়ের বাজেট

ঢাকা → সিঙ্গাপুরের একটি server, একটি সাধারণ API call:

  DNS lookup (cache miss)          :  40 ms
  TCP handshake (1 RTT)            :  60 ms
  TLS 1.3 handshake (1 RTT)        :  60 ms
  HTTP request → প্রথম byte (1 RTT) :  60 ms
  ────────────────────────────────────────────
  Network-এর মোট                    : 220 ms
  Server-এর processing              :  30 ms
  ────────────────────────────────────────────
  ব্যবহারকারী যা অনুভব করেন           : 250 ms

★ ৮৮% সময় শুধু ★অপেক্ষা★ — কোনো কাজ হচ্ছে না,
  শুধু packet যাওয়া-আসা করছে।

একই request, connection পুনর্ব্যবহার করে:
  HTTP request → response          :  60 ms
  Server processing                :  30 ms
  ────────────────────────────────────────────
                                   :  90 ms   ★ ৬৪% কম

একই request, CDN edge থেকে (ঢাকায়):
  HTTP request → response          :   8 ms
  Cache HIT                        :   1 ms
  ────────────────────────────────────────────
                                   :   9 ms   ★ ৯৬% কম
⚙️ Developer Perspective — যেখানে জয় আছে

উপরের তিনটি সংখ্যা (২৫০ / ৯০ / ৯) এই বইয়ের সবচেয়ে ব্যবহারিক শিক্ষা:

  1. Connection reuse — প্রায় বিনামূল্যে ৬০% উন্নতি। Keep-alive, connection pool, HTTP/2।
  2. CDN — দূরত্ব কমানোই সবচেয়ে বড় জয়। ৯৬% পর্যন্ত।
  3. Round trip কমানো — ধারাবাহিক API call-এর waterfall ভাঙুন।

লক্ষ্য করুন — এই তিনটির কোনোটিই "কোড দ্রুত করা" নয়। Server-এর ৩০ms optimize করে ২০ms করলে ব্যবহারকারী ৪% উন্নতি দেখবেন। কিন্তু CDN বসালে ৯৬%। Distributed system-এ latency-র উৎস প্রায়ই CPU নয়, দূরত্ব ও round trip।

🧪 Lab 43 — নিজের packet-এর যাত্রা

আমরা কী দেখতে চাইছি? — একটি প্রকৃত request-এর প্রতিটি hop, প্রতিটি AS, এবং সময়ের প্রকৃত বিভাজন।

bash
TARGET=example.com

echo "=== ১. DNS: নাম → IP ==="
dig +short $TARGET

echo -e "\n=== ২. পথ (AS সহ) ==="
traceroute -A -n -m 20 $TARGET 2>/dev/null | head -20

echo -e "\n=== ৩. প্রতিটি hop-এর loss ও jitter ==="
mtr -r -c 20 -n $TARGET 2>/dev/null

echo -e "\n=== ৪. সময়ের বিভাজন ==="
curl -w "
DNS      : %{time_namelookup}s
TCP      : %{time_connect}s
TLS      : %{time_appconnect}s
TTFB     : %{time_starttransfer}s
মোট      : %{time_total}s
─────────────────────────
Server-এর processing ≈ TTFB − TLS
" -o /dev/null -s https://$TARGET

echo -e "\n=== ৫. দ্বিতীয়বার (connection warm) ==="
curl -w "মোট: %{time_total}s\n" -o /dev/null -s https://$TARGET

echo -e "\n=== ৬. প্রথম hop-এর MAC (ARP) ==="
ip neigh | grep $(ip route | awk '/default/ {print $3}')

যা লক্ষ্য করবেন: Traceroute-এ প্রথম hop আপনার বাসার router, তারপর ISP, তারপর transit/peering, তারপর গন্তব্যের network — AS নম্বর দেখে প্রতিটি চিনতে পারবেন। mtr-এ কোথায় latency লাফ দিচ্ছে দেখুন (সেটিই সাধারণত সমুদ্রতলের cable)। curl-এর দুই দফা তুলনায় connection reuse-এর প্রকৃত লাভ দেখবেন।

আমরা কী শিখলাম: এই বইয়ের সব ধারণা একটি বাস্তব request-এ একসাথে কাজ করছে — DNS, ARP, routing, BGP, TCP, TLS, HTTP। প্রতিটি ধাপের একটি পরিমাপযোগ্য খরচ আছে, এবং আপনি এখন জানেন কোনটি কমানো যায় আর কোনটি ভৌত সীমা।

📌 Chapter Summary
  • একটি packet ১০–২০টি router পেরোয়; প্রতিটিতে নতুন Ethernet header ও TTL−1।
  • Source IP/port শুধু NAT-এ বদলায় (১–২ বার); destination IP শুধু load balancer-এ।
  • TCP payload কেউ বদলায় না — এবং TLS-এ কেউ পড়তেও পারে না।
  • পরিচয়ের পরিধি: MAC = এক hop, IP = end-to-end, 4-tuple = connection, TLS = দুটি application।
  • একটি আন্তঃমহাদেশীয় API call-এ ~৮৮% সময় শুধু অপেক্ষা।
  • সবচেয়ে বড় তিনটি জয়: connection reuse, CDN, কম round trip।
  • Server-এর code optimize করার চেয়ে দূরত্ব ও round trip কমানো প্রায়ই বহুগুণ কার্যকর।
✓ Quick Check
একটি packet ১৫টি router পেরোল। Destination IP কতবার বদলাল?

সাধারণত ০ বার। Router-রা destination IP ছোঁয় না — সেটিই end-to-end পরিচয়। ব্যতিক্রম: গন্তব্যে একটি load balancer DNAT করলে destination IP একবার বদলাতে পারে (public VIP → internal backend IP)। বিপরীতে source IP ১–২ বার বদলায় (বাসার NAT এবং সম্ভবত CGNAT)।

একটি ২৫০ms-এর API call-এ কোথায় optimize করলে সবচেয়ে বেশি লাভ?

প্রথমে দেখুন কোথায় সময় যাচ্ছে (curl -w)। সাধারণত: (১) Connection reuse — DNS, TCP ও TLS handshake বাদ দিয়ে ~৬০% সাশ্রয়, প্রায় বিনা খরচে। (২) CDN/edge — দূরত্ব কমিয়ে ~৯৬% পর্যন্ত। (৩) Round trip কমানো — ধারাবাহিক call একত্র করা। Server-এর ৩০ms code optimize করা তালিকার সবচেয়ে নিচে — সেখানে ৩৩% উন্নতিও শেষ ফলাফলে মাত্র ৪%।

আপনার packet-এর source IP পথে কে কে বদলাতে পারে?

শুধুমাত্র NAT করে এমন যন্ত্র: (১) আপনার বাসার router (private → public), (২) ISP-র CGNAT (যদি থাকে), (৩) কর্পোরেট NAT gateway, (৪) cloud-এর NAT Gateway (যদি আপনি private subnet-এ থাকেন), (৫) কিছু VPN। সাধারণ router, switch বা firewall source IP বদলায় না। প্রতিটি NAT-কে সেই mapping-এর state রাখতে হয়।
