Chapter 45

HTTP/3 এবং QUIC

QUIC হলো এই বইয়ের বহু chapter-এর সমস্যাগুলোর সম্মিলিত উত্তর। TCP-র HOL blocking, handshake-এর RTT, IP বদলালে connection ভাঙা, এবং TCP-র বিবর্তনের অচলাবস্থা — সবগুলো একসাথে।

45.1 Stack-এর তুলনা

  HTTP/1.1 ও HTTP/2              HTTP/3

   ┌─────────────┐            ┌─────────────┐
   │   HTTP      │            │   HTTP/3    │
   ├─────────────┤            ├─────────────┤
   │   TLS       │            │             │
   ├─────────────┤            │    QUIC     │ ← TLS 1.3
   │   TCP       │            │             │   ভেতরেই
   ├─────────────┤            ├─────────────┤
   │   IP        │            │    UDP      │
   └─────────────┘            ├─────────────┤
                              │    IP       │
                              └─────────────┘

  kernel-এ TCP                user space-এ QUIC
  আলাদা TLS handshake         একীভূত handshake

45.2 QUIC যে চারটি সমস্যা সমাধান করে

সমস্যা ১ — TCP-স্তরের Head-of-Line Blocking

HTTP/2 over TCP:

  Stream 1: [A][B][C]
  Stream 2: [D][E][F]
  Stream 3: [G][H][I]

  সবই একটি TCP byte stream-এ:
  [A][D][G][B][E][H][C][F][I]
          ↑ এই segment হারাল

  TCP: "ক্রম রক্ষা করতে হবে" (Ch 19)
  → এর পরের সব byte আটকে গেল
  → ★ তিনটি stream-ই থেমে গেল ★
  → যদিও stream 1 ও 3-এর data পৌঁছে গেছে!


QUIC:

  Stream 1: [A][B][C]  ← নিজস্ব sequence, নিজস্ব reliability
  Stream 2: [D][E][F]  ← হারালে শুধু এটিই অপেক্ষা করে
  Stream 3: [G][H][I]  ← অপ্রভাবিত

  QUIC packet হারালে সে জানে কোন stream-এর data ছিল
  → ★ শুধু সেই stream আটকায় ★
  → বাকিরা নির্বিঘ্নে চলতে থাকে

★ এই একটি বৈশিষ্ট্যই QUIC তৈরির প্রধান কারণ।
  উচ্চ packet loss-এর network-এ (mobile, খারাপ Wi-Fi)
  পার্থক্যটি নাটকীয়।

সমস্যা ২ — Handshake-এর RTT

TCP + TLS 1.3 (আলাদা আলাদা):

  Client                          Server
    │──── SYN ──────────────────────▶│
    │◀─── SYN-ACK ───────────────────│  RTT 1: TCP
    │──── ACK ──────────────────────▶│
    │──── ClientHello ──────────────▶│
    │◀─── ServerHello, Cert, Fin ────│  RTT 2: TLS
    │──── Finished + HTTP request ──▶│
                                      ⇒ ২ RTT


QUIC (একীভূত):

  Client                          Server
    │──── Initial (ClientHello) ────▶│
    │◀─── Initial + Handshake ───────│  RTT 1: সবকিছু
    │──── Handshake + HTTP request ─▶│
                                      ⇒ ১ RTT


QUIC 0-RTT (আগে connect করেছিলেন এমন server-এ):

  Client                          Server
    │──── Initial + ★HTTP request★ ─▶│
    │◀─── response ──────────────────│
                                      ⇒ ০ RTT!

★ কারণ QUIC-এ transport ও crypto handshake আলাদা নয় —
  একই message-এ দুটোই।

সমস্যা ৩ — Connection Migration

TCP-তে connection চিহ্নিত হয় 4-tuple দিয়ে:
  (src IP, src port, dst IP, dst port)   [Ch 15]

আপনি Wi-Fi থেকে mobile data-তে গেলেন:
  → src IP বদলে গেল
  → ★ 4-tuple বদলে গেল ★
  → connection মৃত
  → download শুরু থেকে
  → video call কেটে গেল


QUIC-এ connection চিহ্নিত হয় ★Connection ID★ দিয়ে:

  Connection ID: 0x4f2a9b3c...   ← IP-নিরপেক্ষ

  Wi-Fi:        192.168.1.5:51234 ──▶ [CID: 4f2a9b3c]
  Mobile data:  10.20.30.40:38900 ──▶ [CID: 4f2a9b3c]
                                            │
                                    Server চিনতে পারে:
                                    "একই connection,
                                     নতুন path"

  → ★ Download চলতে থাকে, video call কাটে না ★

  (Server path validation করে নিশ্চিত হয় যে এটি
   প্রকৃত client, কেউ connection ছিনতাই করছে না)

★ Mobile-first দুনিয়ায় এটি একটি বিশাল ব্যবহারিক জয়।

সমস্যা ৪ — Protocol Ossification

TCP kernel-এ, তাই:
  • নতুন TCP feature = OS update
  • OS update = বছরের পর বছর
  • Middlebox (firewall, NAT, proxy) TCP header
    "বোঝে" এবং অচেনা কিছু দেখলে ফেলে দেয়
  • ফলে নতুন TCP option deploy করাই যায় না

  একে বলে ★ossification★ — protocol পাথর হয়ে গেছে

  উদাহরণ: TCP Fast Open (0-RTT-র TCP সংস্করণ)
  ২০১১ সালে তৈরি, কিন্তু middlebox-এর কারণে
  আজও কার্যত ব্যবহার করা যায় না।


QUIC-এর সমাধান:

  1. ★ User space-এ ★
     → browser update করলেই নতুন version
     → Chrome/Firefox মাসে মাসে উন্নতি আনতে পারে

  2. ★ প্রায় সব কিছু encrypted ★
     → middlebox শুধু UDP header দেখে
     → ভেতরে হস্তক্ষেপ করতে পারে না
     → তাই ossify হতে পারে না

  3. ★ UDP-র উপর ★
     → নতুন transport protocol deploy করা অসম্ভব
       (middlebox অচেনা protocol number ফেলে দেয়)
     → কিন্তু UDP সবাই চেনে ও যেতে দেয়

★ QUIC-এর নকশায় "ভবিষ্যতে বদলানো যাবে" —
  এটি একটি স্পষ্ট লক্ষ্য ছিল।

45.3 QUIC-এর মূল্য

দিকবিবেচনা
CPU খরচUser space-এ চলায় প্রতিটি packet kernel↔user সীমানা পেরোয়। TCP-র চেয়ে বেশি CPU (যদিও GSO/GRO ও hardware offload দিয়ে ব্যবধান কমছে)।
UDP blockingকিছু কর্পোরেট network UDP 443 আটকায়। তাই সব client-কে TCP-তে fallback রাখতে হয়।
Middlebox-এর অনভ্যস্ততাপুরনো firewall UDP-র বড় flow-কে সন্দেহজনক মনে করতে পারে।
Debugging কঠিনসব encrypted — tcpdump-এ শুধু UDP packet দেখা যায়। Wireshark-এ দেখতে SSLKEYLOGFILE লাগে।
Amplification-এর ঝুঁকিUDP-ভিত্তিক বলে সতর্ক নকশা দরকার — QUIC-এ নিয়ম আছে: address যাচাই না হওয়া পর্যন্ত server পাওয়া data-র ৩ গুণের বেশি পাঠাতে পারবে না।
✓ HTTP/3 কীভাবে আবিষ্কৃত হয়

Browser জানে না কোন site HTTP/3 support করে। তাই প্রক্রিয়াটি এমন:

1. Browser TCP+TLS দিয়ে HTTP/2-তে connect করে

2. Server response-এ একটি header পাঠায়:
     alt-svc: h3=":443"; ma=86400
              │              │
        "HTTP/3 আছে"    "৮৬৪০০ সেকেন্ড মনে রাখো"

3. Browser এটি মনে রাখে

4. ★ পরের বার ★ সে সরাসরি QUIC চেষ্টা করে
   (এবং সমান্তরালে TCP-ও, যদি QUIC ব্যর্থ হয় —
    একে বলে "happy eyeballs")

এজন্যই একটি site-এ প্রথমবার গেলে HTTP/2 দেখবেন, দ্বিতীয়বার HTTP/3।

⚙️ Developer Perspective
  • HTTP/3 সাধারণত CDN-এর মাধ্যমে আসে — Cloudflare, Fastly, CloudFront-এ একটি toggle। নিজে nginx-এ চালু করাও সম্ভব (1.25+), কিন্তু CDN-এ সবচেয়ে সহজ।
  • Application code বদলাতে হয় না — HTTP-র semantics অপরিবর্তিত। শুধু transport বদলায়।
  • সবচেয়ে বেশি লাভ mobile ও উচ্চ-loss network-এ — HOL blocking ও connection migration সেখানেই সবচেয়ে বেশি কাজে লাগে। ভালো wired সংযোগে পার্থক্য কম।
  • Monitoring মনে রাখুন — আপনার observability tool HTTP/3 বোঝে কিনা যাচাই করুন; অনেক পুরনো tool শুধু TCP দেখে।
🧪 Lab 45 — HTTP/3 পরীক্ষা করুন

আমরা কী দেখতে চাইছি? — কোন site HTTP/3 support করে, কীভাবে তা ঘোষণা করে, এবং QUIC traffic দেখতে কেমন।

bash
# alt-svc header — HTTP/3-এর ঘোষণা
curl -sI https://www.cloudflare.com | grep -i alt-svc
curl -sI https://www.google.com | grep -i alt-svc

# HTTP/3 দিয়ে চেষ্টা (curl-এ HTTP/3 support লাগবে)
curl --http3 -sI https://www.cloudflare.com | head -1

# QUIC traffic দেখুন — শুধু UDP 443
sudo tcpdump -i any -n 'udp port 443' -c 10
# তারপর একটি HTTP/3-সক্ষম site ব্রাউজ করুন

# তুলনা: HTTP/2 vs HTTP/3 সময়
for v in --http2 --http3; do
  echo -n "$v: "
  curl $v -o /dev/null -s -w "%{time_total}s\n" https://www.cloudflare.com 2>/dev/null || echo "সমর্থিত নয়"
done

# আপনার curl কি HTTP/3 জানে?
curl --version | grep -o HTTP3

যা লক্ষ্য করবেন: alt-svc: h3=":443"; ma=86400 — এটিই HTTP/3-এর ঘোষণা। tcpdump-এ QUIC traffic দেখবেন শুধুই UDP packet হিসেবে — কোনো handshake, কোনো flag, কিছুই পড়া যায় না, কারণ সব encrypted। এটি TCP-র tcpdump output-এর সাথে তীব্র বৈপরীত্য।

আমরা কী শিখলাম: QUIC-এর "সব encrypted" নীতি middlebox-কে হস্তক্ষেপ থেকে আটকায় — কিন্তু একই সাথে আপনার নিজের debugging-ও কঠিন করে তোলে। এটি একটি সচেতন ট্রেড-অফ: ভবিষ্যতে বিবর্তনের স্বাধীনতার বিনিময়ে দৃশ্যমানতা।

📌 Chapter Summary
  • QUIC = UDP-র উপর নির্মিত একটি সম্পূর্ণ transport, TLS 1.3 অন্তর্নির্মিত।
  • Stream-প্রতি স্বাধীন reliability → TCP-স্তরের HOL blocking সম্পূর্ণ দূর।
  • একীভূত handshake → ১ RTT (পুনঃসংযোগে ০ RTT)।
  • Connection ID → IP বদলালেও connection টিকে থাকে (connection migration)।
  • User space + encrypted header → ossification এড়ায়, দ্রুত বিবর্তন সম্ভব।
  • মূল্য: বেশি CPU, কিছু network-এ UDP blocking, debugging কঠিন।
  • alt-svc header দিয়ে HTTP/3 আবিষ্কৃত হয়; প্রথম সংযোগ TCP-তেই হয়।
  • সবচেয়ে বেশি লাভ mobile ও উচ্চ-loss network-এ।
✓ Quick Check
QUIC কীভাবে TCP-স্তরের HOL blocking দূর করে?

QUIC-এর transport layer নিজেই stream-এর ধারণা জানে। প্রতিটি stream-এর নিজস্ব sequence number ও reliability ব্যবস্থা আছে। একটি QUIC packet হারালে সে জানে সেটি কোন stream-এর data বহন করছিল, তাই শুধু সেই stream অপেক্ষা করে — বাকি stream গুলোর data সঙ্গে সঙ্গে application-কে দেওয়া যায়। TCP এটি পারে না কারণ তার কাছে সবটাই একটি অবিভাজ্য ordered byte stream।

Wi-Fi থেকে mobile data-তে গেলে QUIC connection কেন টিকে থাকে?

কারণ QUIC connection চিহ্নিত হয় একটি Connection ID দিয়ে, 4-tuple দিয়ে নয়। IP ও port বদলালেও Connection ID অপরিবর্তিত থাকে, তাই server চিনতে পারে এটি একই connection — শুধু নতুন network path থেকে আসছে। সে path validation করে নিশ্চিত হয় এবং তারপর সেখানেই পাঠাতে শুরু করে। TCP-তে 4-tuple-ই পরিচয় হওয়ায় IP বদলানো মানেই connection-এর মৃত্যু।

QUIC কেন UDP-র উপর তৈরি হলো, একটি নতুন protocol number নিয়ে নয়?

কারণ Internet-এ নতুন transport protocol deploy করা কার্যত অসম্ভব। অসংখ্য middlebox (firewall, NAT, load balancer) শুধু TCP ও UDP চেনে এবং অচেনা IP protocol number দেখলে packet ফেলে দেয়। SCTP ও DCCP-র ভাগ্যে এটাই ঘটেছে। UDP সর্বজনীনভাবে অনুমোদিত, তাই QUIC তার উপর নিজের সম্পূর্ণ transport তৈরি করেছে — একটি ব্যবহারিক আপস, তাত্ত্বিক আদর্শ নয়।

QUIC-এ প্রায় সবকিছু encrypted রাখার সুবিধা ও অসুবিধা কী?

সুবিধা: Middlebox protocol-এর ভেতরে হস্তক্ষেপ করতে পারে না, তাই ossification হয় না — ভবিষ্যতে protocol বদলানো সম্ভব। গোপনীয়তাও বাড়ে। অসুবিধা: আপনার নিজের network monitoring, troubleshooting ও performance analysis কঠিন হয়ে যায় — tcpdump-এ শুধু অস্বচ্ছ UDP packet দেখা যায়। এটি একটি সচেতন ট্রেড-অফ: বিবর্তনের স্বাধীনতার বিনিময়ে দৃশ্যমানতা।
