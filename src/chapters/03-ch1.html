Chapter 1

What Is a Computer Network?

প্রশ্নটা "network কী" নয়। আসল প্রশ্ন হলো — দুটি আলাদা computer-এ চলা দুটি program একে অপরের সাথে কথা বলতে চাইলে ঠিক কী কী সমস্যা সমাধান করতে হয়?

1.1 Why does this exist?

একটি program যখন একই machine-এ অন্য program-এর সাথে data আদান-প্রদান করে, কাজটা তুলনামূলক সহজ। Operating System fundamentals থেকে আপনি হয়তো মনে করতে পারবেন — pipe, shared memory, Unix domain socket, signal। এগুলো কাজ করে কারণ দুটো process-ই একই kernel-এর অধীনে, একই physical memory-তে, একই বিশ্বস্ত পরিবেশে আছে।

এখন একটি লাইন বদলান: program দুটো দুটো আলাদা machine-এ, ৮০০০ কিলোমিটার দূরে। সঙ্গে সঙ্গে যেসব জিনিস এতদিন বিনামূল্যে পাওয়া যাচ্ছিল, সেগুলো হারিয়ে যায়:

একই machine-এদুই machine-এ
Shared memory আছেকোনো shared memory নেই — data-কে physically পাঠাতে হবে
Kernel জানে কে কোন processকোন process, কোন machine — সব identify করতে হবে
Data হারায় নাData হারাতে পারে, নষ্ট হতে পারে, দেরিতে পৌঁছাতে পারে
ক্রম বজায় থাকেযে ক্রমে পাঠানো, সে ক্রমে না-ও পৌঁছাতে পারে
দুটো process একই ভাষা বোঝেদুটো ভিন্ন OS, ভিন্ন CPU architecture, ভিন্ন byte order
কেউ মাঝখান থেকে শুনতে পারে নাপথের যে কেউ শুনতে বা বদলাতে পারে
💡 Why

Computer network হলো এই ছয়টি সমস্যার organized সমাধান। এই বইয়ের প্রতিটি protocol — ARP, IP, TCP, DNS, TLS — উপরের কোনো না কোনো row-এর উত্তর। যখনই কোনো নতুন protocol-এর নাম শুনবেন, নিজেকে জিজ্ঞেস করুন: "এটা এই টেবিলের কোন সমস্যাটা সমাধান করছে?"

1.2 Core Concept — Network কী

একটি computer network (কম্পিউটার নেটওয়ার্ক) হলো এমন কতগুলো computing device-এর সমষ্টি যারা একটি shared medium এবং একগুচ্ছ agreed-upon নিয়ম ব্যবহার করে একে অপরের সাথে data বিনিময় করতে পারে।

সংজ্ঞাটির তিনটি অংশ গুরুত্বপূর্ণ, এবং তিনটিই অপরিহার্য:

  • Device — যারা কথা বলবে
  • Medium — যার মধ্য দিয়ে signal যাবে (তার, radio wave, fiber)
  • Rules — কীভাবে কথা বলবে (এগুলোই protocol)

তিনটির যেকোনো একটি না থাকলে network নেই। দুটি computer-কে তার দিয়ে জুড়ে দিলেই তারা কথা বলতে পারে না — যেভাবে দুজন মানুষকে একই ঘরে বসিয়ে দিলেই তারা কথা বলতে পারে না যদি একজন বাংলা আর অন্যজন শুধু জাপানি জানে। Medium থাকা আর communication হওয়া এক জিনিস নয়।

1.3 Communication-এর ছয়টি উপাদান

যেকোনো communication — মানুষের হোক বা machine-এর — এই ছয়টি উপাদান ছাড়া সম্ভব নয়। পুরো বইয়ে বারবার এই ছয়টিতে ফিরে আসব।

┌──────────┐                                    ┌──────────┐
│  SENDER  │ ── MESSAGE ──▶  MEDIUM  ──────────▶│ RECEIVER │
│          │                                    │          │

│    A     │                                    │    B     │
└──────────┘                                    └──────────┘
উপাদানমানেNetworking-এ এর রূপ

Receiverযে গ্রহণ করেঅন্য একটি process, অন্য host
Messageযা পাঠানো হচ্ছেbytes — HTTP request, JSON, video frame

Protocol মানে কী

একটি protocol (প্রোটোকল) হলো communication-এর পূর্বনির্ধারিত নিয়মাবলি — কে আগে কথা বলবে, message-এর গঠন কেমন হবে, কোন byte কী অর্থ বহন করবে, উত্তর না এলে কী করতে হবে।

একটা পরিচিত উদাহরণ — টেলিফোন কথোপকথনের protocol:

Caller:  (dial করে, ring হয়)
Callee:  "হ্যালো"                    ← receiver আগে কথা বলে
Caller:  "হ্যালো, আমি রেজা বলছি"       ← caller নিজেকে identify করে
Callee:  "হ্যাঁ বলুন"                  ← acknowledgment
...      (data transfer)
Caller:  "আচ্ছা, রাখছি"               ← close-এর ইঙ্গিত
Callee:  "ঠিক আছে, রাখুন"             ← close-এর acknowledgment
(দুজনেই রাখল)

লক্ষ্য করুন — এখানে নির্দিষ্ট একটি sequence আছে, identification আছে, acknowledgment আছে, এবং একটি ভদ্র termination আছে। TCP-এর connection setup এবং teardown প্রায় হুবহু এই কাঠামো অনুসরণ করে (Chapter 18 এবং 22)। মানুষের protocol আর machine-এর protocol একই সমস্যার সমাধান করে।

ℹ️ Protocol ≠ Software

Protocol একটি specification — একটি লিখিত চুক্তি। HTTP একটি protocol; nginx এবং Apache দুটোই সেই protocol-এর implementation। এজন্যই Python-এ লেখা একটি client Go-তে লেখা একটি server-এর সাথে কথা বলতে পারে — তারা একই চুক্তি মানছে, একই code চালাচ্ছে না।

Networking শেখা মানে হলো মাঝখানের ওই NETWORK বাক্সটির ভেতরে ঢোকা — এবং একই সাথে উপরের-নিচের বাক্স দুটোর ভেতরে (Computer A থেকে Application A পর্যন্ত পথটা)। বেশিরভাগ networking course শুধু মাঝখানের বাক্সটা পড়ায়। কিন্তু একজন developer হিসেবে আপনার code বসে আছে সবার উপরে — তাই আপনার জানা দরকার উপর থেকে নিচে নামার পুরো পথটা।

1.6 Developer Perspective

আপনি যখন লেখেন:

js
const res = await fetch("https://api.example.com/users");

এই এক লাইনের নিচে যা যা ঘটে, তার একটি সংক্ষিপ্ত তালিকা (প্রতিটি এই বইয়ে আলাদা chapter পাবে):

1.  URL parse হয় → scheme(https), host(api.example.com), path(/users)
2.  DNS lookup → api.example.com এর IP address                   [Ch 25–27]
3.  OS একটি socket তৈরি করে                                       [Ch 16]
4.  TCP three-way handshake (বা QUIC)                            [Ch 18]
5.  TLS handshake — certificate যাচাই, key বিনিময়                 [Ch 33]
6.  HTTP request bytes তৈরি হয়                                    [Ch 28]
7.  Kernel সেই bytes কে TCP segment-এ ভাগ করে                     [Ch 17]
8.  প্রতিটি segment IP packet-এ মোড়া হয়                            [Ch 9]
9.  প্রতিটি packet Ethernet/Wi-Fi frame-এ মোড়া হয়                  [Ch 6]
10. Gateway-এর MAC address জানতে ARP                              [Ch 8]
11. NIC bits হিসেবে পাঠায়
12. Router-রা hop by hop forward করে                              [Ch 12, 13]
13. Server-এর kernel সব খুলে নিয়ে socket buffer-এ রাখে
14. Server process read() করে, response লেখে
15. পুরো পথ উল্টো দিকে
⚙️ Developer Perspective

এই ১৫টি ধাপের যেকোনো একটি ব্যর্থ হলে আপনার fetch() ব্যর্থ হয় — কিন্তু error message প্রায়ই বলে না কোথায়। ENOTFOUND মানে ধাপ ২। ECONNREFUSED মানে ধাপ ৪ (packet পৌঁছেছে, কিন্তু কেউ ওই port-এ শুনছে না)। ETIMEDOUT মানে packet গেছে কিন্তু কোনো উত্তর আসেনি — ধাপ ৪ বা ১২। CERT_HAS_EXPIRED মানে ধাপ ৫। Error message পড়ে কোন ধাপে সমস্যা তা বোঝা — এটাই এই বইয়ের সবচেয়ে ব্যবহারিক সুফল।

1.7 Common Confusions

MYTH

Internet এবং Web একই জিনিস।

REALITY

Internet হলো অবকাঠামো — পরস্পর যুক্ত অসংখ্য network, যেখানে IP দিয়ে packet চলাচল করে। Web হলো সেই অবকাঠামোর উপর চলা একটি application — HTTP protocol এবং hyperlink-যুক্ত document। Email, SSH, BitTorrent, online game, video call — এগুলো Internet ব্যবহার করে কিন্তু Web নয়। Web হলো Internet-এর উপর চলা অনেক application-এর একটি।

MYTH

Network মানে তার এবং যন্ত্রপাতি — এটা hardware-এর ব্যাপার, software engineer-এর নয়।

REALITY

Physical medium hardware, কিন্তু network-এর প্রায় সমস্ত বুদ্ধি software-এ — এবং তার একটি বড় অংশ আপনার নিজের machine-এর kernel-এ। TCP-এর retransmission logic, routing table-এর lookup, DNS resolution — সবই code। Networking hardware-এর বিষয় নয়, distributed software-এর বিষয়।

🧪 Lab 1 — আপনার machine কি আসলেই network-এ আছে?

আমরা কী দেখতে চাইছি? — এই chapter-এর "sender / receiver / address / medium" ধারণাগুলোর বাস্তব প্রতিরূপ আপনার নিজের machine-এ খুঁজে বের করা।

bash
# আপনার machine-এর network interface গুলো দেখুন
ip addr        # Linux
ifconfig       # macOS

# আপনার machine বাইরের দুনিয়ায় পৌঁছাতে পারে কিনা
ping -c 3 1.1.1.1

যা লক্ষ্য করবেন: ip addr-এর output-এ অন্তত দুটি interface পাবেন — একটি lo (loopback, নিজের সাথে নিজের কথা) এবং একটি আসল interface (eth0, enp3s0, wlan0, বা macOS-এ en0)। প্রতিটির সাথে একটি IP address আছে — এটাই আপনার machine-এর "address"। ping-এর প্রতিটি লাইনে time= দেখুন — এটাই সেই "medium" পেরিয়ে যাওয়া-আসার সময়।

আমরা কী শিখলাম: "Network-এ যুক্ত থাকা" কোনো বিমূর্ত ধারণা নয় — এর মানে হলো আপনার machine-এর একটি interface আছে, সেই interface-এর একটি address আছে, এবং সেই address ব্যবহার করে অন্য address-এ message পাঠিয়ে উত্তর পাওয়া যাচ্ছে। বাকি বইটা এই তিনটি জিনিসের বিস্তারিত।

📌 Chapter Summary
  • Network দরকার কারণ দুটি আলাদা machine-এ shared memory নেই, বিশ্বাস নেই, এবং delivery-র নিশ্চয়তা নেই।
  • যেকোনো communication-এর ছয়টি উপাদান: sender, receiver, message, medium, address, protocol।
  • Protocol একটি লিখিত চুক্তি (specification), কোনো নির্দিষ্ট software নয় — তাই ভিন্ন ভাষায় লেখা program-রাও কথা বলতে পারে।
  • Networking-এর প্রতিটি protocol নির্দিষ্ট একটি সমস্যার উত্তর। নতুন protocol শিখলে প্রথম প্রশ্ন: "এটা কোন সমস্যাটা সমাধান করছে?"
  • Internet হলো অবকাঠামো; Web হলো তার উপর চলা একটি application মাত্র।
✓ Quick Check
একই machine-এ দুটি process-এর মধ্যে data আদান-প্রদানের তুলনায় দুই machine-এর মধ্যে কী কী নতুন সমস্যা তৈরি হয়?

Shared memory থাকে না (data physically পাঠাতে হয়), delivery-র নিশ্চয়তা থাকে না (data হারাতে পারে), ক্রম বজায় থাকার নিশ্চয়তা থাকে না, দুই প্রান্তে ভিন্ন OS/architecture থাকতে পারে, এবং পথটি অবিশ্বস্ত — মাঝখানের যে কেউ data দেখতে বা বদলাতে পারে।

Protocol এবং implementation-এর পার্থক্য কী? একটি উদাহরণ দিন।

Protocol হলো নিয়মের লিখিত specification; implementation হলো সেই নিয়ম মেনে লেখা প্রকৃত software। HTTP একটি protocol; nginx, Apache, Caddy, এবং Node.js-এর http module — সবগুলো তার আলাদা আলাদা implementation। একই protocol মানার কারণেই এরা পরস্পরের সাথে কাজ করতে পারে।

দুটি computer-কে একটি তার দিয়ে যুক্ত করলেই কি তারা যোগাযোগ করতে পারবে? কেন নয়?

না। তার শুধু medium সরবরাহ করে। যোগাযোগের জন্য আরও দরকার — signal-কে bit-এ রূপান্তরের নিয়ম, কে কখন পাঠাবে তার নিয়ম, message-এর গঠন, এবং কে কার উদ্দেশ্যে পাঠাচ্ছে তা বোঝার জন্য address। অর্থাৎ protocol ছাড়া medium অর্থহীন।

"Internet এবং Web একই জিনিস" — এই বক্তব্যের ভুল কোথায়?

Internet হলো IP-ভিত্তিক পরস্পর-যুক্ত network-এর বিশ্বব্যাপী অবকাঠামো। Web (HTTP + hyperlinked document) হলো সেই অবকাঠামোর উপর চলা অনেক application-এর মধ্যে একটি। Email (SMTP), SSH, DNS, video call — এগুলোও Internet ব্যবহার করে কিন্তু Web-এর অংশ নয়।
