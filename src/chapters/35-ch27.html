Chapter 27

DNS Caching এবং TTL

DNS প্রতিদিন কোটি কোটি query সামলায় মাত্র কয়েকশ authoritative server দিয়ে। কীভাবে? উত্তর একটাই শব্দ — cache। কিন্তু cache মানেই পুরনো তথ্য, এবং সেখান থেকেই "DNS বদলেছি কিন্তু কাজ করছে না" সমস্যার জন্ম।

27.1 Why does this exist?

Caching না থাকলে:

  প্রতিটি HTTP request-এর আগে একটি পূর্ণ resolution
      = root + TLD + authoritative
      = ৩টি round trip
      = হয়তো ২০০–৫০০ms

  একটি web page-এ ৫০টি resource, ১০টি ভিন্ন domain
      = ১০টি পূর্ণ resolution = কয়েক সেকেন্ড শুধু DNS-এ

  আর root server-দের অবস্থা:
      পৃথিবীর প্রতিটি DNS query তাদের কাছে যেত
      = কার্যত অসম্ভব একটি load

Caching সহ:
  ৯০%+ query কোনো না কোনো cache থেকেই মিটে যায়
  Root server-রা কার্যত ফাঁকা বসে থাকে

✓ Referral-ও cache হয়

একটি গুরুত্বপূর্ণ কিন্তু কম আলোচিত বিষয়: resolver শুধু চূড়ান্ত উত্তর নয়, পথের প্রতিটি referral-ও cache করে। .com-এর nameserver-এর তথ্য (TTL ২ দিন) একবার জানার পর সে আর কখনো root-এ যায় না। তাই দ্বিতীয় query-তে root এবং TLD দুটোই বাদ পড়ে — সরাসরি authoritative server-এ যায়।

27.3 TTL — cache-এর আয়ু

example.com.    300    IN    A    93.184.215.14
                 │
                 └─ TTL: এই উত্তর ৩০০ সেকেন্ড বৈধ

সময়ের সাথে:
  t=0    resolver authoritative থেকে পেল, TTL=300
  t=60   cache থেকে দিল, TTL দেখাল 240
  t=200  cache থেকে দিল, TTL দেখাল 100
  t=300  cache expire, পরের query আবার authoritative-এ

★ TTL একটি ★প্রতিশ্রুতি★, একটি সুপারিশ নয়।
  আপনি TTL=300 দিলে ধরে নিতে হবে পুরনো উত্তর
  ৩০০ সেকেন্ড পর্যন্ত ব্যবহৃত হবে।
TTLকখন উপযুক্তট্রেড-অফ
60s বা কমদ্রুত failover দরকার, ঘন ঘন IP বদলায়বেশি query, বেশি latency, resolver-এ চাপ
300s (৫ মিনিট)সক্রিয় পরিবর্তনশীল service — সাধারণ পছন্দভারসাম্যপূর্ণ
3600s (১ ঘণ্টা)স্থিতিশীল serviceপরিবর্তন ছড়াতে ১ ঘণ্টা
86400s (১ দিন)NS record, MX record — যা প্রায় বদলায় নাজরুরি পরিবর্তন কঠিন
⚙️ Developer Perspective — migration-এর নিয়ম

Server migrate করার আগে অন্তত পুরনো TTL-এর সমান সময় আগে TTL কমিয়ে দিন:

বর্তমান: TTL = 86400 (২৪ ঘণ্টা)

দিন 1  : TTL কমিয়ে 300 করুন (কিন্তু IP অপরিবর্তিত)
         → পুরনো ২৪ ঘণ্টার cache expire হতে ২৪ ঘণ্টা লাগবে

দিন 2  : এখন সবার cache-এ TTL=300
         → এবার IP বদলান
         → ৫ মিনিটে সবাই নতুন IP পেয়ে যাবে

দিন 3  : স্থিতিশীল হলে TTL আবার বাড়িয়ে দিন

এই ধাপ এড়িয়ে সরাসরি IP বদললে কিছু ব্যবহারকারী ২৪ ঘণ্টা পর্যন্ত পুরনো server-এ যেতে থাকবে। এজন্য পুরনো server-কে অন্তত পুরনো TTL-এর সময়কাল পর্যন্ত চালু রাখতে হয় (বা redirect করতে হয়)।

27.4 Negative Caching

"এই নাম নেই" (NXDOMAIN) — এই উত্তরটিও cache হয়। নাহলে একটি typo বা ভুল configure করা client বারবার একই ব্যর্থ query পাঠিয়ে authoritative server-এ চাপ ফেলত।

Negative caching-এর TTL আসে SOA record-এর শেষ field থেকে:

  example.com. IN SOA ns1.example.com. admin.example.com. (
      2026090201  ; serial
      7200        ; refresh
      3600        ; retry
      1209600     ; expire
      300 )       ; ★ minimum = negative cache TTL

এর মানে: "example.com-এ নেই" এই তথ্যটি ৩০০ সেকেন্ড cache হবে।

⚠️ বাস্তব সমস্যা:
   একটি নতুন subdomain তৈরি করার আগে কেউ যদি সেটি
   query করে ফেলে, NXDOMAIN cache হয়ে যাবে।
   তারপর record তৈরি করলেও negative TTL শেষ না হওয়া
   পর্যন্ত সেটি "নেই" দেখাবে।

   এজন্যই negative TTL কম রাখা ভালো (৩০০ বা তার কম),
   এবং নতুন record তৈরির আগে query না করাই বুদ্ধিমানের কাজ।

27.5 Cache-জনিত সমস্যা যা সবাই দেখে

সমস্যা

"DNS record বদলেছি, কিন্তু আমার machine পুরনো IP-তেই যাচ্ছে।"

কারণ ও সমাধান

চারটি স্তরের যেকোনো একটিতে পুরনো উত্তর আটকে আছে। ক্রম অনুযায়ী পরীক্ষা করুন:

bash
# 1. Authoritative server কী বলছে (cache সম্পূর্ণ এড়িয়ে)?
dig @$(dig +short NS example.com | head -1) example.com
# এখানে পুরনো হলে → আপনার DNS provider-এ পরিবর্তন হয়নি

# 2. Public resolver কী বলছে?
dig @8.8.8.8 example.com
dig @1.1.1.1 example.com
# পুরনো হলে → TTL শেষ হওয়ার অপেক্ষা করুন

# 3. আপনার OS cache পরিষ্কার করুন
sudo resolvectl flush-caches        # systemd
sudo dscacheutil -flushcache        # macOS
ipconfig /flushdns                  # Windows

# 4. Browser cache
# chrome://net-internals/#dns → "Clear host cache"
⚠️ যেসব জায়গায় TTL উপেক্ষিত হয়
  • Java (পুরনো JVM): default networkaddress.cache.ttl ছিল -1 — অর্থাৎ চিরকালীন cache। একটি দীর্ঘচলমান JVM application DNS পরিবর্তন কখনো দেখত না। আধুনিক JDK-তে এটি ৩০ সেকেন্ড, কিন্তু legacy system-এ এখনো এই সমস্যা দেখা যায়।
  • Connection pool: একটি চলমান TCP connection তার IP ধরে রাখে — DNS বদলালেও সেটি বদলায় না। শুধু নতুন connection নতুন IP পাবে।
  • Browser: Chrome নিজের cache-এ ~৬০ সেকেন্ড রাখে, TTL কম হলেও।
  • Kubernetes: CoreDNS-এর নিজস্ব cache, এবং pod-এর ndots configuration অপ্রত্যাশিত আচরণ তৈরি করতে পারে।

উপসংহার: DNS-ভিত্তিক failover-কে "তাৎক্ষণিক" ধরে নেবেন না। প্রকৃত দ্রুত failover-এর জন্য load balancer, anycast, বা application-স্তরের retry দরকার।

27.6 Anycast — একটি IP, বহু server

1.1.1.1 — এই একটি IP পৃথিবীর ২৫০+ শহরে ঘোষিত হয়

    ঢাকার ব্যবহারকারী  ──▶ 1.1.1.1 ──▶ সিঙ্গাপুরের server
    লন্ডনের ব্যবহারকারী ──▶ 1.1.1.1 ──▶ লন্ডনের server
    নিউইয়র্কের          ──▶ 1.1.1.1 ──▶ নিউইয়র্কের server

কীভাবে? BGP (Ch 42)। একাধিক জায়গা থেকে একই prefix
ঘোষণা করা হয়, এবং routing স্বাভাবিকভাবেই প্রত্যেককে
নিকটতম টিতে পাঠায়।

সুবিধা:
  • কম latency (সবাই কাছের server পায়)
  • স্বয়ংক্রিয় failover (একটি site বন্ধ হলে route
    পরের নিকটতম টিতে চলে যায়)
  • DDoS প্রতিরোধ (আক্রমণ বহু site-এ ছড়িয়ে যায়)

এজন্যই root server "১৩টি" হলেও বাস্তবে ১৫০০+ যন্ত্র —
প্রতিটি নাম একটি anycast গুচ্ছ।
🧪 Lab 27 — Cache-এর আচরণ পরিমাপ করুন

আমরা কী দেখতে চাইছি? — cache hit এবং miss-এর মধ্যে সময়ের প্রকৃত পার্থক্য, এবং TTL-এর ক্ষয়।

bash
# প্রথম query (সম্ভবত cache miss)
dig example.com | grep -E "Query time|ANSWER SECTION" -A1

# সঙ্গে সঙ্গে আবার (cache hit)
dig example.com | grep -E "Query time|IN.*A"

# TTL কমতে দেখুন
for i in 1 2 3; do
  dig +short +ttlunits example.com A | head -1
  dig example.com | grep "^example.com" | awk '{print "TTL:", $2}'
  sleep 5
done

# একটি খুব কম TTL-এর domain (CDN-এর হয়)
dig www.cloudflare.com | grep "^www"

# NXDOMAIN-এর negative caching দেখুন
dig thisdoesnotexist12345.example.com | grep -E "status|SOA"

যা লক্ষ্য করবেন: প্রথম query-তে Query time: 45 msec, দ্বিতীয়টিতে Query time: 0 msec — প্রায় ৫০ গুণ পার্থক্য, এবং এটি শুধু cache। TTL-এর সংখ্যাটি ৫ সেকেন্ড পরপর ৫ করে কমবে। NXDOMAIN-এর ক্ষেত্রে status: NXDOMAIN এবং AUTHORITY section-এ SOA record দেখবেন — সেই SOA-র শেষ সংখ্যাটিই negative cache TTL।

আমরা কী শিখলাম: Cache DNS-এর একটি বৈশিষ্ট্য নয়, এটি DNS-এর কার্যক্ষমতার ভিত্তি। এবং TTL কোনো নিছক সংখ্যা নয় — এটি আপনার পরিবর্তন কত দ্রুত পৃথিবীতে ছড়াবে তার সরাসরি নিয়ন্ত্রক।

📌 Chapter Summary
  • Caching ছাড়া DNS scale করত না — ৯০%+ query কোনো না কোনো cache থেকে মেটে।
  • চারটি স্তর: browser → application/runtime → OS → recursive resolver।
  • Referral-ও cache হয়, তাই দ্বিতীয় query-তে root ও TLD সম্পূর্ণ বাদ পড়ে।
  • TTL একটি প্রতিশ্রুতি: পুরনো উত্তর ততক্ষণ পর্যন্ত ব্যবহৃত হতে পারে।
  • Migration-এর আগে TTL কমান, পুরনো TTL-এর সময় অপেক্ষা করুন, তারপর IP বদলান।
  • NXDOMAIN-ও cache হয় (negative caching), TTL আসে SOA-র minimum field থেকে।
  • JVM, connection pool, browser — অনেক জায়গায় TTL উপেক্ষিত হয়; DNS failover তাৎক্ষণিক নয়।
  • Anycast একই IP-কে বহু জায়গায় ঘোষণা করে — কম latency ও স্বয়ংক্রিয় failover দেয়।
✓ Quick Check
DNS record বদলানোর ৫ মিনিট পরেও কিছু ব্যবহারকারী পুরনো server-এ যাচ্ছে। কেন?

পুরনো record-এর TTL এখনো শেষ হয়নি। যদি আগে TTL ছিল ৩৬০০ সেকেন্ড, তাহলে যারা পরিবর্তনের ঠিক আগে query করেছিল তাদের cache ১ ঘণ্টা পর্যন্ত পুরনো IP রাখবে। এছাড়া browser cache, JVM-এর চিরকালীন cache, বা চলমান TCP connection — সব মিলিয়ে বিলম্ব আরও বাড়তে পারে। সমাধান: পরিবর্তনের আগে TTL কমানো।

Negative caching কী এবং কোন সমস্যা তৈরি করতে পারে?

"এই নাম নেই" (NXDOMAIN) — এই উত্তরটিও নির্দিষ্ট সময়ের জন্য cache করা হয়, TTL আসে SOA record-এর minimum field থেকে। সমস্যা: একটি নতুন subdomain তৈরির আগে কেউ সেটি query করলে NXDOMAIN cache হয়ে যায়; তারপর record তৈরি করলেও negative TTL শেষ না হওয়া পর্যন্ত সেটি "নেই" দেখাবে। এজন্যই negative TTL কম রাখা এবং নতুন record তৈরির আগে query না করা ভালো।

Server migration-এর পরিকল্পনায় TTL কীভাবে ব্যবহার করবেন?

(১) Migration-এর অন্তত পুরনো TTL-এর সমান সময় আগে TTL কমিয়ে ৩০০ বা ৬০ করুন, IP অপরিবর্তিত রেখে। (২) পুরনো TTL-এর সমান সময় অপেক্ষা করুন যাতে সব cache নতুন কম TTL গ্রহণ করে। (৩) এবার IP বদলান — পরিবর্তন কয়েক মিনিটে ছড়াবে। (৪) পুরনো server অন্তত কয়েক ঘণ্টা চালু রাখুন। (৫) স্থিতিশীল হলে TTL আবার বাড়ান।

Anycast কীভাবে একই IP-কে বহু জায়গায় থাকতে দেয়?

একাধিক ভৌগোলিক অবস্থান থেকে BGP-র মাধ্যমে একই IP prefix ঘোষণা করা হয়। প্রতিটি router স্বাভাবিক routing নিয়ম অনুযায়ী নিকটতম ঘোষণাকারীর দিকে packet পাঠায় — কোনো বিশেষ ব্যবস্থা লাগে না, এটি routing-এর স্বাভাবিক আচরণেরই ব্যবহার। ফলে ব্যবহারকারীরা স্বয়ংক্রিয়ভাবে কাছের server পান, এবং একটি site বন্ধ হলে route পরেরটিতে চলে যায়।
