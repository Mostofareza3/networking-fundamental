Chapter 34

NAT — Network Address Translation

NAT ছিল IPv4-এর address সংকটের একটি অস্থায়ী সমাধান। তিন দশক পরেও এটি সর্বত্র, এবং এটি Internet-এর মৌলিক নকশাকে গভীরভাবে বদলে দিয়েছে — বেশিরভাগই খারাপভাবে।

34.1 Why does this exist?

IPv4-এ মোট address: 2³² ≈ ৪৩০ কোটি
পৃথিবীর জনসংখ্যা:    ৮০০ কোটি
প্রতিজনে device:      ৩–১০টি

সংখ্যাটি কোনোভাবেই মেলে না।

আপনার বাসায়:
  Laptop, ফোন ×৩, TV, tablet, smart bulb ×৫,
  printer, watch... ১৫টি device
  কিন্তু ISP আপনাকে দিয়েছে ★একটি★ public IP

সমাধান: NAT
  ভেতরে সবাই private address ব্যবহার করুক,
  বাইরে যাওয়ার সময় সেই একটি public IP-তে
  অনুবাদ হোক।

34.2 কীভাবে কাজ করে

┌──── আপনার বাসা (192.168.1.0/24) ────┐
│                                     │
│  Laptop   192.168.1.10              │
│  ফোন      192.168.1.11              │
│  TV       192.168.1.12              │
│                                     │
└──────────────┬──────────────────────┘
               │
        ┌──────▼──────┐
        │ NAT ROUTER  │
        │             │
        │ ভেতরে: 192.168.1.1
        │ বাইরে: 103.55.20.7  ← একমাত্র public IP
        └──────┬──────┘
               │
          INTERNET


বাইরে যাওয়ার পথে (outbound):

  Laptop পাঠাল:
    src 192.168.1.10:51234  →  dst 93.184.215.14:443

  NAT বদলে দিল:
    src ★103.55.20.7:42001★ →  dst 93.184.215.14:443
         ↑ নিজের public IP    ↑ port-ও বদলাতে পারে

  এবং একটি table-এ লিখে রাখল:
  ┌──────────────────┬───────────────────┬────────────┐
  │ ভেতরের           │ বাইরের             │ গন্তব্য     │
  ├──────────────────┼───────────────────┼────────────┤
  │192.168.1.10:51234│103.55.20.7:42001  │93.184.x:443│
  │192.168.1.11:38900│103.55.20.7:42002  │93.184.x:443│
  │192.168.1.12:44100│103.55.20.7:42003  │142.250.x:80│
  └──────────────────┴───────────────────┴────────────┘


ফেরার পথে (inbound):

  Server পাঠাল:
    src 93.184.215.14:443  →  dst 103.55.20.7:★42001★

  NAT table-এ 42001 খুঁজল, পেল 192.168.1.10:51234

  বদলে দিল:
    src 93.184.215.14:443  →  dst 192.168.1.10:51234

  এবং laptop-এ পাঠিয়ে দিল।
🧠 Mental Model — অফিসের রিসেপশন

একটি অফিসে একটিমাত্র বাইরের ফোন নম্বর। ভেতরে ৫০টি extension।

  • ভেতর থেকে কেউ ফোন করলে বাইরে অফিসের নম্বরটাই দেখায়। রিসেপশনিস্ট লিখে রাখেন "এই কলটি extension 23-এর"।
  • উত্তর এলে তিনি সঠিক extension-এ পাঠিয়ে দেন।
  • কিন্তু বাইরে থেকে কেউ সরাসরি extension 23-এ ফোন করতে পারে না — সে extension নম্বরটি জানেই না, এবং রিসেপশনিস্টও জানেন না কাকে দেবেন।

শেষ পয়েন্টটিই NAT-এর সবচেয়ে গুরুত্বপূর্ণ পরিণতি — এবং এটি Internet-এর মৌলিক নকশা ভেঙে দিয়েছে।

34.3 NAT-এর প্রকারভেদ

ধরনকী করেকোথায়
Static NATএকটি private ↔ একটি public, স্থায়ীভাবেবিরল; একটি নির্দিষ্ট server-কে বাইরে দেখাতে
Dynamic NATএকটি pool থেকে অস্থায়ীভাবে বরাদ্দবিরল
PAT / NAPT
(Port Address Translation)		বহু private → একটি public, port দিয়ে আলাদা★ কার্যত সব জায়গায় — এটিই "NAT" বলতে যা বোঝায়
CGNAT
(Carrier-Grade NAT)		ISP নিজেই আরেক স্তরের NAT করে — গ্রাহকরাও private IP পায়Mobile network, অনেক ISP
⚠️ CGNAT — দুই স্তরের NAT

অনেক ISP (বিশেষত mobile operator) গ্রাহকদেরও public IP দেয় না — 100.64.0.0/10 range থেকে একটি "carrier-grade private" address দেয়। ফলে:

আপনার device      : 192.168.1.10   (বাসার NAT)
আপনার router      : 100.64.5.20    (CGNAT-এর ভেতরে!)
ISP-র public IP   : 103.55.20.7    (হাজারো গ্রাহকের সাথে ভাগ)

⇒ Port forwarding সম্পূর্ণ অসম্ভব — কারণ আপনি
  ISP-র NAT নিয়ন্ত্রণ করেন না
⇒ অনেক peer-to-peer application কাজ করে না
⇒ আপনার "public IP" আসলে হাজারো মানুষের সাথে ভাগ করা

এটি পরীক্ষা করা সহজ: curl ifconfig.me দিয়ে পাওয়া IP যদি আপনার router-এর WAN interface-এর IP-র সাথে না মেলে, আপনি CGNAT-এর পেছনে আছেন।

34.4 NAT কী ভেঙে দিয়েছে

⚠️ End-to-End Principle-এর মৃত্যু

মূল Internet-এর নকশায় যেকোনো host যেকোনো host-এর সাথে সরাসরি যোগাযোগ করতে পারত। NAT এটি ভেঙে দিয়েছে:

  1. Inbound connection অসম্ভব। কেউ বাইরে থেকে আপনার laptop-এ connect করতে পারবে না — কারণ NAT table-এ কোনো entry নেই, তাই router জানে না packet কাকে দেবে।
  2. Peer-to-peer কঠিন। দুটি device দুটি NAT-এর পেছনে থাকলে কেউ কারো সাথে সরাসরি connect করতে পারে না। এজন্যই STUN, TURN, ICE-এর মতো জটিল প্রযুক্তি তৈরি করতে হয়েছে (WebRTC-র ভিত্তি)।
  3. Router-কে state রাখতে হয়। IP-র মূল নকশা ছিল stateless (Ch 12)। NAT সেটি ভাঙে — এবং state মানে memory, timeout, এবং router reboot হলে সব connection মৃত।
  4. Layer violation। একটি Layer 3 যন্ত্র Layer 4 header (port) বদলাচ্ছে।
  5. Idle connection মরে যায়। NAT-এর mapping-এর timeout আছে (TCP-তে সাধারণত ৫–৩০ মিনিট, UDP-তে ৩০ সেকেন্ড–৫ মিনিট)। কোনো traffic না থাকলে entry মুছে যায় এবং connection চুপচাপ ভেঙে যায়।
⚙️ Developer Perspective — NAT timeout-এর বাস্তব প্রভাব

"আমার WebSocket connection ৫ মিনিট পরে চুপচাপ মরে যায়" — এটি প্রায় সবসময় NAT timeout। কোনো error আসে না, কারণ NAT নীরবে entry মুছে দেয়; পরের packet-টি কোথায় পাঠাতে হবে সে জানে না, তাই ফেলে দেয়।

সমাধান: keepalive। নিয়মিত ছোট packet পাঠিয়ে NAT-এর entry জীবিত রাখুন:

  • WebSocket: প্রতি ৩০–৬০ সেকেন্ডে ping frame
  • TCP: SO_KEEPALIVE (কিন্তু default ২ ঘণ্টা — অনেক দেরি; TCP_KEEPIDLE কমিয়ে ৬০ করুন)
  • SSH: ServerAliveInterval 60
  • Database connection pool: idle connection নিয়মিত validate করুন, বা maxIdleTime NAT timeout-এর কম রাখুন
  • gRPC: keepalive_time_ms configure করুন

এটি cloud environment-এও প্রযোজ্য — AWS NAT Gateway-র idle timeout ৩৫০ সেকেন্ড, এবং এই কারণে বহু "রহস্যময়" connection drop ঘটে।

34.5 বাইরে থেকে ভেতরে আসার উপায়

পদ্ধতিকীভাবেসীমাবদ্ধতা
Port forwardingRouter-এ হাতে নিয়ম: "port 8080 → 192.168.1.10:8080"Router-এ access লাগে; CGNAT-এ অসম্ভব
UPnP / NAT-PMPApplication নিজেই router-কে বলে port খুলতেনিরাপত্তা ঝুঁকি; অনেক router-এ বন্ধ
STUNএকটি বাইরের server বলে দেয় আপনার public IP:port কীশুধু কিছু NAT-এ কাজ করে
TURNএকটি relay server সব traffic মাঝখান দিয়ে চালায়কাজ করে সবসময়, কিন্তু bandwidth ব্যয়বহুল
Hole punchingদুই পক্ষ একসাথে বাইরে পাঠায়, দুই NAT-এ entry তৈরি হয়NAT-এর ধরনের উপর নির্ভরশীল
Reverse tunnelভেতরের machine নিজে বাইরে connect করে, সেই connection পুনর্ব্যবহারসবচেয়ে নির্ভরযোগ্য; ngrok, Cloudflare Tunnel, ssh -R এভাবেই কাজ করে
✓ ngrok কীভাবে কাজ করে

আপনার local dev server-কে Internet-এ দেখাতে ngrok যা করে:

1. আপনার machine ★বাইরের দিকে★ ngrok server-এ connect করে
   → NAT-এ একটি entry তৈরি হলো (outbound তো অনুমোদিত)

2. ngrok আপনাকে একটি public URL দেয়

3. কেউ সেই URL-এ এলে ngrok server সেই request-টি
   ★ইতিমধ্যে খোলা★ connection দিয়ে আপনার machine-এ পাঠায়

★ NAT-কে হারানো হয়নি — বরং তার নিয়ম মেনেই কাজ করা
  হয়েছে: outbound connection সবসময় অনুমোদিত, তাই
  সেটিকেই দ্বিমুখী করে ব্যবহার করা হচ্ছে।

34.6 IPv6 এবং NAT

ℹ️ IPv6-এ NAT দরকার নেই

IPv6-এ ৩.৪ × ১০³⁸ address — প্রতিটি device পেতে পারে একটি প্রকৃত global address। NAT-এর মূল কারণটিই অনুপস্থিত।

কিন্তু একটি সাধারণ ভুল ধারণা: "NAT নিরাপত্তা দেয়"। এটি সত্য নয়। NAT-এর inbound blocking একটি পার্শ্বপ্রতিক্রিয়া, নিরাপত্তা-বৈশিষ্ট্য নয়। IPv6-এ প্রতিটি device-এর global address থাকলেও stateful firewall ঠিক একই সুরক্ষা দেয় — এবং সেটি স্পষ্ট নীতি হিসেবে, দুর্ঘটনাক্রমে নয়। প্রতিটি IPv6 router default-এ unsolicited inbound connection আটকায়।

পার্থক্যটি গুরুত্বপূর্ণ: NAT নিরাপত্তা দুর্ঘটনাক্রমে দেয়, firewall উদ্দেশ্যপ্রণোদিতভাবে। উদ্দেশ্যপ্রণোদিত ব্যবস্থা যাচাই করা যায়, নিরীক্ষা করা যায়, এবং প্রয়োজনে সঠিকভাবে শিথিল করা যায়।

🧪 Lab 34 — নিজের NAT পরীক্ষা করুন

আমরা কী দেখতে চাইছি? — আপনার local IP এবং বাইরের দুনিয়া যে IP দেখে, তার পার্থক্য; এবং আপনি CGNAT-এর পেছনে কিনা।

bash
# আপনার local IP
ip -brief addr | grep -v lo        # Linux
ipconfig getifaddr en0             # macOS

# বাইরের দুনিয়া যা দেখে
curl -s ifconfig.me; echo
curl -s https://api.ipify.org; echo

# আপনার router-এর WAN IP (router-এর admin page থেকে)
# যদি সেটি ifconfig.me-র থেকে ভিন্ন হয় → আপনি CGNAT-এ

# CGNAT range পরীক্ষা: 100.64.0.0/10-এর মধ্যে?
# 100.64.x.x থেকে 100.127.x.x পর্যন্ত

# NAT-এর port translation দেখুন
sudo tcpdump -i any -n 'tcp[tcpflags] & tcp-syn != 0' -c 3 &
curl -s https://example.com > /dev/null
# আপনার machine যে source port ব্যবহার করছে তা দেখুন,
# তারপর ifconfig.me-র মতো একটি service ব্যবহার করে
# বাইরে থেকে কোন port দেখা যাচ্ছে তা তুলনা করুন

যা লক্ষ্য করবেন: আপনার local IP 192.168.x.x বা 10.x.x.x, কিন্তু ifconfig.me একটি সম্পূর্ণ ভিন্ন public IP দেখাচ্ছে। এই দুটির মাঝখানেই NAT কাজ করছে। আপনার বাড়ির সব device একই public IP দেখাবে — সেটিও পরীক্ষা করে দেখতে পারেন ফোন থেকে একই URL খুলে।

আমরা কী শিখলাম: আপনার "IP address" বলে একক কিছু নেই — আপনার machine-এর একটি ঠিকানা আছে, আর Internet আপনাকে সম্পূর্ণ ভিন্ন একটি ঠিকানায় চেনে। এবং সেই দ্বিতীয় ঠিকানাটি আপনার পুরো বাড়ির (বা CGNAT হলে হাজারো মানুষের) সাথে ভাগ করা।

📌 Chapter Summary
  • NAT একটি public IP-র পেছনে বহু private device চালাতে দেয় — IPv4 সংকটের সমাধান।
  • PAT/NAPT (port দিয়ে আলাদা করা) — এটিই বাস্তবে সর্বত্র ব্যবহৃত রূপ।
  • NAT router-কে state রাখতে হয়, তাই সে stateless IP-র নকশা ভাঙে।
  • Inbound connection অসম্ভব → peer-to-peer কঠিন → STUN/TURN/ICE-এর প্রয়োজন।
  • NAT timeout idle connection মেরে ফেলে → keepalive অপরিহার্য।
  • CGNAT-এ ISP-ও NAT করে — port forwarding সম্পূর্ণ অসম্ভব হয়ে যায়।
  • Reverse tunnel (ngrok, Cloudflare Tunnel) NAT-এর নিয়ম মেনেই ভেতরে পৌঁছানোর সবচেয়ে নির্ভরযোগ্য উপায়।
  • NAT নিরাপত্তা-ব্যবস্থা নয় — তার inbound blocking একটি পার্শ্বপ্রতিক্রিয়া মাত্র; প্রকৃত সুরক্ষা firewall-এর কাজ।

NAT কীভাবে জানে ফেরত আসা packet কোন internal device-কে দিতে হবে?

একটি translation table-এর মাধ্যমে। Outbound packet পাঠানোর সময় NAT একটি entry তৈরি করে: (internal IP, internal port) ↔ (public IP, নির্বাচিত external port), সাথে গন্তব্যের তথ্য। Response এলে সে destination port দেখে table-এ খুঁজে বের করে কোন internal endpoint-এর জন্য, এবং সেই অনুযায়ী header বদলে দেয়। এই table-ই সেই "state" যা সাধারণ router-এর থাকে না।

আপনার WebSocket connection নিয়মিত ৫ মিনিট পরে মরে যাচ্ছে। কারণ ও সমাধান?

NAT timeout। কোনো traffic না থাকলে NAT (বা cloud NAT Gateway, বা firewall) idle mapping মুছে দেয় — নীরবে, কোনো notification ছাড়াই। পরের packet-এর জন্য আর কোনো entry না থাকায় সেটি ফেলে দেওয়া হয়। সমাধান: NAT timeout-এর চেয়ে কম ব্যবধানে keepalive/ping পাঠান (সাধারণত ৩০–৬০ সেকেন্ড)। WebSocket-এ ping frame, TCP-তে SO_KEEPALIVE সহ কম TCP_KEEPIDLE।

"NAT আমার নিরাপত্তা দেয়" — এই বক্তব্য কতটা সঠিক?

আংশিক সত্য কিন্তু বিভ্রান্তিকর। NAT unsolicited inbound connection আটকায় — কিন্তু এটি একটি পার্শ্বপ্রতিক্রিয়া (table-এ entry নেই বলে packet ফেলে দিতে হয়), কোনো নিরাপত্তা-নীতি নয়। এটি outbound traffic, malware, বা compromised device-এর বিরুদ্ধে কিছুই করে না। প্রকৃত সুরক্ষা আসে stateful firewall থেকে — যা স্পষ্ট নীতি অনুযায়ী কাজ করে, যাচাইযোগ্য, এবং IPv6-এও সমানভাবে কার্যকর।

ngrok NAT-এর সীমাবদ্ধতা কীভাবে এড়ায়?

সে NAT-কে "হারায়" না, বরং তার নিয়ম মেনেই কাজ করে। আপনার machine নিজে বাইরের দিকে ngrok server-এ একটি connection খোলে — যা NAT সবসময় অনুমোদন করে এবং যার জন্য একটি mapping তৈরি হয়। এরপর ngrok সেই ইতিমধ্যে-খোলা connection-টিকে দ্বিমুখীভাবে ব্যবহার করে বাইরের request গুলো আপনার machine-এ পৌঁছে দেয়। Cloudflare Tunnel এবং ssh -R-ও একই নীতিতে কাজ করে।
