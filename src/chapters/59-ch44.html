Chapter 44

HTTP/2 — গভীরে

Chapter 30-এ আমরা HTTP/2-এর ভূমিকা দেখেছি। এখানে দেখব তার প্রকৃত যন্ত্রপাতি — binary framing, stream, এবং HPACK — এবং কেন এগুলো আপনার application-এর নকশাকে প্রভাবিত করে।

44.1 Binary Framing Layer

HTTP/1.1 — text, একটি request একটি connection দখল করে:

  GET /users HTTP/1.1\r\n
  Host: api.example.com\r\n
  \r\n

HTTP/2 — সবকিছু ছোট ছোট binary FRAME:

  ┌──────────────────────────────────────┐
  │ Length (24 bit) │ Type (8) │Flags(8) │
  ├──────────────────────────────────────┤
  │ R │      Stream Identifier (31 bit)  │  ★ কোন stream ★
  ├──────────────────────────────────────┤
  │            Frame Payload             │
  └──────────────────────────────────────┘

Frame-এর ধরন:
  HEADERS       — HTTP header (HPACK-এ compressed)
  DATA          — body-র অংশ
  SETTINGS      — connection-এর parameter
  WINDOW_UPDATE — flow control (stream-প্রতি!)
  RST_STREAM    — একটি stream বাতিল
  PRIORITY      — অগ্রাধিকার
  PING          — জীবিত আছে কি
  GOAWAY        — connection বন্ধ করছি
💡 Binary কেন — শুধু "দ্রুত" নয়

Binary format-এর প্রকৃত সুবিধা parsing-এর গতি নয় (যদিও সেটিও আছে), বরং দ্ব্যর্থহীনতা। Text protocol-এ whitespace, line ending, header folding, encoding — এই সব নিয়ে ব্যাখ্যার ভিন্নতা তৈরি হয়। সেই ভিন্নতাই HTTP request smuggling-এর মতো নিরাপত্তা-দুর্বলতার উৎস (Ch 28)।

Binary frame-এ length স্পষ্টভাবে দেওয়া — কোনো parsing-এর দ্ব্যর্থতা নেই। এটি একই সাথে দ্রুত এবং নিরাপদ।

44.2 Stream — সমান্তরাল কথোপকথন

একটি TCP connection = বহু stream

  Stream 1 ─── HEADERS ── DATA ── DATA ──────▶
  Stream 3 ────── HEADERS ─── DATA ──────────▶
  Stream 5 ─ HEADERS ─── DATA ── DATA ── DATA▶

তারে frame গুলো মিশে যায়:

  [H:1][H:3][D:1][H:5][D:3][D:1][D:5][D:5][D:3]
     │    │    │    │
     └────┴────┴────┴─ stream ID দিয়ে আলাদা করা যায়

Stream ID-র নিয়ম:
  বিজোড় (1,3,5...) → client শুরু করেছে
  জোড়  (2,4,6...) → server শুরু করেছে (push, এখন অপ্রচলিত)

প্রতিটি stream-এর নিজস্ব:
  • state machine (idle → open → closed)
  • flow control window ★
  • priority

★ Stream-প্রতি flow control একটি গুরুত্বপূর্ণ বৈশিষ্ট্য:
  একটি ধীর consumer শুধু নিজের stream-কে ধীর করে,
  পুরো connection-কে নয়।

44.3 HPACK — Header Compression

সমস্যা: HTTP header-এ প্রচুর পুনরাবৃত্তি

  Request 1:                  Request 2:
    :method: GET                :method: GET
    :path: /users               :path: /orders    ← শুধু এটাই ভিন্ন
    :authority: api.example.com :authority: api.example.com
    user-agent: Mozilla/5.0...  user-agent: Mozilla/5.0...
    accept: application/json    accept: application/json
    cookie: session=abc123...   cookie: session=abc123...

  একটি সাধারণ page-এ ১০০টি request × ~৮০০ bytes header
  = ৮০ KB শুধু header-এ, যার ৯৫% হুবহু একই!

HPACK-এর তিনটি কৌশল:

১. STATIC TABLE — ৬১টি প্রচলিত header পূর্বনির্ধারিত
     index 2  = :method: GET
     index 4  = :path: /
     index 16 = accept-encoding: gzip, deflate

২. DYNAMIC TABLE — connection-এর জীবনকালে শেখা
     প্রথমবার পুরো header পাঠান, একটি index পান
     পরেরবার শুধু সেই index

৩. HUFFMAN CODING — বাকি string গুলোর জন্য

ফল:
  Request 1: ~800 bytes
  Request 2: ~30 bytes   ★ ৯৬% সাশ্রয় ★
⚠️ HPACK এবং CRIME/HEARTBLEED-জাতীয় ঝুঁকি

Compression এবং encryption একসাথে থাকলে একটি সূক্ষ্ম ঝুঁকি তৈরি হয়: compressed data-র আকার থেকে তার বিষয়বস্তু সম্পর্কে অনুমান করা যায় (CRIME/BREACH আক্রমণ)। HPACK এই সমস্যা মাথায় রেখেই নকশা করা হয়েছে — এটি DEFLATE-এর মতো সাধারণ compression নয়, বরং একটি সীমিত, নিয়ন্ত্রিত ব্যবস্থা যেখানে আক্রমণকারীর নিয়ন্ত্রিত data ও গোপন data-র মধ্যে cross-reference সীমিত।

শিক্ষা: "compression যোগ করলেই ভালো" — এটি নিরাপত্তার প্রেক্ষিতে সবসময় সত্য নয়।

⚙️ Developer Perspective — gRPC এবং HTTP/2

gRPC সম্পূর্ণভাবে HTTP/2-এর উপর নির্মিত, এবং এটি HTTP/2-এর বৈশিষ্ট্যগুলোর সবচেয়ে ভালো ব্যবহার:

  • Streaming — একটি stream দীর্ঘ সময় খোলা রেখে দুই দিকেই message পাঠানো (bidirectional streaming)।
  • Multiplexing — একটি TCP connection-এ হাজারো সমান্তরাল RPC।
  • Long-lived connection — handshake ও slow start-এর খরচ একবারই।
  • HPACK — metadata-র পুনরাবৃত্তি প্রায় বিনামূল্যে।

কিন্তু একটি ফাঁদ: HTTP/2-এর long-lived connection load balancing-এর সাথে খারাপভাবে মেশে। একটি L4 load balancer connection-স্তরে বণ্টন করে — কিন্তু gRPC-তে একটি connection-ই হাজারো request বহন করে, তাই সব request একটি backend-এ চলে যায়। সমাধান: L7 (gRPC-সচেতন) load balancer, বা client-side load balancing।

📌 Chapter Summary
  • HTTP/2 সবকিছুকে binary frame-এ ভাগ করে, প্রতিটিতে একটি stream ID।
  • Binary format দ্রুত এবং দ্ব্যর্থহীন — request smuggling-এর মতো দুর্বলতা কমায়।
  • একটি connection-এ বহু stream; প্রতিটির নিজস্ব state ও flow control window।
  • HPACK static table, dynamic table ও Huffman coding দিয়ে header ৯০%+ সংকুচিত করে।
  • Domain sharding, sprite, inline asset — HTTP/2-তে এগুলো এখন ক্ষতিকর।
  • gRPC HTTP/2-এর সবচেয়ে পূর্ণ ব্যবহার, কিন্তু L4 load balancing-এর সাথে সমস্যা তৈরি করে।
✓ Quick Check
HTTP/2-তে stream ID-র বিজোড়/জোড় বিভাজন কেন?

যাতে client ও server স্বাধীনভাবে নতুন stream শুরু করতে পারে, কোনো সমন্বয় বা সংঘাত ছাড়াই। Client শুধু বিজোড় সংখ্যা (1, 3, 5...) ব্যবহার করে, server শুধু জোড় (2, 4, 6...)। এটি একটি সরল কিন্তু কার্যকর কৌশল — distributed ID বণ্টনের একটি ধ্রুপদী সমাধান।

HTTP/2 ব্যবহার করলে JavaScript bundle করা কি বন্ধ করে দেওয়া উচিত?

সম্পূর্ণ নয়, কিন্তু ভারসাম্য বদলে যায়। HTTP/1.1-এ ৫০টি ফাইল মানে ছিল ৫০টি request-এর queue — তাই bundle অপরিহার্য ছিল। HTTP/2-তে সেই খরচ প্রায় নেই, এবং আলাদা ফাইল রাখলে cache invalidation অনেক ভালো হয় (একটি module বদলালে শুধু সেটিই আবার নামাতে হয়)। তবে অতিরিক্ত ছোট ফাইলে (শত শত) compression-এর কার্যকারিতা কমে এবং প্রতিটির নিজস্ব overhead থাকে। ব্যবহারিক পরামর্শ: যুক্তিসঙ্গত আকারের কয়েকটি chunk — চরম কোনোটিই নয়।

gRPC-তে L4 load balancer ব্যবহার করলে কী সমস্যা?

L4 load balancer connection-স্তরে বণ্টন করে। কিন্তু gRPC একটি long-lived HTTP/2 connection খুলে তার উপর হাজারো RPC পাঠায়। ফলে একটি client-এর সব request একটিই backend-এ যায় — load সম্পূর্ণ অসম হয়ে পড়ে, এবং নতুন backend যোগ করলেও পুরনো connection সেখানে যায় না। সমাধান: L7 (gRPC-সচেতন) proxy যেমন Envoy, বা client-side load balancing।
