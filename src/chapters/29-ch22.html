Chapter 22

TCP Connection Termination এবং TIME_WAIT

Connection বন্ধ করা খোলার চেয়ে জটিল, কারণ দুই দিকের data stream স্বাধীনভাবে শেষ হতে পারে। আর TIME_WAIT — সেই অবস্থা যা দেখলে সবাই বিরক্ত হয় এবং অনেকে ভুল করে বন্ধ করে দেয়।

22.1 Four-Way Handshake

TCP connection full-duplex — দুটি স্বাধীন byte stream। তাই প্রতিটি দিক আলাদাভাবে বন্ধ করতে হয়।

   CLIENT                                    SERVER
      │                                         │
 ESTABLISHED                              ESTABLISHED
      │                                         │
      │  close() করলাম                           │
      │  FIN, seq=1000                          │
      ├────────────────────────────────────────▶│
      │                                         │
 FIN_WAIT_1                                CLOSE_WAIT
      │                                         │
      │◀────────────────────────────────────────┤
      │            ACK=1001                     │
 FIN_WAIT_2                                     │
      │                                         │
      │      ◀── server এখনো data পাঠাতে পারে ──│
      │      ◀── ("half-close" অবস্থা)          │
      │                                         │
      │                              server-ও close() করল
      │            FIN, seq=5000                │
      │◀────────────────────────────────────────┤
      │                                    LAST_ACK
      │            ACK=5001                     │
      ├────────────────────────────────────────▶│
      │                                         │
  TIME_WAIT                                  CLOSED
      │                                         
      │  2 × MSL অপেক্ষা (সাধারণত 60s)
      │
   CLOSED
ℹ️ কেন চারটি packet, তিনটি নয়

খোলার সময় SYN-ACK একটি packet-এ দুটি কাজ করে। বন্ধ করার সময় সেটি সবসময় সম্ভব নয়, কারণ একদিকে data শেষ হলেও অন্যদিকে চলতে পারে।

উদাহরণ: আপনি একটি বড় ফাইল upload করছেন এবং শেষ করে FIN পাঠালেন। Server তখনো processing করছে এবং কয়েক সেকেন্ড পরে response পাঠাবে। সে সঙ্গে সঙ্গে FIN পাঠাতে পারে না — শুধু ACK দিয়ে বলে "তোমার শেষ, বুঝেছি", তারপর নিজের কাজ শেষ করে আলাদাভাবে FIN পাঠায়। (তবে server-এর কিছু বলার না থাকলে ACK ও FIN একসাথেও যেতে পারে।)

22.2 TIME_WAIT — সবচেয়ে ভুল বোঝা অবস্থা

যে পক্ষ প্রথমে close করে, সে শেষ ACK পাঠানোর পর TIME_WAIT অবস্থায় যায় এবং 2 × MSL সময় অপেক্ষা করে (MSL = Maximum Segment Lifetime, সাধারণত ৩০ সেকেন্ড; তাই মোট ~৬০ সেকেন্ড, Linux-এ hard-coded)।

💡 কেন এই অপেক্ষা — দুটি কারণ

কারণ ১ — শেষ ACK হারিয়ে যেতে পারে

Client শেষ ACK পাঠাল ──✗ হারিয়ে গেল

Server তখনো LAST_ACK-এ অপেক্ষা করছে
  → timeout হলে সে FIN আবার পাঠাবে

  যদি client সঙ্গে সঙ্গে CLOSED হয়ে যেত:
    → সে ওই FIN-এর জবাবে RST পাঠাত
    → server একটি ভুল error দেখত
    → "connection reset by peer"

  TIME_WAIT-এ থাকায়:
    → client FIN-টি চিনতে পারে
    → আবার ACK পাঠায়
    → server শান্তিতে বন্ধ হয়

কারণ ২ — পুরনো packet নতুন connection-এ ঢুকে পড়া

ধরুন একটি packet network-এ কোথাও আটকে ছিল (routing loop)।
Connection বন্ধ হয়ে গেল।

সঙ্গে সঙ্গে একই 4-tuple দিয়ে নতুন connection খোলা হলো:
    (192.168.1.5:51234 → 10.0.0.5:443)

এখন সেই পুরনো, দেরিতে পৌঁছানো packet এসে হাজির।
Sequence number কাকতালীয়ভাবে মিলে গেলে
নতুন connection পুরনো data গ্রহণ করে ফেলবে!
    → data corruption

TIME_WAIT নিশ্চিত করে যে ওই 4-tuple পুনর্ব্যবহারের আগে
network-এ ভাসমান সব পুরনো packet মরে গেছে
(2 × MSL = একটি packet-এর সর্বোচ্চ আয়ুর দ্বিগুণ)।
⚠️ "Address already in use" — সবচেয়ে পরিচিত বিরক্তি

আপনি server বন্ধ করে আবার চালু করলেন, এবং পেলেন:

text
Error: listen EADDRINUSE: address already in use :::8080

কারণ: আগের connection গুলো TIME_WAIT-এ, তাই ওই local port তখনো "ব্যবহৃত" হিসেবে গণ্য।

সঠিক সমাধান — SO_REUSEADDR socket option। এটি kernel-কে বলে "TIME_WAIT-এ থাকা socket থাকলেও এই address-এ bind করতে দাও"। এটি নিরাপদ, কারণ TIME_WAIT-এর সুরক্ষা তখনো 4-tuple-ভিত্তিকভাবে বজায় থাকে।

js
// Node.js — server.listen() নিজেই SO_REUSEADDR সেট করে

// Python
sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)

// Go — net.Listen() default-এ সেট করে

// C
int yes = 1;
setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &yes, sizeof(yes));

ভুল সমাধান — net.ipv4.tcp_tw_recycle = 1 সেট করা। এটি NAT-এর পেছনের client-দের জন্য connection ভেঙে দেয় এবং এটি Linux 4.12 থেকে সরিয়েই ফেলা হয়েছে। Internet-এ পুরনো blog post-এ এই পরামর্শ এখনো পাওয়া যায় — অনুসরণ করবেন না।

22.3 কে TIME_WAIT-এ যায় — এবং এটি কেন গুরুত্বপূর্ণ

✓ যে প্রথমে close করে, সেই TIME_WAIT-এ যায়

এটি একটি নকশাগত সিদ্ধান্ত যার বড় বাস্তব প্রভাব আছে:

  • Server আগে close করলে — server-এ হাজার হাজার TIME_WAIT socket জমে। প্রতিটি কিছু memory খায় এবং port-এর সীমা তৈরি করতে পারে।
  • Client আগে close করলে — TIME_WAIT client-এর দিকে যায়, যেখানে সাধারণত connection-এর সংখ্যা অনেক কম।

এজন্যই HTTP-তে সাধারণত client-ই connection বন্ধ করে (বা keep-alive দিয়ে খোলা রাখা হয়)। একটি ব্যস্ত API server-এ যদি প্রতিটি response-এর পর server নিজে close করে, সেখানে দ্রুত লক্ষাধিক TIME_WAIT socket জমতে পারে।

22.4 RST — রূঢ় সমাপ্তি

FIN (ভদ্র)RST (রূঢ়)
অর্থ"আমার পাঠানো শেষ""এই connection বাতিল, এখনই"
Buffer-এর dataপাঠানো সম্পূর্ণ হয়ফেলে দেওয়া হয়
উত্তরACK আশা করেকোনো উত্তরের আশা নেই
TIME_WAITহয়হয় না

RST কখন পাঠানো হয়:

  • বন্ধ port-এ connect করলে → এটিই connection refused-এর প্রকৃত রূপ
  • একটি মৃত/অজানা connection-এ packet এলে
  • Application SO_LINGER=0 দিয়ে জোর করে বন্ধ করলে
  • Process crash করলে — kernel বাকি connection গুলোতে RST পাঠায়
  • Firewall জোর করে connection কাটলে
⚙️ Developer Perspective — error message-এর মানে
  • ECONNREFUSED — SYN-এর জবাবে RST এল। Machine পৌঁছানো গেছে, routing ঠিক আছে, কিন্তু ওই port-এ কেউ শুনছে না। প্রায়ই মানে: service চলছে না, বা ভুল port, বা 127.0.0.1-এ bind করা।
  • ECONNRESET — প্রতিষ্ঠিত connection-এ RST এল। অপর পক্ষ crash করেছে, বা জোর করে বন্ধ করেছে, বা মাঝখানের কোনো firewall/load balancer idle connection কেটে দিয়েছে।
  • ETIMEDOUT — কোনো উত্তরই আসেনি। Packet হারাচ্ছে, বা firewall নীরবে ফেলে দিচ্ছে (DROP, REJECT নয়), বা host পৌঁছানো যাচ্ছে না।
  • EPIPE — বন্ধ হয়ে যাওয়া connection-এ লিখতে চেয়েছেন। সাধারণত আগেই একটি ECONNRESET বা FIN এসেছিল।

এই চারটির পার্থক্য জানা debugging-এর সময় সরাসরি সঠিক দিকে নিয়ে যায়: RST মানে packet পৌঁছেছে (network ঠিক), timeout মানে পৌঁছায়নি (network বা firewall দেখুন)।

🧪 Lab 22 — TIME_WAIT এবং RST তৈরি করে দেখুন

আমরা কী দেখতে চাইছি? — TIME_WAIT বাস্তবে কখন তৈরি হয়, কতক্ষণ থাকে, এবং RST কেমন দেখায়।

bash
# বর্তমান TIME_WAIT socket গুলো গুনুন
ss -tan | awk '{print $1}' | sort | uniq -c

# অনেকগুলো ছোট connection তৈরি করুন
for i in $(seq 1 30); do curl -s -o /dev/null http://example.com; done

# আবার গুনুন — TIME_WAIT বেড়েছে
ss -tan state time-wait | wc -l

# ৬০ সেকেন্ড পরে আবার দেখুন — কমে গেছে

# RST দেখুন: একটি বন্ধ port-এ connect করুন
sudo tcpdump -i lo -n 'tcp port 9999' &
curl -s http://127.0.0.1:9999 ; echo "exit code: $?"

যা লক্ষ্য করবেন: curl গুলো চালানোর পর TIME_WAIT-এর সংখ্যা লাফিয়ে বাড়ে, তারপর প্রায় ৬০ সেকেন্ডে ধীরে ধীরে শূন্যে নামে। বন্ধ port-এ connect করলে tcpdump-এ দেখবেন Flags [S]-এর সঙ্গে সঙ্গে Flags [R.] — অর্থাৎ RST, এবং curl বলবে Connection refused।

আমরা কী শিখলাম: TIME_WAIT কোনো ত্রুটি নয়, এটি একটি নিরাপত্তা-ব্যবস্থা যার নির্দিষ্ট আয়ু আছে। আর connection refused আসলে একটি প্রকৃত RST packet — অর্থাৎ আপনার packet গন্তব্যে পৌঁছেছে, যা নিজেই একটি মূল্যবান তথ্য।

📌 Chapter Summary
  • TCP full-duplex, তাই বন্ধ করতে চারটি packet: FIN → ACK → FIN → ACK।
  • একদিক বন্ধ হলেও অন্যদিক চলতে পারে (half-close)।
  • যে প্রথমে close করে সে TIME_WAIT-এ যায়, ২ × MSL (~৬০s) সময়ের জন্য।
  • TIME_WAIT-এর দুটি কারণ: হারানো শেষ ACK সামলানো, এবং পুরনো packet নতুন connection-এ ঢুকতে না দেওয়া।
  • "Address already in use"-এর সঠিক সমাধান SO_REUSEADDR; tcp_tw_recycle নয় (এটি বিপজ্জনক ও অপসারিত)।
  • RST = তাৎক্ষণিক, রূঢ় সমাপ্তি; buffer-এর data হারায়, TIME_WAIT হয় না।
  • ECONNREFUSED (RST এল) ≠ ETIMEDOUT (কিছুই এল না) — এই পার্থক্য debugging-এ মূল্যবান।
✓ Quick Check
TIME_WAIT কেন প্রয়োজন — দুটি কারণ বলুন।

(১) শেষ ACK হারালে: peer FIN আবার পাঠাবে; TIME_WAIT-এ থাকা socket সেটি চিনে আবার ACK পাঠাতে পারে। CLOSED হয়ে গেলে সে RST পাঠাত এবং peer একটি ভুল error দেখত। (২) পুরনো packet: network-এ ভাসমান কোনো দেরিতে আসা packet যেন একই 4-tuple-এর নতুন connection-এ ঢুকে data corrupt না করে। ২ × MSL সময় নিশ্চিত করে সেই সব packet মরে গেছে।

একটি ব্যস্ত API server-এ লক্ষাধিক TIME_WAIT socket। সম্ভাব্য কারণ ও সমাধান?

Server-ই প্রতিটি response-এর পর প্রথমে close() করছে — তাই TIME_WAIT server-এর দিকে জমছে। সমাধান: (১) HTTP keep-alive সক্রিয় করে connection পুনর্ব্যবহার করা — সবচেয়ে কার্যকর; (২) client-কে প্রথমে close করতে দেওয়া; (৩) load balancer ব্যবহার করে backend-এ persistent connection রাখা। tcp_tw_recycle ব্যবহার করবেন না।

connection refused এবং connection timed out — কোনটি বেশি তথ্য দেয়?

connection refused বেশি তথ্য দেয় — এর মানে আপনার SYN packet গন্তব্যে পৌঁছেছে এবং সেখানকার kernel সক্রিয়ভাবে RST দিয়ে জবাব দিয়েছে। অর্থাৎ routing, DNS, firewall — সব ঠিক আছে; শুধু ওই port-এ কেউ শুনছে না। timed out অনেক কম নির্দিষ্ট: packet হারাচ্ছে, বা firewall নীরবে DROP করছে, বা host পৌঁছানো যাচ্ছে না — অনেক সম্ভাবনা।

Half-close কী এবং কখন কাজে লাগে?

একদিকের stream বন্ধ করে অন্যদিক খোলা রাখা — shutdown(fd, SHUT_WR) দিয়ে করা হয়। Client বলে "আমার পাঠানো শেষ" কিন্তু response গ্রহণ করতে থাকে। ক্লাসিক ব্যবহার: cat file | nc host port — client সব data পাঠিয়ে FIN দেয়, server তখন বুঝতে পারে input শেষ, processing করে উত্তর পাঠায়। FIN না দিলে server জানতই না কখন data শেষ হলো।
