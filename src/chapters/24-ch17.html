Chapter 17

TCP — অবিশ্বস্ত network-এর উপর নির্ভরযোগ্যতা

"TCP নির্ভরযোগ্য" — এই বাক্যটি সত্য কিন্তু অর্থহীন, যতক্ষণ না আপনি জানেন কীভাবে। IP packet হারাতে পারে, নকল হতে পারে, উল্টো ক্রমে আসতে পারে। এই বিশৃঙ্খলার উপর একটি পরিচ্ছন্ন byte stream কীভাবে দাঁড় করানো হয় — সেটাই এই chapter।

17.1 Why does this exist?

IP-এর প্রতিশ্রুতি অত্যন্ত সীমিত। সে বলে: "আমি চেষ্টা করব।" ব্যস।

IP যা নিশ্চিত করে না:

  ✗ Packet পৌঁছাবে       — router-এর queue ভরে গেলে ফেলে দেয়
  ✗ ক্রম বজায় থাকবে       — ভিন্ন পথে গেলে ভিন্ন সময়ে পৌঁছায়
  ✗ একবারই আসবে          — retransmission-এ duplicate হতে পারে
  ✗ অবিকৃত থাকবে         — bit নষ্ট হতে পারে (checksum ধরে, কিন্তু ঠিক করে না)
  ✗ সময়মতো আসবে          — কোনো সময়সীমা নেই

IP যা নিশ্চিত করে:
  ✓ চেষ্টা করবে। (best effort)

এখন আপনি একটি database driver লিখছেন। আপনার দরকার: যা পাঠিয়েছি তার সবটুকু, ঠিক যে ক্রমে পাঠিয়েছি, ঠিক একবার করে। কেউ একজনকে IP-এর বিশৃঙ্খলা আর আপনার এই চাহিদার মাঝখানে দাঁড়াতে হবে।

💡 Why TCP

TCP-র কাজ একটি বাক্যে: একটি অবিশ্বস্ত, ক্রমহীন packet-ব্যবস্থাকে একটি নির্ভরযোগ্য, ক্রমবদ্ধ byte stream-এ রূপান্তর করা।

এবং সে এটি করে শুধুমাত্র দুই প্রান্তে — মাঝের কোনো router TCP-র কিছু জানে না। এটিই end-to-end principle: যে কাজ শুধু প্রান্তে সঠিকভাবে করা সম্ভব, সেটি প্রান্তেই করো, মাঝখানে নয়। এই নীতিই Internet-এর মাঝখানটাকে সরল ও দ্রুত রাখতে দিয়েছে।

17.2 TCP-এর প্রতিশ্রুতি

প্রতিশ্রুতিকীভাবে অর্জন করে
কিছু হারাবে নাACK + timeout + retransmission
ক্রম বজায় থাকবেSequence number দিয়ে receiver পুনর্বিন্যাস করে
Duplicate হবে নাএকই sequence number দুবার এলে দ্বিতীয়টি ফেলে দেয়
অবিকৃত থাকবেChecksum; ভুল হলে ফেলে দেয় → ACK আসে না → আবার পাঠায়
Receiver ডুববে নাFlow control — receive window (Ch 20)
Network ডুববে নাCongestion control — congestion window (Ch 21)
⚠️ TCP যা প্রতিশ্রুতি দেয় না
  • নির্দিষ্ট সময়ে পৌঁছানো — TCP নির্ভরযোগ্য, দ্রুত নয়। Retransmission মানেই বিলম্ব।
  • Message-এর সীমানা — এটি byte stream (Ch 4)। আপনার message কোথায় শেষ, তা আপনাকেই বলতে হবে।
  • নিরাপত্তা — TCP encryption করে না, প্রমাণীকরণ করে না। সেটি TLS-এর কাজ (Ch 31–33)।
  • Application পড়েছে — TCP-র ACK মানে receiver-এর kernel পেয়েছে। Application process টি crash করলেও ACK চলে গিয়ে থাকতে পারে।

17.3 TCP-এর মৌলিক ধারণা — একটি চিঠির উপমা

🧠 Mental Model

ধরুন আপনি একটি ৫০০ পৃষ্ঠার পাণ্ডুলিপি ডাকযোগে পাঠাচ্ছেন, কিন্তু ডাক ব্যবস্থা অনির্ভরযোগ্য — কিছু খাম হারায়, কিছু উল্টো ক্রমে পৌঁছায়। আপনি যা করবেন:

  1. প্রতিটি পৃষ্ঠায় নম্বর দেবেন → sequence number
  2. প্রাপককে বলবেন "প্রতিটি পৃষ্ঠা পেলে জানাবেন" → ACK
  3. নির্দিষ্ট সময়ে জবাব না এলে আবার পাঠাবেন → timeout + retransmission
  4. প্রাপক নম্বর দেখে সাজিয়ে নেবেন → reordering
  5. একই পৃষ্ঠা দুবার এলে একটি ফেলে দেবেন → duplicate detection
  6. প্রাপক বলবেন "আস্তে পাঠান, আমার টেবিল ভরে গেছে" → flow control
  7. ডাকঘরে ভিড় দেখলে ধীরে পাঠাবেন → congestion control

TCP ঠিক এই সাতটি কাজ করে, শুধু byte-এর হিসাবে, মাইক্রোসেকেন্ডে। এই তালিকাটিই TCP।

17.5 Sequence Number — byte গোনা হয়, packet নয়

✓ একটি গুরুত্বপূর্ণ সূক্ষ্মতা

TCP-এর sequence number packet গোনে না, byte গোনে। এটি একটি মৌলিক নকশাগত সিদ্ধান্ত।

ভুল ধারণা:      packet 1, packet 2, packet 3
আসল ব্যবস্থা:    byte 1000-2459, byte 2460-3919, ...

কেন byte? কারণ segment-এর আকার পরিবর্তনশীল — MTU বদলাতে পারে, TCP পুনরায় পাঠানোর সময় ভিন্ন আকারে ভাগ করতে পারে (repacketization)। Byte গুনলে এই সবকিছু নির্বিঘ্নে কাজ করে; packet গুনলে করত না।

Application 5000 bytes লিখল। TCP ভাগ করল (MSS = 1460):

  Segment 1:  seq = 1000    →  bytes 1000 – 2459   (1460 B)
  Segment 2:  seq = 2460    →  bytes 2460 – 3919   (1460 B)
  Segment 3:  seq = 3920    →  bytes 3920 – 5379   (1460 B)
  Segment 4:  seq = 5380    →  bytes 5380 – 5999   ( 620 B)

পরের segment-এর seq = আগেরটির seq + তার data-র দৈর্ঘ্য

Receiver ACK পাঠায় "পরবর্তী প্রত্যাশিত byte" হিসেবে:
  Segment 1 পেয়ে → ACK = 2460   ("2459 পর্যন্ত পেয়েছি")
  Segment 2 পেয়ে → ACK = 3920
ℹ️ প্রাথমিক sequence number এলোমেলো কেন

TCP connection ০ থেকে শুরু করে না — প্রতিটি connection একটি random Initial Sequence Number (ISN) দিয়ে শুরু হয়। দুটি কারণ: (১) আগের কোনো connection-এর দেরিতে পৌঁছানো packet যেন নতুন connection-এ ঢুকে না পড়ে; (২) নিরাপত্তা — sequence অনুমানযোগ্য হলে আক্রমণকারী নকল packet ঢুকিয়ে connection ছিনিয়ে নিতে পারত (TCP sequence prediction attack)।

17.6 ACK এবং Retransmission — নির্ভরযোগ্যতার মূল যন্ত্র

স্বাভাবিক অবস্থা:

  Sender                              Receiver
    │  seq=1000, 1460 bytes              │
    ├───────────────────────────────────▶│
    │                                    │  buffer-এ রাখল
    │◀───────────────────────────────────┤
    │            ACK=2460                │  "2459 পর্যন্ত পেয়েছি"
    │                                    │


হারানোর অবস্থা:

  Sender                              Receiver
    │  seq=1000                          │
    ├──────────────✗ (router ফেলে দিল)   │
    │                                    │
    │  ⏱ RTO timer চলছে...                │
    │  (কোনো ACK আসছে না)                 │
    │                                    │
    │  ⏰ Timeout! আবার পাঠাও              │
    │  seq=1000  (retransmission)        │
    ├───────────────────────────────────▶│
    │◀───────────────────────────────────┤
    │            ACK=2460                │

RTO — কতক্ষণ অপেক্ষা করবে

RTO (Retransmission Timeout) স্থির নয় — TCP নিজে RTT মেপে এটি হিসাব করে।

প্রতিটি ACK-এ TCP RTT মাপে (কতক্ষণে উত্তর এল)

  SRTT  = মসৃণ করা গড় RTT      (smoothed)
  RTTVAR = RTT-এর ওঠানামা        (variance)

  RTO = SRTT + 4 × RTTVAR

কেন variance যোগ করা হয়?
  স্থিতিশীল network-এ (RTT সবসময় ~20ms):
      RTO ≈ 25ms  →  দ্রুত পুনরুদ্ধার
  অস্থির network-এ (RTT 20–200ms):
      RTO ≈ 400ms →  ধৈর্য ধরে, ভুল retransmit এড়ায়

Timeout হলে RTO দ্বিগুণ হয় (exponential backoff):
  1s → 2s → 4s → 8s → 16s ...
কারণ: বারবার ব্যর্থ মানে network সত্যিই খারাপ,
      আরও চাপ দেওয়া পরিস্থিতি খারাপ করবে।
⚙️ Developer Perspective — কেন প্রথম হারানোটি সবচেয়ে ব্যয়বহুল

একটি packet loss শুধু একটি packet-এর দেরি নয়। Timeout-ভিত্তিক retransmission-এ কমপক্ষে একটি RTO (সাধারণত ২০০ms থেকে ১ সেকেন্ড) অপেক্ষা করতে হয় — যেখানে স্বাভাবিক RTT হয়তো ৩০ms। উপরন্তু congestion control window অর্ধেক বা তারও কম করে দেয় (Ch 21), তাই তার পরের কিছুক্ষণ throughput কমে থাকে।

এজন্যই ০.১% packet loss-ও একটি TCP connection-এর throughput নাটকীয়ভাবে কমিয়ে দিতে পারে — বিশেষ করে দীর্ঘ RTT-র পথে। Fast retransmit (পরের chapter) এই খরচ অনেকটা কমায়, কিন্তু পুরোপুরি নয়।

📌 Chapter Summary
  • IP best-effort; TCP-র কাজ সেই অবিশ্বস্ততার উপর নির্ভরযোগ্য byte stream তৈরি করা।
  • TCP-র সব বুদ্ধি দুই প্রান্তে — মাঝের router-রা কিছু জানে না (end-to-end principle)।
  • Sequence number byte গোনে, packet নয় — তাই আকার বদলালেও কাজ চলে।
  • ACK = "এই byte পর্যন্ত পেয়েছি, এখন এটি চাই"।
  • RTO গতিশীল: SRTT + 4 × RTTVAR, এবং ব্যর্থ হলে দ্বিগুণ হয়।
  • TCP নির্ভরযোগ্যতা দেয়, কিন্তু সময়ের নিশ্চয়তা, message সীমানা বা নিরাপত্তা দেয় না।
  • ACK মানে receiver-এর kernel পেয়েছে — application পড়েছে বা process করেছে, তা নয়।
✓ Quick Check
TCP sequence number packet না গুনে byte গোনে কেন?

কারণ segment-এর আকার স্থির নয়। MTU বদলাতে পারে, এবং retransmission-এর সময় TCP ভিন্ন আকারে ভাগ করে পাঠাতে পারে (repacketization)। Byte-ভিত্তিক গণনায় "১০০০ থেকে ২৪৫৯ নম্বর byte পেয়েছি" — এই বক্তব্য packet কীভাবে ভাগ হয়েছে তার উপর নির্ভর করে না। Packet গুনলে পুনরায় ভাগ করা মাত্রই হিসাব ভেঙে পড়ত।

TCP নির্ভরযোগ্য — এর মানে কি আপনার data সবসময় পৌঁছাবে?

না। TCP প্রতিশ্রুতি দেয় — যদি data পৌঁছায়, তবে সেটি সঠিক ক্রমে, অবিকৃত এবং একবারই পৌঁছাবে; আর না পৌঁছালে সে চেষ্টা করবে এবং শেষ পর্যন্ত ব্যর্থ হলে আপনাকে জানাবে (connection reset/timeout)। কিন্তু তার ফেলে দেওয়া নীরবে হারানো ঠেকানোর ক্ষমতা নেই — cable কাটলে বা host crash করলে connection ভাঙবে। নির্ভরযোগ্যতা মানে "নীরবে ভুল হবে না", "কখনো ব্যর্থ হবে না" নয়।

RTO কেন স্থির না রেখে RTT থেকে হিসাব করা হয়?

কারণ network-ভেদে RTT-র পার্থক্য বিশাল — একই data center-এ ০.৫ms, আন্তঃমহাদেশীয় পথে ৩০০ms। RTO খুব ছোট হলে সুস্থ packet-কেও হারানো ভেবে অপ্রয়োজনীয় retransmission হবে (network-এ আরও চাপ)। খুব বড় হলে প্রকৃত loss থেকে পুনরুদ্ধারে অনেক দেরি হবে। তাই TCP নিজেই RTT মেপে অভিযোজিত হয়, এবং variance যোগ করে অস্থিরতার জন্য জায়গা রাখে।

TCP-র ACK পেলে কি নিশ্চিত হওয়া যায় যে receiver application data টি process করেছে?

না। ACK পাঠায় receiver-এর kernel, data টি receive buffer-এ পৌঁছানোমাত্র। Application তখনো read() করেনি হতে পারে, এমনকি সেই মুহূর্তে crash করতে পারে। এজন্যই নির্ভরযোগ্য application-এ application-level acknowledgment দরকার — যেমন HTTP-র 200 response, বা message queue-র explicit ack। "TCP ACK পেয়েছি তাই কাজ হয়েছে" — এই ধারণা distributed system-এ একটি ধ্রুপদী ভুল।
