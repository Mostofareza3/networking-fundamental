Chapter 26

DNS Resolution — একটি নাম যেভাবে IP হয়

আপনি browser-এ example.com লিখলেন। মিলিসেকেন্ডের মধ্যে একটি IP পাওয়া গেল। এই সময়ের মধ্যে সম্ভবত চারটি ভিন্ন server-কে জিজ্ঞেস করা হয়েছে — এবং প্রত্যেকে ভিন্ন ধরনের উত্তর দিয়েছে।

26.1 চরিত্র পরিচিতি

ভূমিকাকাজউদাহরণ
Stub resolverআপনার OS-এর ভেতরের ক্ষুদ্র client। সে নিজে কিছু খুঁজে বের করে না — শুধু recursive resolver-কে জিজ্ঞেস করে।getaddrinfo(), systemd-resolved
Recursive resolverআসল পরিশ্রমটি করে — root থেকে শুরু করে ধাপে ধাপে খুঁজে বের করে, এবং cache রাখে।ISP-র resolver, 8.8.8.8, 1.1.1.1
Root serverশুধু বলে TLD-র server কারা। ১৩টি "নাম" (a–m.root-servers.net), কিন্তু anycast-এর কারণে বাস্তবে বিশ্বজুড়ে ১৫০০+ যন্ত্র।a.root-servers.net
TLD serverশুধু বলে একটি নির্দিষ্ট domain-এর authoritative server কারা।.com-এর server
Authoritative serverপ্রকৃত উত্তর জানে — কারণ record গুলো তারই।ns1.example.com

www.example.com খোঁজা

Recursive resolver-কে জিজ্ঞেস করো

বাস্তবে ৯০%+ query cache থেকেই মিটে যায়। নিচের পুরো প্রক্রিয়াটি তুলনামূলকভাবে বিরল।

ধাপ ১ — Stub → Recursive resolver

আপনার machine ──▶ 8.8.8.8 (বা ISP-র resolver)

  "www.example.com এর A record কী?

ধাপ ২ — Resolver → Root server

Resolver ──▶ a.root-servers.net
  "www.example.com এর A record?"

Root ──▶ Resolver
  "আমি জানি না। কিন্তু .com-এর জন্য
   এদের কাছে যাও:
     a.gtld-servers.net  192.5.6.30
     b.gtld-servers.net  192.33.14.30
     ..."

  ★ এটি একটি REFERRAL, উত্তর নয়।
    Root server কখনো প্রকৃত IP দেয় না।

Resolver root server-দের IP আগে থেকেই জানে — এগুলো তার configuration-এ hard-coded ("root hints")। এটাই একমাত্র জায়গা যেখানে কিছু hard-code করা আছে।

ধাপ ৩ — Resolver → TLD server

Resolver ──▶ a.gtld-servers.net (.com এর server)
  "www.example.com এর A record?"

TLD ──▶ Resolver
  "আমিও জানি না। কিন্তু example.com-এর
   authoritative server হলো:
     ns1.example.com  93.184.216.1
     ns2.example.com  93.184.216.2"

  ★ আরেকটি referral।
    লক্ষ্য করুন — server-এর নামের সাথে IP-ও
    দেওয়া হয়েছে (একে বলে "glue record")।
    নাহলে ns1.example.com খুঁজতে গিয়ে
    আবার example.com খুঁজতে হতো — অসীম চক্র।

ধাপ ৪ — Resolver → Authoritative server

Resolver ──▶ ns1.example.com
  "www.example.com এর A record?"

Authoritative ──▶ Resolver
  "www.example.com.  300  IN  A  93.184.215.14"
       │              │    │   │      │
       │              │    │   │      └─ উত্তর!

  ★ AA (Authoritative Answer) flag সেট করা —
    "এটি আমার নিজের record, আমি নিশ্চিত"

ধাপ ৫ — Cache এবং উত্তর

Recursive resolver উত্তরটি cache-এ রাখে (৩০০ সেকেন্ড)
                    এবং আপনাকে পাঠিয়ে দেয়

Resolver ──▶ আপনার machine

আপনার OS-ও এটি cache করে।
Browser-ও নিজের মতো cache করে।

★ পরের ১০,০০০ ব্যবহারকারী একই resolver ব্যবহার করলে
  তারা কেউ root বা TLD পর্যন্ত যাবে না।
  এটাই DNS-এর scale-এর রহস্য।

ℹ️ "Recursive" এবং "Iterative" — নামের বিভ্রান্তি

আপনার machine একটি recursive query পাঠায়: "সব কাজ তুমি করো, আমাকে চূড়ান্ত উত্তর দাও।"

Resolver তারপর iterative query পাঠায়: root, TLD, authoritative — প্রতিটিকে আলাদাভাবে, প্রতিবার একটু এগিয়ে। এদের প্রত্যেকে বলে "আমি জানি না, ওখানে যাও"।

অর্থাৎ resolver-কে "recursive resolver" বলা হয় কারণ সে recursive query গ্রহণ করে, নিজে recursive query পাঠায় বলে নয়।

26.3 Record Type

Typeকী দেয়উদাহরণ
AIPv4 addressexample.com. 300 IN A 93.184.215.14
AAAAIPv6 addressexample.com. 300 IN AAAA 2606:2800::1
CNAMEঅন্য নামের aliaswww.example.com. IN CNAME example.com.
NSএই domain-এর authoritative serverexample.com. IN NS ns1.example.com.
MXEmail কোথায় পাঠাতে হবে (priority সহ)example.com. IN MX 10 mail.example.com.
TXTযেকোনো text — SPF, DKIM, domain মালিকানা যাচাই"v=spf1 include:_spf.google.com ~all"
SRVService-এর host ও port_sip._tcp.example.com. IN SRV 10 60 5060 sip.example.com.
PTRReverse lookup: IP → নাম14.215.184.93.in-addr.arpa. IN PTR example.com.
SOAZone-এর মূল তথ্য (serial, refresh, negative TTL)প্রতিটি zone-এ একটি
CAAকোন CA এই domain-এর certificate দিতে পারবেexample.com. IN CAA 0 issue "letsencrypt.org"
⚠️ CNAME-এর দুটি নিয়ম যা সবাই ভাঙতে চায়
  1. CNAME-এর সাথে অন্য কোনো record থাকতে পারে না। একটি নামে CNAME থাকলে সেখানে MX, TXT, A — কিছুই থাকতে পারবে না।
  2. ফলে zone apex-এ (example.com, subdomain ছাড়া) CNAME অসম্ভব — কারণ apex-এ SOA ও NS record বাধ্যতামূলক।

এজন্যই example.com-কে সরাসরি একটি CDN-এর নামে point করা যায় না, কিন্তু www.example.com-কে যায়। সমাধান হিসেবে DNS provider-রা অ-প্রমিত ব্যবস্থা তৈরি করেছে: ALIAS, ANAME, বা "CNAME flattening" (Cloudflare) — যা মূলত provider-এর দিকেই CNAME resolve করে A record হিসেবে ফেরত দেয়।

এছাড়া CNAME-এর একটি লুকানো খরচ আছে: প্রতিটি CNAME একটি অতিরিক্ত lookup — www → CNAME → তারপর সেই নামের A record খোঁজা। শৃঙ্খল দীর্ঘ হলে latency বাড়ে।

26.4 dig-এর output পড়া

bash
$ dig example.com

; <<>> DiG 9.18.1 <<>> example.com
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 43521
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1
                    ↑
    qr = query response   rd = recursion desired
    ra = recursion available   (aa থাকলে authoritative)

;; QUESTION SECTION:
;example.com.                   IN      A          ← কী জিজ্ঞেস করেছি

;; ANSWER SECTION:
example.com.            285     IN      A       93.184.215.14
                         ↑                            ↑
                     অবশিষ্ট TTL                    উত্তর
        (৩০০ ছিল, ১৫ সেকেন্ড আগে cache হয়েছে)

;; Query time: 2 msec              ← ২ms মানে cache থেকে এসেছে
;; SERVER: 127.0.0.53#53(127.0.0.53)   ← কোন resolver ব্যবহার হলো
;; WHEN: Wed Sep 02 20:30:00 +06 2026
;; MSG SIZE  rcvd: 56
✓ TTL দেখে cache শনাক্ত করা

একই query দুবার চালিয়ে TTL-এর সংখ্যাটি লক্ষ্য করুন। যদি এটি কমতে থাকে (300 → 285 → 270), তার মানে উত্তরটি cache থেকে আসছে এবং resolver গণনা করে দেখাচ্ছে আর কতক্ষণ বৈধ। প্রতিবার পূর্ণ TTL দেখালে বুঝবেন এটি authoritative server থেকে সরাসরি আসছে। Query time-ও সংকেত দেয়: ১–৫ms মানে cache, ৫০–৩০০ms মানে প্রকৃত resolution হয়েছে।

26.5 DNS-এর নিরাপত্তা ও গোপনীয়তা

প্রযুক্তিকী সমাধান করেকীভাবে
DNSSECউত্তর জাল করা (integrity)Record-এ cryptographic signature; root থেকে শুরু করে বিশ্বাসের শৃঙ্খল
DoT (DNS over TLS)আড়ি পাতা (privacy)Port 853-এ TLS-এর ভেতরে DNS
DoH (DNS over HTTPS)আড়ি পাতা + অবরোধPort 443-এ HTTPS-এর ভেতরে; সাধারণ web traffic থেকে আলাদা করা কঠিন
ℹ️ DNSSEC এবং DoH আলাদা জিনিস

সাধারণ DNS query plaintext UDP — যে কেউ পথে বসে দেখতে পারে আপনি কোন site খুঁজছেন, এবং জাল উত্তরও পাঠাতে পারে।

  • DNSSEC নিশ্চিত করে উত্তরটি খাঁটি — কিন্তু encryption করে না। সবাই তখনো দেখতে পায় আপনি কী খুঁজছেন।
  • DoH/DoT query-টি গোপন করে — কিন্তু resolver নিজে মিথ্যা বললে ধরার উপায় নেই।

দুটি ভিন্ন সমস্যার ভিন্ন সমাধান, এবং একসাথে ব্যবহার করাই আদর্শ। লক্ষণীয় — TLS থাকলেও DNS query আপনার ব্রাউজিং ফাঁস করে দেয়, এবং SNI (Ch 33) সেটি আরও করে।

🧪 Lab 26 — পুরো resolution পথটি নিজে অনুসরণ করুন

আমরা কী দেখতে চাইছি? — root থেকে authoritative পর্যন্ত প্রকৃত delegation শৃঙ্খল, নিজের চোখে।

bash
# সম্পূর্ণ পথটি ধাপে ধাপে দেখুন
dig +trace example.com

# শুধু উত্তর
dig +short example.com

# নির্দিষ্ট record type
dig example.com MX
dig example.com NS
dig example.com TXT
dig example.com AAAA

# একটি নির্দিষ্ট resolver ব্যবহার করে
dig @1.1.1.1 example.com
dig @8.8.8.8 example.com

# Authoritative server-কে সরাসরি জিজ্ঞেস করুন (cache এড়িয়ে)
dig @$(dig +short NS example.com | head -1) example.com

# Reverse lookup
dig -x 93.184.215.14

যা লক্ষ্য করবেন: +trace-এ দেখবেন প্রথমে ১৩টি root server-এর তালিকা, তারপর .com-এর NS record গুলো, তারপর example.com-এর NS, এবং সবশেষে প্রকৃত A record। প্রতিটি ধাপে "Received X bytes from ..." লাইনে দেখবেন কোন server উত্তর দিয়েছে। ভিন্ন resolver (@1.1.1.1 বনাম @8.8.8.8) কখনো কখনো ভিন্ন IP ফেরত দেবে — CDN-এর geographic routing-এর কারণে।

আমরা কী শিখলাম: Delegation শৃঙ্খলটি বাস্তব — প্রতিটি স্তর সত্যিই বলছে "আমি জানি না, ওখানে যাও"। আর একই নামের জন্য বিভিন্ন resolver ভিন্ন উত্তর দেওয়া স্বাভাবিক ও উদ্দেশ্যপ্রণোদিত।

📌 Chapter Summary
  • চারটি ভূমিকা: stub resolver (OS), recursive resolver (সব কাজ করে), root/TLD (referral দেয়), authoritative (উত্তর জানে)।
  • আপনার machine একটি recursive query পাঠায়; resolver iterative query দিয়ে ধাপে ধাপে খোঁজে।
  • Root ও TLD কখনো প্রকৃত IP দেয় না — শুধু "পরে কার কাছে যাবে" বলে।
  • Glue record ছাড়া nameserver খোঁজা একটি অসীম চক্রে পড়ত।
  • Record type: A, AAAA, CNAME, NS, MX, TXT, SRV, PTR, SOA, CAA।
  • CNAME-এর সাথে অন্য record থাকতে পারে না, তাই zone apex-এ CNAME অসম্ভব।
  • DNSSEC = সত্যতা যাচাই; DoH/DoT = গোপনীয়তা। দুটি আলাদা সমস্যা।
✓ Quick Check
Root server কি কখনো একটি website-এর IP address জানে?

না, এবং এটিই নকশা। Root server শুধু TLD-দের (.com, .org, .bd) nameserver-এর তথ্য রাখে। সে সবসময় একটি referral দেয়, কখনো প্রকৃত উত্তর নয়। এই সীমিত দায়িত্বের কারণেই মাত্র ১৩টি root server "নাম" দিয়ে পুরো Internet চলে — তাদের data খুব ছোট এবং প্রায় কখনো বদলায় না।

Glue record কী এবং না থাকলে কী হতো?

Glue record হলো একটি nameserver-এর নামের সাথে তার IP-ও একসাথে দেওয়া। example.com-এর nameserver যদি ns1.example.com হয়, তাহলে তার IP জানতে example.com-এ query করতে হতো — কিন্তু সেটি জানতে আবার ns1.example.com-এর IP লাগত। অসীম চক্র। TLD server তাই nameserver-এর নামের সাথে IP-ও (glue) দিয়ে দেয়।

example.com-কে সরাসরি CDN-এর নামে CNAME করা যায় না কেন?

কারণ CNAME record-এর সাথে অন্য কোনো record সহাবস্থান করতে পারে না, আর zone apex-এ (example.com) SOA ও NS record বাধ্যতামূলক। ফলে apex-এ CNAME বসানো protocol-বিরুদ্ধ। DNS provider-রা ALIAS/ANAME/CNAME-flattening নামে অ-প্রমিত সমাধান দেয় — তারা নিজেরাই target resolve করে A record হিসেবে ফেরত দেয়।

dig-এর output-এ TTL 285 দেখাচ্ছে অথচ record-এ 300 সেট করা। কেন?

উত্তরটি cache থেকে আসছে। Resolver ১৫ সেকেন্ড আগে এটি authoritative server থেকে পেয়েছিল (তখন TTL ছিল 300), এবং এখন সে অবশিষ্ট সময় দেখাচ্ছে। এটি cache শনাক্ত করার সবচেয়ে সহজ উপায় — বারবার query করে দেখুন TTL কমছে কিনা। শূন্যে নামলে পরের query আবার authoritative server পর্যন্ত যাবে।

DNSSEC থাকলে কি আপনার DNS query গোপন থাকে?

না। DNSSEC শুধু সত্যতা (authenticity ও integrity) নিশ্চিত করে — উত্তরটি প্রকৃত মালিকের দেওয়া এবং পথে বদলানো হয়নি। কিন্তু query ও response তখনো plaintext, তাই পথের যে কেউ দেখতে পায় আপনি কোন domain খুঁজছেন। গোপনীয়তার জন্য দরকার DoH বা DoT, যা সম্পূর্ণ ভিন্ন একটি সমাধান।
