Chapter 39

Debugging Toolkit এবং Socket Inspection

সমস্যা নির্ণয়ের সবচেয়ে বড় দক্ষতা হলো — কোন layer-এ সমস্যা তা দ্রুত সংকীর্ণ করে আনা। প্রতিটি tool একটি নির্দিষ্ট layer-এর জানালা। সঠিক ক্রমে সঠিক জানালা খুললে সমস্যা মিনিটে ধরা পড়ে।

39.2 ss — Socket Statistics

ss হলো netstat-এর আধুনিক উত্তরসূরি, এবং transport layer-এ সবচেয়ে গুরুত্বপূর্ণ tool।

bash
# সবচেয়ে বেশি ব্যবহৃত: কে কোন port-এ শুনছে
ss -tlnp
#  -t  TCP
#  -l  শুধু LISTEN
#  -n  নাম resolve করো না (দ্রুত)
#  -p  কোন process (root লাগে)

$ ss -tlnp
State  Recv-Q Send-Q  Local Address:Port  Peer Address:Port  Process
LISTEN 0      128         127.0.0.1:5432       0.0.0.0:*      users:(("postgres",pid=890))
LISTEN 0      511           0.0.0.0:80         0.0.0.0:*      users:(("nginx",pid=1201))
LISTEN 0      4096          0.0.0.0:22         0.0.0.0:*      users:(("sshd",pid=755))
         │      │              │
         │      │              └─ ★ 127.0.0.1 না 0.0.0.0? ★
         │      └─ backlog-এর সর্বোচ্চ আকার
         └─ এখন queue-তে কতগুলো অপেক্ষমাণ
⚙️ এই output থেকে যা তাৎক্ষণিকভাবে বোঝা যায়
  • PostgreSQL 127.0.0.1:5432-এ — শুধু এই machine থেকে পৌঁছানো যাবে। বাইরে থেকে চেষ্টা করলে "connection refused"। নিরাপত্তার দিক থেকে ভালো, কিন্তু অন্য machine থেকে connect করতে চাইলে এটাই আপনার সমস্যা।
  • nginx 0.0.0.0:80-এ — সব interface-এ শুনছে, বাইরে থেকে পৌঁছানো যাবে।
  • Recv-Q ধারাবাহিকভাবে বড় — application accept() যথেষ্ট দ্রুত করছে না (Ch 18-এর accept queue overflow)।
  • Send-Q (LISTEN-এ) = backlog-এর সর্বোচ্চ মান, যা listen()-এ দেওয়া হয়েছিল।

⚠️ CLOSE_WAIT জমে যাওয়া = আপনার code-এ bug

এটি সবচেয়ে গুরুত্বপূর্ণ diagnostic সূত্রগুলোর একটি। CLOSE_WAIT মানে: peer FIN পাঠিয়ে বলেছে "আমি শেষ", kernel সেটি ACK করেছে, কিন্তু আপনার application close() call করেনি।

Kernel নিজে থেকে এটি পরিষ্কার করতে পারে না — কারণ application হয়তো এখনো data পাঠাতে চাইতে পারে। ফলে socket ও file descriptor আটকে থাকে চিরকাল, এবং শেষ পর্যন্ত EMFILE: too many open files।

সাধারণ কারণ: exception path-এ connection বন্ধ না করা, connection pool-এ leak, বা finally block-এ close() না থাকা। যদি CLOSE_WAIT-এর সংখ্যা ক্রমাগত বাড়ে, সমস্যা network-এ নয়, আপনার code-এ।

  rtt:35.5/8.2→ SRTT 35.5ms, variance 8.2ms
  rto:236     → retransmission timeout (Ch 17)
  cwnd:24     → congestion window (MSS-এর একক)
  ssthresh:18 → slow start threshold
  retrans:0/2 → এখন 0, মোট 2 বার retransmit হয়েছে

ss -ti দেখে:

  retrans বেশি?        → packet loss (Ch 38)
  cwnd ছোট, retrans 0? → congestion control সীমাবদ্ধ করছে
  rcv_space ছোট?       → receiver-এর window সীমাবদ্ধ (Ch 20)
  rtt বেশি?            → দূরত্বই মূল বাধা (Ch 36)
  cwnd বড়, তবু ধীর?    → application নিজেই ধীর

39.3 দ্রুত reference — অন্যান্য tool

bash
# ── Layer 2/3 ──
ip link                      # interface up/down, MTU, MAC
ip -brief addr               # সব IP, সংক্ষিপ্ত
ip route                     # routing table
ip route get 8.8.8.8         # ★ এই গন্তব্যের জন্য kernel কী করবে
ip neigh                     # ARP table

# ── পৌঁছানো যায় কি ──
ping -c 4 host               # ICMP echo
ping -c 4 -s 1400 -M do host # MTU পরীক্ষা (Ch 5)
traceroute -n host           # পথ
mtr -r -c 50 host            # ★ traceroute + ping, loss সহ

# ── Port ও connection ──
ss -tlnp                     # কে শুনছে
ss -tan state established    # সক্রিয় connection
nc -zv host 443              # port খোলা কি (দ্রুত)
nc -zv host 20-25            # port range scan
lsof -i :8080                # কোন process এই port-এ
lsof -p PID -a -i            # একটি process-এর সব socket

# ── DNS ──
dig example.com              # সম্পূর্ণ
dig +short example.com       # শুধু উত্তর
dig +trace example.com       # root থেকে পুরো পথ
dig @1.1.1.1 example.com     # নির্দিষ্ট resolver
dig -x 1.1.1.1               # reverse

# ── HTTP ──
curl -v https://host         # সব header
curl -I https://host         # শুধু header (HEAD)
curl -sL -o /dev/null -w "%{http_code} %{time_total}s\n" URL
curl --resolve host:443:1.2.3.4 https://host   # ★ DNS bypass করে
                                               #   নির্দিষ্ট server পরীক্ষা

# ── Packet capture ──
sudo tcpdump -i any -n port 443
sudo tcpdump -i any -n host 1.1.1.1 -w capture.pcap
✓ curl --resolve — একটি অবমূল্যায়িত tool

একটি নির্দিষ্ট backend server সরাসরি পরীক্ষা করতে চান, load balancer বা DNS এড়িয়ে?

bash
curl --resolve api.example.com:443:10.0.1.50 https://api.example.com/health

এতে DNS lookup সম্পূর্ণ বাদ যায় এবং সরাসরি 10.0.1.50-এ connect করা হয় — কিন্তু Host header ও TLS-এর SNI ঠিক api.example.com-ই থাকে। ফলে virtual host ও certificate সঠিকভাবে কাজ করে। "একটি server খারাপ উত্তর দিচ্ছে কিন্তু কোনটি?" — এই প্রশ্নের উত্তর খোঁজার সেরা উপায়।

🧪 Lab 39 — একটি সম্পূর্ণ diagnostic pass

আমরা কী দেখতে চাইছি? — একটি সংগঠিত ক্রমে নিচ থেকে উপরে সব layer পরীক্ষা করা, যাতে সমস্যা থাকলে ঠিক কোথায় তা বোঝা যায়।

bash
#!/bin/bash
TARGET=${1:-example.com}
echo "=== Layer 2: Interface ==="
ip link show | grep -E "state (UP|DOWN)"

echo -e "\n=== Layer 3: IP ও Route ==="
ip -brief addr | grep -v " lo "
ip route get 1.1.1.1

echo -e "\n=== Layer 3: পৌঁছানো ==="
ping -c 2 -W 2 1.1.1.1 | tail -2

echo -e "\n=== DNS ==="
dig +short $TARGET | head -3
echo "resolver: $(grep nameserver /etc/resolv.conf | head -1)"

echo -e "\n=== Layer 4: Port ==="
nc -zv -w 3 $TARGET 443 2>&1

echo -e "\n=== Layer 7: HTTP + timing ==="
curl -sS -o /dev/null -w "code=%{http_code} dns=%{time_namelookup}s \
tcp=%{time_connect}s tls=%{time_appconnect}s ttfb=%{time_starttransfer}s \
total=%{time_total}s\n" https://$TARGET

echo -e "\n=== আমার সক্রিয় connection ==="
ss -tan state established | wc -l

যা লক্ষ্য করবেন: প্রতিটি ধাপ পরেরটির পূর্বশর্ত। কোনো ধাপে ব্যর্থ হলে সেখানেই থামুন — পরের ধাপগুলো পরীক্ষা করে লাভ নেই। উদাহরণ: ping কাজ করছে কিন্তু dig ব্যর্থ মানে network ঠিক আছে, শুধু DNS ভাঙা।

আমরা কী শিখলাম: Debugging হলো সম্ভাবনা সংকীর্ণ করার প্রক্রিয়া। একটি সুসংগঠিত ক্রম এলোমেলো অনুমানের চেয়ে বহুগুণ দ্রুত — এবং এই script-টি সংরক্ষণ করে রাখলে যেকোনো সমস্যার শুরুতে চালাতে পারবেন।

📌 Chapter Summary
  • প্রতিটি tool একটি নির্দিষ্ট layer-এর জানালা — সঠিক ক্রমে ব্যবহার করলে সমস্যা দ্রুত সংকীর্ণ হয়।
  • Debugging-এর ক্রম: interface → IP → gateway → Internet → DNS → port → HTTP → packet capture।
  • ss -tlnp — কে কোন address:port-এ শুনছে; 127.0.0.1 বনাম 0.0.0.0 সবচেয়ে গুরুত্বপূর্ণ পার্থক্য।
  • ss -ti — একটি connection-এর ভেতরের অবস্থা: rtt, cwnd, retrans, rcv_space।
  • CLOSE_WAIT জমা = application close() করছে না = code-এর bug।
  • SYN-SENT আটকে থাকা = গন্তব্যে পৌঁছানো যাচ্ছে না (firewall/host down)।
  • curl --resolve দিয়ে DNS ও load balancer এড়িয়ে নির্দিষ্ট server পরীক্ষা করা যায়।
✓ Quick Check
ss -tlnp-এ 127.0.0.1:5432 দেখাচ্ছে, কিন্তু অন্য machine থেকে connect করা যাচ্ছে না। কারণ?

PostgreSQL শুধু loopback interface-এ bind করা (Ch 9)। অন্য machine থেকে আসা packet Ethernet/Wi-Fi interface-এ পৌঁছায়, কিন্তু সেখানে ওই port-এ কোনো listener নেই — তাই kernel RST পাঠায় ("connection refused")। সমাধান: listen_addresses = '0.0.0.0' (বা নির্দিষ্ট IP) করে PostgreSQL restart করুন — এবং অবশ্যই firewall দিয়ে সুরক্ষিত করুন।

একটি service-এ CLOSE_WAIT-এর সংখ্যা ক্রমাগত বাড়ছে। এটি কার সমস্যা?

আপনার application-এর। CLOSE_WAIT মানে peer FIN পাঠিয়েছে এবং kernel সেটি ACK করেছে, কিন্তু আপনার code close() call করেনি। Kernel নিজে এটি পরিষ্কার করতে পারে না। এটি একটি file descriptor leak — সাধারণত exception path-এ বা connection pool-এ connection বন্ধ না করার ফল। শেষ পর্যন্ত EMFILE: too many open files-এ পৌঁছাবে।

ping 1.1.1.1 কাজ করে কিন্তু ping google.com করে না। কোন layer-এ সমস্যা?

শুধুমাত্র নাম সমাধানে (DNS)। IP-তে ping কাজ করা প্রমাণ করে Layer 2, 3 এবং routing সব ঠিক আছে — packet বাইরে যাচ্ছে ও ফিরে আসছে। সমস্যা DNS-এ: /etc/resolv.conf-এ ভুল বা অপ্রাপ্য resolver, DNS server বন্ধ, বা port 53 firewall-এ আটকানো। dig @1.1.1.1 google.com দিয়ে যাচাই করুন — এটি কাজ করলে আপনার configured resolver-ই সমস্যা।

একটি download ধীর। ss -ti-তে retrans:0/0 এবং cwnd:180। সম্ভাব্য কারণ?

Packet loss নেই এবং congestion window বড় — তাই network-এর দিক থেকে সব ঠিক। সন্দেহ করুন: (১) receive window ছোট (rcv_space দেখুন) — receiver ধীরে পড়ছে; (২) server-এর দিক থেকে সীমাবদ্ধতা (disk I/O, CPU, rate limiting); (৩) আপনার নিজের application ধীরে data process করছে, ফলে buffer ভরে যাচ্ছে। মোটকথা bottleneck TCP-তে নয়, দুই প্রান্তের কোনো একটিতে।
