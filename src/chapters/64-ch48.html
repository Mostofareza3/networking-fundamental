Chapter 48 · Capstone

What Happens When You Type a URL?

এটি সবচেয়ে বিখ্যাত interview প্রশ্ন — কিন্তু সেটি এর গুরুত্বের কারণ নয়। এটি গুরুত্বপূর্ণ কারণ এই একটি প্রশ্নের সম্পূর্ণ উত্তরে networking-এর প্রতিটি স্তর একসাথে দেখা যায়, এবং সেই সংযোগগুলোই আসল জ্ঞান।

আপনি লিখলেন:

        https://example.com


এবং Enter চাপলেন। এখন ১৭টি ধাপ।
URL থেকে rendered page পর্যন্ত

ধাপ ১ — Browser URL ব্যাখ্যা করে

"example.com" লিখলে browser প্রথমে সিদ্ধান্ত নেয়:
  এটি কি একটি URL, নাকি search query?

তারপর parse করে:
  scheme  : https  (দেওয়া না থাকলে https ধরে নেয়)
  host    : example.com
  port    : 443     (https-এর default)
  path    : /
  query   : (নেই)
  fragment: (নেই)   ← server-এ কখনো যায় না [Ch 28]

★ HSTS পরীক্ষা: browser-এর preload list বা আগের
  Strict-Transport-Security header থেকে যদি জানা
  থাকে এই domain শুধু HTTPS ব্যবহার করে, তাহলে
  http:// লিখলেও সে ★নিজেই★ https-এ যাবে —
  কোনো network request ছাড়াই।

ধাপ ২ — DNS Resolution

ক্রমান্বয়ে খোঁজা [Ch 26, 27]:

  1. Browser-এর নিজস্ব cache      → পেলে শেষ
  2. OS cache (systemd-resolved)  → পেলে শেষ
  3. /etc/hosts                   → পেলে শেষ
  4. Recursive resolver-কে জিজ্ঞেস

Cache miss হলে সম্পূর্ণ পথ:

  Stub → Recursive resolver (8.8.8.8)
                ↓ "example.com এর A record?"
         Root server → ".com এর জন্য এদের কাছে যাও"
                ↓
         .com TLD  → "example.com এর NS এরা"
                ↓
         ns1.example.com → "93.184.215.14"
                ↓
  Resolver cache করে, আপনাকে দেয়

সময়: cache hit ~0ms, পূর্ণ resolution ~50-200ms

★ IPv6-ও চাওয়া হয় (AAAA) — দুটোই থাকলে
  browser "Happy Eyeballs" দিয়ে দুটোই সমান্তরালে
  চেষ্টা করে, যেটি আগে সফল হয় সেটি রাখে।

ধাপ ৩ — IP পাওয়া গেল, routing সিদ্ধান্ত

93.184.215.14

Kernel-এর প্রশ্ন [Ch 10, 11]:
  এটি কি আমার subnet 192.168.0.0/24-এ?

  192.168.0.107 AND /24 = 192.168.0.0
  93.184.215.14 AND /24 = 93.184.215.0
  মেলে না → ★ local নয় ★

  → Routing table: default via 192.168.0.1
  → Gateway-কে দিতে হবে

Gateway-এর MAC দরকার [Ch 8]:
  ARP cache দেখো → না থাকলে broadcast:
    "192.168.0.1 কার?"
    "আমার — a4:2b:b0:11:22:33"

★ লক্ষ্য করুন: 93.184.215.14-এর MAC কখনো
  জানা হচ্ছে না, জানার দরকারও নেই।

ধাপ ৪ — Socket তৈরি

Browser-এর নেটওয়ার্ক stack করে [Ch 16]:

  fd = socket(AF_INET, SOCK_STREAM, 0)

Kernel:
  • একটি socket structure তৈরি করে
  • একটি ephemeral source port বেছে দেয় (51234) [Ch 15]
  • fd ফেরত দেয়

এখন connection-এর পরিচয় নির্ধারিত হবে:
  (192.168.0.107, 51234, 93.184.215.14, 443)
   └───────────────── 4-tuple ─────────────────┘

★ কিন্তু আগে দেখা হয় — এই origin-এর জন্য কি
  ইতিমধ্যে একটি খোলা connection আছে?
  থাকলে ধাপ ৫ ও ৬ সম্পূর্ণ বাদ (keep-alive, Ch 30)।

ধাপ ৫ — TCP Three-Way Handshake

connect(fd, 93.184.215.14:443) [Ch 18]

  Client                          Server
    │──── SYN, seq=1000 ───────────▶│
    │◀─── SYN-ACK, seq=5000, ────── │
    │     ack=1001                  │
    │──── ACK, ack=5001 ───────────▶│

  ⏱ ১ RTT খরচ হলো

এখানে যা আলোচিত হলো:
  • MSS (1460)          [Ch 5]
  • Window scaling      [Ch 19]
  • SACK permitted      [Ch 19]

দুই প্রান্তে state: ESTABLISHED
connect() ফেরত এল।

(HTTP/3 হলে এই ধাপটি QUIC-এর ভেতরেই
 ধাপ ৬-এর সাথে মিশে যেত, Ch 45)

ধাপ ৬ — TLS Handshake

[Ch 33]

  Client ──▶ ClientHello
             • TLS 1.3
             • cipher suite-এর তালিকা
             • ★ key share (ephemeral DH) ★
             • ★ SNI: example.com ★ (plaintext!)
             • ALPN: h2, http/1.1

  Server ──▶ ServerHello (key share)
             ═══ এখান থেকে encrypted ═══
             {Certificate}
             {CertificateVerify}  ← private key-র প্রমাণ
             {Finished}

  Client যাচাই করে:
    ✓ Certificate chain → intermediate → root
    ✓ Root আমার trust store-এ আছে?
    ✓ মেয়াদ ঠিক?
    ✓ ★ SAN-এ example.com আছে? ★
    ✓ Revoke হয়নি? (OCSP)

  Client ──▶ {Finished} + প্রথম HTTP request

  ⏱ আরও ১ RTT
  ⇒ এখন উভয়ের কাছে একটি session key আছে

ধাপ ৮ — Encapsulation

[Ch 3, 4]

  HTTP request (plaintext)
        ↓ TLS encrypt + record header
  TLS record
        ↓ TCP header (src 51234, dst 443, seq, ack)
  TCP segment
        ↓ IP header (src 192.168.0.107,
        ↓            dst 93.184.215.14, TTL 64)
  IP packet
        ↓ Ethernet/Wi-Fi header
        ↓ (dst = gateway-এর MAC!)
  Frame
        ↓ NIC
  Bits → radio wave

┌────────┬───────┬────────┬─────┬──────────────┬─────┐
│Eth Hdr │IP Hdr │TCP Hdr │ TLS │ encrypted    │ FCS │
│14 B    │20 B   │20 B    │ 5 B │ HTTP request │ 4 B │
└────────┴───────┴────────┴─────┴──────────────┴─────┘

ধাপ ৯ — Router Hop

[Ch 12, 13, 34, 42]

  বাসার router:
    • Ethernet header ফেলে দিল
    • ★ NAT: src 192.168.0.107:51234
             → 103.55.20.7:42001 ★
    • Firewall নিয়ম প্রয়োগ
    • TTL: 64 → 63
    • নতুন frame, ISP-র দিকে

  ISP-র router গুলো:
    • Routing table lookup (longest prefix match)
    • প্রতিটিতে TTL−1, নতুন Ethernet header
    • BGP-নির্ধারিত পথে

  সমুদ্রতলের cable:
    • ★ propagation delay-র সিংহভাগ এখানে ★

  গন্তব্য ISP → data center edge → firewall
  → load balancer → top-of-rack switch → server

  পুরো পথে:
    Ethernet header — ১০-২০ বার নতুন করে লেখা
    Destination IP  — ★ অপরিবর্তিত ★
    TCP payload     — ★ অপরিবর্তিত এবং অপঠনীয় ★

ধাপ ১০ — Server-এর NIC packet গ্রহণ করে

NIC:
  • Signal → bits → frame
  • dst MAC কি আমার? ✓
  • FCS checksum ঠিক? ✓
  • DMA দিয়ে memory-তে রাখল
  • Kernel-কে interrupt দিল
    (উচ্চ throughput-এ NAPI polling — Ch 2)

ধাপ ১১ — Server-এর Kernel: de-encapsulation

[Ch 3]

  Frame  → Ethernet header ফেলো, EtherType=IPv4
     ↓
  Packet → dst IP আমার? ✓ checksum ✓
           Protocol = 6 → TCP
     ↓
  Segment→ dst port 443
           4-tuple দিয়ে socket খুঁজে বের করো [Ch 15]
           Sequence number দেখে ক্রমে বসাও [Ch 19]
           ACK পাঠাও
     ↓
  Socket receive buffer-এ bytes জমা হলো

  ★ এই মুহূর্তে TCP ACK চলে গেছে — কিন্তু
    application এখনো কিছুই দেখেনি! (Ch 17)

ধাপ ১৫ — Response ফিরে আসে

• Router hop গুলো উল্টো দিকে
  ★ কিন্তু একই পথে নাও হতে পারে ★ (Ch 12)

              → 192.168.0.107:51234 (table lookup)

• আপনার kernel:

    - হারানো থাকলে অপেক্ষা করে (HOL blocking)
    - receive buffer-এ জমা করে
    - ACK পাঠায়, window ঘোষণা করে [Ch 20]

• Browser-এর read() bytes পায়
• TLS decrypt
• HTTP parse
• gzip decompress

48.3 এই প্রশ্নের ভালো উত্তর কেমন হয়

✓ Interview-এ এই প্রশ্নের উত্তর দেওয়ার কৌশল

সব বিস্তারিত একসাথে বলা ভালো উত্তর নয় — বরং কাঠামোবদ্ধভাবে বলা এবং গভীরতা নিয়ন্ত্রণ করা:

  1. প্রথমে কাঠামো দিন (৩০ সেকেন্ড): "মোটামুটি ছয়টি পর্যায় — URL parsing, DNS, connection setup (TCP+TLS), HTTP request/response, server-side processing, এবং rendering।"
  2. তারপর জিজ্ঞেস করুন: "কোন অংশটি বিস্তারিত শুনতে চান?" — এটি দেখায় আপনি প্রশ্নের পরিধি বোঝেন।
  3. সংযোগ দেখান: "DNS UDP ব্যবহার করে কারণ বিনিময়টি ছোট, handshake-এর খরচ অযৌক্তিক হতো" — এই ধরনের কেন ব্যাখ্যাই মুখস্থ তালিকা থেকে আলাদা করে।
  4. ট্রেড-অফ উল্লেখ করুন: "এই ৪টি RTT-র কারণেই connection reuse ও CDN এত গুরুত্বপূর্ণ।"
  5. সততা রাখুন: "TLS-এর গণিতটা আমার মুখস্থ নেই, কিন্তু ধারণাটা হলো..." — এটি দুর্বলতা নয়।
🧪 Lab 48 — পুরো যাত্রাটি নিজে অনুসরণ করুন

আমরা কী দেখতে চাইছি? — উপরের ১৭টি ধাপের প্রতিটি বাস্তবে ঘটছে কিনা, নিজের চোখে।

bash
#!/bin/bash
D=example.com
echo "════ ধাপ ২ — DNS ════"
dig +short $D
IP=$(dig +short $D | head -1)

echo -e "\n════ ধাপ ৩ — Routing সিদ্ধান্ত ════"
ip route get $IP 2>/dev/null || route get $IP

echo -e "\n════ ধাপ ৩ — Gateway-এর ARP ════"
GW=$(ip route | awk '/default/{print $3; exit}')
ip neigh | grep "$GW"

echo -e "\n════ ধাপ ৫,৬ — Handshake-এর সময় ════"
curl -w "TCP: %{time_connect}s | TLS: %{time_appconnect}s\n" \
     -o /dev/null -s https://$D

echo -e "\n════ ধাপ ৬ — Certificate ════"
echo | openssl s_client -connect $D:443 -servername $D 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates 2>/dev/null

echo -e "\n════ ধাপ ৭,১৪ — HTTP ════"
curl -sI https://$D | head -8

echo -e "\n════ ধাপ ৯ — Router hop ════"
traceroute -n -m 12 $D 2>/dev/null | head -12

echo -e "\n════ ধাপ ৪,১১ — Socket ════"
(curl -s https://$D > /dev/null &) ; sleep 0.3
ss -tn dst $IP 2>/dev/null | head -3

echo -e "\n════ সম্পূর্ণ সময়ের ভাগ ════"
curl -w "DNS %{time_namelookup}s → TCP %{time_connect}s → \
TLS %{time_appconnect}s → TTFB %{time_starttransfer}s → \
মোট %{time_total}s\n" -o /dev/null -s https://$D

যা লক্ষ্য করবেন: প্রতিটি ধাপের একটি বাস্তব, পরিমাপযোগ্য চিহ্ন আছে — DNS-এর উত্তর, routing table-এর সিদ্ধান্ত, ARP cache-এর entry, handshake-এর সময়, certificate-এর বিবরণ, প্রতিটি router-এর IP, kernel-এর socket table-এ 4-tuple। কিছুই বিমূর্ত নয়।

আমরা কী শিখলাম: "URL লিখলে কী হয়" প্রশ্নের উত্তর মুখস্থ করার দরকার নেই — আপনি প্রতিটি ধাপ নিজের machine-এ দেখতে পারেন। এবং এখন আপনি জানেন প্রতিটি ধাপে কী হচ্ছে, কেন হচ্ছে, এবং কোন component সেটি করছে।

📌 Chapter Summary
  • ১৭টি ধাপ, কিন্তু ছয়টি পর্যায়: parse → DNS → connect → request → server → render।
  • Connection setup-এ ন্যূনতম ৩ RTT (DNS + TCP + TLS), তারপর request-এর ১টি।
  • প্রতিটি sub-resource এই চক্রের কিছু অংশ পুনরাবৃত্তি করে — ভিন্ন origin হলে পুরোটাই।
  • Connection reuse, HTTP/2 multiplexing, ও CDN — তিনটিই এই RTT গুলো কমানোর কৌশল।
  • Server-side-এ একই গল্প ছোট পরিসরে পুনরাবৃত্ত হয় (app → cache → database)।
  • পুরো পথে: MAC বারবার বদলায়, IP অপরিবর্তিত, payload অস্পৃশ্য ও (TLS-এ) অপঠনীয়।
✓ Quick Check
একটি HTTPS page লোড হতে ন্যূনতম কতগুলো round trip লাগে (cache খালি, HTTP/1.1)?

ন্যূনতম চারটি: (১) DNS resolution, (২) TCP handshake, (৩) TLS 1.3 handshake, (৪) HTTP request/response। RTT ২০০ms হলে এটিই ৮০০ms — কোনো server processing time ছাড়াই। তারপর প্রতিটি sub-resource (CSS, JS, image) আরও round trip যোগ করে, যদিও একই origin হলে connection পুনর্ব্যবহৃত হয়।

পুরো যাত্রায় destination MAC address কতবার বদলায়? Destination IP কতবার?

Destination MAC প্রতিটি hop-এ বদলায় — সাধারণত ১০–২০ বার, কারণ MAC কেবল এক hop-এর জন্য। Destination IP সাধারণত ০ বার — এটি end-to-end পরিচয়। ব্যতিক্রম: গন্তব্যে load balancer DNAT করলে একবার। বিপরীতে source IP NAT-এ ১–২ বার বদলায়।

একটি page-এ ৫০টি resource আছে, সবই একই origin-এ। DNS lookup কতবার হবে?

একবার (বা শূন্য, যদি ইতিমধ্যে cache-এ থাকে)। DNS resolution hostname-প্রতি, resource-প্রতি নয় — এবং ফলাফল browser ও OS দুই জায়গাতেই cache হয়। তবে resource গুলো যদি ভিন্ন origin-এ থাকে (CDN, font provider, analytics), তাহলে প্রতিটি নতুন hostname-এর জন্য আলাদা DNS + TCP + TLS লাগবে — এজন্যই তৃতীয়-পক্ষের domain-এর সংখ্যা page speed-এর একটি বড় নিয়ামক।

ধাপ ১৩-এ (application logic) কেন বলা হলো "এখানে পুরো গল্পটি আবার ঘটছে"?

কারণ application থেকে cache (Redis) বা database-এ প্রতিটি call নিজেই একটি সম্পূর্ণ network operation — socket, TCP connection (বা pool থেকে পুনর্ব্যবহার), request, response, latency। শুধু পরিসর ছোট (একই data center, RTT ~০.৫ms)। এজন্যই N+1 query সমস্যা এত ব্যয়বহুল: ১০০টি ধারাবাহিক database call মানে ১০০টি round trip, যদিও প্রতিটি মাত্র ০.৫ms।
