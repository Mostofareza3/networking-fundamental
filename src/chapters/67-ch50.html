Final Knowledge Check

৪০টি scenario-ভিত্তিক প্রশ্ন। কোনোটিরই উত্তর মুখস্থ তথ্য নয় — প্রতিটির জন্য দরকার একটি mental model প্রয়োগ করা। প্রতিটি প্রশ্নে নিজে ভাবুন, তারপর উত্তর খুলুন।

Part A — নির্ণয় ও সমস্যা সমাধান
১. আপনি example.com-কে একটি IP-তে resolve করতে পারছেন, কিন্তু curl timeout হয়ে যাচ্ছে। কোন কোন স্তর তদন্ত করবেন এবং কোন ক্রমে?

Timeout মানে packet গেছে কিন্তু কিছু ফেরেনি — অর্থাৎ কেউ নীরবে ফেলে দিচ্ছে (DROP), REJECT করছে না।

  1. L3: ping ও traceroute <IP> — কোথায় থামছে? (ICMP block থাকতে পারে, তাই নিশ্চায়ক নয়)
  2. L4: nc -zv IP 443 — TCP handshake কি হচ্ছে?
  3. Packet: tcpdump — SYN যাচ্ছে? SYN-ACK আসছে? না এলে বুঝবেন প্রশ্নটি "কোথায় হারাচ্ছে"।
  4. Firewall: local (iptables), cloud security group, NACL (stateless — outbound নিয়মও লাগে)।
  5. Server-side: service কি চলছে? 0.0.0.0-তে bind? Server-এ tcpdump চালিয়ে দেখুন SYN আদৌ পৌঁছাচ্ছে কিনা — এটিই নির্ণায়ক।
  6. MTU: handshake হয় কিন্তু বড় data আটকায়? PMTUD black hole।
২. দুটি application port 3000-এ listen করতে চায়। কেন সাধারণত পারে না, এবং কোন ক্ষেত্রে পারে?

Kernel-এর socket lookup table-এ (protocol, IP, port) একটি অনন্য key — দুটি listener থাকলে আগত packet কাকে দেবে তা অনির্ধারিত। ব্যতিক্রম: (১) ভিন্ন protocol (TCP 3000 ও UDP 3000), (২) ভিন্ন IP (127.0.0.1:3000 ও 192.168.1.5:3000), (৩) SO_REUSEPORT — ইচ্ছাকৃত sharing, kernel load balance করে, (৪) ভিন্ন network namespace (container)।

৩. Ping কাজ করে কিন্তু HTTPS করে না। কী কী তদন্ত করবেন?

ping (ICMP, L3) সফল মানে host পৌঁছানো যায় এবং routing ঠিক। সমস্যা L4 বা তার উপরে: (১) port 443-এ কি কিছু শুনছে? nc -zv host 443; (২) firewall কি শুধু ICMP অনুমোদন করছে? (৩) TLS handshake ব্যর্থ? openssl s_client; (৪) certificate সমস্যা? (৫) Server চলছে কিন্তু overloaded? (৬) SNI-ভিত্তিক routing ভুল?

৪. একটি API কখনো কখনো ৫ সেকেন্ড ধীর, কখনো ৫০ms। কারণ কী হতে পারে?

ঠিক ৫ সেকেন্ডের ধরন খুবই ইঙ্গিতবাহী — এটি সাধারণত একটি timeout-এর মান, বিলম্ব নয়। সন্দেহ: (১) DNS-এ AAAA lookup timeout (IPv6 configure আছে কিন্তু কাজ করে না) — সবচেয়ে সম্ভাব্য; (২) একটি backend response দিচ্ছে না, ৫s timeout-এর পর অন্যটিতে retry; (৩) connection pool খালি, ৫s অপেক্ষা করে নতুন connection। যাচাই: curl -w-এর timing breakdown দেখুন — time_namelookup-এ ৫s হলে DNS নিশ্চিত।

৫. একটি service-এ CLOSE_WAIT socket-এর সংখ্যা ক্রমাগত বাড়ছে। কারণ ও প্রতিকার?

Peer FIN পাঠিয়েছে, kernel ACK করেছে, কিন্তু আপনার application close() call করেনি। এটি একটি file descriptor leak — code-এর bug, network-এর সমস্যা নয়। Kernel নিজে পরিষ্কার করতে পারে না। সাধারণ কারণ: exception path-এ connection বন্ধ না করা, connection pool-এ leak, finally/defer ছাড়া resource management। শেষ পরিণতি EMFILE: too many open files। → Ch 39

৬. Homepage দ্রুত খোলে কিন্তু একটি বড় file download সবসময় ৩০ সেকেন্ডে আটকে যায়। প্রথম সন্দেহ?

PMTUD black hole। ছোট packet (handshake, ছোট response) MTU-র নিচে থাকায় নির্বিঘ্নে যায়। বড় data-র packet পথের কোনো সংকীর্ণ link-এ (VPN, tunnel) আটকায়, router সেগুলো ফেলে দেয়, কিন্তু ICMP "Fragmentation Needed" কোথাও block থাকায় sender কখনো জানতে পারে না — শুধু retransmit করতে থাকে। যাচাই: ping -M do -s 1400। সমাধান: MTU কমান বা ICMP type 3 code 4 অনুমোদন করুন। → Ch 5

৭. একই request browser-এ কাজ করে কিন্তু আপনার backend service থেকে "unable to verify certificate" দেয়।

Server অসম্পূর্ণ certificate chain পাঠাচ্ছে — intermediate certificate বাদ পড়েছে। Browser AIA extension দেখে অনুপস্থিত intermediate নিজে ডাউনলোড করে নেয়; curl, Java, Go, Python করে না। যাচাই: openssl s_client -showcerts — কতগুলো certificate আসছে (অন্তত ২টি হওয়া উচিত)। সমাধান: nginx-এ fullchain.pem ব্যবহার করুন। → Ch 33

৮. AWS-এ security group-এ port খোলা, service 0.0.0.0-তে চলছে, তবু connection timeout। আর কী দেখবেন?

Network ACL — এটি stateless, তাই inbound নিয়মের পাশাপাশি outbound নিয়মও দরকার (response-এর জন্য ephemeral port range 1024–65535)। এটি সবচেয়ে বেশি উপেক্ষিত। এছাড়া: route table-এ Internet Gateway আছে কি? Instance কি public subnet-এ? Public IP আছে? Host firewall (iptables/ufw)? সবশেষে instance-এ tcpdump চালিয়ে দেখুন SYN আসছে কিনা — এটিই সবচেয়ে নির্ণায়ক পরীক্ষা।

৯. mtr-এ ৪ নম্বর hop-এ ৩০% loss কিন্তু শেষ hop-এ ০%। উদ্বেগের কারণ আছে?

না। ওই router শুধু নিজের উদ্দেশ্যে আসা ICMP-র উত্তর rate limit করছে — একটি সাধারণ ও যুক্তিসঙ্গত নীতি। প্রকৃত packet loss হলে সেটি ওই hop থেকে শেষ পর্যন্ত সব hop-এ দেখাত, কারণ packet সেখানেই হারিয়ে যেত। মাঝের hop-এর loss উপেক্ষা করুন যদি শেষ hop পরিষ্কার থাকে। → Ch 38

১০. Deploy-এর পর কিছু ব্যবহারকারী পুরনো version দেখছেন, কিছু নতুন। ব্যাখ্যা করুন।

একাধিক স্তরের cache: (১) CDN edge — কিছু edge-এ এখনো পুরনো copy; (২) Browser cache — max-age শেষ হয়নি; (৩) DNS — কিছু ব্যবহারকারী পুরনো IP-তে যাচ্ছেন (blue-green deploy হলে); (৪) Rolling deployment — কিছু server এখনো পুরনো code চালাচ্ছে। প্রতিরোধ: content hash সহ ফাইলের নাম (Ch 46), HTML-এ no-cache, deploy-এর সাথে CDN purge, এবং backward-compatible API।

Part B — ধারণাগত
১১. TCP handshake-এ তিনটি packet কেন প্রয়োজন?

দুই দিকেই ISN প্রতিষ্ঠা ও নিশ্চিত করতে। SYN-এ client-এর ISN যায়; SYN-ACK-এ server তা স্বীকার করে ও নিজেরটা পাঠায়; ACK-এ client server-এর ISN স্বীকার করে। দুটি packet-এ server নিশ্চিত হতে পারত না যে তার নিজের ISN পৌঁছেছে। → Ch 18

১২. TCP sequence number byte গোনে, packet নয় — কেন?

কারণ segment-এর আকার স্থির নয়: MTU বদলাতে পারে, এবং retransmission-এর সময় TCP ভিন্ন আকারে ভাগ করতে পারে (repacketization)। Byte-ভিত্তিক গণনা এই পুনর্বিন্যাসে অক্ষত থাকে; packet-ভিত্তিক হলে ভেঙে পড়ত। → Ch 17

১৩. Flow control এবং congestion control-এর মৌলিক পার্থক্য?

Flow control receiver-কে রক্ষা করে, সংকেত স্পষ্ট (receiver window ঘোষণা করে)। Congestion control network-কে রক্ষা করে, সংকেত অনুমাননির্ভর (loss বা delay দেখে sender নিজে সিদ্ধান্ত নেয়)। কার্যকর সীমা = min(rwnd, cwnd)। → Ch 20, 21

১৪. HTTP/2-তে multiplexing থাকা সত্ত্বেও একটি packet loss কেন সব stream আটকায়?

কারণ সব stream একটি TCP connection-এর উপর, এবং TCP নিচের স্তরে কঠোরভাবে ক্রম রক্ষা করে। TCP জানেই না ভেতরে একাধিক stream আছে — তার কাছে সবটাই একটি byte stream। একটি segment হারালে পরের সব byte আটকে যায়। QUIC transport layer-এই stream-এর ধারণা এনে এটি সমাধান করে। → Ch 30, 45

১৫. NAT-কে state রাখতে হয় কিন্তু সাধারণ router-কে হয় না — কেন?

সাধারণ router প্রতিটি packet স্বাধীনভাবে বিচার করে: destination IP দেখে table lookup, ব্যস। NAT-কে মনে রাখতে হয় কোন external port কোন internal (IP, port)-এ mapped — নাহলে ফেরত আসা packet কাকে দেবে তা জানা অসম্ভব। এই state memory খায়, timeout-এ মুছে যায় (তাই idle connection মরে), এবং router reboot হলে সব connection ভাঙে। → Ch 34

১৬. ARP request broadcast কিন্তু reply unicast — কেন?

জিজ্ঞাসাকারী জানে না কার কাছে জিজ্ঞেস করবে (সেটাই তো প্রশ্ন), তাই broadcast ছাড়া উপায় নেই। কিন্তু উত্তরদাতা ঠিক জানে কাকে উত্তর দিতে হবে, কারণ request-এর ভেতরেই sender-এর IP ও MAC আছে। তাই unicast যথেষ্ট এবং তাতে অপ্রয়োজনীয় network-শব্দ এড়ানো যায়। → Ch 8

১৭. TLS-এ certificate পাঠানোই যথেষ্ট নয় কেন?

Certificate public — যে কেউ ডাউনলোড করে নিজের বলে পাঠাতে পারে। প্রশ্ন হলো সে কি সংশ্লিষ্ট private key-র মালিক? CertificateVerify সেটি প্রমাণ করে: server তার private key দিয়ে এখন পর্যন্ত সব handshake message-এর signature তৈরি করে, যা কেবল প্রকৃত মালিকই পারে। → Ch 33

১৮. Forward secrecy না থাকলে কী ঝুঁকি?

আক্রমণকারী আজকের encrypted traffic রেকর্ড করে রাখতে পারে, এবং ভবিষ্যতে (হয়তো বছর পরে) server-এর private key চুরি করে সব পুরনো traffic decrypt করতে পারে। Forward secrecy (ECDHE)-তে প্রতিটি session-এর key আলাদা ও ephemeral, তাই private key চুরি হলেও পুরনো traffic নিরাপদ। TLS 1.3-এ এটি বাধ্যতামূলক। → Ch 32

১৯. DNS root server কি কখনো একটি website-এর IP জানে?

না। Root server শুধু TLD-দের nameserver জানে এবং সবসময় একটি referral দেয় — কখনো প্রকৃত উত্তর নয়। এই সীমিত দায়িত্বের কারণেই মাত্র ১৩টি root server "নাম" (anycast-এর কারণে বাস্তবে ১৫০০+ যন্ত্র) দিয়ে পুরো Internet চলে। → Ch 26

২০. Switch এবং router — কে broadcast domain ভাঙে?

Router। Switch প্রতি port-এ আলাদা collision domain তৈরি করে কিন্তু broadcast frame সব port-এ পাঠায় — তাই সব port একই broadcast domain-এ। Router broadcast forward করে না, তাই প্রতিটি interface একটি আলাদা broadcast domain। এজন্যই ARP router পেরোয় না। → Ch 7

Part C — নকশা ও সিদ্ধান্ত
২১. একটি real-time multiplayer game-এর জন্য TCP না UDP? যুক্তি দিন।

খেলোয়াড়ের অবস্থান/গতিবিধির জন্য UDP — কারণ ৫০ms পুরনো একটি update-এর কোনো মূল্য নেই, এবং TCP-র retransmission ও HOL blocking নতুন update গুলোকে আটকে রাখত (rubber-banding)। কিন্তু chat, inventory, লেনদেনের জন্য নির্ভরযোগ্যতা দরকার — সেগুলো TCP বা QUIC-এ। বাস্তবে আধুনিক game-রা প্রায়ই QUIC বা নিজস্ব UDP protocol ব্যবহার করে যেখানে বার্তা-ভেদে ভিন্ন reliability দেওয়া যায়। → Ch 23, 24

২২. ৫০০টি device-এর একটি অফিসে কোন subnet নকশা বেছে নেবেন?

/23 দিলে ৫১০টি host — গাণিতিকভাবে মানানসই। কিন্তু ভালো নকশা হলো বিভাগ অনুযায়ী একাধিক /24 এবং তাদের মাঝে router/VLAN: broadcast domain ছোট থাকে, নিরাপত্তা-নীতি প্রয়োগ করা যায় (guest Wi-Fi আলাদা, server আলাদা), এবং একটি সমস্যা সবাইকে প্রভাবিত করে না। → Ch 10

২৩. আপনার API-র ব্যবহারকারীরা তিনটি মহাদেশে। Latency কমাতে কী করবেন, অগ্রাধিকার অনুযায়ী?

(১) CDN/edge — static তো বটেই, dynamic API-র জন্যও (TLS handshake কাছে হওয়ায় বড় সাশ্রয়)। (২) Connection reuse — keep-alive, HTTP/2। (৩) Round trip কমানো — ধারাবাহিক call-এর waterfall ভাঙা, একটি aggregate endpoint। (৪) Multi-region deployment — read replica কাছে। (৫) HTTP/3। শেষে server-এর code optimization — কারণ সেখানে লাভ সবচেয়ে কম। → Ch 36, 43, 46

২৪. gRPC service-এর সামনে কোন load balancer এবং কেন?

L7 (gRPC-সচেতন) — যেমন Envoy, বা client-side load balancing। L4 LB connection বণ্টন করে, কিন্তু gRPC একটি long-lived HTTP/2 connection-এ হাজারো RPC পাঠায় — ফলে একটি client-এর সব request একটিই backend-এ যায়, ভারসাম্য নষ্ট হয়, এবং নতুন backend যোগ করলেও traffic পায় না। → Ch 44, 47

২৫. Health check endpoint-এ কী কী পরীক্ষা করবেন এবং কী করবেন না?

Liveness: শুধু "process সাড়া দিচ্ছে কি" — একটি সরল 200 OK। কখনো dependency পরীক্ষা করবেন না, কারণ database সাময়িকভাবে ধীর হলে সব server একসাথে pool থেকে বেরিয়ে যাবে বা restart হবে — cascading failure। Readiness: dependency-র অবস্থা দেখতে পারেন, কিন্তু সেখানেও graceful degradation-এর কথা ভাবুন — dependency ছাড়াও যতটুকু সেবা সম্ভব ততটুকু দিন। → Ch 47

২৬. একটি static asset-এ কোন Cache-Control নীতি এবং কেন?

ফাইলের নামে content hash থাকলে: Cache-Control: public, max-age=31536000, immutable — এক বছর, যাচাইও করার দরকার নেই। কারণ content বদলালে নামই বদলে যায়, তাই পুরনো URL-এ ভুল content আসার সম্ভাবনা শূন্য। আর যে HTML এই নামগুলো উল্লেখ করে সেটিতে no-cache — সবসময় যাচাই, কিন্তু 304 হলে সস্তা। → Ch 46

২৭. একটি payment API-তে idempotency কীভাবে নিশ্চিত করবেন?

Client প্রতিটি নতুন লেনদেনের জন্য একটি অনন্য Idempotency-Key (UUID) তৈরি করে header-এ পাঠায়। Server সেই key ও ফলাফল সংরক্ষণ করে (একটি নির্দিষ্ট সময়ের জন্য)। একই key-তে দ্বিতীয় request এলে নতুন লেনদেন না করে আগের ফলাফলটিই ফেরত দেয়। এতে network timeout-এর পর নিরাপদে retry করা যায়। POST নিজে idempotent নয় বলেই এই ব্যবস্থা প্রয়োজন। → Ch 29

২৮. Internal microservice-এর মধ্যে TLS দরকার? "আমাদের private network তো"।

হ্যাঁ, দরকার। Local network কখনোই স্বতঃসিদ্ধভাবে বিশ্বস্ত নয়: ARP spoofing (Ch 8), MAC flooding (Ch 7), একটি compromised host, বা একটি ভুল configure করা VLAN — যেকোনোটিই traffic উন্মুক্ত করে দেয়। Zero-trust নীতি বলে: network-এর অবস্থান দিয়ে বিশ্বাস নির্ধারণ করবেন না। mTLS (দুই পক্ষেরই certificate) internal service-এর জন্য আদর্শ, এবং service mesh এটি স্বয়ংক্রিয় করে। → Ch 31

২৯. Server migration-এর আগে DNS TTL নিয়ে কী পরিকল্পনা?

(১) Migration-এর অন্তত পুরনো TTL-এর সমান সময় আগে TTL কমিয়ে ৩০০ বা ৬০ করুন (IP অপরিবর্তিত রেখে)। (২) পুরনো TTL-এর সমান সময় অপেক্ষা করুন যাতে সব cache নতুন কম TTL গ্রহণ করে। (৩) এবার IP বদলান — কয়েক মিনিটে ছড়াবে। (৪) পুরনো server কয়েক ঘণ্টা চালু রাখুন (কিছু client TTL উপেক্ষা করে)। (৫) স্থিতিশীল হলে TTL বাড়ান। → Ch 27

৩০. আপনার team "custom reliable UDP protocol" লিখতে চায়। কী প্রশ্ন করবেন?

(১) TCP বা QUIC ঠিক কোন জায়গায় যথেষ্ট নয় — সুনির্দিষ্টভাবে? (২) Congestion control কে লিখবে ও কীভাবে পরীক্ষা করা হবে? (এটি ছাড়া আপনার protocol network-এর প্রতি অন্যায্য ও ক্ষতিকর।) (৩) NAT traversal, MTU discovery, retransmission timing, security — এসব কে সামলাবে? (৪) QUIC কি ব্যবহার করা যায়, যেখানে এসব ইতিমধ্যে সমাধান করা? বেশিরভাগ ক্ষেত্রে উত্তর — QUIC ব্যবহার করুন। → Ch 24

Part D — গভীর সংযোগ
৩১. Encapsulation-এর ধারণা ব্যবহার করে ব্যাখ্যা করুন কেন HTTP/3-এ যাওয়ার জন্য application code বদলাতে হয় না।

Layering-এর সংজ্ঞা অনুযায়ী প্রতিটি layer উপরেরটির কাছে একটি নির্দিষ্ট service interface দেয় এবং তার ভেতরের বাস্তবায়ন লুকিয়ে রাখে। HTTP-র semantics (method, header, status) transport-নিরপেক্ষ। HTTP/3 সেই একই semantics ধরে রেখে নিচের transport বদলে দিয়েছে (TCP → QUIC)। যেহেতু আপনার code শুধু HTTP-র interface ব্যবহার করে, নিচে কী আছে তা তার জানার দরকার নেই। এটিই separation of concerns-এর সবচেয়ে মূল্যবান সুফল — স্বাধীন বিবর্তন। → Ch 3, 45

৩২. "ARP cache-এর aging" এবং "DNS-এর TTL" — এই দুটি ধারণার মিল কোথায়?

দুটিই একই নকশা-নীতির প্রয়োগ: প্রয়োজনমতো শেখো, cache করো, এবং সময়ের সাথে ভুলে যাও। Cache কার্যক্ষমতা দেয়, কিন্তু পুরনো তথ্যে আটকে থাকার ঝুঁকি তৈরি করে। মেয়াদ নির্ধারণ করে সেই ঝুঁকি সীমিত করা হয় — ভুল তথ্য থেকে স্বয়ংক্রিয় পুনরুদ্ধারের ব্যবস্থা। Switch-এর MAC table aging, routing table, TLS session ticket, এমনকি HTTP cache — একই নীতি। → Ch 7, 8, 27

৩৩. TCP-র backpressure এবং আপনার application-এর stream API-র সম্পর্ক ব্যাখ্যা করুন।

একটি অবিচ্ছিন্ন শৃঙ্খল: receiver-এর application ধীরে read() করছে → তার kernel buffer ভরছে → rwnd ছোট হয়ে ACK-এ ঘোষিত হচ্ছে → sender-এর kernel পাঠানো কমাচ্ছে → sender-এর send buffer ভরছে → write() block করছে বা false ফেরত দিচ্ছে → Node.js-এ 'drain'-এর অপেক্ষা। অর্থাৎ receiver-এর ধীরগতি network পেরিয়ে sender-এর application পর্যন্ত পৌঁছাচ্ছে। এটি উপেক্ষা করলে data application-এর heap-এ জমে (আপাত memory leak)। → Ch 16, 20

৩৪. "Delegation" নীতিটি এই বইয়ের কোন কোন জায়গায় ফিরে এসেছে?

অন্তত পাঁচ জায়গায়: (১) Default gateway — "যা জানি না তা gateway-কে দাও" (Ch 11)। (২) Routing — প্রতিটি router শুধু next hop জানে, পুরো পথ নয় (Ch 12)। (৩) DNS hierarchy — root → TLD → authoritative, প্রত্যেকে "পরে ওকে জিজ্ঞেস করো" (Ch 26)। (৪) BGP — ISP তার upstream-কে (Ch 42)। (৫) Certificate chain — root → intermediate → leaf (Ch 32)। প্রতিটি ক্ষেত্রেই কেউ সবকিছু জানে না, এবং সেটিই ব্যবস্থাটিকে scalable করে।

৩৫. Head-of-line blocking কোন কোন স্তরে দেখা যায় এবং কীভাবে সমাধান হয়েছে?

HTTP/1.1-এ application-স্তরে — একটি connection-এ একবারে একটি request; সমাধান HTTP/2-র multiplexing। TCP-স্তরে — একটি segment হারালে পরের সব byte আটকে; HTTP/2-তে এটি আরও তীব্র হয় (সব stream আটকায়); সমাধান QUIC-এর stream-প্রতি স্বাধীন reliability। এটি একটি চমৎকার উদাহরণ যে একটি layer-এর সমস্যা কখনো কখনো সেই layer-এ সমাধান করা যায় না — নিচের layer বদলাতে হয়। → Ch 19, 30, 45

৩৬. "State রাখা" কোথায় কোথায় সমস্যা তৈরি করে?

(১) NAT — mapping-এর state timeout-এ মরে, তাই idle connection ভাঙে; router reboot-এ সব হারায় (Ch 34)। (২) Stateful firewall — একই সমস্যা। (৩) Sticky session — load অসম, server মরলে session হারায় (Ch 47)। (৪) TIME_WAIT — port আটকে থাকে (Ch 22)। বিপরীতে IP-র statelessness (Ch 12) এবং HTTP-র statelessness (Ch 28) — এই দুটিই তাদের নিজ নিজ স্তরকে অসাধারণভাবে scalable করেছে।

৩৭. একটি packet-এর যাত্রায় কোন কোন "নাম/ঠিকানা" ব্যবস্থা জড়িত, এবং প্রতিটির পরিধি কত?

Domain name — মানুষের জন্য, global, DNS দিয়ে IP-তে অনুবাদ। IP address — end-to-end, পুরো যাত্রায় অপরিবর্তিত (NAT ছাড়া)। MAC address — এক hop, প্রতিটি link-এ নতুন। Port — একটি host-এর ভেতরে process নির্বাচন। 4-tuple — একটি নির্দিষ্ট connection-এর পরিচয়। TLS session — দুটি application-এর মধ্যে নিরাপদ চ্যানেল। প্রতিটির পরিধি বোঝাই networking বোঝার মূল।

৩৮. একটি ৫ KB JSON API response ধীর। কোন কোন সম্ভাবনা, অগ্রাধিকার অনুযায়ী?

৫ KB-তে bandwidth কোনো বিষয়ই নয় — এটি স্পষ্টভাবে latency বা server-bound। ক্রম অনুযায়ী: (১) curl -w দিয়ে ভাগ করুন — DNS? TCP? TLS? TTFB? (২) নতুন connection প্রতিবার? → keep-alive; (৩) দূরত্ব? → CDN/edge; (৪) TTFB বড়? → server-side (database query, N+1, cache miss); (৫) ধারাবাহিক downstream call? → সমান্তরাল করুন। মাপার আগে optimize করবেন না।

৩৯. আপনি একটি নতুন junior developer-কে networking-এর সবচেয়ে গুরুত্বপূর্ণ তিনটি ধারণা শেখাতে চান। কোনগুলো?

একটি যুক্তিসঙ্গত উত্তর: (১) Layering ও encapsulation — প্রতিটি layer একটি সমস্যা সমাধান করে এবং উপরেরটির data-কে অস্বচ্ছ payload হিসেবে দেখে; এটি বাকি সব কিছুর কাঠামো। (২) MAC = এক hop, IP = end-to-end, port = process — পরিচয়ের পরিধি। (৩) Error message-এর অর্থ — refused (পৌঁছেছে, listener নেই) বনাম timeout (নীরবে হারাচ্ছে) বনাম unreachable (আমার routing table); এটি প্রতিদিনের কাজে সবচেয়ে বেশি ব্যবহৃত।

৪০. GET https://api.example.com/users — এই এক লাইন দেখে আপনি এখন কী কী দেখতে পান?

  ↓
