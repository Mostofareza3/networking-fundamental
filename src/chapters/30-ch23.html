Chapter 23

UDP — যখন কম বেশি

TCP-র সব সুবিধা পড়ার পর প্রশ্ন জাগে — কেউ UDP ব্যবহার করবে কেন? উত্তরটি চমকপ্রদ: কারণ TCP-র "সুবিধা"গুলো কিছু application-এর জন্য আসলে অসুবিধা।

23.1 UDP কী দেয় — এবং কী দেয় না

UDP Header — মাত্র ৮ bytes (TCP-র ২০+ এর তুলনায়):

┌───────────────────┬───────────────────┐
│   Source Port     │ Destination Port  │
│     2 bytes       │     2 bytes       │
├───────────────────┼───────────────────┤
│     Length        │    Checksum       │
│     2 bytes       │     2 bytes       │
└───────────────────┴───────────────────┘

লক্ষ্য করুন কী নেই:
  ✗ Sequence number     → ক্রমের কোনো ধারণা নেই
  ✗ Acknowledgment      → পৌঁছেছে কিনা জানার উপায় নেই
  ✗ Window              → flow control নেই
  ✗ Flags               → connection state নেই

UDP আসলে IP-এর উপর শুধু দুটি জিনিস যোগ করে:
  1. Port number (কোন process পাবে)
  2. Checksum (data অবিকৃত কিনা — ঐচ্ছিক IPv4-এ)

ব্যস। এর বেশি কিছু নয়।
🧠 Mental Model

TCP = ফোন কল। সংযোগ স্থাপন করতে হয়, দুজনেই জানে অন্যজন আছে, কথা ক্রমানুসারে যায়, না শুনলে "আবার বলুন" বলা যায়, শেষে "রাখছি" বলে বিদায়।

UDP = পোস্টকার্ড। ঠিকানা লিখে ফেলে দিলেন। পৌঁছেছে কিনা জানবেন না। দশটি পাঠালে তিনটি হারাতে পারে, পাঁচ নম্বরটি দুই নম্বরের আগে পৌঁছাতে পারে। কিন্তু — খুব দ্রুত, কোনো আনুষ্ঠানিকতা নেই, এবং একটি হারালেও পরেরটি আটকে থাকে না।

শেষ বাক্যটিই মূল কথা। বহু application-এর জন্য "একটি হারালেও পরেরটি আটকে থাকে না" — এই বৈশিষ্ট্যটি নির্ভরযোগ্যতার চেয়ে বেশি মূল্যবান।

23.2 Why would anyone choose UDP?

কারণ ১ — পুরনো data মূল্যহীন

একটি ভিডিও কল, ৩০ frame/সেকেন্ড:

  Frame 100 হারিয়ে গেল।

  TCP-র আচরণ:
    → frame 100 আবার পাঠাও
    → frame 101, 102, 103 পৌঁছে গেলেও আটকে রাখো
      (head-of-line blocking)
    → 200ms পরে frame 100 এল
    → এখন 100, 101, 102, 103 একসাথে দাও
    → ব্যবহারকারী দেখল: ভিডিও জমে গেল, তারপর লাফ দিল

  UDP-র আচরণ:
    → frame 100 হারিয়েছে? ভুলে যাও।
    → frame 101 এসেছে, সেটাই দেখাও
    → ব্যবহারকারী দেখল: এক frame-এর সামান্য glitch

  ★ ২০০ms পুরনো একটি video frame-এর কোনো মূল্য নেই।
    সেটি পাওয়ার চেয়ে না পাওয়াই ভালো।

কারণ ২ — একটি request, একটি response

DNS query:

  TCP দিয়ে হলে:
    SYN, SYN-ACK, ACK        (3 packet, 1 RTT)
    query, response          (2 packet, 1 RTT)
    FIN, ACK, FIN, ACK       (4 packet)
    ─────────────────────────────────
    মোট 9 packet, 2+ RTT

  UDP দিয়ে:
    query, response
    ─────────────────────────────────
    মোট 2 packet, 1 RTT

  ★ handshake-এর খরচ প্রকৃত data-র চেয়ে বেশি হলে
    connection স্থাপন করাই অপচয়।

কারণ ৩ — Multicast ও broadcast

TCP সংজ্ঞাগতভাবে point-to-point — দুটি নির্দিষ্ট endpoint-এর মধ্যে। একসাথে ১০০০ জনকে পাঠাতে হলে TCP দিয়ে ১০০০টি আলাদা connection লাগবে। UDP multicast দিয়ে একটি packet পাঠালেই সবাই পায়। IPTV, service discovery (mDNS), routing protocol — সবই এই কারণে UDP।

কারণ ৪ — নিজের নিয়মে reliability

✓ সবচেয়ে গুরুত্বপূর্ণ কারণ

TCP-র reliability একটি package deal — আপনি ordering ছাড়া retransmission নিতে পারবেন না, বা congestion control ছাড়া flow control নিতে পারবেন না। কিন্তু আপনার application-এর হয়তো দরকার:

  • Retransmission হ্যাঁ, কিন্তু strict ordering না
  • নিজস্ব congestion control (real-time video-র জন্য ভিন্ন কৌশল)
  • Stream-প্রতি স্বাধীন reliability
  • Connection migration (IP বদলালেও connection টিকে থাকবে)

UDP আপনাকে খালি ক্যানভাস দেয়, এবং আপনি ঠিক যতটুকু দরকার ততটুকুই তৈরি করে নেন। QUIC ঠিক এই কাজটিই করে — সে UDP-র উপর TCP-র চেয়ে ভালো একটি reliability layer তৈরি করেছে (Ch 45)।

23.3 কারা UDP ব্যবহার করে

Applicationকেন UDP
DNSছোট query/response; handshake-এর খরচ অযৌক্তিক। Response বড় হলে TCP-তে যায়।
QUIC / HTTP3নিজস্ব উন্নত transport তৈরি করেছে; TCP-র HOL blocking এড়াতে।
VoIP, video callপুরনো audio/video frame মূল্যহীন; latency নির্ভরযোগ্যতার চেয়ে গুরুত্বপূর্ণ।
Online gameখেলোয়াড়ের অবস্থান ৫০ms পুরনো হলে অকেজো; নতুন update-ই আসল।
Live streamingনির্দিষ্ট সময়ের মধ্যে না এলে ফেলে দেওয়াই ভালো।
DHCPBroadcast দরকার — তখনো নিজের IP নেই।
NTPএকটি ছোট বিনিময়; latency নিজেই পরিমাপের অংশ।
syslog, metricsবিপুল পরিমাণ; কিছু হারালেও চলে, কিন্তু sender-কে ধীর করা যাবে না।
WireGuard, VPNTCP-over-TCP এড়াতে (দুই স্তরের retransmission ভয়াবহ)।
⚠️ TCP-over-TCP সমস্যা

একটি TCP tunnel-এর ভেতরে TCP চালালে দুই স্তরের retransmission ও congestion control একে অপরের সাথে লড়াই করে: বাইরের TCP retransmit করছে, ভেতরের TCP-ও timeout দেখে retransmit করছে — ফলে exponentially খারাপ পরিস্থিতি, যাকে বলে TCP meltdown। এজন্যই আধুনিক VPN (WireGuard, OpenVPN-এর UDP mode) UDP-র উপর চলে।

23.4 UDP-তে code লেখা

python
# ---------- SERVER ----------
import socket
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)   # DGRAM!
s.bind(("0.0.0.0", 9999))
# listen() নেই। accept() নেই। কোনো connection-ই নেই।

while True:
    data, addr = s.recvfrom(65535)
    # ★ প্রতিটি recvfrom একটি সম্পূর্ণ datagram দেয় —
    #   কখনো আংশিক নয়, কখনো দুটি জোড়া লাগানো নয়
    print(f"{addr} থেকে: {data}")
    s.sendto(b"pong", addr)     # প্রতিবার গন্তব্য বলে দিতে হয়

# ---------- CLIENT ----------
c = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
c.sendto(b"ping", ("127.0.0.1", 9999))   # সরাসরি পাঠান
c.settimeout(2.0)                         # নিজেই timeout সামলান
try:
    data, _ = c.recvfrom(65535)
    print("পেলাম:", data)
except socket.timeout:
    print("কোনো উত্তর নেই — হারিয়ে গেছে?")
    # ★ retry করবেন? কতবার? কত পরে?
    #   এই সিদ্ধান্তগুলো এখন আপনার।
⚙️ Developer Perspective — UDP মানে দায়িত্ব

UDP ব্যবহার করা মানে TCP যা যা করত তার প্রয়োজনীয় অংশগুলো আপনাকে লিখতে হবে:

  • Timeout ও retry — কতক্ষণ অপেক্ষা? কতবার চেষ্টা? Exponential backoff?
  • Duplicate detection — নিজের sequence number দিতে হবে
  • Ordering — দরকার হলে নিজে সাজাতে হবে
  • Congestion control — না করলে আপনি network-এর জন্য ক্ষতিকর (এবং অন্যায্য)
  • MTU — datagram ছোট রাখতে হবে, নাহলে fragmentation (Ch 5)

একটি সৎ পরামর্শ: নতুন করে "UDP-র উপর নিজের reliable protocol" লেখার আগে দুবার ভাবুন। QUIC ইতিমধ্যে এটি করেছে, বহু বছরের গবেষণা ও বাস্তব পরীক্ষার পর। বেশিরভাগ ক্ষেত্রে সঠিক পছন্দ হলো TCP, অথবা QUIC — নিজের হাতে লেখা অর্ধ-সম্পূর্ণ reliability layer নয়।

23.5 UDP-র আকার এবং ঝুঁকি

⚠️ Datagram ছোট রাখুন

তাত্ত্বিকভাবে একটি UDP datagram ৬৫,৫০৭ bytes পর্যন্ত হতে পারে। কিন্তু MTU সাধারণত ১৫০০ — তাই বড় datagram fragment হয়ে যায়, এবং একটি fragment হারালে পুরো datagram হারায় (Ch 5)।

ব্যবহারিক নির্দেশনা: datagram ১২০০ bytes-এর নিচে রাখুন (VPN ও tunnel-এর জায়গা রেখে)। DNS ঐতিহাসিকভাবে ৫১২ bytes-এ সীমাবদ্ধ ছিল ঠিক এই কারণেই; QUIC-ও তার প্রাথমিক packet ১২০০-এর নিচে রাখে।

⚠️ Amplification Attack

UDP-তে source IP যাচাই করার কোনো ব্যবস্থা নেই (কোনো handshake নেই)। তাই আক্রমণকারী ভুক্তভোগীর IP-কে source হিসেবে লিখে একটি ছোট query পাঠাতে পারে, এবং server-এর বড় response ভুক্তভোগীর কাছে গিয়ে পৌঁছায়।

Attacker → [60 byte query, src IP = ভুক্তভোগীর]  → DNS server
ভুক্তভোগী ← [4000 byte response] ← DNS server

Amplification factor ≈ 60x
১ Mbps পাঠিয়ে ৬০ Mbps আক্রমণ!

NTP monlist-এ এটি ৫০০x পর্যন্ত পৌঁছেছিল।

এজন্যই: public UDP service-এ response rate limiting দরকার, খোলা DNS resolver চালানো উচিত নয়, এবং QUIC-এ একটি নিয়ম আছে — server client-এর address যাচাই না করা পর্যন্ত পাওয়া data-র ৩ গুণের বেশি পাঠাতে পারবে না।

🧪 Lab 23 — UDP-র আচরণ পরীক্ষা করুন

আমরা কী দেখতে চাইছি? — UDP-তে connection নেই, তাই "কেউ শুনছে না" অবস্থাটি TCP-র চেয়ে সম্পূর্ণ ভিন্নভাবে প্রকাশ পায়।

bash
# TCP: বন্ধ port → তাৎক্ষণিক refused
nc -zv 127.0.0.1 9999          # "Connection refused"

# UDP: বন্ধ port → ICMP Port Unreachable
sudo tcpdump -i lo -n icmp &
echo "hello" | nc -u -w2 127.0.0.1 9999
# tcpdump-এ: "ICMP udp port 9999 unreachable"

# একটি UDP server চালিয়ে দেখুন
nc -u -l 9999 &
echo "hello" | nc -u -w1 127.0.0.1 9999

# DNS — বাস্তব জীবনের UDP
sudo tcpdump -i any -n 'udp port 53' -c 4 &
dig +short example.com

যা লক্ষ্য করবেন: UDP-তে কোনো handshake নেই — nc -u সরাসরি data পাঠায়। কেউ না শুনলে kernel একটি ICMP Port Unreachable পাঠায় (TCP-র RST-এর সমতুল্য, কিন্তু ভিন্ন protocol-এ)। dig-এর tcpdump-এ দেখবেন ঠিক দুটি packet — একটি query, একটি response। কোনো SYN, কোনো FIN নেই।

আমরা কী শিখলাম: UDP-তে "connection" বলে কিছু নেই — তাই connection-সংক্রান্ত সব ধারণা (refused, reset, established) এখানে অনুপস্থিত। DNS-এর দুই-packet বিনিময় দেখলেই বোঝা যায় কেন এখানে TCP-র নয় packet অপচয় হতো।

📌 Chapter Summary
  • UDP header মাত্র ৮ bytes — IP-এর উপর শুধু port ও checksum যোগ করে।
  • কোনো connection নেই, ACK নেই, ordering নেই, retransmission নেই, flow/congestion control নেই।
  • Datagram-এর সীমানা সংরক্ষিত — এক sendto() = এক recvfrom() (TCP-র উল্টো)।
  • UDP বেছে নেওয়া হয় যখন: পুরনো data মূল্যহীন, বিনিময় ছোট, multicast দরকার, বা নিজস্ব transport তৈরি করতে হবে।
  • TCP-র head-of-line blocking এড়ানোই real-time application-এ UDP-র প্রধান আকর্ষণ।
  • Datagram ১২০০ bytes-এর নিচে রাখুন — fragmentation এড়াতে।
  • UDP-তে source IP যাচাই হয় না → amplification attack-এর ঝুঁকি → rate limiting দরকার।
✓ Quick Check
একটি ভিডিও কলে TCP ব্যবহার করলে কী সমস্যা হতো?

Head-of-line blocking। একটি frame-এর packet হারালে TCP সেটি retransmit করত এবং পরবর্তী সব frame পৌঁছে গিয়েও আটকে থাকত ক্রম রক্ষার জন্য। ব্যবহারকারী দেখতেন — ভিডিও জমে গেল, তারপর হঠাৎ লাফ দিয়ে এগোল। অথচ ২০০ms পুরনো একটি frame-এর কোনো মূল্যই নেই। UDP-তে হারানো frame ভুলে গিয়ে পরেরটি দেখানো যায়।

DNS কেন UDP ব্যবহার করে, কিন্তু কখনো কখনো TCP-তেও যায়?

একটি DNS query ও response সাধারণত কয়েকশ bytes — একটি TCP handshake (৩ packet) + teardown (৪ packet) এর জন্য অযৌক্তিক অপচয়। UDP-তে মাত্র ২টি packet, ১ RTT। কিন্তু response যদি বড় হয় (DNSSEC signature, বহু record) এবং UDP-তে না আঁটে, server TC (truncated) flag সেট করে; তখন client TCP-তে আবার query করে, যেখানে আকারের সীমা নেই।

UDP-তে এক sendto() = এক recvfrom() — TCP-তে কেন এই নিশ্চয়তা নেই?

কারণ UDP datagram-ভিত্তিক: প্রতিটি datagram একটি স্বয়ংসম্পূর্ণ একক, এবং তার সীমানা protocol-এ সংরক্ষিত। TCP byte stream-ভিত্তিক: আপনার write গুলো kernel-এর buffer-এ মিশে যায় এবং segment-এ ভাগ হয় সম্পূর্ণ ভিন্নভাবে। TCP-তে message-এর সীমানা application-কে নিজেই সংজ্ঞায়িত করতে হয় (length prefix, delimiter, Content-Length)।

UDP amplification attack কীভাবে কাজ করে?

UDP-তে কোনো handshake নেই, তাই source IP যাচাই হয় না। আক্রমণকারী ভুক্তভোগীর IP-কে source হিসেবে লিখে একটি ছোট query (~৬০ bytes) পাঠায় একটি public server-এ। Server-এর বড় response (~৪০০০ bytes) চলে যায় ভুক্তভোগীর কাছে। ফলে আক্রমণকারী তার নিজের bandwidth-এর বহু গুণ traffic ভুক্তভোগীর দিকে পাঠাতে পারে। প্রতিকার: response rate limiting, খোলা resolver না চালানো, এবং amplification-বিরোধী নকশা (QUIC-এর ৩x নিয়ম)।
