Chapter 41

Packet Capture — tcpdump

যখন আর সব tool ব্যর্থ হয়, একটি প্রশ্ন থেকে যায়: তারে আসলে কী যাচ্ছে? tcpdump সেই প্রশ্নের চূড়ান্ত উত্তর দেয় — এবং প্রায়ই সেটিই একমাত্র নিশ্চিত উত্তর।

গুরুত্বপূর্ণ সূক্ষ্মতা:
  • tcpdump kernel-এর ★ভেতরে★ দেখে, তারে নয়
  • তাই outbound packet সে দেখে ★firewall-এর আগে★,
    এবং inbound packet দেখে ★firewall-এর পরে★ —
    (netfilter hook-এর অবস্থানের উপর নির্ভর করে)
  • Loopback traffic-ও দেখা যায় (-i lo)
  • Encrypted (TLS) traffic-এর ভেতরটা দেখা যাবে না —
    শুধু বাইরের মোড়ক

41.2 মৌলিক ব্যবহার

bash
# সবচেয়ে সাধারণ শুরু
sudo tcpdump -i any -n port 443

# গুরুত্বপূর্ণ flag গুলো
#  -i any     সব interface (বা eth0, lo)
#  -n         IP resolve করো না (★ দ্রুত, এবং DNS lookup
#             নিজেই traffic তৈরি করে বলে বিভ্রান্তি এড়ায় ★)
#  -nn        port-এর নামও resolve করো না
#  -c 20      ২০টি packet পরে থামো
#  -v -vv     আরও বিস্তারিত
#  -e         Ethernet header দেখাও (MAC address)
#  -A         ASCII-তে payload দেখাও (plaintext-এর জন্য)
#  -X         hex + ASCII
#  -s 0       সম্পূর্ণ packet ধরো (আধুনিক version-এ default)
#  -w f.pcap  ফাইলে লেখো (Wireshark-এ খোলার জন্য)
#  -r f.pcap  ফাইল থেকে পড়ো

41.3 Filter — সবচেয়ে গুরুত্বপূর্ণ দক্ষতা

⚠️ Filter ছাড়া tcpdump কার্যত অকেজো

একটি ব্যস্ত server-এ প্রতি সেকেন্ডে হাজার হাজার packet। Filter ছাড়া output এত দ্রুত চলে যাবে যে কিছুই পড়া যাবে না — এবং packet drop-ও হতে পারে। সবসময় যতটা সম্ভব সংকীর্ণ filter দিন।

bash
# ── Host ──
tcpdump -n host 1.1.1.1
tcpdump -n src 10.0.0.5
tcpdump -n dst 10.0.0.5
tcpdump -n net 192.168.1.0/24

# ── Port ──
tcpdump -n port 443
tcpdump -n portrange 8000-8100
tcpdump -n dst port 5432

# ── Protocol ──
tcpdump -n icmp
tcpdump -n udp port 53
tcpdump -n arp

# ── যৌক্তিক সংযোজন ──
tcpdump -n 'host 10.0.0.5 and port 443'
tcpdump -n 'port 80 or port 443'
tcpdump -n 'host 10.0.0.5 and not port 22'   # ★ SSH বাদ দিন,
                                              #   নাহলে নিজের
                                              #   session দেখবেন

# ── TCP flag (উন্নত কিন্তু অত্যন্ত কার্যকর) ──
tcpdump -n 'tcp[tcpflags] & tcp-syn != 0'    # শুধু SYN
tcpdump -n 'tcp[tcpflags] & tcp-rst != 0'    # ★ শুধু RST — কে
                                              #   connection ভাঙছে
tcpdump -n 'tcp[tcpflags] & (tcp-syn|tcp-fin) != 0'  # শুরু ও শেষ

# ── HTTP method (payload-এ খোঁজা) ──
tcpdump -n -A 'tcp port 80 and tcp[((tcp[12:1] & 0xf0) >> 2):4] = 0x47455420'
#                                                                  G E T (space)

41.5 বাস্তব diagnostic pattern

যা দেখছেনযা বোঝায়
শুধু [S], বারবার, কোনো [S.] নেইPacket পৌঁছাচ্ছে না বা উত্তর ফিরছে না — firewall DROP, বা host down, বা routing সমস্যা
[S]-এর জবাবে [R]Port-এ কেউ শুনছে না — "connection refused"
Handshake হলো, তারপর [R]Application connection ভেঙেছে — crash, timeout, বা ইচ্ছাকৃত reset
একই seq বারবারRetransmission — packet loss (Ch 19)
একই ack বারবারDuplicate ACK — receiver-এর কাছে ফাঁক আছে
win 0Receiver-এর buffer ভরা — zero window (Ch 20)
শুধু একদিকের packetAsymmetric routing, বা return path-এ সমস্যা
কোনো packet-ই নেইভুল interface বা ভুল filter; বা traffic এই machine-এ আসছেই না
✓ সবচেয়ে দরকারি একটি প্রশ্ন

একটি সমস্যায় tcpdump চালিয়ে প্রথমেই জিজ্ঞেস করুন: "packet কি এখানে আসছে?"

  • আসছে না → সমস্যা এই machine-এর আগে (routing, firewall, DNS ভুল IP, load balancer)।
  • আসছে কিন্তু উত্তর যাচ্ছে না → সমস্যা এই machine-এ (application শুনছে না, বা outbound firewall)।
  • উত্তর যাচ্ছে কিন্তু client পাচ্ছে না → return path-এ সমস্যা (asymmetric routing, NAT, firewall)।

এই একটি প্রশ্ন সমস্যার পরিসর তিন ভাগের এক ভাগে নামিয়ে আনে — এবং অন্য কোনো tool এত নিশ্চিতভাবে এর উত্তর দিতে পারে না।

41.6 Wireshark

bash
# Server-এ capture করুন, নিজের machine-এ বিশ্লেষণ করুন
sudo tcpdump -i any -n -s 0 -w capture.pcap 'host 10.0.0.5 and port 443'
# Ctrl+C দিয়ে থামান, তারপর:
scp server:capture.pcap .
wireshark capture.pcap

Wireshark যা tcpdump-এর চেয়ে ভালো করে:

  • Follow TCP Stream — একটি connection-এর সম্পূর্ণ কথোপকথন একসাথে দেখা
  • Protocol dissector — HTTP, DNS, TLS ইত্যাদি সুন্দরভাবে ভেঙে দেখানো
  • Statistics — conversation, I/O graph, retransmission-এর হার
  • Expert Info — সমস্যাগুলো স্বয়ংক্রিয়ভাবে চিহ্নিত করা
  • TLS decryption — SSLKEYLOGFILE environment variable সেট করে browser চালালে Wireshark encrypted traffic-ও পড়তে পারে
ℹ️ একটি বাস্তব workflow

Production server-এ GUI চালানো যায় না, এবং সেখানে দীর্ঘক্ষণ tcpdump দেখাও অসুবিধাজনক। তাই প্রচলিত পদ্ধতি: server-এ সংকীর্ণ filter দিয়ে -w ব্যবহার করে ফাইলে capture করুন, তারপর সেটি নিজের machine-এ এনে Wireshark-এ বিশ্লেষণ করুন। Capture-এর সময় -c বা -G/-W (rotating file) ব্যবহার করে আকার নিয়ন্ত্রণে রাখুন — নাহলে disk ভরে যেতে পারে।

⚠️ Production-এ tcpdump চালানোর সতর্কতা
  • CPU খরচ — উচ্চ traffic-এ প্রতিটি packet কপি করা ব্যয়বহুল। সংকীর্ণ filter অপরিহার্য।
  • Disk — -w ব্যবহারে ফাইল দ্রুত গিগাবাইটে পৌঁছাতে পারে। -C/-W দিয়ে rotate করুন।
  • গোপনীয়তা ও compliance — capture-এ ব্যবহারকারীর data, token, এমনকি plaintext password থাকতে পারে। সংরক্ষণ ও শেয়ার করার আগে ভাবুন; অনেক প্রতিষ্ঠানে এর জন্য অনুমোদন লাগে।
  • নিজের SSH session বাদ দিন — and not port 22, নাহলে আপনার নিজের output নিজেই traffic তৈরি করে অসীম প্রতিক্রিয়া তৈরি করবে।
🧪 Lab 41 — একটি সম্পূর্ণ connection ধরুন

আমরা কী দেখতে চাইছি? — একটি বাস্তব HTTP connection-এর প্রতিটি packet, শুরু থেকে শেষ পর্যন্ত, এবং সেখানে এই বইয়ের ধারণাগুলো চিনে নেওয়া।

bash
# Terminal 1 — capture শুরু করুন
sudo tcpdump -i any -n 'host example.com and port 80'

# Terminal 2 — একটি request
curl -s http://example.com > /dev/null

# ── তারপর এগুলো চেষ্টা করুন ──

# শুধু handshake ও termination
sudo tcpdump -i any -n 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0'

# Plaintext HTTP-র বিষয়বস্তু
sudo tcpdump -i any -n -A -c 30 'tcp port 80'

# DNS query দেখুন
sudo tcpdump -i any -n -c 6 'udp port 53' &
dig +short example.com

# ফাইলে লিখুন, পরে পড়ুন
sudo tcpdump -i any -n -c 50 -w /tmp/cap.pcap 'port 443'
tcpdump -r /tmp/cap.pcap -n | head -20

যা লক্ষ্য করবেন: তিনটি handshake packet, তারপর একটি [P.] (আপনার GET), তারপর server-এর ACK ও data packet গুলো, শেষে FIN/ACK-এর জোড়া। প্রথম দুটি packet-এর সময়ের পার্থক্যই আপনার RTT। যদি length 1448 দেখেন, সেটাই MSS (Ch 5)।

আমরা কী শিখলাম: এই বইয়ের সব ধারণা — handshake, sequence number, ACK, MSS, window, termination — একটি tcpdump output-এ একসাথে দৃশ্যমান। কোনো tool যখন উত্তর দিতে পারছে না, তখন packet capture-ই চূড়ান্ত সত্য।

📌 Chapter Summary
  • tcpdump kernel-এর ভেতরে প্রতিটি frame-এর কপি পায় — তারে যাওয়ার আগে বা পরে।
  • Filter অপরিহার্য — সংকীর্ণ filter ছাড়া output অপঠনীয় ও ব্যয়বহুল।
  • -n সবসময় ব্যবহার করুন — DNS lookup নিজেই traffic তৈরি করে বিভ্রান্তি বাড়ায়।
  • Flags পড়ুন: [S], [S.], [.], [P.], [F.], [R]।
  • Diagnostic-এর মূল প্রশ্ন: packet কি আসছে? উত্তর কি যাচ্ছে?
  • বারবার একই seq = retransmission; বারবার একই ack = duplicate ACK; win 0 = receiver ভরা।
  • Production-এ: সংকীর্ণ filter + -w দিয়ে ফাইলে, তারপর Wireshark-এ বিশ্লেষণ।
  • Capture-এ সংবেদনশীল data থাকতে পারে — গোপনীয়তা ও compliance মাথায় রাখুন।
✓ Quick Check
tcpdump-এ শুধু [S] দেখছেন, কোনো [S.] নেই। কী বোঝায়?

আপনার SYN বেরিয়ে যাচ্ছে কিন্তু কোনো SYN-ACK ফিরছে না। সম্ভাবনা: (১) firewall নীরবে DROP করছে (RST নয়, তাই "timeout" হবে), (২) host down বা পৌঁছানো যাচ্ছে না, (৩) routing সমস্যা, (৪) return path ভাঙা (asymmetric routing)। গন্তব্য server-এ একই সাথে tcpdump চালালে বোঝা যাবে packet সেখানে পৌঁছাচ্ছে কিনা — এটিই নির্ণায়ক পরীক্ষা।

-n flag কেন সবসময় ব্যবহার করা উচিত?

দুটি কারণ। (১) গতি — প্রতিটি IP-র জন্য reverse DNS lookup করলে output ধীর হয় এবং packet drop হতে পারে। (২) বিভ্রান্তি এড়ানো — সেই DNS lookup গুলো নিজেই network traffic তৈরি করে, যা আপনার capture-এ দেখা যায় এবং বিশ্লেষণ জটিল করে তোলে। DNS সমস্যা নির্ণয় করতে গিয়ে DNS traffic তৈরি করা বিশেষভাবে সমস্যাজনক।

একই seq নম্বর বারবার দেখা যাচ্ছে। কী ঘটছে?

Retransmission — sender একই data আবার পাঠাচ্ছে কারণ সে ACK পায়নি (Ch 19)। এর মানে হয় original packet হারিয়েছে, নয় তার ACK হারিয়েছে। সাথে যদি duplicate ACK-ও দেখেন, তাহলে fast retransmit ঘটছে। ঘন ঘন retransmission মানে উল্লেখযোগ্য packet loss — ss -ti-তেও এটি retrans counter-এ দেখা যাবে।

Production server-এ tcpdump চালানোর আগে কী কী সতর্কতা?

(১) যতটা সম্ভব সংকীর্ণ filter — CPU ও packet drop এড়াতে। (২) -c বা -W দিয়ে আকার সীমিত করুন — disk ভরে যাওয়া একটি বাস্তব ঝুঁকি। (৩) and not port 22 দিয়ে নিজের SSH session বাদ দিন। (৪) Capture-এ ব্যবহারকারীর সংবেদনশীল data থাকতে পারে — সংরক্ষণ, স্থানান্তর ও শেয়ারের ক্ষেত্রে প্রতিষ্ঠানের নীতি মানুন। (৫) সম্ভব হলে ফাইলে capture করে অন্যত্র বিশ্লেষণ করুন।
