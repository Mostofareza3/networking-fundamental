Chapter 12

What Is Routing?

Routing-এর সবচেয়ে বিস্ময়কর দিক হলো — কোনো router-ই পুরো পথটা জানে না। প্রতিটি router শুধু একটি সিদ্ধান্ত নেয়: "পরের জন কে?" তবু packet ঠিক গন্তব্যে পৌঁছে যায়।

12.1 Why does this exist?

Chapter 11-এ আমরা দেখলাম আপনার machine একটি সিদ্ধান্ত নেয় — local নাকি gateway। Router-এর কাজ একই, শুধু বড় পরিসরে: "এই packet-টি আমার কোন interface দিয়ে, কার কাছে পাঠাব?"

💡 Why hop-by-hop

একটি বিকল্প design হতে পারত — sender পুরো পথটি নির্ধারণ করে packet-এ লিখে দেবে (source routing)। কিন্তু:

  • Sender-কে পুরো Internet-এর topology জানতে হতো,
  • কোনো link ভেঙে গেলে চলমান সব packet অকেজো হয়ে যেত,
  • নিরাপত্তার ঝুঁকি — যে কেউ traffic-কে ইচ্ছেমতো পথে চালাতে পারত (এই কারণেই IPv4-এর source routing option কার্যত সব জায়গায় বন্ধ)।

Hop-by-hop routing এই সবগুলোর সমাধান করে। প্রতিটি router শুধু নিজের প্রতিবেশীদের চেনে এবং একটি স্থানীয় সিদ্ধান্ত নেয়। কোনো link ভাঙলে শুধু কাছের router-দের নতুন করে ভাবতে হয়, বাকিদের নয়। এটি একটি distributed algorithm — কোনো কেন্দ্রীয় নিয়ন্ত্রক ছাড়াই সবাই মিলে একটি বৈশ্বিক সমস্যা সমাধান করে।

🧠 Mental Model

Routing-কে ভাবুন অচেনা শহরে পথ জিজ্ঞেস করার মতো। আপনি কাউকে জিজ্ঞেস করলেন "রেলস্টেশন কোন দিকে?" সে পুরো manzil-এর মানচিত্র দেয় না — শুধু বলে "সোজা গিয়ে ডানে ঘুরুন"। পরের মোড়ে আবার জিজ্ঞেস করবেন। প্রত্যেকে শুধু পরের ধাপ জানে, তবু আপনি পৌঁছে যান।

একটি packet-ও ঠিক তাই করে। এবং packet নিজে কিছু মনে রাখে না — প্রতিটি router-ই স্বাধীনভাবে সিদ্ধান্ত নেয়। এজন্যই IP-কে বলা হয় stateless।

12.2 Routing Table

প্রতিটি router (এবং প্রতিটি host) একটি routing table রাখে। প্রতিটি entry-তে থাকে:

অংশঅর্থউদাহরণ
Destination prefixকোন network-এর জন্য এই নিয়ম10.0.5.0/24
Next hopকার কাছে দিতে হবেvia 172.16.0.2
Interfaceকোন NIC দিয়ে বেরোবেdev eth1
Metric / costএকাধিক পথ থাকলে অগ্রাধিকারmetric 100

12.3 Longest Prefix Match — সবচেয়ে নির্দিষ্ট route জেতে

একটি destination একাধিক route-এর সাথে মিলতে পারে। কোনটি প্রয়োগ হবে? উত্তর: যেটি সবচেয়ে নির্দিষ্ট, অর্থাৎ যার prefix সবচেয়ে দীর্ঘ।

Destination: 10.0.5.20

Routing Table:
┌─────────────────┬────────────┬──────────────────────────┐
│ Prefix          │ Next hop   │ মিলছে?                    │
├─────────────────┼────────────┼──────────────────────────┤
│ 10.0.5.0/24     │ Router A   │ ✓ 10.0.5.x → হ্যাঁ  (24)  │ ← জিতল
│ 10.0.0.0/16     │ Router B   │ ✓ 10.0.x.x → হ্যাঁ  (16)  │
│ 10.0.0.0/8      │ Router C   │ ✓ 10.x.x.x → হ্যাঁ  (8)   │
│ 0.0.0.0/0       │ Router D   │ ✓ যেকোনো কিছু      (0)    │
└─────────────────┴────────────┴──────────────────────────┘

চারটিই মিলছে। কিন্তু /24 সবচেয়ে নির্দিষ্ট → Router A জেতে।

Bit-এর ভাষায়:
  10.0.5.20  = 00001010.00000000.00000101.00010100
  /24 মানে প্রথম 24 bit মিলতে হবে  → সবচেয়ে কঠিন শর্ত
  /0  মানে ০টি bit মিলতে হবে       → সবচেয়ে সহজ শর্ত

  যে বেশি bit মিলিয়েছে, সে বেশি "জানে" ⇒ তার সিদ্ধান্ত নির্ভরযোগ্য
💡 কেন এই নিয়ম যুক্তিসঙ্গত

একটি /24 route মানে কেউ বলছে "আমি ঠিক এই ২৫৪টি address সম্পর্কে জানি"। একটি /0 route মানে "আমি কিছুই জানি না, সব আমাকে দাও"। স্বভাবতই নির্দিষ্ট জ্ঞান অস্পষ্ট অনুমানের চেয়ে ভালো।

এই একটি নিয়মই route aggregation-কে সম্ভব করে: একটি ISP 203.0.113.0/24 ঘোষণা করতে পারে, আর তার নিজের ভেতরে 203.0.113.64/26-এর জন্য আলাদা নিয়ম রাখতে পারে। বাইরের পৃথিবীর কাছে একটি লাইন, ভেতরে বিস্তারিত।

12.4 Routing table-এ ঢোকে কীভাবে

উৎসকীভাবেকোথায় ব্যবহৃত
Directly connectedInterface-এ IP দেওয়ামাত্র kernel নিজে যোগ করেসব জায়গায়
Static routeমানুষ হাতে লিখে দেয় (ip route add)ছোট network, বিশেষ ক্ষেত্র
DHCPDHCP server default gateway জানিয়ে দেয়client machine
IGP (OSPF, IS-IS)একটি প্রতিষ্ঠানের ভেতরের router-রা নিজেদের মধ্যে route বিনিময় করেenterprise, data center
BGPভিন্ন ভিন্ন প্রতিষ্ঠান (AS) নিজেদের মধ্যে route বিনিময় করেInternet-এর মেরুদণ্ড
ℹ️ এই বইয়ের সীমানা

OSPF ও BGP-র configuration এই বইয়ের বিষয় নয়। যা জানা দরকার তা হলো: routing table কেউ না কেউ পূরণ করে — হয় মানুষ (static), নয় protocol (OSPF/BGP)। Forwarding-এর প্রক্রিয়া (longest prefix match) দুই ক্ষেত্রেই অভিন্ন। BGP নিয়ে সংক্ষিপ্ত আলোচনা Chapter 42-এ।

12.5 Control Plane এবং Data Plane

একটি router-এর ভেতরে দুটি ভিন্ন জগৎ, এবং এই পার্থক্যটি আধুনিক networking-এ কেন্দ্রীয়:

┌───────────────────────────────────────────────────────┐
│  CONTROL PLANE  —  "কী করা উচিত?"                     │
│                                                       │
│  • BGP/OSPF-এর সাথে কথা বলে                            │
│  • Route হিসাব করে, সেরা পথ বাছে                       │
│  • Routing table (RIB) তৈরি করে                        │
│  • ধীর, জটিল, software-এ চলে (CPU)                     │
│  • সেকেন্ড/মিনিটের হিসাবে কাজ করে                       │
└──────────────────────┬────────────────────────────────┘
                       │ forwarding table (FIB) তৈরি করে দেয়
                       ▼
┌───────────────────────────────────────────────────────┐
│  DATA PLANE  —  "এই packet-টি এখন কোথায় পাঠাব?"        │
│                                                       │
│  • প্রতিটি packet-এর জন্য lookup                        │
│  • অত্যন্ত দ্রুত, প্রায়ই বিশেষ hardware-এ (ASIC/TCAM)   │
│  • ন্যানোসেকেন্ডের হিসাবে কাজ করে                        │
│  • কোটি কোটি packet প্রতি সেকেন্ডে                       │
└───────────────────────────────────────────────────────┘
⚙️ Developer-এর জন্য সমান্তরাল

এটি ঠিক সেই pattern যা আপনি application-এও ব্যবহার করেন: একটি ব্যয়বহুল হিসাব একবার করে ফলাফল cache-এ রাখা, তারপর প্রতিটি request-এ শুধু সেই cache পড়া। Control plane = cache তৈরি করা; data plane = cache থেকে পড়া। BGP-র হিসাব করতে সেকেন্ড লাগতে পারে, কিন্তু packet forward করতে ন্যানোসেকেন্ড — কারণ কঠিন কাজটা আগেই হয়ে গেছে।

12.6 একটি router-এর ভেতরে — ধাপে ধাপে

Router একটি packet নিয়ে যা করে

ধাপ ১ — Frame গ্রহণ ও যাচাই

NIC একটি frame পেল। Destination MAC কি router-এর নিজের? না হলে ফেলে দাও। FCS checksum ঠিক আছে? না হলে চুপচাপ ফেলে দাও। EtherType দেখে বুঝল ভেতরে IPv4।

ধাপ ২ — Ethernet header ফেলে দাও

Frame-এর মোড়ক এখন অপ্রয়োজনীয় — সেটি ছিল শুধু আগের hop থেকে এখানে আসার জন্য। এখন হাতে আছে খাঁটি IP packet।

ধাপ ৩ — TTL কমাও

TTL: 64 → 63

যদি TTL 0 হয়ে যায়:
  • packet ফেলে দাও
  • sender-কে ICMP "Time Exceeded" পাঠাও
  • (এই আচরণটিই traceroute-এর ভিত্তি → Ch 14)

TTL কমানোর কারণে IP header-এর checksum-ও নতুন করে হিসাব করতে হয়।

ধাপ ৪ — Forwarding table lookup

Destination IP: 10.0.5.20

FIB lookup (longest prefix match):
  10.0.5.0/24 → next hop 172.16.0.2, interface eth1  ✓

আধুনিক router-এ এটি TCAM-এ হয় — একটি বিশেষ memory
যা একসাথে সব entry-র সাথে মিলিয়ে দেখে, এক ধাপে।

ধাপ ৫ — নতুন Ethernet header তৈরি

পরের hop 172.16.0.2-এর MAC দরকার
  → ARP cache দেখো (না থাকলে ARP করো)

নতুন frame:
  dst MAC = 172.16.0.2-এর MAC     ← নতুন
  src MAC = eth1-এর নিজের MAC      ← নতুন
  dst IP  = 10.0.5.20              ← অপরিবর্তিত!
  src IP  = মূল sender             ← অপরিবর্তিত!

ধাপ ৬ — পাঠাও, এবং ভুলে যাও

Frame টি eth1 দিয়ে বেরিয়ে গেল। Router এই packet সম্পর্কে কিছুই মনে রাখল না — কোনো connection state নেই, কোনো session নেই। পরের packet এলে সে আবার শূন্য থেকে একই হিসাব করবে।

এই statelessness-ই IP-কে অসাধারণভাবে scalable করেছে। (NAT router এর ব্যতিক্রম — তাকে state রাখতেই হয়, এবং সেটাই NAT-এর জটিলতার মূল, Ch 34।)

12.7 Common Confusions

MYTH

Router পুরো পথটি জানে এবং packet-এর জন্য একটি route ঠিক করে দেয়।

REALITY

কোনো router পুরো পথ জানে না। প্রতিটি router শুধু পরের hop জানে। পথটি তৈরি হয় স্বতঃস্ফূর্তভাবে, অনেকগুলো স্বাধীন স্থানীয় সিদ্ধান্তের ফল হিসেবে। এমনকি একই connection-এর দুটি packet ভিন্ন পথে যেতে পারে (load balancing, route পরিবর্তন) — এবং এজন্যই packet উল্টো ক্রমে পৌঁছাতে পারে, যা TCP-কে সামলাতে হয় (Ch 19)।

MYTH

Packet যে পথে যায়, উত্তরও সেই পথেই ফেরে।

REALITY

মোটেও নয়। Forward path এবং return path সম্পূর্ণ ভিন্ন হতে পারে — একে বলে asymmetric routing, এবং Internet-এ এটি অত্যন্ত সাধারণ। কারণ প্রতিটি দিকের routing সিদ্ধান্ত আলাদাভাবে নেওয়া হয়, এবং ISP-দের business চুক্তি (peering vs transit) দুই দিকে আলাদা হতে পারে। এজন্যই traceroute শুধু একদিকের পথ দেখায়, এবং একদিকে সমস্যা থাকলেও অন্যদিক ঠিক থাকতে পারে।

🧪 Lab 12 — Longest prefix match নিজে পরীক্ষা করুন

আমরা কী দেখতে চাইছি? — একটি নির্দিষ্ট route যোগ করলে kernel-এর সিদ্ধান্ত বদলে যায় কিনা, অর্থাৎ longest prefix match বাস্তবে কাজ করছে কিনা।

bash
# এখন 1.1.1.1-এর জন্য kernel কী সিদ্ধান্ত নেয়?
ip route get 1.1.1.1
# → default route ব্যবহার করবে

# একটি বেশি নির্দিষ্ট route যোগ করুন (sudo লাগবে)
sudo ip route add 1.1.1.0/24 via 192.168.0.1 dev wlan0

# আবার জিজ্ঞেস করুন
ip route get 1.1.1.1
ip route get 1.1.2.1        # এটি /24-এর বাইরে

# পরিষ্কার করুন
sudo ip route del 1.1.1.0/24

যা লক্ষ্য করবেন: Route যোগ করার পরও gateway একই থাকতে পারে, কিন্তু ip route get এখন ভিন্ন route entry ব্যবহার করছে — এবং 1.1.2.1 (যা /24-এর বাইরে) এখনো default route ব্যবহার করছে। একটি ভিন্ন gateway IP দিয়ে চেষ্টা করলে পার্থক্যটি আরও স্পষ্ট হবে।

আমরা কী শিখলাম: Longest prefix match কোনো তাত্ত্বিক নিয়ম নয় — এটি প্রতিটি packet-এর জন্য আপনার kernel-এর চালানো প্রকৃত algorithm। আপনি নিজে route যোগ করে সেই সিদ্ধান্ত বদলে দিতে পারেন — এবং VPN, container runtime ও Kubernetes-এর CNI ঠিক এই কাজটিই করে।

📌 Chapter Summary
  • Routing hop-by-hop — কোনো router পুরো পথ জানে না, প্রত্যেকে শুধু "পরের জন কে" জানে।
  • Routing table entry = prefix + next hop + interface + metric।
  • Longest prefix match: সবচেয়ে নির্দিষ্ট (দীর্ঘতম prefix) route জেতে; 0.0.0.0/0 সবচেয়ে দুর্বল।
  • Route আসে: directly connected, static, DHCP, IGP (OSPF), বা BGP থেকে।
  • Control plane route হিসাব করে (ধীর, software); data plane packet forward করে (দ্রুত, hardware)।
  • Router প্রতিটি packet-এ TTL কমায়, Ethernet header নতুন করে লেখে, কিন্তু IP address ছোঁয় না।
  • IP forwarding stateless — router packet সম্পর্কে কিছু মনে রাখে না।
  • Forward ও return path ভিন্ন হতে পারে (asymmetric routing) — এটি স্বাভাবিক।

Destination 172.16.5.10। Table-এ আছে 172.16.0.0/16 → A, 172.16.5.0/24 → B, 0.0.0.0/0 → C। কোনটি ব্যবহৃত হবে?

B (172.16.5.0/24)। তিনটিই মেলে, কিন্তু /24 সবচেয়ে দীর্ঘ prefix — সবচেয়ে নির্দিষ্ট জ্ঞান। Longest prefix match অনুসারে সেটিই জেতে।

Router প্রতিটি packet-এ কী বদলায় এবং কী বদলায় না?

বদলায়: সম্পূর্ণ Ethernet header (নতুন src ও dst MAC), TTL (১ কমে), IP header checksum (TTL বদলানোর কারণে)।
বদলায় না: Source IP, Destination IP, TCP/UDP header, এবং সম্পূর্ণ payload। (ব্যতিক্রম NAT — সে IP ও port বদলায়, Ch 34।)

Control plane এবং data plane আলাদা রাখার সুবিধা কী?

দুটির কাজের ধরন ও গতির প্রয়োজন সম্পূর্ণ ভিন্ন। Route হিসাব করা জটিল ও অনিয়মিত — general-purpose CPU ও software দরকার। Packet forward করা সরল ও অত্যন্ত পুনরাবৃত্তিমূলক — বিশেষায়িত hardware (ASIC/TCAM) দিয়ে ন্যানোসেকেন্ডে করা যায়। আলাদা রাখলে দুটোই নিজের মতো optimize করা যায়, এবং control plane ব্যস্ত থাকলেও forwarding থামে না।

একটি HTTP response-এর packet গুলো কি সব একই পথে আসে?

অগত্যা নয়। Router-রা load balancing করতে পারে (ECMP), পথ পরিবর্তন হতে পারে, বা ভিন্ন ISP-র মধ্য দিয়ে যেতে পারে। ফলে packet ভিন্ন ভিন্ন বিলম্বে এবং উল্টো ক্রমে পৌঁছাতে পারে। এই বিশৃঙ্খলা সামলানোই TCP-এর sequence number-এর কাজ (Ch 19)। (বাস্তবে ECMP সাধারণত একই flow-এর packet একই পথে রাখে hash করে — ঠিক এই কারণেই।)
