Chapter 4

Bits, Bytes, Frames, Packets, and Segments

Networking-এর terminology নতুনদের কাছে এলোমেলো মনে হয় কারণ একই জিনিসের পাঁচটি নাম। আসলে নাম গুলো এলোমেলো নয় — প্রতিটি নাম বলে দেয় আপনি এই মুহূর্তে কোন layer-এর দৃষ্টিকোণ থেকে তাকাচ্ছেন।

4.1 Why does this exist?

একটি HTTP request তারের ভেতর দিয়ে যাওয়ার সময় সেটি একই সাথে:

  • একটি message (application-এর চোখে),
  • একটি segment (TCP-এর চোখে),
  • একটি packet (IP-এর চোখে),
  • একটি frame (Ethernet-এর চোখে),
  • এবং একগুচ্ছ bit (তারের চোখে)।

পাঁচটি নাম কারণ পাঁচটি layer, এবং প্রতিটি layer তার নিজের header যোগ করার পরে জিনিসটাকে নিজের নামে ডাকে। নামটি বলে দেয় কোন header গুলো এই মুহূর্তে জোড়া আছে।

💡 Why এই নামগুলো গুরুত্বপূর্ণ

যখন কেউ বলে "packet loss হচ্ছে" — সে Layer 3-এর কথা বলছে। "Frame error" মানে Layer 2, সাধারণত cable বা NIC-এর সমস্যা। "Segment retransmission" মানে TCP-এর ব্যাপার। ভুল শব্দ ব্যবহার করলে ভুল জায়গায় debugging শুরু হয়। শব্দগুলোর মধ্যে দিয়েই আসলে layer-এর ধারণা ঢুকে যায়।

4.2 নিচ থেকে উপরে — প্রতিটি একক

এককLayerকী থাকেকে এটি নিয়ে কাজ করে
BitPhysicalএকটি 0 বা 1 — voltage, আলোর pulse, radio stateতার, NIC-এর transceiver
Byte / Octet—৮টি bit। Networking RFC-তে "octet" বলা হয় (কিছু পুরনো architecture-এ byte ≠ ৮ bit ছিল)সব layer
FrameLink (L2)Ethernet/Wi-Fi header + payload + FCS। MAC address এখানে।NIC, switch
PacketNetwork (L3)IP header + payload। IP address, TTL এখানে।Router, host-এর IP stack
SegmentTransport (L4)TCP header + data। Port, sequence, ACK এখানে।শুধু দুই প্রান্তের kernel
DatagramL4 (UDP) বা L3UDP header + data। "স্বয়ংসম্পূর্ণ, স্বাধীন" বোঝাতে ব্যবহৃত।UDP stack
MessageApplication (L7)একটি সম্পূর্ণ HTTP request, একটি JSON body, একটি DNS queryআপনার code
ℹ️ "Datagram" শব্দটি নিয়ে বিভ্রান্তি

"Datagram" শব্দের মানে হলো — একটি স্বয়ংসম্পূর্ণ, স্বাধীন একক, যার delivery-র কোনো নিশ্চয়তা নেই এবং যে অন্যদের সাথে সম্পর্কহীন। তাই এটি দুই জায়গায় ব্যবহৃত হয়: UDP datagram (L4) এবং IP datagram (L3, যেটাকে আমরা সাধারণত packet বলি)। প্রসঙ্গ থেকে বুঝে নিতে হয়। মূল কথা — শব্দটি "সংযোগহীন ও অনিশ্চিত" এই বৈশিষ্ট্যটাই বোঝাচ্ছে, TCP segment-এর ঠিক উল্টো।

4.3 একটি end-to-end উদাহরণ

ধরা যাক আপনার code লিখল:

js
socket.write("Hello, World!");   // 13 bytes

এবার প্রতিটি স্তরে এই ১৩টি byte-এর কী নাম, এবং মোট আকার কত:

┌─ APPLICATION ─────────────────────────────────────────────┐
│  MESSAGE: "Hello, World!"                     13 bytes    │
└───────────────────────────────────────────────────────────┘
                          ↓ socket.write() → kernel buffer
┌─ TRANSPORT (TCP) ─────────────────────────────────────────┐
│  SEGMENT                                      33 bytes    │
│  ┌──────────────────┬──────────────────┐                  │
│  │ TCP Header 20 B  │ "Hello, World!"  │                  │
│  │ srcPort: 51234   │                  │                  │
│  │ dstPort: 8080    │                  │                  │
│  │ seq: 1001        │                  │                  │
│  └──────────────────┴──────────────────┘                  │
└───────────────────────────────────────────────────────────┘
                          ↓
┌─ NETWORK (IP) ────────────────────────────────────────────┐
│  PACKET                                       53 bytes    │
│  ┌─────────────────┬─────────────────────────┐            │
│  │ IP Header 20 B  │      SEGMENT 33 B       │            │
│  │ src: 192.168.1.5│                         │            │
│  │ dst: 93.184.x.x │                         │            │
│  │ ttl: 64         │                         │            │
│  │ proto: 6 (TCP)  │                         │            │
│  └─────────────────┴─────────────────────────┘            │
└───────────────────────────────────────────────────────────┘
                          ↓
┌─ LINK (Ethernet) ─────────────────────────────────────────┐
│  FRAME                                        71 bytes    │
│  ┌──────────────┬──────────────────┬─────┐                │
│  │ Eth Hdr 14 B │   PACKET 53 B    │FCS 4│                │
│  │ dst: gateway │                  │     │                │
│  │      MAC     │                  │     │                │
│  │ src: my MAC  │                  │     │                │
│  └──────────────┴──────────────────┴─────┘                │
│  (Ethernet-এর সর্বনিম্ন 64 B — এখানে পূরণ হয়েছে)            │
└───────────────────────────────────────────────────────────┘
                          ↓
┌─ PHYSICAL ────────────────────────────────────────────────┐
│  BITS: 71 × 8 = 568 bits                                  │
│  0101101000110101110100101101...                          │
└───────────────────────────────────────────────────────────┘

আপনার data:  13 bytes
তারে গেল:    71 bytes
Overhead:    58 bytes (82%!)
⚙️ Developer Perspective

এই ৮২% overhead-এর হিসাবটাই ব্যাখ্যা করে কেন chatty protocol ধীর। আপনি যদি একটি loop-এ ১০০০ বার socket.write() করে ১৩ bytes করে পাঠান, তারে যাবে ৭১ KB — অথচ data মাত্র ১৩ KB। একবারে buffer করে পাঠালে যেত প্রায় ১৩.৩ KB। এটাই buffering এবং batching-এর মূল যুক্তি — শুধু syscall বাঁচানো নয়, header overhead বাঁচানোও।

4.4 TCP-এর ক্ষেত্রে একটি সূক্ষ্ম কিন্তু গুরুত্বপূর্ণ কথা

উপরের ছবিটি একটি ভুল ধারণা দিতে পারে — যেন আপনার একটি write() সমান একটি segment। এটি সত্য নয়, এবং এই ভুল বোঝাবুঝি বাস্তবে বহু bug-এর কারণ।

TCP হলো একটি byte stream, message stream নয়। Kernel আপনার লেখা bytes-গুলো একটি buffer-এ জমা করে এবং নিজের সুবিধামতো সেগুলো segment-এ ভাগ করে:

আপনি লিখলেন:
    write("Hello, ")      7 bytes
    write("World!")       6 bytes
    write("How are you?") 12 bytes

Network-এ যেতে পারে:
    Segment 1: "Hello, World!How ar"     ← তিনটি write একসাথে, কাটা পড়েছে
    Segment 2: "e you?"

Receiver-এ read() দিতে পারে:
    read() → "Hello, Wor"               ← যা পাওয়া গেছে তাই
    read() → "ld!How are you?"
⚠️ সবচেয়ে সাধারণ networking bug

নতুন developer-রা ধরে নেন একটি write()-এর বিপরীতে একটি read() ঠিক সেই bytes ফেরত দেবে। TCP-তে এই নিশ্চয়তা নেই। TCP শুধু নিশ্চয়তা দেয়: bytes গুলো সঠিক ক্রমে, একটিও না হারিয়ে পৌঁছাবে — কিন্তু কোন read()-এ কতটুকু আসবে তার কোনো নিশ্চয়তা নেই।

এজন্যই প্রতিটি TCP-ভিত্তিক protocol-কে নিজের message framing ঠিক করতে হয়: HTTP ব্যবহার করে Content-Length বা chunked encoding; অনেক binary protocol প্রতিটি message-এর আগে ৪-byte length লেখে; কিছু protocol delimiter (\n) ব্যবহার করে। UDP-তে এই সমস্যা নেই — সেখানে একটি datagram মানেই একটি সম্পূর্ণ message (Ch 23)।

4.5 Bandwidth-এর একক নিয়ে সতর্কতা

Networking-এ প্রায় সব কিছু bit-এ মাপা হয়, কিন্তু file-এর আকার byte-এ। এটি ধারাবাহিক বিভ্রান্তির উৎস।

100 Mbps  =  100 megabits per second       ← ISP এভাবে বিজ্ঞাপন দেয়
          =  100 / 8 = 12.5 MB/s           ← download manager এভাবে দেখায়

তাই "100 Mbps" line-এ 1 GB file নামাতে:
    1024 MB ÷ 12.5 MB/s ≈ 82 সেকেন্ড (তাত্ত্বিক সর্বোচ্চ)

বাস্তবে protocol overhead-এর কারণে ~90-94% পাওয়া যায় → ~90 সেকেন্ড

লিখিত রূপে পার্থক্যটি ছোট হাতের/বড় হাতের 'b'-তে: Mb = megabit, MB = megabyte। Mbps vs MB/s — আট গুণ পার্থক্য।

🧪 Lab 4 — Frame-এর আকার নিজে দেখুন

আমরা কী দেখতে চাইছি? — একই application data ভিন্ন ভিন্ন আকারের frame তৈরি করে, এবং header overhead বাস্তবে কতটা।

bash
# ছোট packet: ICMP ping, 1 byte payload
ping -c 1 -s 1 1.1.1.1

# বড় packet: 1400 bytes payload
ping -c 1 -s 1400 1.1.1.1

যা লক্ষ্য করবেন: ping output বলে 9 bytes from ... এবং 1408 bytes from ...। খেয়াল করুন: আপনি -s 1 দিলেন, ping দেখাল ৯ bytes — কারণ ৮ bytes ICMP header যুক্ত হয়েছে। আর এই ৯ bytes-এর সাথে ২০ bytes IP header এবং ১৪+৪ bytes Ethernet যুক্ত হয়ে তারে যাচ্ছে ~৪৭ bytes (padding সহ ৬৪)। ১ byte পাঠাতে ৬৪ bytes।

আমরা কী শিখলাম: Header overhead কোনো তাত্ত্বিক ব্যাপার নয় — ছোট payload-এ এটি data-র চেয়ে বহু গুণ বড়। বড় payload-এ overhead-এর অনুপাত নগণ্য (1400-এ ~4%)। এটিই MTU-এর গুরুত্বের ভিত্তি, যা পরের chapter-এর বিষয়।

📌 Chapter Summary
  • একই data-এর পাঁচটি নাম কারণ পাঁচটি layer — নামটি বলে দেয় কোন header গুলো যুক্ত।
  • Bit → Byte → Segment (L4) → Packet (L3) → Frame (L2) → Bits (L1)।
  • "Datagram" মানে স্বয়ংসম্পূর্ণ ও অনিশ্চিত একক — UDP এবং IP দুই জায়গাতেই ব্যবহৃত।
  • TCP একটি byte stream — এক write() ≠ এক read()। Message framing application-এর দায়িত্ব।
  • Bandwidth bit-এ (Mbps), file byte-এ (MB) — ৮ গুণ পার্থক্য।
✓ Quick Check
একই HTTP request-কে কখন packet এবং কখন frame বলা উচিত?

IP header যুক্ত হওয়ার পর এবং Ethernet header যুক্ত হওয়ার আগে সেটি packet। Ethernet header ও FCS যুক্ত হওয়ার পর সেটি frame। অর্থাৎ frame হলো packet-এর মোড়ক। Router-এর সিদ্ধান্ত নিয়ে কথা বললে "packet", cable/switch/NIC নিয়ে কথা বললে "frame"।

আপনার server তিনবার write() করল। Client কি ঠিক তিনবার read()-এ সেই তিনটি অংশ পাবে?

না — এটি TCP-তে সম্পূর্ণ অনিশ্চিত। TCP byte stream; kernel আপনার write গুলো জোড়া লাগাতে বা ভাগ করতে পারে। Client এক read()-এ তিনটাই পেতে পারে, বা পাঁচ read()-এ ভাঙা অবস্থায় পেতে পারে। তাই application-কে নিজেই message-এর সীমানা নির্ধারণ করতে হয় (length prefix, delimiter, বা Content-Length)।

একটি 50 Mbps connection-এ 500 MB file নামাতে তাত্ত্বিকভাবে কত সময় লাগে?

50 Mbps = 50/8 = 6.25 MB/s। 500 MB ÷ 6.25 MB/s = 80 সেকেন্ড। বাস্তবে protocol overhead ও TCP-এর ramp-up-এর কারণে কিছুটা বেশি — সাধারণত ৮৫–৯৫ সেকেন্ড।

কেন UDP-তে message framing-এর সমস্যা নেই?

কারণ UDP datagram-ভিত্তিক, stream নয়। আপনি একটি sendto()-তে যত bytes দেবেন, receiver ঠিক একটি recvfrom()-এ সেই পুরো datagram-টিই পাবে (বা কিছুই পাবে না — কারণ datagram হারাতে পারে)। সীমানা সংরক্ষিত থাকে। বিনিময়ে আপনি reliability হারান।
