Chapter 25

Why DNS Exists

DNS-কে প্রায়ই "Internet-এর ফোনবুক" বলা হয়। উপমাটি ভুল নয়, কিন্তু এটি DNS-এর সবচেয়ে আকর্ষণীয় দিকটি লুকিয়ে ফেলে — কোনো কেন্দ্রীয় ফোনবুক নেই, এবং সেটাই মূল নকশা।

25.1 Why does this exist?

মানুষ মনে রাখে:      example.com
                     github.com
                     আমার-কোম্পানি.com

Machine-এর দরকার:   93.184.215.14
                     140.82.121.4
                     2606:2800:21f:cb07:6820:80da:af6b:8b2c

এই দুটোর মাঝে একটি অনুবাদ ব্যবস্থা দরকার।

এখানেই থামলে বিষয়টি তুচ্ছ মনে হয় — একটি lookup table। কিন্তু সমস্যাটি আসলে অনেক গভীর:

💡 প্রকৃত সমস্যাগুলো
  • IP address বদলায়। Server migrate হয়, hosting provider বদলায়, IP পুনর্বণ্টিত হয়। নাম স্থির থাকে — এই স্থিতিশীলতাই DNS-এর প্রধান মূল্য।
  • একটি নামের একাধিক IP। Load balancing, geographic routing, redundancy — সবই একটি নামের পেছনে বহু server।
  • Scale। কয়েক শ কোটি নাম, প্রতি সেকেন্ডে কোটি কোটি query।
  • বণ্টিত নিয়ন্ত্রণ। example.com-এর ভেতরে কী থাকবে তা example.com-এর মালিক ঠিক করবে — কোনো কেন্দ্রীয় কর্তৃপক্ষ নয়।
  • একক ব্যর্থতা-বিন্দু না থাকা। একটি কেন্দ্রীয় server হলে সেটি বন্ধ হলে পুরো Internet অচল হতো।

25.2 ইতিহাস — HOSTS.TXT-এর মৃত্যু

১৯৭০-৮০ দশক: ARPANET-এ কয়েকশ computer

  Stanford-এর একটি machine-এ একটি ফাইল: HOSTS.TXT
  10.0.0.1    mit-machine
  10.0.0.2    stanford-lab
  10.0.0.3    ucla-node

  প্রতিটি site সপ্তাহে একবার FTP দিয়ে এটি নামাত।

সমস্যা যখন network বাড়ল:
  ✗ ফাইলটি বিশাল হয়ে গেল
  ✗ সবাই একই server থেকে নামাচ্ছে → bottleneck
  ✗ নতুন host যোগ হলে সবার update-এর অপেক্ষা
  ✗ নামের সংঘাত — দুজন একই নাম চাইলে?
  ✗ একটি ফাইল, একটি কর্তৃপক্ষ — scale করে না

১৯৮৩ — Paul Mockapetris DNS design করলেন।
মূল ধারণা: কেন্দ্রীভূত করো না, বরং
             শ্রেণিবদ্ধভাবে দায়িত্ব বণ্টন করো।
ℹ️ HOSTS.TXT আজও আছে

আপনার machine-এ /etc/hosts (Windows-এ C:\Windows\System32\drivers\etc\hosts) সেই ফাইলটিরই উত্তরাধিকারী। DNS query করার আগে OS এই ফাইলটি দেখে। এজন্যই local development-এ এটি এত কার্যকর:

text
127.0.0.1    api.myapp.local
127.0.0.1    dashboard.myapp.local
10.0.0.50    staging-db

এখানে একটি entry থাকলে DNS-এ কখনো query-ই যাবে না। Debugging-এর সময় মনে রাখবেন — "DNS ভুল উত্তর দিচ্ছে" মনে হলে প্রথমে /etc/hosts দেখুন।

25.3 Domain Name-এর শ্রেণিবিন্যাস

            www.api.example.com.
             │   │      │     │ │
             │   │      │     │ └─ root (অদৃশ্য বিন্দু)
             │   │      │     └─── TLD (Top Level Domain)
             │   │      └───────── Second Level Domain
             │   └──────────────── Subdomain
             └──────────────────── Subdomain / host

পড়তে হয় ★ ডান থেকে বামে ★ — এটিই মূল কথা:

                    . (root)
                    │
        ┌───────────┼───────────┬────────┐
       com         org          net      bd
        │           │            │        │
   ┌────┼────┐      │            │     ┌──┴──┐
example github  wikipedia      ...    com   edu
   │       │
   │    ┌──┴──┐
  www   api  gist


প্রতিটি স্তর নিচের স্তরের দায়িত্ব "অর্পণ" (delegate) করে:

  root বলে      : ".com-এর জন্য Verisign-এর server-এ যাও"
  .com বলে      : "example.com-এর জন্য ns1.example.com-এ যাও"
  example.com   : "api.example.com এর IP হলো 1.2.3.4"

★ কেউ সবকিছু জানে না। প্রত্যেকে জানে
  "পরের ধাপে কার কাছে যেতে হবে।"
🧠 Mental Model — চেনা প্যাটার্ন

এই "কেউ সব জানে না, প্রত্যেকে পরের ধাপ জানে" কাঠামোটি চেনা লাগছে? এটি ঠিক routing-এর মতো (Ch 12)। Router জানে না পুরো পথ, শুধু next hop জানে। DNS server জানে না চূড়ান্ত উত্তর, শুধু জানে পরে কাকে জিজ্ঞেস করতে হবে।

Delegation এবং hierarchy — এই দুটি নকশা-নীতি বারবার ফিরে আসছে, কারণ এগুলোই বৈশ্বিক scale-এ কাজ করে। কেন্দ্রীভূত কিছু এত বড় হতে পারে না।

25.4 DNS কী কী সমাধান করে

সমস্যাDNS-এর সমাধান
মানুষ IP মনে রাখতে পারে নানাম → IP অনুবাদ
Server-এর IP বদলায়নাম অপরিবর্তিত রেখে record-এ নতুন IP
একটি service, বহু serverএকাধিক A record, বা geo-ভিত্তিক ভিন্ন উত্তর
Failover দরকারTTL কমিয়ে দ্রুত অন্য IP-তে সরানো
Global scaleHierarchy + delegation + caching
IPv6-এ রূপান্তরএকই নামে A (IPv4) ও AAAA (IPv6) record
Email routingMX record
Service discoverySRV record (Kubernetes-এ ব্যাপকভাবে ব্যবহৃত)
⚙️ Developer Perspective — DNS একটি নিয়ন্ত্রণ-ব্যবস্থা

DNS শুধু অনুবাদ নয় — এটি traffic নিয়ন্ত্রণের একটি স্তর:

  • Blue-green deployment: DNS record নতুন environment-এ ঘুরিয়ে দিন।
  • CDN: আপনার ভৌগোলিক অবস্থান অনুযায়ী DNS ভিন্ন IP ফেরত দেয় (Ch 46)।
  • Failover: Health check ব্যর্থ হলে DNS provider স্বয়ংক্রিয়ভাবে অন্য IP দেয়।
  • Kubernetes: ভেতরে my-service.default.svc.cluster.local — সম্পূর্ণ DNS-ভিত্তিক service discovery।

কিন্তু সতর্কতা: DNS-ভিত্তিক failover তাৎক্ষণিক নয়, কারণ TTL। ৩০০ সেকেন্ড TTL মানে পুরনো IP ৫ মিনিট পর্যন্ত cache-এ থাকতে পারে — এবং কিছু client TTL সম্পূর্ণ উপেক্ষা করে (Java-র পুরনো default ছিল চিরকালীন cache)। দ্রুত failover-এর জন্য load balancer বা anycast বেশি নির্ভরযোগ্য।

📌 Chapter Summary
  • DNS নাম ও IP-র মধ্যে একটি স্তর তৈরি করে — IP বদলালেও নাম অপরিবর্তিত থাকে।
  • HOSTS.TXT-এর কেন্দ্রীভূত মডেল scale করেনি; DNS তার বদলে hierarchy ও delegation ব্যবহার করে।
  • Domain name পড়তে হয় ডান থেকে বামে: root → TLD → domain → subdomain।
  • প্রতিটি স্তর পরের স্তরের দায়িত্ব অর্পণ করে — কেউ সম্পূর্ণ তথ্য রাখে না।
  • /etc/hosts DNS-এর আগে দেখা হয় — local development ও debugging-এ কার্যকর।
  • DNS একটি traffic নিয়ন্ত্রণ-স্তরও — deployment, CDN, failover, service discovery-তে ব্যবহৃত।
✓ Quick Check
DNS কেন একটি কেন্দ্রীয় database নয়?

(১) Scale — কয়েক শ কোটি নাম ও প্রতি সেকেন্ডে কোটি কোটি query একটি system সামলাতে পারত না। (২) একক ব্যর্থতা-বিন্দু — সেটি বন্ধ হলে পুরো Internet অচল হতো। (৩) নিয়ন্ত্রণ — প্রতিটি প্রতিষ্ঠান নিজের domain-এর ভেতরের record নিজে নিয়ন্ত্রণ করতে চায়, কোনো কেন্দ্রীয় কর্তৃপক্ষের অনুমতি ছাড়া। Hierarchy + delegation তিনটিরই সমাধান।

www.api.example.com-এ কোন অংশটি TLD এবং কে এটি নিয়ন্ত্রণ করে?

TLD হলো com। এটি নিয়ন্ত্রণ করে Verisign (ICANN-এর তত্ত্বাবধানে)। example.com নিবন্ধিত হয় একটি registrar-এর মাধ্যমে, এবং তারপর api.example.com ও www.api.example.com সম্পূর্ণভাবে example.com-এর মালিকের নিয়ন্ত্রণে — নতুন subdomain তৈরি করতে কারো অনুমতি লাগে না।

Domain name ডান থেকে বামে পড়া হয় কেন?

কারণ শ্রেণিবিন্যাসটি ডান থেকে শুরু হয়। সবচেয়ে ডানে root (অদৃশ্য .), তারপর TLD, তারপর ক্রমে সংকীর্ণ হতে থাকে। Resolution-ও এই ক্রমেই ঘটে: প্রথমে root-কে জিজ্ঞেস, তারপর TLD, তারপর domain। এটি ফাইল path-এর উল্টো (/usr/local/bin বাম থেকে সংকীর্ণ হয়) — যা প্রথমে বিভ্রান্তিকর লাগতে পারে।
