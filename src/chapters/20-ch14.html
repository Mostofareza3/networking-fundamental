Chapter 14

ICMP — Network-এর নিজস্ব বার্তাবাহক

IP নিজে কিছু বলে না — সে শুধু packet পাঠায়, আর কিছু ভুল হলে চুপচাপ ফেলে দেয়। ICMP হলো সেই protocol যা এই নীরবতা ভাঙে এবং জানায় "কী ভুল হলো"। ping এবং traceroute — দুটোই এর উপর দাঁড়িয়ে।

14.1 Why does this exist?

IP-এর নকশা "best effort" — সে চেষ্টা করে, কিন্তু নিশ্চয়তা দেয় না। Packet হারালে IP কিছু বলে না। কিন্তু বাস্তবে কিছু তথ্য জানা অপরিহার্য:

  • "গন্তব্যে পৌঁছানো যাচ্ছে না" — নাহলে sender চিরকাল অপেক্ষা করত
  • "Packet খুব বড়, ভাঙতে হবে" — PMTUD এর উপর নির্ভরশীল (Ch 5)
  • "TTL শেষ হয়ে গেছে" — routing loop শনাক্ত করতে
  • "তুমি কি বেঁচে আছ?" — সংযোগ পরীক্ষা করতে
💡 Why একটি আলাদা protocol

ICMP (Internet Control Message Protocol) হলো IP-এর নিয়ন্ত্রণ ও ত্রুটি-বার্তার ব্যবস্থা। এটি IP-এর ভেতরে বহন করা হয় (protocol number 1), কিন্তু এটি কোনো transport protocol নয় — এতে port নেই, connection নেই, application data নেই। এটি network-এর নিজের সাথে নিজের কথা বলা।

একটি গুরুত্বপূর্ণ সূক্ষ্মতা: ICMP নির্ভরযোগ্য নয় এবং বাধ্যতামূলক নয়। একটি router চাইলে ICMP পাঠানো বন্ধ করে দিতে পারে। এজন্যই ICMP-র উপর ভিত্তি করে সিদ্ধান্ত নেওয়ার সময় সতর্ক থাকতে হয়।

ℹ️ TCP-র ক্ষেত্রে ICMP লাগে না

একটি বন্ধ TCP port-এ connect করলে আপনি ICMP পান না — আপনি পান একটি TCP RST packet, যা TCP-র নিজস্ব ব্যবস্থা। কিন্তু UDP-তে কোনো connection বা RST নেই, তাই বন্ধ UDP port-এর খবর দিতে ICMP Port Unreachable ব্যবহৃত হয়। এই পার্থক্যটি মনে রাখলে connection refused vs timeout-এর ব্যাখ্যা পরিষ্কার হয়।

✓ ping-এর output যেভাবে পড়বেন
  • icmp_seq এড়িয়ে যাওয়া (1,2,4 — 3 নেই) = packet loss
  • time-এর বড় ওঠানামা (10ms, 200ms, 15ms) = jitter, সাধারণত congestion বা wireless সমস্যা
  • ttl থেকে hop সংখ্যা অনুমান
  • mdev (mean deviation) = কতটা অস্থির — real-time application-এর জন্য এটি গুরুত্বপূর্ণ
  • DUP! লেখা থাকলে duplicate packet — সাধারণত routing loop বা ভুল configure করা network

14.4 traceroute — TTL-এর চতুর ব্যবহার

Traceroute-এর কৌশলটি অসাধারণ সরল: ইচ্ছাকৃতভাবে TTL কম দিয়ে packet পাঠাও, এবং যে router অভিযোগ করে তার ঠিকানা নোট করো।

Round 1 — TTL = 1
  Host ──[TTL=1]──▶ R1
                    R1: TTL 1→0! ফেলে দাও।
  Host ◀──[ICMP Time Exceeded, from 192.168.1.1]── R1
  ⇒ Hop 1 = 192.168.1.1

Round 2 — TTL = 2
  Host ──[TTL=2]──▶ R1 (2→1, ঠিক আছে) ──▶ R2
                                          R2: 1→0! ফেলে দাও।
  Host ◀──[ICMP Time Exceeded, from 10.1.0.1]────── R2
  ⇒ Hop 2 = 10.1.0.1

Round 3 — TTL = 3
  ... একইভাবে R3-এর ঠিকানা পাওয়া গেল

Round N — TTL যথেষ্ট বড়
  Packet গন্তব্যে পৌঁছাল।
  গন্তব্য উত্তর দেয় Echo Reply (ICMP মোডে) বা
  ICMP Port Unreachable (UDP মোডে — কারণ traceroute
  ইচ্ছাকৃতভাবে একটি অব্যবহৃত উঁচু port-এ পাঠায়)
  ⇒ যাত্রা শেষ

⚠️ * * * মানে কী নয়

* * * দেখলে অনেকে ভাবেন "এখানে packet আটকে গেছে"। এটি প্রায় সবসময় ভুল ব্যাখ্যা। এর মানে হলো ওই hop-এর router ICMP Time Exceeded পাঠায়নি — কারণ:

  • সে ICMP পাঠানো বন্ধ করে রেখেছে (নিরাপত্তা নীতি, খুব সাধারণ),
  • বা তার ICMP তৈরির হার সীমিত (rate limiting),
  • বা কোনো firewall মাঝপথে ICMP আটকাচ্ছে।

মাঝখানে * * * থাকলেও শেষ লাইনে গন্তব্য দেখা গেলে পথটি ঠিকই কাজ করছে। traffic দিব্যি যাচ্ছে, শুধু ওই router নিজের পরিচয় দিতে রাজি নয়।

ℹ️ traceroute-এর সীমাবদ্ধতা
  • শুধু একদিকের পথ দেখায়। ফেরার পথ সম্পূর্ণ ভিন্ন হতে পারে (asymmetric routing, Ch 12)। একটি hop-এ বেশি latency দেখলে সেটি ওই hop-এর সমস্যা নাও হতে পারে — ফেরার পথের সমস্যা হতে পারে।
  • Router-রা নিজেদের উদ্দেশ্যে আসা packet-কে কম অগ্রাধিকার দেয়। তাই মাঝের একটি hop-এ ২০০ms দেখেও পরের hop-এ ৫০ms হতে পারে — এটি স্বাভাবিক, এবং এর মানে ওই router ব্যস্ত, পথটি ধীর নয়।
  • Load balancing-এর কারণে প্রতিটি probe ভিন্ন পথে যেতে পারে। mtr (my traceroute) এই সমস্যাগুলো ভালোভাবে সামলায়।

14.5 Developer Perspective

⚙️ ICMP আর application-এর সম্পর্ক

ping কাজ করে কিন্তু website খোলে না — খুবই সাধারণ পরিস্থিতি, এবং এতে অবাক হওয়ার কিছু নেই। ping পরীক্ষা করে Layer 3 (host পৌঁছানো যায় কিনা)। Website-এর জন্য দরকার Layer 4 (port 443 খোলা) এবং Layer 7 (server চলছে ও সাড়া দিচ্ছে)। Host সচল থাকতেই পারে যখন nginx বন্ধ।

উল্টোটাও সত্য — website খোলে কিন্তু ping যায় না। কারণ বহু server ও CDN নীতিগতভাবে ICMP Echo-র উত্তর দেয় না, অথচ TCP 443 দিব্যি খোলা। ping ব্যর্থ হওয়া মানেই host down নয়।

তাই আধুনিক health check-এ ICMP ping-এর বদলে প্রকৃত protocol-level check ব্যবহার করা হয়: curl -sf https://host/health — কারণ এটিই আসল প্রশ্নের উত্তর দেয়: "service টি কাজ করছে কি?"

🧪 Lab 14 — ICMP-র তিনটি রূপ দেখুন

আমরা কী দেখতে চাইছি? — Echo, Time Exceeded এবং Port Unreachable — তিন ধরনের ICMP বার্তা বাস্তবে তৈরি করে দেখা।

bash
# Terminal 1 — সব ICMP দেখুন
sudo tcpdump -i any -n icmp

# Terminal 2 — তিনটি পরীক্ষা:

# 1. Echo request/reply
ping -c 2 1.1.1.1

# 2. Time Exceeded (TTL ইচ্ছাকৃতভাবে কম)
ping -c 1 -t 1 1.1.1.1

# 3. Port Unreachable (একটি বন্ধ UDP port-এ পাঠান)
echo "test" | nc -u -w1 127.0.0.1 9999

# 4. পুরো পথ
traceroute -n 1.1.1.1

যা লক্ষ্য করবেন: tcpdump-এ দেখবেন ICMP echo request / echo reply জোড়ায় জোড়ায়। -t 1-এ দেখবেন ICMP time exceeded in-transit এবং সেই বার্তা পাঠানো router-এর IP। UDP-র ক্ষেত্রে ICMP udp port 9999 unreachable। Traceroute চালালে পরপর অনেকগুলো time exceeded বার্তা দেখবেন — প্রতিটি ভিন্ন router থেকে।

আমরা কী শিখলাম: ICMP কোনো আলাদা "diagnostic tool" নয় — এটি network-এর স্বাভাবিক কাজের অংশ, প্রতিনিয়ত ঘটছে। ping এবং traceroute নতুন কিছু আবিষ্কার করে না, তারা শুধু এই বিদ্যমান আচরণকে চতুরভাবে কাজে লাগায়।

📌 Chapter Summary
  • ICMP হলো IP-এর নিয়ন্ত্রণ ও ত্রুটি-বার্তার protocol — port নেই, connection নেই।
  • ping = Echo Request/Reply; kernel সরাসরি উত্তর দেয়, কোনো application লাগে না।
  • traceroute = ক্রমবর্ধমান TTL দিয়ে ইচ্ছাকৃতভাবে প্রতিটি router-কে অভিযোগ করানো।
  • * * * মানে ওই router ICMP পাঠায় না — পথ ভাঙা নয়।
  • ICMP Fragmentation Needed ছাড়া PMTUD ভেঙে পড়ে — তাই ICMP পুরোপুরি block করা ক্ষতিকর।
  • TCP-তে বন্ধ port-এর উত্তর RST; UDP-তে ICMP Port Unreachable।
  • ping ব্যর্থ ≠ host down; ping সফল ≠ service কাজ করছে। ping শুধু Layer 3 পরীক্ষা করে।
✓ Quick Check
traceroute-এর মূল কৌশলটি এক বাক্যে ব্যাখ্যা করুন।

TTL = 1, 2, 3... করে ক্রমাগত packet পাঠানো হয়; প্রতিটি TTL মান ঠিক ততটি hop পরে শূন্য হয়ে যায়, ফলে ওই hop-এর router ICMP Time Exceeded পাঠায় এবং সেই বার্তার source IP থেকেই router-টির পরিচয় পাওয়া যায়।

একটি site-এ ping যাচ্ছে না কিন্তু browser-এ খুলছে। ব্যাখ্যা করুন।

Server বা পথের কোনো firewall ICMP Echo Request-এর উত্তর দেওয়া বন্ধ রেখেছে — এটি খুবই সাধারণ নীতি (Cloudflare, AWS ALB ইত্যাদিতে প্রায়ই default)। কিন্তু TCP port 443 খোলা এবং web server চলছে, তাই HTTPS দিব্যি কাজ করছে। ping পরীক্ষা করে ICMP-র প্রাপ্যতা, service-এর নয়।

traceroute-এর ৫ নম্বর hop-এ ৩০০ms দেখাচ্ছে, কিন্তু ১২ নম্বর hop-এ ৮০ms। এটা কীভাবে সম্ভব?

সম্পূর্ণ স্বাভাবিক। ৫ নম্বর router-টি নিজের উদ্দেশ্যে আসা packet (TTL expiry) কম অগ্রাধিকারে process করে — ICMP তৈরি করা তার control plane-এর কাজ, যা ধীর। কিন্তু মধ্য দিয়ে যাওয়া packet সে hardware-এ (data plane) দ্রুত forward করে। তাই তার ICMP-র বিলম্ব প্রকৃত forwarding-এর বিলম্বের প্রতিনিধিত্ব করে না। এছাড়া ফেরার পথ ভিন্ন হওয়াও একটি কারণ হতে পারে।

ICMP সম্পূর্ণ block করলে কী কী ভাঙে?

(১) PMTUD ভেঙে পড়ে — বড় packet নীরবে হারায়, "ছোট request কাজ করে বড়টা hang করে" সমস্যা (Ch 5)। (২) ping ও traceroute দিয়ে সমস্যা নির্ণয় অসম্ভব হয়। (৩) UDP-র "port unreachable" সংকেত না আসায় client দীর্ঘ timeout পর্যন্ত অপেক্ষা করে। নিরাপত্তার জন্য ICMP সীমিত করা যেতে পারে, কিন্তু অন্তত type 3 code 4 (Fragmentation Needed) সবসময় অনুমোদিত থাকা উচিত।
