Chapter 40

DNS Debugging

"DNS-এর সমস্যা" এতটাই সাধারণ যে এটি প্রায় একটি কৌতুক হয়ে গেছে। কিন্তু DNS সমস্যা নির্ণয় আসলে সহজ — কারণ dig আপনাকে ঠিক দেখায় প্রতিটি স্তরে কী ঘটছে।

40.2 সাধারণ DNS সমস্যা ও তাদের নির্ণয়

"Record বদলেছি কিন্তু পুরনো IP আসছে"

bash
# ধাপ ১ — Authoritative server কী বলছে? (সব cache এড়িয়ে)
NS=$(dig +short NS example.com | head -1)
dig @$NS example.com
# এখানে পুরনো হলে → আপনার DNS provider-এ পরিবর্তনই হয়নি

# ধাপ ২ — Public resolver গুলো?
dig @8.8.8.8 example.com
dig @1.1.1.1 example.com
# পুরনো হলে → TTL শেষ হওয়ার অপেক্ষা করুন

# ধাপ ৩ — আপনার নিজের resolver?
dig example.com

# ধাপ ৪ — OS cache পরিষ্কার করুন
sudo resolvectl flush-caches      # systemd
sudo dscacheutil -flushcache      # macOS
ipconfig /flushdns                # Windows

# ধাপ ৫ — Browser cache
# chrome://net-internals/#dns

এই ক্রমটি সমস্যাটিকে ঠিক একটি স্তরে সংকীর্ণ করে আনে। প্রতিটি ধাপে TTL-এর মানও দেখুন — কমতে থাকলে সেটি cache থেকে আসছে (Ch 27)।

"DNS একেবারেই কাজ করছে না"

bash
# ধাপ ১ — Network কি ঠিক আছে? (DNS ছাড়া পরীক্ষা)
ping -c 2 1.1.1.1
# ব্যর্থ হলে → এটি DNS-এর সমস্যা নয়, network-এর

# ধাপ ২ — আমার configured resolver কে?
cat /etc/resolv.conf
resolvectl status | head -20      # systemd

# ধাপ ৩ — সেই resolver-এ পৌঁছাই?
ping -c 2 $(grep nameserver /etc/resolv.conf | head -1 | awk '{print $2}')

# ধাপ ৪ — একটি ভিন্ন resolver দিয়ে চেষ্টা
dig @1.1.1.1 example.com
# কাজ করলে → আপনার configured resolver-ই সমস্যা

# ধাপ ৫ — Port 53 কি খোলা?
nc -zvu 1.1.1.1 53
sudo tcpdump -i any -n port 53 -c 5 &
dig example.com
# কোনো packet না দেখলে → firewall আটকাচ্ছে

# ধাপ ৬ — /etc/hosts কি হস্তক্ষেপ করছে?
grep example.com /etc/hosts

"বিভিন্ন জায়গায় ভিন্ন IP আসছে"

bash
dig @8.8.8.8 +short cdn.example.com
dig @1.1.1.1 +short cdn.example.com
dig @9.9.9.9 +short cdn.example.com
# ভিন্ন উত্তর এলে — এটি প্রায়ই ★স্বাভাবিক ও উদ্দেশ্যপ্রণোদিত★

কেন ভিন্ন হয়:

  • GeoDNS / CDN — resolver-এর অবস্থান অনুযায়ী নিকটতম edge-এর IP দেওয়া হয় (Ch 46)।
  • Load balancing — একাধিক A record ঘুরিয়ে ঘুরিয়ে দেওয়া (round-robin)।
  • Split-horizon DNS — internal ও external ব্যবহারকারীর জন্য ইচ্ছাকৃতভাবে ভিন্ন উত্তর।
  • Anycast — একই IP, কিন্তু ভিন্ন ভৌগোলিক অবস্থানের server (Ch 27)।

একটি VPN চালু করে আবার পরীক্ষা করুন — উত্তর বদলে গেলে GeoDNS নিশ্চিত।

"DNS lookup ধীর"

bash
# সময় মাপুন
dig example.com | grep "Query time"

# বিভিন্ন resolver-এর তুলনা
for r in 8.8.8.8 1.1.1.1 9.9.9.9 208.67.222.222; do
  t=$(dig @$r example.com | grep "Query time" | awk '{print $4}')
  echo "$r → ${t}ms"
done

# একটি application-এ DNS কত সময় নিচ্ছে
curl -w "DNS: %{time_namelookup}s\n" -o /dev/null -s https://example.com

সাধারণ কারণ:

  • IPv6 timeout — system AAAA record চাইছে কিন্তু IPv6 কাজ করছে না, তাই timeout-এর অপেক্ষা করে তারপর IPv4-এ যায়। উপসর্গ: ঠিক ৫ সেকেন্ডের বিলম্ব।
  • দূরবর্তী resolver — একটি কাছের resolver ব্যবহার করুন।
  • Kubernetes-এ ndots:5 — example.com-এর জন্যও প্রথমে example.com.default.svc.cluster.local, তারপর আরও কয়েকটি চেষ্টা করা হয় — একটি external lookup-এ ৫টি ব্যর্থ query! সমাধান: FQDN ব্যবহার করুন (শেষে dot দিয়ে), বা pod-এ ndots কমান।
  • Cache কাজ করছে না — প্রতিটি query-ই প্রকৃত lookup হচ্ছে।

40.3 dig-এর দরকারি বিকল্প

bash
dig +short example.com          # শুধু উত্তর, script-এর জন্য আদর্শ
dig +trace example.com          # root থেকে সম্পূর্ণ delegation পথ
dig +noall +answer example.com  # শুধু ANSWER section
dig +nssearch example.com       # সব authoritative server-কে জিজ্ঞেস
dig +dnssec example.com         # DNSSEC record সহ
dig +tcp example.com            # UDP-র বদলে TCP-তে
dig -t ANY example.com          # সব record (অনেক server এখন অস্বীকার করে)
dig -x 93.184.215.14            # reverse lookup

# একাধিক record type একসাথে
dig example.com A AAAA MX NS TXT +noall +answer

# সব authoritative server একই উত্তর দিচ্ছে কি? (গুরুত্বপূর্ণ)
for ns in $(dig +short NS example.com); do
  echo "$ns → $(dig @$ns +short example.com | head -1)"
done
⚠️ Nameserver-দের মধ্যে অসঙ্গতি — একটি নীরব ঘাতক

উপরের শেষ command-টি অত্যন্ত মূল্যবান। যদি আপনার দুটি nameserver ভিন্ন উত্তর দেয় (যেমন zone transfer ব্যর্থ হয়েছে বা একটিতে পরিবর্তন হয়নি), তাহলে ব্যবহারকারীরা এলোমেলোভাবে কখনো সঠিক কখনো ভুল উত্তর পাবেন — কারণ resolver যেকোনো একটি nameserver বেছে নেয়।

উপসর্গ: "কিছু ব্যবহারকারীর কাজ করছে, কিছুর করছে না", বা "refresh করলে কখনো কাজ করে কখনো করে না"। এটি নির্ণয় করা কঠিন যদি না আপনি প্রতিটি nameserver আলাদাভাবে পরীক্ষা করেন।

🧪 Lab 40 — একটি DNS সমস্যা নির্ণয় করুন

আমরা কী দেখতে চাইছি? — DNS-এর প্রতিটি স্তর আলাদাভাবে পরীক্ষা করে সমস্যা সংকীর্ণ করার একটি পুনরাবৃত্তিযোগ্য পদ্ধতি।

bash
#!/bin/bash
D=${1:-example.com}

echo "=== 1. আমার resolver ==="
grep nameserver /etc/resolv.conf

echo -e "\n=== 2. আমার resolver কী বলে ==="
dig +short $D | head -3
echo "status: $(dig $D | grep -o 'status: [A-Z]*')"

echo -e "\n=== 3. Public resolver গুলো ==="
for r in 8.8.8.8 1.1.1.1; do
  echo "$r → $(dig @$r +short $D | head -1)"
done

echo -e "\n=== 4. Authoritative nameserver গুলো ==="
for ns in $(dig +short NS $D); do
  echo "$ns → $(dig @$ns +short $D | head -1)"
done

echo -e "\n=== 5. TTL (cache-এর অবস্থা) ==="
dig $D | grep -E "^$D" | head -1

echo -e "\n=== 6. /etc/hosts-এ কিছু আছে? ==="
grep -i "$D" /etc/hosts || echo "(কিছু নেই)"

echo -e "\n=== 7. সময় ==="
dig $D | grep "Query time"

যা লক্ষ্য করবেন: ধাপ ৩ ও ৪-এর উত্তর ভিন্ন হলে সেটি cache-এর সমস্যা (TTL শেষ হওয়ার অপেক্ষা)। ধাপ ৪-এর ভেতরেই ভিন্নতা থাকলে সেটি nameserver-এর অসঙ্গতি — অনেক বেশি গুরুতর। ধাপ ৬-এ কিছু পাওয়া গেলে DNS-এর দোষ দেওয়া বন্ধ করুন।

আমরা কী শিখলাম: DNS-এর সমস্যা নির্ণয় মূলত "কোন স্তরে ভুল উত্তরটি ঢুকল" খুঁজে বের করা। Authoritative থেকে শুরু করে নিচে নামলে (বা নিচ থেকে উপরে উঠলে) সেই স্তরটি স্পষ্টভাবে চিহ্নিত হয়।

📌 Chapter Summary
  • dig-এর status প্রথমেই দেখুন: NOERROR, NXDOMAIN, SERVFAIL, REFUSED।
  • NXDOMAIN (নাম নেই) ≠ NOERROR + ANSWER: 0 (নাম আছে, এই type নেই)।
  • aa flag = authoritative উত্তর; tc = truncated, TCP-তে যেতে হবে।
  • Query time ০–৫ms মানে cache; ৫০ms+ মানে প্রকৃত resolution।
  • পুরনো উত্তরের নির্ণয়: authoritative → public resolver → নিজের resolver → OS cache → browser।
  • সব authoritative nameserver একই উত্তর দিচ্ছে কিনা পরীক্ষা করুন — অসঙ্গতি এলোমেলো ব্যর্থতা তৈরি করে।
  • ঠিক ৫ সেকেন্ডের বিলম্ব প্রায় সবসময় IPv6 (AAAA) timeout।
  • Kubernetes-এ ndots:5 external DNS lookup-কে বহুগুণ ধীর করে।
✓ Quick Check
dig NXDOMAIN দিচ্ছে কিন্তু আপনি record টি তৈরি করেছেন। কী ঘটছে?

সম্ভবত negative caching (Ch 27) — record তৈরির আগে কেউ query করেছিল, তখন NXDOMAIN উত্তরটি cache হয়ে গেছে এবং SOA-র minimum TTL পর্যন্ত থাকবে। যাচাই: authoritative server-কে সরাসরি জিজ্ঞেস করুন (dig @ns1.example.com ...)। সেখানে ঠিক থাকলে শুধু অপেক্ষা করতে হবে। অন্য সম্ভাবনা: ভুল zone-এ record তৈরি, বা প্রকাশ (publish) করা হয়নি।

NOERROR কিন্তু ANSWER: 0 — এর মানে কী?

নামটি অস্তিত্বশীল, কিন্তু আপনি যে record type চেয়েছেন সেটি নেই। উদাহরণ: dig example.com AAAA দিলে NOERROR + ANSWER 0 আসবে যদি domain-টির শুধু IPv4 (A record) থাকে। এটি NXDOMAIN থেকে সম্পূর্ণ ভিন্ন — সেখানে নামটিই নেই। এই পার্থক্য না বুঝলে আপনি ভুল সমস্যা সমাধানের চেষ্টা করবেন।

দুটি nameserver ভিন্ন IP ফেরত দিচ্ছে। কেন এটি বিপজ্জনক?

Resolver গুলো এলোমেলোভাবে যেকোনো একটি nameserver বেছে নেয়। ফলে কিছু ব্যবহারকারী সঠিক server-এ যাবেন, কিছু ভুল/পুরনো server-এ — এবং একই ব্যবহারকারীও refresh করলে ভিন্ন ফল পেতে পারেন। উপসর্গটি অসামঞ্জস্যপূর্ণ ও বিভ্রান্তিকর ("কখনো কাজ করে কখনো করে না")। সাধারণ কারণ: zone transfer ব্যর্থ, একটি nameserver-এ পরিবর্তন প্রয়োগ হয়নি, বা ভুল configuration।

একটি application-এ প্রতিটি request-এ ঠিক ৫ সেকেন্ডের অতিরিক্ত বিলম্ব। DNS-এর দিক থেকে সন্দেহ কী?

IPv6 (AAAA) lookup timeout। System প্রথমে AAAA record চায়; IPv6 configure করা থাকলেও কাজ না করলে (বা resolver উত্তর না দিলে) ৫ সেকেন্ডের default timeout-এর পরে A record-এ যায়। যাচাই: dig AAAA yourhost এবং curl -4 দিয়ে তুলনা করুন। সমাধান: IPv6 ঠিক করুন, বা application-এ IPv4 বাধ্যতামূলক করুন, বা resolver configuration ঠিক করুন।
