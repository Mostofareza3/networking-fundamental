Chapter 28

HTTP Fundamentals

HTTP-র সবচেয়ে বিস্ময়কর দিক হলো এর সরলতা। পৃথিবীর প্রায় সমস্ত application traffic যে protocol-এ চলে, সেটি মূলত কয়েক লাইন text — যা আপনি নিজের হাতে লিখতে পারেন।

28.1 Why does this exist?

TCP আপনাকে একটি নির্ভরযোগ্য byte stream দিয়েছে। কিন্তু এখন দুটি program-কে ঠিক করতে হবে:

  • একটি request কোথায় শুরু, কোথায় শেষ? (framing)
  • Client কী চাইছে তা কীভাবে বলবে?
  • Server সফল হয়েছে না ব্যর্থ, তা কীভাবে জানাবে?
  • Data-র ধরন (JSON? HTML? ছবি?) কীভাবে বোঝাবে?
  • Authentication, caching, compression — এসব কীভাবে আলোচনা করবে?
💡 Why HTTP

HTTP এই সব প্রশ্নের একটি সাধারণ, text-ভিত্তিক উত্তর দেয়। এর সাফল্যের মূল কারণ তিনটি নকশাগত সিদ্ধান্ত:

  1. সরল ও মানুষ-পাঠযোগ্য — telnet দিয়ে হাতে টাইপ করা যায়, তাই শেখা ও debug করা সহজ।
  2. Stateless — প্রতিটি request স্বয়ংসম্পূর্ণ। Server-কে আগের request মনে রাখতে হয় না, তাই load balancing ও horizontal scaling সহজ।
  3. সম্প্রসারণযোগ্য — নতুন header, নতুন method, নতুন status code যোগ করা যায় পুরনো client ভাঙা ছাড়াই।

✓ Host header কেন বাধ্যতামূলক

HTTP/1.0-তে Host ছিল না — কারণ ধরে নেওয়া হতো একটি IP মানে একটি website। কিন্তু আজ একটি server-এ শত শত site চলে (virtual hosting)।

203.0.113.50 এই একটি IP-তে:
    example.com
    myblog.com
    shop.example.org

TCP connection-এ শুধু IP আছে, নাম নেই।
Server কীভাবে জানবে কোন site চাওয়া হচ্ছে?

    → Host header।

এজন্যই Host ছাড়া HTTP/1.1 request পাঠালে server 400 Bad Request দেয়। HTTP/2-তে এটি :authority pseudo-header হিসেবে এসেছে, এবং HTTPS-এ TLS-এর SNI extension একই কাজ করে encryption শুরুর আগে (Ch 33)।

28.4 Message Framing — HTTP কীভাবে TCP-র byte stream-কে ভাগ করে

Chapter 4-এ আমরা দেখেছি TCP একটি byte stream — message-এর কোনো সীমানা নেই। তাহলে HTTP কীভাবে জানে একটি response কোথায় শেষ?

তিনটি পদ্ধতি:

১. Content-Length (সবচেয়ে সাধারণ)
   Content-Length: 87
   → "header-এর পরে ঠিক ৮৭ bytes পড়ো, তারপর শেষ"
   ✓ সরল    ✗ আগে থেকে আকার জানতে হবে

২. Transfer-Encoding: chunked
   Transfer-Encoding: chunked

   1a\r\n              ← এই chunk-এ 0x1a = 26 bytes
   {"partial":"data..."}\r\n
   f\r\n               ← পরের chunk 15 bytes
   more content\r\n
   0\r\n               ← 0 মানে শেষ
   \r\n

   ✓ আকার আগে জানার দরকার নেই — streaming সম্ভব
   ✓ Server তৈরি হতে হতেই পাঠাতে পারে
   এজন্যই streaming API, SSE, বড় generated response
   এতে ব্যবহার হয়।

৩. Connection close (HTTP/1.0-র পদ্ধতি)
   Connection: close
   → "connection বন্ধ হওয়া মানেই response শেষ"
   ✗ প্রতিটি response-এ নতুন connection — অত্যন্ত অদক্ষ
⚙️ Developer Perspective — কেন এটি জানা দরকার

"আমার API response কেটে যাচ্ছে" বা "client hang করে আছে" — এই সমস্যাগুলোর মূল প্রায়ই framing-এ:

  • Content-Length প্রকৃত body-র চেয়ে বড় → client বাকি bytes-এর জন্য অপেক্ষা করতে থাকে → timeout।
  • Content-Length ছোট → response কেটে যায়, বা পরের response-এর সাথে মিশে যায়।
  • Proxy যদি response পরিবর্তন করে (compression, injection) কিন্তু Content-Length update না করে → একই সমস্যা।
  • HTTP Request Smuggling — একটি নিরাপত্তা-দুর্বলতা যেখানে Content-Length ও Transfer-Encoding দুটোই থাকে এবং frontend ও backend ভিন্নভাবে ব্যাখ্যা করে। এজন্যই আধুনিক server দুটো একসাথে থাকলে request প্রত্যাখ্যান করে।

28.5 URL-এর গঠন

https://user:pass@api.example.com:8443/v1/users?limit=10&sort=name#top
└─┬─┘   └───┬───┘ └──────┬───────┘ └┬─┘└───┬───┘└──────┬───────┘└┬─┘
scheme   userinfo      host        port   path       query    fragment
                                                                  │
                                              ★ কখনো server-এ পাঠানো হয় না!
                                                শুধু browser ব্যবহার করে

প্রতিটি অংশ কে ব্যবহার করে:

  scheme   → কোন protocol, default port (http=80, https=443)
  host     → ★ DNS resolution ★ এবং Host header
  port     → TCP connect
  path     → request line-এ যায়, server routing-এ ব্যবহৃত
  query    → path-এর সাথে যায়, application parse করে
  fragment → শুধু browser-এর ভেতরে (scroll position, SPA route)
ℹ️ Fragment কখনো তারে যায় না

#-এর পরের অংশ HTTP request-এ অন্তর্ভুক্ত হয় না। https://example.com/docs#section-3-এ server শুধু /docs দেখে; #section-3 সম্পূর্ণভাবে browser-এর ব্যাপার। এজন্যই server-এর log-এ fragment কখনো দেখবেন না, এবং এজন্যই পুরনো SPA-রা routing-এর জন্য hash ব্যবহার করত — server-এ কোনো পরিবর্তন ছাড়াই client-side navigation সম্ভব হতো।

28.7 HTTP-র statelessness এবং cookie

🧠 Mental Model

HTTP stateless — server-কে কিছু মনে রাখতে হয় না। প্রতিটি request স্বয়ংসম্পূর্ণ।

কিন্তু বাস্তবে login, shopping cart, session — সবই state। সমাধান: state-টি প্রতিটি request-এর সাথে পাঠিয়ে দাও।

Request 1:  POST /login {user, pass}
Response 1: 200 OK
            Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax

Request 2:  GET /profile
            Cookie: session=abc123      ← client নিজেই পাঠাচ্ছে
Response 2: 200 OK {profile data}

Request 3:  GET /orders
            Cookie: session=abc123      ← আবার পাঠাচ্ছে

★ Server প্রতিটি request-এ নতুন করে session=abc123
  দেখে সিদ্ধান্ত নেয়। সে "মনে রাখেনি" — তাকে
  প্রতিবার বলে দেওয়া হচ্ছে।

এই নকশার সুবিধা বিশাল: যেকোনো server যেকোনো request handle করতে পারে, তাই load balancing তুচ্ছ ব্যাপার। JWT-ভিত্তিক authentication এই ধারণাটিকে আরও এগিয়ে নেয় — token-এর ভেতরেই সব তথ্য থাকে, তাই server-এ কোনো session store-ও লাগে না।

🧪 Lab 28 — হাতে HTTP লিখুন

আমরা কী দেখতে চাইছি? — HTTP যে সত্যিই কয়েক লাইন text, তা নিজের হাতে টাইপ করে প্রমাণ করা।

bash
# netcat দিয়ে হাতে একটি HTTP request
printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' \
  | nc example.com 80

# বা interactive ভাবে (টাইপ করে দুবার Enter দিন)
nc example.com 80
GET / HTTP/1.1
Host: example.com

# curl-এ সবকিছু দেখুন
curl -v http://example.com 2>&1 | head -30
#   > দিয়ে শুরু = আপনার পাঠানো
#   < দিয়ে শুরু = server-এর উত্তর

# Host header ছাড়া কী হয়?
printf 'GET / HTTP/1.1\r\n\r\n' | nc example.com 80

যা লক্ষ্য করবেন: আপনার হাতে টাইপ করা তিনটি লাইনের বিনিময়ে একটি সম্পূর্ণ HTML page ফেরত আসছে। Host ছাড়া পাঠালে 400 Bad Request পাবেন — HTTP/1.1-এর নিয়ম। curl-এর -v-তে > এবং < দিয়ে দুই দিকের প্রতিটি লাইন আলাদা করে দেখা যায়।

আমরা কী শিখলাম: HTTP কোনো রহস্যময় binary protocol নয় — এটি কয়েক লাইন text, যা মানুষ পড়তে ও লিখতে পারে। এই সরলতাই HTTP-র বিশ্বজয়ের একটি বড় কারণ, এবং এজন্যই HTTP debug করা তুলনামূলকভাবে সহজ।

📌 Chapter Summary
  • HTTP request = request line + headers + ফাঁকা লাইন + (ঐচ্ছিক) body।
  • Response = status line + headers + ফাঁকা লাইন + body।
  • Host header HTTP/1.1-এ বাধ্যতামূলক — virtual hosting-এর জন্য অপরিহার্য।
  • Framing-এর তিনটি উপায়: Content-Length, chunked, বা connection close।
  • URL-এর fragment (#...) কখনো server-এ যায় না।
  • HTTP stateless; cookie/token দিয়ে state প্রতিটি request-এ বহন করা হয়।
  • এই statelessness-ই horizontal scaling ও load balancing-কে সহজ করেছে।
✓ Quick Check
Host header ছাড়া HTTP/1.1 request পাঠালে কী হয় এবং কেন?

Server 400 Bad Request দেয়। কারণ একটি IP address-এ শত শত website চলতে পারে (virtual hosting), এবং TCP connection-এ শুধু IP আছে, কোনো নাম নেই। Host header ছাড়া server জানতেই পারে না কোন site-এর জন্য request এসেছে। HTTP/1.0-তে এটি ঐচ্ছিক ছিল, কারণ তখন এক IP মানে এক site ধরে নেওয়া হতো।

Chunked transfer encoding কখন Content-Length-এর চেয়ে ভালো?

যখন response-এর আকার আগে থেকে জানা নেই — যেমন database থেকে stream করা বড় result, real-time generated content, বা server-sent events। Content-Length ব্যবহার করতে হলে পুরো response তৈরি করে memory-তে রাখতে হতো আকার জানার জন্য। Chunked-এ server তৈরি হতে হতেই পাঠাতে পারে — কম memory, দ্রুত first byte।

URL-এর #section-2 অংশটি কি server-এর log-এ দেখা যাবে?

না। Fragment (#-এর পরের অংশ) কখনো HTTP request-এ অন্তর্ভুক্ত হয় না — এটি সম্পূর্ণভাবে client-side। Browser এটি ব্যবহার করে page-এর ভেতরে scroll করতে বা SPA-র রুটিং-এ। Server শুধু path ও query দেখে।

HTTP stateless হলে login কীভাবে কাজ করে?

State টি client-এর কাছে রাখা হয় এবং প্রতিটি request-এর সাথে পাঠানো হয় — সাধারণত cookie-তে একটি session ID, বা Authorization header-এ একটি token। Server প্রতিবার সেটি দেখে সিদ্ধান্ত নেয়; সে আগের request "মনে রাখে" না। এই নকশার সুবিধা: যেকোনো server যেকোনো request handle করতে পারে, তাই load balancing ও scaling সহজ।
